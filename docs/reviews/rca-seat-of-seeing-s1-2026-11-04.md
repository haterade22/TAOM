## Root-cause patterns

**A rule written from one caller or one branch (1, 3, 5, 12, 17, 18, 28, 29, 41).** The contract read the path it wanted and wrote a rule about the whole method. A swap back has more than one caller, a mission has two exits, the glide branch has a null case, and `UpdateCamera` has a first-person path. Round 2 made the same mistake one level up: the first fix for row 1 guarded a caller and not the write. The check is mechanical: state the harm as a write, list every route to that write, list the engine's exits, and read every branch of an engine method the feature calls for its side effect.

**A search that cannot see what it looks for (2, 34, 40).** Six categories sit on the mission's scene layer, and the contract read two. A method with a cheap name allocates. A search with parentheses misses a method group, and a search of a dump that lacks the assembly returns nothing with no error. A known hit proves the search works: find one first, then trust an empty result.

**Prose with no reader (4, 11, 22, 24, 27, 38, 42).** Every wrong sentence was written from memory while the code was fresh. Lens 2's claim list and the Tooling lens were the first readers. Ten of lens 2's ten claims were real.

**A gate bent to fit a draft or a line count (6, 7, 8, 9, 10, 33).** The manifest started from "what lets the gate pass", not "what a reader needs". `0.toml` keeps the gate as it was. Three statements on one line passed a line count and helped nobody. Deleting two unused events paid for the same lines.

**Structure and pins with no use (31, 36, 39, 43).** A contract shape copied without its reason cost a null adapter and a `Bind` method. Tests pinned what must not exist, and left the one line that makes the feature work unpinned.
