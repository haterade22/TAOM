## Top-line

The implementation moved roster discovery into the first custom battle (the object manager does not exist at the main menu), which created a new seam: the walk's plan is a placeholder until batch 1 reports back. Every path that could end batch 1 before it reported was handled for the item, and none was handled for the plan. A 120-second start timeout, sized for a single scene load, now sat in front of a load that also pays TAOM's full module-data pass, and on that timeout the runner would advance past a one-item placeholder plan straight to `Finish()` and toast "COMPLETE ... You can play now" having compiled nothing. The abort counter that was added so a partial walk would never read as full coverage missed one of the four skip paths. The review caught both before the first in-game run; neither has a unit test, because both live in the engine-boundary runner.

## Root-cause pattern

Findings 1 and 2 share one shape: **a new mechanism (discovery re-plan, abort accounting) was added on top of an existing state machine, and its failure paths were enumerated from memory instead of from the code.** Both fixes were one-line once the path was named; the cost was in finding the path. The generalizable check is: when a change adds a step whose outcome the rest of the walk depends on, list every way that step can NOT complete (timeout, throw, empty result, stale callback) and say what the walk reports in each case; when a change adds a counter, grep every call of the method it counts.

## Why each agent did or did not catch these

- **Data flow (sonnet):** caught findings 1 through 4 by tracing both orderings of "the item renders" versus "the start timeout fires", the one ordering the author had not walked. This is the agent the skill calls highest-value, and it was again.
- **Standards (haiku):** caught finding 5 by counting; the review prompt gives it the ceiling and it measured.
- **Efficiency (haiku):** caught finding 6; correctly rated nothing HIGH because no per-frame path allocates.
- **Completeness (haiku):** caught finding 7; confirmed the docs, issue, strings and IoC.
- **Compatibility (sonnet):** 29 engine usages verified on the installed 1.4.8, 0 incompatible. Both load-bearing claims hold: the preload view is in the `CustomBattle` view list and `PreloadHelper.PreloadCharacters` walks both combatants' rosters; the one-troop side gets `ceil(share * battleSize) >= 1` initial spawns as a mathematical invariant for every Battle Size and ratio, `Mission.SpawnTroop` flags the `PlayerTroop` as player-controlled and `Mission.BuildAgent` writes `_initialPlayerAgent`, the Order of Battle gate resolves through `DefaultBattleMissionAgentSpawnLogic.GetNumberOfPlayerControllableTroops()` to the player supplier's `CountOfCharacters` (1 < 20, cached per model), `SetupTeams` auto-calls `FinishDeployment` in the same tick, and `OrderOfBattleVM.OnDeploymentFinalized(false)` never reaches `SaveConfiguration()` (which, per the Codex pass, is empty in the base VM Custom Battle constructs anyway; the first draft's profile-write claim came from the campaign subclass). `agent.Team` is assigned in `Mission.SpawnAgent` well before the `OnAgentBuild` broadcast, so the guard's team gate can fire. `{newline}` expands through `GameTexts.InitializeGlobalTags()`. **Root-cause pattern across C1, C3 and C4:** the runner treated its own state as the truth about the engine. "Ending" meant "a teardown was requested", not "the game is gone"; "Running" meant "we started a mission", not "the mission on screen is ours". Every engine transition the runner relies on now has a matching check on the engine's side (`Game.Current` before `EndGame`, resolution before advancing, `TryClaimMission` before acting on a mission). Lesson appended to `docs/reviews/lessons/state-lifecycle-save.md`.

**What Codex did well.** It read `EndGame`'s body and the loading-state tick instead of the runner's comments about them; it reproduced the `{newline}` behaviour in a fresh process rather than arguing from the call graph; and it disputed a claim we had made in its favour (C6) with the exact subclass the mission constructs. Its focused suite ran 94 tests green.
