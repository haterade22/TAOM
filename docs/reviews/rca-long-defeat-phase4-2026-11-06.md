# RCA: The Long Defeat Phase 4 (#1079), 2026-11-06

Findings from each slice's build and review, with why each was missed and what now prevents it. The plan is `docs/features/long-defeat/phase4-plan.md`.

**Slice 1, locations config and plan.** Built by the implementer tier; reviewed by a cross-system data-flow reader and a Python reader (rows 4 to 8).

| # | Sev | Bug | Category | Why missed | Preventive action |

| 1 | MED | Section 5 says a gear set's `classes` are "class ids from classes.json" and that unknown ids are dropped with a warning, but the reader of `shop.json` holds no class ids, and the plan's wiring list ("`ShopReader.cs` (calls it)") gives it none. The first build passed the catalog's class ids eagerly (`_classes.Value`), which made loading `shop.json` also load `classes.json`: `LongDefeatRecorderTests.TheTowersAndVolleyBlocksOfAnExport_AreReadBackByTheFortressCatalog`, whose fixture has no `classes.json`, went red on a new "classes.json: was not found" warning, in a slice that is meant to change nothing for a shop without the new blocks | Plan rule needs data its reader does not hold; a load-order side effect on an unrelated file | The reader rule was written from the rules table alone, and the wiring list was written from the file list. The full `LongDefeat` filter caught it; the slice's own tests passed | The catalog hands the reader a function that returns the ids, and the reader calls it at most once and only when a set lists a class (`LocationsReader.Read`, `ShopReader.Read`). `TheClassIds_AreAskedForOnlyWhenASetListsAClass_AndOnlyOnce` and `AShopWithNoListedClass_LoadsWithoutClassesJson_AndWithoutItsWarning` pin it, and `TheCatalog_ChecksAListedClassAgainstClassesJson` pins the check itself |
| 2 | LOW | Section 5 drops unknown class ids and skips "a weapons set left with none", and says nothing of an armour set left with none. Read as written, an armour set whose every listed class is a typo would have no list left and would be offered to every class | Plan rule with a missing branch | The row names the weapons case because a weapons set must list its classes; the armour case was not enumerated | An armour set left with no known class is skipped, never widened (one warning for the drop, one for the skip); the shared cases `an armour set whose every listed class is unknown is skipped, never widened to every class` and `an armour set with an empty class list is skipped` pin it on both sides. Mike may prefer the other reading |
| 3 | LOW | `LongDefeatGearItems.Missing` was written together with its tests, so its tests were never seen red. The round-trip and director tests are pins, named as such in their summaries |
| 4 | LOW | `RunPlan.Armoury`, `.Yard` and `.Marshal` held the same data as `RunPlan.Shop.Locations`, set twice (`BuildPlan` and every test fixture by hand).
