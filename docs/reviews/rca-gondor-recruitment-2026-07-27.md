# RCA — Gondor volunteer pools: 80/20 rebalance, JSON typo gate, C#/JSON lockstep (2026-07-27)

## Top-line

The session began as a read-only audit: *"check the Gondor troop XML and ensure all troops are accounted for (upgrade paths count) for each region in the volunteer service."* The audit's answer was **yes** — all 189 Gondor troops resolve, 181 reachable from a `gondor.json` pool root through the upgrade closure and 8 intentionally excluded, with zero orphans globally and zero in each of the 26 regional id-prefixes. Nothing was unreachable.

What the audit found instead were three defects hiding *behind* that clean result, none of which affected reachability and none of which any existing test could see. All three were fixed in-session, plus a Gondor-wide rebalance the user directed (noble / settlement-specific line to 20%, regular line to 80%).

`/deep-review` then ran 5 parallel agents over the changeset. **Agents 1, 2, 3 passed clean; Agents 4 and 5 returned three LOW findings**, all fixed in-session. Agent 2 independently confirmed against installed v1.4.7 the load-bearing engine claim the rebalance rests on (`MaxVolunteerTier` gates only in-slot upgrade drift, never `GetBasicVolunteer`), and Agent 5 independently re-derived the reachability closure in its own script rather than trusting the audit or the tests — matching 189 / 181 / 8 exactly, in both live and degraded modes.

Suite green at 4484 passed / 0 failed / 2 pre-existing skips.

## Root cause pattern — a deferred preventive action decays into no preventive action

F2 is a repeat. The RCA for [`rca-rhun-gondor-recruitment-2026-05-23.md`](rca-rhun-gondor-recruitment-2026-05-23.md) F1 diagnosed this exact class — a pool referencing a troop id that does not exist (`wain_cavalry` vs `wainrider_cavalry`) — and wrote its own preventive action as:

> A separate `validate_all_troop_refs.py` script-level check could catch this class of bug at PR time — **open as follow-up if recurrence happens.**

It was never built. Two months later the hole was still open, and had widened: the JSON pool file added since then had *no* id validation at all.

The conditional is the defect. **"If recurrence happens" is an unusable trigger for a bug class whose defining property is that it fails silently.** A null `CharacterObject` drops a volunteer slot; nobody files a bug for a recruit that didn't appear. The recurrence signal the follow-up was waiting on does not exist, so the follow-up waits forever. The same reasoning applies to F1 and F6: an over-100 group normalises into a working-but-wrong pool, and F3's drift was masked by tests that asserted the wrong layer.

All four share one shape: **the failure mode produces a plausible, working, wrong result rather than an error.** For that class, deferred and conditional prevention is equivalent to no prevention, because the condition can never be observed.

Second, narrower pattern — **dual source of truth inverted by the test harness** (F3). When layer A overwrites layer B at runtime but the test bin only ever exercises B, passing tests are evidence about a configuration the game never runs. The fix is not vigilance; it is a lockstep assertion between the layers.

## Why each deep-review agent missed F1–F3

Stated plainly: **the deep-review did not find F1–F3 — the preceding audit did.** The 5 agents reviewed the changeset that already fixed them. This section records why the agents' scopes would not have caught them had they run first, which is the useful question.

- **Agent 1 (Standards):** structural conventions only (ADR-002/003/004/005/007, service locator, naming). An over-100 percentage group and a drifted data table are both perfectly well-structured. Out of scope by design.
- **Agent 2 (Compatibility):** verifies TaleWorlds API surface against installed DLLs. All three defects are TAOM-internal data, not engine API. Correctly out of scope — though note the standing prompt gap first raised in the 2026-05-23 RCA (extend Agent 2 to cross-check `NPCCharacter` ids referenced from C# against the troop XML) is *still* unimplemented, which is the same decay pattern as F2.
- **Agent 3 (Efficiency):** performance only. Out of scope.
- **Agent 4 (Completeness):** checks that tests *exist* and that docs/CHANGELOG/IoC are present. Tests did exist and did pass — that is precisely the problem in F3, where they passed while asserting the wrong layer. "Tests exist and are green" cannot distinguish a correct guard from a guard pointed at the wrong input set. It did catch F4.
- **Agent 5 (Data Flow):** the designed catch-net for all three, and it caught F6 (a fourth instance of the same class) unprompted. On this run it was explicitly told not to trust the new drift guard and to re-derive reachability itself, which it did — the right instinct to keep, since a guard authored in the same session as the fix it guards is self-certification.

## Preventive actions taken this session

1. Three new tests (unfiltered id gate, group-total + duplicate-settlement gate, C#↔JSON drift gate) — **each verified RED by injecting its failure before being accepted as GREEN.** A guard never observed failing is not a guard.
2. One load-time validation warning, closing the test-only gap the same session it was identified rather than deferring it.
3. Feature doc updated to record the standard, the lockstep guarantee, and the typo gate.
4. Lessons appended to `docs/reviews/lessons/testing-qa.md` and `docs/reviews/lessons/data-content-cultures.md`.
