# RCA: Gondor volunteer pools, four vale fixes and the household-line retune (2026-09-13)

## Top-line

The user asked for four Gondor fiefs to recruit the vale they stand in (Glanhir and its Ringló villages, Morlad and its villages, Blackroot Village Haven, Bar-en-Siril) and relayed a player report that the household lines (Swan Knights, Blackroot Vale bowmen, Methir archers) were too rare next to the regional levies. The change is data only: `recruitment_pools/gondor.json` regrouped and reweighted, the hand-written C# mirror in `VolunteerRecruitmentService.Gondor.cs` held in lockstep, two production-JSON tests added and five roll tests re-derived. Castles with a household line became exclusive to it; towns moved from 80/20 to 60/40 (Minas Tirith and Osgiliath 50/40/10). No troop id or settlement key was added or removed.

`/deep-review` ran the five core agents. Agents 2 (API compatibility, 7 signatures verified on the installed 1.4.8 DLLs), 3 (efficiency) and 5 (data flow, 8 flows traced, 0 gaps) passed clean on the runtime; Agent 1 returned one disputed finding, Agent 4 the known missing issue, Agent 5 one dormant inconsistency. A self-check turned up one documentation error none of the five caught. Nothing changed at runtime as a result of the review.

Suite: 9084 passed, 0 failed, 2 pre-existing skips (full run before the review); the volunteer suite 389 passed, 0 failed, re-run after every follow-up below (a mirror comment, the JSON note, the docs; no runtime line changed after the full run).

## Observations (no action)

- A castle captured by Gondor from another culture resolves, once converted, to `CultureMap["gondor"]` (Anórien peasants plus one each of Belfalas, Lamedon, Lossarnach), never to a household line, because the household pools are keyed by Gondor settlement ids. Pre-existing behaviour of the CultureConversion branch (`VolunteerRecruitmentService.cs:89-115`), unchanged here.
- With `MaxVolunteerTier => 6`, a castle slot seeded with a tier-3 household root can be promoted in place by the daily upgrade roll up to tier 6 before the player buys it, exactly as a regional root could before. The exclusive pools make this the norm at six castles rather than a one-in-five case. Agent 2 read both fill loops (`RecruitmentCampaignBehavior.cs:235-249`, `CastleNotableMaintainer.cs:155-169`): the assignment of the root is unconditional, the tier check gates only the later promotion, nothing rejects or drops a level-16 or level-51 root. Left to the Codex pass (KS3) to quantify.

## Root cause pattern

Both real findings are the same shape: a layer of the pool data that nothing observes. F3 is a fallback layer no live settlement reaches, so it drifted for two months without a test noticing. F4 is a prose layer (the `notes` array) that the loader ignores, so a wrong sentence costs nothing at runtime and nothing checks it. The 2026-07-27 RCA closed the C#-mirror instance of this with a lockstep test; the clan layer and the notes were outside that test's reach and stayed unobserved.

- Agent 5 (data flow) traced the groups outward to the loader, the model and the live map, all correctly; a claim inside the file about the file was not one of its traces.
