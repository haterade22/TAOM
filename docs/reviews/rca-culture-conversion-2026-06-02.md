# RCA — CultureConversion deep-review (2026-06-02)

## Top-line summary

The CultureConversion feature (gradual culture conversion of conquered fiefs) went through a multi-agent deep-review: 5 dimension agents (standards / API-compat / efficiency / completeness / data-flow) in parallel, **each finding then adversarially verified by an independent skeptic**, plus a completeness critic whose findings were also verified. 16 agents, ~1.03M subagent tokens.

- **4 dimensions PASS** (standards, API-compat, efficiency, completeness) — the in-file implementation was clean.
- **10 findings raised → 6 confirmed, 4 refuted** by the adversarial verifiers.
- **Exactly 1 real code bug** (HIGH #1). The other 5 confirmed findings are documentation gaps (2) and test gaps (3). All 6 fixed or deferred-with-rationale in-session.
- The 4 refutations include a plausible-sounding HIGH (R6 "store cleared while `Settlement.Culture` still holds an in-memory converted value") that was proven **architecturally impossible** — store-clearing only happens at session/campaign boundaries where settlements re-init from XML, or via deserialize during a save-load that resets `Settlement.Culture` anyway. The adversarial-verify pass earned its keep here.

Build green after fixes; **3003/3005 tests pass (2 skipped, 0 failed)** — 3 new tests added.

## Root-cause pattern

**The feature's risk was not in-file correctness — it was (a) failure-mode reconciliation of persisted state, and (b) coupling through a shared engine field with sibling features.** 5 of 6 confirmed findings came from cross-method / cross-feature tracing that per-file review structurally cannot see; all 5 were caught by the two highest-value sonnet-model agents (data-flow + completeness critic). The three haiku dimension agents and the api-compat agent passed clean — correct for their scope.

The single shared-field coupling (`Settlement.Culture`, mutated here, read by RevoltTuning's loyalty model AND CultureMarketplace's `TownRosterAdapter`) produced **3 of the 6 findings** (#2, #3, and the spirit of #1's recruitment path). That is the systemic lesson: a feature that mutates a *shared* engine field inherits a documentation + test obligation toward every other feature that reads it.

## Why each dimension agent missed these (or didn't)

- **Standards (haiku):** PASS — correct. ADR compliance is in-file; none of the 6 findings is an ADR breach.
- **API-compat (taleworlds-researcher):** PASS — correct. It verified `Settlement.Culture` is a settable, non-`[SaveableField]` public field (the load-bearing fact) and all other signatures. Findings #1–#5 are usage/coupling/test issues, not signature mismatches — out of its scope by design.
- **Efficiency (haiku):** PASS — correct. No hot-path issue exists.
- **Completeness (haiku):** caught #4/#5/#6 territory partially but rated COMPLETE because it checks *presence* of tests, not *intentional-absence* assertions or documented-negative-contracts. This is the one scope tightening worth noting: "tests exist per class" ≠ "every documented behavioral contract (including 'runs regardless of toggle' and 'does NOT call X') has an asserting test."
- **Data-flow (sonnet):** caught #1 (the real bug) — exactly the class of bug it exists for. ✅
- **Completeness critic (sonnet):** caught #2/#3/#4/#5/#6 — the cross-feature couplings and the test-contract gaps the dimension agents structurally couldn't.

## Feedback memories to codify

- **Shared-engine-field cross-feature coupling.** Extends the existing `feedback_cross_feature_handshake_via_shared_adapter.md` (shared *adapter*) to shared *engine fields*: when a feature mutates a field other features read off the live engine object (`Settlement.Culture`, `Hero.Culture`, `Clan.Kingdom`, etc.), grep every other feature/GameModel/adapter that reads that field and (a) confirm the coupling is intended, (b) document it in both feature docs, (c) add a cross-feature test where practical. This produced 3 of 6 findings here. *(Not writing a separate memory file — MEMORY.md is already over its size budget; this RCA is the durable record. Fold into the existing memory on its next edit.)*
- **Completeness agent scope tightening (candidate):** the completeness dimension prompt could add "for every method whose XML-doc/comment states it runs regardless of a toggle, or intentionally omits an operation a sibling method performs, require an asserting test (positive contract + `DidNotReceive` negative)." Low-priority — the critic caught it; only worth doing if this recurs.

## Codex adversarial pass (2026-06-02, gpt-5.5 xhigh)

After the deep-review fixes, Codex ran an independent adversarial pass ([codex-adversarial-culture-conversion-2026-06-02.md](raw/codex-adversarial-culture-conversion-2026-06-02.md)). It **DISPUTED 5 of 7 Known Suspects with decompiled evidence** — confirming the load-bearing assumptions are safe: (1) `ChangeOwnerOfSettlementAction.ApplyInternal` sets `Town.OwnerClan` at line 30 BEFORE dispatching the event at line 94, so the handler reads the NEW owner; (5) the R6 original-culture capture has no store-cleared-while-culture-live path (matches the deep-review refutation, verified independently); (6) the `_justLoadedFromSave` save/load guard mirrors MessengerCampaignBehavior correctly; (3) `ResolveStandardCascade` is the old cascade moved intact. It found **1 HIGH + 3 LOW**, all fixed in-session:

**Codex pass root-cause (C1, the only would-have-mattered finding):** the gate's allowlist was implicitly defined by "whatever cultures already have a recruitment pool," not by "the set of playable fief-owning cultures." This is the same enumerate-from-source-of-truth lesson as `feedback_enumerate_from_source_of_truth.md` (player-startup-gold) and the new-factions `alignment.json` whole-file-omission (RCA `rca-new-factions-2026-06-02.md`): **targeted reviewers audit the data that exists; completeness comes from enumerating the domain that *should* have an entry.** The new enumeration test institutionalizes that for the conversion gate.
