## Root-cause pattern — "generalize the template, but keep vanilla's hardcodes"

F3, F5, and F8 share one cause: **DeliverGoodsLotrIssue was built by mirroring the vanilla `HeadmanNeedsGrain`
decompile, and vanilla's *hardcoded* values (task text, `-10f` relation) + *codegen* members (`AutoGenerated*`) were
carried over instead of being replaced by the config-driven equivalents.** Vanilla is a single bespoke issue, so it
hardcodes; a generic config-driven template must wire every such value to the `LotrIssueDefinition`. F2 and F6 are the
inverse symptom of the same seam: config fields/enum values declared for the generic but not actually wired to a
reachable consumer.

**Why this matters for Waves 1–6:** each of the 7 remaining templates will be built the same way (mirror a vanilla
issue → generalize). The systemic preventive rule: **when generalizing a vanilla issue into a config template, every
vanilla literal that has a `LotrIssueDefinition` field MUST read the field, not the literal; every declared config
field MUST have a reachable consumer; and all `AutoGenerated*` codegen members MUST be stripped.** A per-template
checklist (text keys wired? counts/rewards/relation from def? item/troop source from def? no cargo-cult codegen? every
giver occupation reachable?) should run before each wave's review.

session avoids a blind restructure whose benefit is unverifiable here.
