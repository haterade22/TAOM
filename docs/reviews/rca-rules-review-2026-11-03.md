`/deep-review` of branch `chore/rules-review`, at tier 2: the code only (gate tests, tools, hooks), no production C# and no game data. Wave 1 ran Data flow and Tooling. It found ten HIGH findings, so wave 2 re-reviewed those fixes and ran Standards, Engine compatibility, Efficiency, Completeness and Design, and a convergence pass closed it. Every finding below was checked against the files, a probe or a RED test before it was fixed. `CODEX: NOT AUTHORIZED`: tier 2 asks once per session, and this session never got that word, so a Codex pass on this diff is owed.

**Top line:** the branch added commit gates that claimed to bind every committer, and three of them did not hold in the conditions they exist for. The git inside Visual Studio and GitHub Desktop refused every commit. The linter's `--staged` mode read the working tree for most checks. The branch's own no-growth ratchet would have refused its own merge. The tests were green throughout, because they ran one git, stubbed the tools and never crossed a merge.

## Root-cause pattern

Findings 1 to 3, 8 to 10, 12, 13, 16 and 29 share one cause, the same one [rca-quality-gates-2026-10-26.md](rca-quality-gates-2026-10-26.md) named: a gate is proven on the state its author's machine is in, and never on the states a later run meets. Here those states were another git, another session's unstaged edit, a merge, a machine with no install, and a path spelled the way the rule spells it. The repeat matters, because that RCA's remedy was to test those states one by one, and that did not reach the next gate. The stronger action is below.

Findings 14, 15 and 31 share a second cause: a table that feeds a decision was trusted because its tests passed. Reading a sample of real rows found all three within minutes.

## Why each agent missed these

The builders reported green suites, truthfully. A green suite here proved the stubs. Wave 1 split the diff by area and asked each lens what a gate can pass without checking, which is what found most of this. The findings only wave 2 could find came from comparing the new hook with the old one form by form (11), crossing the fix's own widening with the checks it did not fix (12), and simulating the merge (13). No first-wave lens had a brief that named those. The convergence pass then found a regression in a wave 2 fix (40), and gaps in the rewrite (41 to 44): each fix is new code, and the re-review after it earned its place every time. Wave 2's brief also called its diff "exactly the fixes", which was false: the orchestrator's snapshot was only HEAD's tree, because a stdin newline made `update-index` do nothing. So wave 2 read the whole uncommitted change, which is more than it was told, and no finding was lost.

## Preventive actions

- **A hook that claims to bind every committer runs through each git that exists:** `BundledGit` in `tools/tests/test_githooks_pre_commit.py` does this on this machine.
- **A check under `--staged` reads one tree:** `CommitView`, so a new check inherits it instead of choosing.
- **A commit gate is tested against the real tool at least once:** the merge test with the real linter found finding 16.
- **Before landing a branch that edits an over-cap rule, run** `python tools/lint_docs.py --drift-only --dash-base <trunk>`. The lesson says why, and `/deep-review`'s tier 2 brief can name it when the tier table is next edited.
- **A re-review compares the old gate with the new one, form by form,** because a rewrite that passes its own tests can still narrow a gate.
