# RCA: Long Defeat shop upgrades (#1161)

Findings from the tier 1 review of #1161, the shop step that upgrades the soldiers a player already has. The review covered the groundwork commit 313400cff (its own review was waived to land the branch) and the follow-up that makes it live: nine Rohan steps in `shop.json`, the shop rows, the check and the judge rule. Codex reported one HIGH, so a second wave ran the completeness, design, standards and efficiency lenses on the replace step. Each row was read again against the files before it was fixed.

## Not applied

- Codex F1, the throw path: see row 1.
- Standards 2, a shared pure predicate for `Upgradable()` and the split's filter: a facts type for two callers whose rules differ in part. The pins hold the wiring; the maintainer can weigh the type under the simplicity criterion.
- Efficiency F3: a whole order is replaced in one tick (up to about 130 soldiers in the proof run). Not measured; the feature doc's step 8 now says to read `frame max` against the S8 worst frame before any change.
- Efficiency F4: the row detail text is rebuilt at 4 Hz while the shop is open. Two fields for a few hundred bytes a second fails the simplicity criterion.
- Completeness spec note: the issue asked for a check that reads troop ids back; it now reads the place back, because the engine copies the id from the same troop object (Mission.cs:4079). The closing comment on #1161 records this.
- XML 2: the fallback (non-themed) panel has no scroll, so many rows could overflow. The themed panel is the one players see. FOLLOW-UP no issue: fallback only, and no shipped shop has that many rows.
- XML 3: the "No reinforcements" hint reads only the pack offers. Hypothetical: no shipped shop has upgrades and no packs.
- Data flow T5: an order that never completes (the director stops between the buy and the next tick) keeps its gold. Hypothetical: the run ends in that case.
- Data flow T11: `DefenderGroups` would mislabel a troop in two groups. Latent: no shipped troop is in two groups.

## Why each agent missed these

- Rows 1, 3, 4 and 5 sit between the domain and the engine. The domain tests use fakes that always succeed, and the groundwork's review was waived, so the first reader of the live path was this review. Codex found them by reading the tick order and the engine removal path end to end.
- Row 7 needed an adversarial input for the judge (a pass of the wrong purchase). Codex built one in memory; the builder tested only the happy path.
- Row 8 is the "value read back from the same layer that set it" trap in `.claude/rules/evidence-over-claims.md` B.

## Feedback memories to codify

None. Rows 7 and 8 are standing rules already (a verdict must be earned; prove an effect by an independent signal). The lesson goes to `docs/reviews/lessons/testing-qa.md`.
