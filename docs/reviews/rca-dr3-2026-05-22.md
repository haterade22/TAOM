## Root-cause pattern: version-pin drift in multi-project setups

Findings 1 + 2 share a theme: TAOM has TWO csproj files (Main + Dependencies) that reference the same set of NuGet packages. When the architecture changes (DR3 pivot), both files need updating in lockstep. The compile-time references in Main (`IncludeAssets="compile"`) tell the compiler what API surface to target; the runtime references in Dependencies (no `IncludeAssets` restriction) determine what DLLs actually deploy. **These MUST match** to avoid `MissingMethodException` on features only available in newer versions.

There's no current automated check for this. Options for future:
- Build-time MSBuild target that compares package versions across all csproj in the solution and fails if mismatched.
- Pre-commit hook that diffs `<PackageReference Version="..."/>` across csproj.
- Manual `/deep-review` rule update (done — Agent 1 now explicitly checks).

## Feedback memories to codify

Per `feedback_*.md` convention — promoting one finding to a memory:

**`feedback_version_pin_drift_across_csproj.md`** — When project has multiple csproj files (Main + Dependencies, or any multi-project setup) that reference the same NuGet package, drift between their `Version` pins creates runtime risk. The pattern: compile-time project references the newer version (for API surface); runtime project references the older version (because of caution about what actually deploys). Result: `MissingMethodException` at runtime on any API only in the newer version. **Rule**: ALWAYS keep version pins in lockstep across all csproj. /deep-review now enforces this for changesets touching csproj files.
