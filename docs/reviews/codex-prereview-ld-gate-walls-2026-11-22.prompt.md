## The change

The Long Defeat (issue #1079, a wave survival mode on siege scenes) writes a check line `taom.long-defeat.gate-attacked` for each repaired gate at the next wave clear. It failed whenever a 5-second sample found an attacker within 3 m behind a standing repaired gate (`GateWatch.Through > 0`), on the reasoning that he must have passed the closed gate. At the new fortress Minas Tirith attackers climb the walls by ladder and siege tower in every wave and reach the back of the gate without passing it (runs `E:/Temp/long-defeat-runs/20261122-095258` and `20261122-111133`: `through=99`, `48`, `136`, `156`, with up to 19 attackers "high" at once), so the check failed every later wave.

Now: `GateWatch` (`Main/Features/LongDefeat/Domain/LdGateWrite.cs`) remembers `WallsCrossed`, set when any sample of the watch saw an attacker on the walls. The director's 5-second state sample (`LongDefeatDirector.cs`, `LogState`) passes `read.AttackersHigh > 0` to `SampleGateWatch` (`LongDefeatDirector.Gates.cs`). `LongDefeatGateChecks.GateAttacked` keeps the fail for `Through > 0` while the walls were not crossed, and writes a skip ending `reason=walls-crossed` once they were. The Python judge (`tools/run_long_defeat.py`, `gate_attacked_waived`) treats a run whose gate-attacked skips all read `walls-crossed` as having paid the gate-attacked debt. Tests, a manifest comment and two changelog lines in `docs/features/long-defeat.md` (one of them only records the cause of another check's failure and changes no code).

## What to look for

1. **What "high" means.** Read how `LdReading.AttackersHigh` is computed in `Main/Adapters/LongDefeatBattlefieldAdapter*.cs` (the height rule, which agents count). Does "high" mean an attacker on the wall walk, or can it be true for an attacker who never left the ground (a siege tower's top before it docks, a ladder being climbed, a hill outside the walls, the ram's roof, a mounted attacker, Helm's Deep's causeway or the Deeping Wall culvert)? If it can be true without any attacker having crossed the walls, the fail is now masked in exactly the case it exists for: a repaired gate that attackers walk through. Say how likely that is at Helm's Deep, where the check passed with `through=0` in every run so far.
2. **Order and timing.** `WallsCrossed` is sticky for the watch. A watch lives from a repair to the next clear. An attacker on the walls at second 200 excuses a through count sampled at second 20. Is that a real hole (attackers pass a broken repair early, and later one climbs a wall), and is there a cheap, correct narrowing (count through only from samples taken before the walls were first crossed)? Judge it by the simplicity criterion in `.claude/rules/simplicity-criterion.md`.
3. **The sample call.** `SampleGateWatch(read.AttackersHigh > 0)` runs only in a wave on the 5-second state tick. Is `read` the reading of this tick? Can the watch be sampled with a stale or default reading (the first tick of a wave, a tick with no field)?
4. **The judge.** `gate_attacked_waived`: a run with a repair, in which every later wave wrote a `walls-crossed` skip, now pays the debt with no pass at all. Find a log that should fail and now passes (a `walls-crossed` skip from one watch beside a missing line for another repair; a skip whose reason token is followed by other text; `ended=run` lines). Does `tools/ingame_checks/1079.toml`'s row for this check read a skip line as NOT REACHED and never as a pass or a fail?
5. **Other readers of the line or of `Sample`.** Any caller of `GateWatch.Sample` with one argument that now loses information; any tool, manifest or doc that pins the old rule ("an attacker behind the standing gate fails").
6. **Tests that pin nothing.** Would each new test fail if `WallsCrossed` were never set, or always set?
