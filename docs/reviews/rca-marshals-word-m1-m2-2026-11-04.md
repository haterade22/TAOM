# RCA: Marshal's Word, stages M1 and M2 (deep review, 2026-11-04)

**Top line:** the tier 1 `/deep-review` of the order queue and the arrayed line found its most serious defects in two places that the unit suite could not see: an engine inference the contract stated as fact (a march outlived Charge, Stop and Retreat), and log verdicts that a dead feature also passed (`march-spread`, `finished`). The first wave (lens 5, lens 2, lens 7, Tooling) and Codex at `high` found 4 HIGH findings and a set of MEDIUM and LOW items; fixes D1 to D15 applied them. Those HIGHs called a second wave (lenses 1, 3, 4, 6), which found no HIGH, one behaviour defect that fix D2 had introduced (E1), and tests the contract's rules were owed; fixes E1 to E22 applied them. One gate was the orchestrator's own error: it ordered a guard for a route with no producer, lens 5 found none, a full decompile grep confirmed it, and the guard went (D11). Three re-reviews followed, because each fix to the two verdict rows `finished` and `march-spread` left a new defect: fixes G1 to G11, H1 to H5 and J1 to J6 applied those, and J is the last, because nothing it fixes is above MEDIUM. Neither feature stage has run in the game, so everything here is proved by review, tests and arithmetic only.

## Root-cause patterns

**An engine inference stated as fact in the contract (rows 1, 4, 15, 16).** The builder and the checker work from the contract, so a wrong sentence there passes every check they run. Row 1 said what a reading means without tracing the order kinds, and row 16 said what a click reaches without a producer. Both were caught by a lens that reads the engine and not the contract. Preflight corrected 128 findings before this build, and these four still got through: each read as a plain description, not as a claim.

**A verdict that a broken feature also passes (rows 8, 9, 10, 11, 12).** Each rule was tested for its arithmetic. No test asked what a build without the feature would read. Tooling found them by simulating the broken and the working build through each rule. This repeats the shape of "A spike's log line must report what the engine did, and its PASS must need that line" in the testing lessons: that entry names the log line, and this one names the rule's inputs.

**A fix read less closely than new code (rows 20, 33, 42, 45, 48).** D2 was a small change on a clear finding, and it dropped an input from a pass while a later reader still used what the pass had stored. E1 fixed that and left the proof's baseline behind, G1 fixed that and compared counts where it needed names, G3's mark was set too early, and H1's mark belonged to the whole step. The S1 and harness reviews recorded the same pattern, which is why this review kept its readers on the fixes.

**A verdict's measure and its control use two definitions (rows 33, 34, 44).** The spread stamped arrivals at the slack, and the control stored times to the point. The spread read the survivors, and the control read the first pass's companies. Each number was right in its own terms, and only a dead build fed through both showed that they disagreed.

**Constants swept over speeds nobody has measured (rows 37, 43, 44, 49, 50).** Three rounds set and reset the margin and the floor on a Python restatement of the march, over factors from 0.5 to 1.5. Each round found another corner of that grid, and no round had a real reading of what soldiers do against the cached speed. One game run of a real march would have told more about these rows than the sweeps did, and it was never next in the plan.

**Latch keys decide how many lines a check can see (rows 11, 26).** `IOutcomeLog` writes a line the first time it sees `(id, result, key)`, so the key is part of what a manifest's `min` means. A `min` written without reading the key counts the wrong thing.
