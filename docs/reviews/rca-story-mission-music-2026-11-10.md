# RCA: Story mission music, the tier 1 review (2026-11-10)

**Top line:** the tier 1 review of the story mission music change (#1105) found one HIGH and two MEDIUMs. The HIGH and the first MEDIUM were in the loop; the second MEDIUM was a test gap in the loop's fix, found by the second wave. The cue replayed the track with `SoundEvent.Play()` on the event that had just ended, but native releases an event that ends by itself, so the replay could never work: every story mission longer than the 3 min 12 s track would have gone silent, with the track gone and vanilla music still held off. The maintainer's bar held throughout: no reviewer found a path that pauses, mutes or leaves silenced any music outside the story mission. The first wave ran Codex at `ultra` and lenses 5 and 2; the HIGH started a second wave of lenses 1, 3, 4 and 6 and a Codex `high` re-review of the fix. Nothing here has run in game, and nobody has heard the track.

Two design changes from lens 6 went in with them, both checked by the existing tests: the cue's four lifecycle booleans became one `Phase` enum, and the `events=` count went (row 10), since nothing read it. Lens 3 found no cost issue; it left one UNVERIFIED item, a possible stutter at each replay if the file decodes on the main thread, which is now a human row in the manifest.

The Codex re-review left one question open: whether a `Stop()` in the window between the end of the track and the native release is safe. The native stop (`FUN_180477790`) finds the event stopped and queues its id a second time, and the release (`FUN_180237200`) looks the id up and does nothing when it is gone, so the second entry is harmless. The lens 2 re-review of the final diff read the RTTI vtables in the installed binary and confirmed that the drain releases through `FUN_180237200`. It found no HIGH or MEDIUM, and six LOW text corrections, all applied: the leftover-slot sentence (a new map screen does not clear the slot; only its finalize does), the vtable tag, two code comments about a `Stop` or `Play` before the release, the never-started event (a `Stop` frees it), the unlocked once-per-frame guard, and two manifest claims (a failed decode and an instant stop). It left one question for the first game run: whether the engine reads a just-started event as stopped, which would show as `loop=early` after 0.0 s.

## Root-cause pattern

Rows 1, 6, 7 and 8 share one cause: an engine behaviour was written down from the managed wrapper or from a name, where the effect lives in native code or in a caller the wrapper does not show. The project rule already says to quote the line that produces an effect (AGENTS.md "Research first"). The design asked whether the event loops by itself, a question about the bank, and not whether the event outlives its end, a question about the native lifetime. So the replay went into the code path that every long mission runs, with tests that fake the engine and could not see it. Row 2 is a second pattern: a failure branch that stops the feature must also undo what the feature took, and the tests asserted the stop, not the undo.

## Why each reviewer missed or found these

- **The design review** asked whether `event:/music` loops in the bank and left it open; it did not ask whether a stopped event can play again.
- **Codex at `ultra`** found rows 2 to 5 and 9 and marked the replay UNVERIFIED; its native decompile failed on a Python access error, so it could not read the callback.
- **Lens 5 (data flow)** found rows 2, 3, 6 and 9 and the async note in the doc's section 1.
- **Lens 2 (engine compatibility)** found row 1 from the native callback and the release function, and rows 2, 5 to 8, 10 and 11.
- **The full suite** found row 12.
