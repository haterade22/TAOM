### Advanced Starting Options adapted for Middle-earth

`Main/Features/AdvancedStartOptions/TaomStartOptionsProvider.cs` uses the engine's own
`[StartOptionsProvider]` hook, so no Harmony patch is involved: `AdvancedStartOptionsManager.Initialize()`
reflects over every active assembly with `Static | Public | NonPublic` and binds any method matching
`void (AdvancedStartOptions)`.

- **United Empire removed.** It merges whichever factions hold the three imperial StringIds (Dunland,
  Gondor and Mordor here) into a kingdom built from a hardcoded `TextObject` literally named
  "Calradian Empire". Worse, `HandleKingdomCleanup` and `ResolveKingdom` both branch on
  `Culture.StringId == "empire"`, true for all three imperials in vanilla but only for Dunland in TAOM,
  so **two of its three unifier choices** leave the player ruling an empty, fief-less shell.
- **TAOM's 14 kingdoms added** to all five faction pickers. ASO's lists are hardcoded to the eight
  vanilla ids, so Erebor, Rivendell and the rest were invisible. The fief fallback is guarded
  (`FindFallbackStartingTown`, `if (list.Count > 0)` at each step), so Lindon and Goblin-town, which
  own one town and no castle, degrade to the fallback rather than crashing.
- **Menu re-localised**, 49 overrides. ASO reuses vanilla's kingdom-name string ids, which TAOM's
  renames do not reach, so the screen read "Northern Empire" and dropped the player into Gondor.

One polarity trap worth recording: vanilla's always-available helper is named `GetNeverDisabledItem`
and returns **`false`**. The delegate answers "is this DISABLED", so returning `true` would have
greyed out every kingdom added.

### The execution alignment rule, re-homed onto the Blood Feud seam

v1.5.0 deleted `ExecutionRelationModel` engine-wide, taking `TaomExecutionRelationModel` with it. The
first pass ported only the trait half and left the relation half unported, which Codex correctly
called a gameplay regression rather than neutral cleanup. Both halves now run on the new seam:

| Half | Seam |
|---|---|
| Trait penalty | prefix on `TraitLevelingHelper.OnBloodFeudStarted(Hero)` |
| Relation penalty | postfix on `ExecutionCampaignBehavior.GetBloodFeudStartRelationPenaltyToOtherClan` |

v1.5.0 splits execution fallout in two and only one half is suppressed. The feud itself sets the
victim clan's relation to minimum and starts the vendetta: that is **left alone**, because a clan
whose kinsman you beheaded is entitled to hunt you regardless of side. What is suppressed is the
separate loop over every other clan in the world. Returning zero trips the engine's own `!= 0` guard,
so it is no hit and no notification rather than a smaller one.

The decision itself is unchanged and still lives in `IOnExecutionAction.GetRelationModifier`, which
went from zero consumers back to live. Patching the model method rather than the apply loop also
keeps the pre-execution "this will hurt your relations with N clans" tooltip honest. The genuinely
dead `IOnExecutionAction.IsKinslaying` was deleted with its two tests.

### The character-creation event now fires ten times

`OnCharacterCreationIsOverEvent` became `MbEvent<int>`, and the dispatcher invokes it in a `for (int i = 0; i < 10; i++)` loop as a **phase-ordering index**. Every vanilla subscriber guards on it (`if (index == 1)`, `if (index != 1) return;`, `if (index == 8)`).

Adding a bare `int` parameter without a guard would have run TAOM's handlers **ten times**. One of them seeds the player's starting special resources.

**Phase 8 is where Advanced Starting Options applies the chosen player start** (king / vassal / mercenary / trader / outlaw / beggar), which can hand the player a kingdom, fiefs, a workshop or a caravan. Anything reading settled player state must run after it, so both TAOM handlers are guarded at **phase 9**, the last:

- `Main/Features/SpecialResources/SpecialResourcesBehavior.cs` (seeds culture-keyed starting resources)
- `Main/Features/PlayerPossession/PlayerPossessionBehavior.cs` (records the possessions baseline)

### Banner colours: a startup throw that every gate stayed green through

`MobilePartyVisual.AddCharacterToPartyIcon` lost `bannerKey`, `wieldedItemIndex`, `teamColor1` and `teamColor2`. The old postfix wrote to the last two and declared them as parameters, and it is applied through `ManualPatchApplicator` with `Harmony.Patch`, so it would have thrown at **startup**, not merely misbehaved.

`HarmonyPatchBindingTests` stayed green throughout, because `TargetMethod()` resolves by name only and that still succeeds. **That is a structural hole in the binding gate, not bad luck.**

The colour work moved into the new `SandBox.View.SandBoxViewHelpers+MobilePartyVisualHelper.GetHumanAgentPartyVisual`, where the values are locals read from `party.MapFaction.Color` / `.Color2` and fed to `AgentVisualsData.ClothColor1` / `ClothColor2`. `MapFaction` is the kingdom for a clan in one, which is exactly the value the feature overrides. The seam therefore moved from the signature into the body, so the patch is now a **transpiler** appending `ldarg.2` plus a resolver call after each faction-colour read, stack-neutral and passing the vanilla value through so an unrecognised party keeps the engine's choice.

New gate: `TAOM.Tests/Migration/TranspilerSiteBindingTests.cs` reads the real engine IL via `PatchProcessor.GetOriginalInstructions`, feeds it to the production transpiler, and asserts no `LogWarning` was received. "No warning" is the proof the site resolved, because every fail-safe path announces itself through `IModLogger`.

### Cultures need an executioner (CRITICAL)

**v1.5.0 added `CultureObject.Executioner`** (0 occurrences in the v1.4.8 dump, 11 in v1.5.0):

- declared at `TaleWorlds.CampaignSystem.cs:34147`
- read from XML at `:34332` via `ReadObjectReferenceFromXml<CharacterObject>("executioner", node)`, which returns **null** when the attribute is absent
- dereferenced **unguarded** at `:49380`, `Executer.Culture.Executioner.FirstBattleEquipment.Clone(...)`, inside `HeroExecutionSceneNotificationData.GetSceneNotificationCharacters()`

That dereference sits **above** the `if (_useExecutioner)` guard, so it runs on every execution scene regardless of whether an executioner is displayed. It is keyed on `Executer.Culture`, the executing hero's culture. Reachable from the player execution path, the prisoner-execution UI, and the AI-lord-executes notification.

Vanilla ships `executioner` on 6 of its 16 cultures, each pointing at that culture's top elite troop. **TAOM shipped it on 0 of 24.** Any execution by a TAOM-culture lord was a null dereference, and executions are a headline v1.5.0 feature via Blood Feuds.

Fixed in two places, because TAOM defines cultures two ways:

1. `Main/_Module/ModuleData/taom_spcultures.xml`: added `executioner` to all **24** custom cultures, each set to that culture's own `elite_basic_troop`, matching vanilla's convention.
2. `Main/_Module/ModuleData/spcultures.xslt`: added an `executioner` override to all **6** renamed vanilla cultures. Without it they silently inherited vanilla's Calradian executioner, so Dunlending, Haradrim, Rohirrim, Easterling, Barding and Variag executions would have been performed by an imperial cataphract. This is exactly the defect class the stylesheet's own comment already warns about: *"an attribute this block does not name silently keeps its Calradian binding."*

Verified by running the transform and reading the output attributes, not by reading the markup.

### Advanced Starting Options: the Civil Unrest modifier was inert (HIGH)

v1.5.0's ASO layer lets the player stack global modifiers. **Civil Unrest** works by swinging
vanilla's `DefaultSettlementLoyaltyModel` thresholds on `Campaign.Current.Options.IsHighRebellionEnabled`:
`RebellionStartLoyaltyThreshold` 15 to 50, `RebelliousStateStartLoyaltyThreshold` 25 to 60.

`TaomSettlementLoyaltyModel` overrides both properties with a single hardcoded config pair (5/10),
so the flag was never read and **selecting Civil Unrest changed nothing at all**. That is the
silent-inert class rather than a crash: the option appears in the UI, the player picks it, and the
campaign behaves identically.

Fixed by giving the config a high-rebellion pair and reading the engine flag. TAOM softens vanilla's
base 15/25 to 5/10, a divide by 3 and by 2.5, so the same reduction applied to 50/60 gives **17/24**.
Civil Unrest now does what it says while the campaign stays less revolt-happy than vanilla. Both new
fields are range- and ordering-validated like the existing pair, per the config-provider rule, with
one test per rule.

Worth recording alongside it: v1.5.0's new personality-trait effects pull the same lever. Mercy at
level minus 2 grants `mercy_rebellion_chance` of **-0.4** (the array is `{-0.4, -0.2, 0, 0, 0}` over
levels -2..+2). TAOM has **530 characters at Mercy -2** where vanilla authors none below -1, so a
large slice of TAOM's world carries a 40 percent rebellion reduction that vanilla never applies.
Three systems now move rebellion in different directions: TAOM's thresholds, the ASO modifier, and
trait effects. That interaction is a balance question for in-game testing, not a defect.

### Comment strings lost their variant tags (HIGH, pre-existing)

`comment_strings.xslt` overrides 35 vanilla conversation strings. `<xsl:copy>` copies the element but
not its children, and the templates follow it with an attribute-only `<xsl:apply-templates
select="@*[...]"/>`, so the `<tags>` child was dropped. `<tags>` is what the engine uses to pick the
culture, persona and trait variant, so a stripped string stops matching the case it was written for
and matches everything at once.

Measured against the shipped vanilla file: **23 of 35 overrides lost their tags**. Twelve templates
already carried the fix and a comment explaining it, so this was a known defect that was only
partially applied. Not v1.5.0 drift, but v1.5.0 rewrote `comment_strings.xml` which is what surfaced
it. All 23 now emit `<xsl:apply-templates select="node()"/>`, verified by re-running the transform:
0 strings lose tags and every text override still applies.

New gate `TAOM.Tests/Core/CommentStringTagsTests.cs` uses the sentinel-stub pattern from
`.claude/rules/tests.md`: it reads the overridden ids out of the stylesheet itself so a newly added
override is covered automatically, then asserts on the transform OUTPUT that tags survive and the
text actually changed.

### Advanced Starting Options versus a total conversion

v1.5.0 added a whole pre-campaign layer: campaign scenarios, player starts, global modifiers and a
shareable seed. Three things about it matter for TAOM.

**ASO's faction pickers are hardcoded, not data-driven.** `SandBoxStartOptionsProvider.GetCultureItems()`
returns a literal list of the 8 vanilla StringIds. TAOM's 14 LOTR kingdoms are invisible to ASO, and
the 8 that are offered resolve to TAOM's renamed vanilla kingdoms, so the menu offers "Western Empire"
and the player starts as king of Gondor.

**The Trader start crashed for female players.** It filters
`Culture.NotableTemplates.Where(t => t.IsFemale == MainHero.IsFemale)` and indexes the result with
`MBFastRandom.Next(0, count)`, which returns 0 on an empty list, so `list[0]` throws. Measured: **all
16 TAOM cultures with notable templates had zero female entries**, every reference resolving, against
vanilla's 4 to 5 per culture. Fixed at the root rather than by suppressing the start: one female
notable per culture, cloned from that culture's own donor so `race` and the face template are
preserved. For a LOTR conversion race-correctness beats a gender-tuned face key, and a female dwarf
built on `BodyProperty.townswoman_empire` would be worse than one built on `fighter_erebor`.
New gate `TAOM.Tests/Core/NotableTemplateGenderTests.cs` pins both genders per culture and that every
reference resolves.

**NavalDLC is now declared incompatible.** `Main/_Module/SubModule.xml` gained an
`<IncompatibleModules>` block. NavalDLC is `DefaultModule="true"` and installed here, so it was
enabled unless the player turned it off, and its start-options provider is what registers the
`nordinvasion` scenario whose handler does `Kingdom.All.Find(t => t.StringId == "nord")` and
dereferences the result unguarded. TAOM has no `nord` kingdom.

Still owed on ASO: removing the United Empire scenario (it merges Gondor, Mordor and Dunland into a
hardcoded "Calradian Empire", and because vanilla branches on `Culture.StringId == "empire"` which
only TAOM's Dunland satisfies, two of the three unifier choices leave the player ruling an empty
shell), adding TAOM's 14 kingdoms to the pickers, and re-localising roughly 24 ASO menu strings.

### The engine now overwrites the player's starting gold (CRITICAL, not ASO)

v1.5.0 added two lines to `CharacterCreationState.FinalizeCharacterCreationState` that do not exist
in v1.4.8:

```csharp
Hero.MainHero.Gold = 1000;
MobileParty.MainParty.ItemRoster.AddToCounts(DefaultItems.Grain, 1);
```

The engine runs `ApplyFinalEffects()` then `FinalizeCharacterCreationState()` (CampaignSystem.cs:78947-78948).

`StartupResourcesBehavior` now re-applies at character-creation phase 9, gated on the default start so
