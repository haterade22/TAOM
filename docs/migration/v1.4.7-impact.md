## Code changes made this bump

Two touches; both reversible and behavior-preserving for the runtime outcome.

### `Patch15_BannerLayerLimit` — disabled by default (engine now natively unlimited)

The transpiler removed vanilla's 32-layer cap by transpiling out a `RemoveRange` call. v1.4.7 deleted that call, so the transpiler is a no-op that logged `[BannerColor] Transpiler: RemoveRange not found` on **every load** — the warning fires *before* the config flag is consulted (the flag is only read via injected IL that is never injected when `RemoveRange` is absent), and the patch category is applied unconditionally at `SubModule.cs:795`. So disabling required **three** coordinated edits, not just a flag flip:

- `Main/Features/BannerColorPersistence/BannerColorConfig.cs` — `EnableLayerLimitTranspiler` default `true`→`false` + comment.
- `Main/_Module/ModuleData/configs/banner_color_config.json` — `"EnableLayerLimitTranspiler": true`→`false` (the shipped JSON overrides the C# default at runtime; flipping only one surface would be a runtime no-op).
- `Banner_TryGetBannerDataFromCode_Transpiler.cs` — early quiet-return guard (`if (!ShouldSkipLayerLimit()) return instructions;`) so a disabled feature doesn't scan for the absent `RemoveRange` and log the spurious warning; plus a class doc noting the v1.4.7 status.
- Tests: 3 `BannerColorConfigProviderTests` default assertions flipped to `IsFalse`.

Kept (not deleted) so a future engine that reintroduces the cap can re-enable via config. `HarmonyPatchBindingTests` still covers the target (it still exists).

### `Patch49_ArmyGatheringNreGuard` — comment refresh only

Doc-comment updated to record that both guarded derefs (`Army.cs:726` / `:659`) are verified STILL unguarded in v1.4.7 and that the v1.4.7 AI-NRE fix was a different site — so the guard remains load-bearing. No behavioral change.
