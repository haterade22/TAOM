# v1.4.3 Equipment System Overhaul — Migration Guide

> **Source:** TaleWorlds modding-channel dev posts (Litauen / Prophet thread, posted in v1.4.3 beta window).
> **Status:** Documented from text-only dev notes. **All claims must be verified against decompiled 1.4.5 source in S0 before implementation.**

This is the single largest XML/data migration in the 1.3.15 → 1.4.5 transition. TAOM has **3,372 occurrences of `civilian="true"` across 51 XML files**, plus 1 file using deprecated `EquipmentFlags` values.

## What changed in v1.4.3

### 1. `EquipmentFlags` enum — simplified

**Removed flags (13):**
- `IsWandererEquipment`
- `IsGentryEquipment`
- `IsRebelHeroEquipment`
- `IsNoncombatantTemplate`
- `IsCombatantTemplate`
- `IsCivilianTemplate`
- `IsNobleTemplate`
- `IsMediumTemplate`
- `IsHeavyTemplate`
- `IsFlamboyantTemplate`
- `IsStoicTemplate`
- `IsNomadTemplate`
- `IsWoodlandTemplate`

**New flag set (5):**
- `IsFemaleTemplate`
- `IsLordTemplate`
- `IsChildEquipmentTemplate`
- `IsTeenagerEquipmentTemplate`
- `IsKingdomRulerTemplate`

**Template intent is now expressed as flag combinations:**
- Default male lord = `IsLordTemplate`
- Default female lord child = `IsFemaleTemplate | IsLordTemplate | IsChildEquipmentTemplate`
- Female kingdom ruler = `IsFemaleTemplate | IsKingdomRulerTemplate`

### 2. XML attribute deprecations

| Old | New | Behavior |
|---|---|---|
| `CharacterObject.civilianTemplate="X"` | (removed) | Logs warning. Rely on equipment roster flags + culture instead. |
| `CharacterObject.battleTemplate="X"` | (removed) | Same as above. |
| `EquipmentSet civilian="true"` | `EquipmentSet equipmentType="Civilian"` | Logs warning when old form used. |
| `EquipmentSet` without `culture` attribute | (must add `culture`) | Logs warning at load. |

**Important:** `equipmentType` is an **enum**, not flags. Schema-enforced inline string restriction with only three allowed values:
- `"Battle"`
- `"Civilian"`
- `"Stealth"` ← **NEW in 1.4.3**

`equipmentType="Civilian | Battle"` (flag combination) **does not work** — schema validation fails. Each equipment set must belong to exactly one type.

### 3. `EquipmentSelectionModel` API change

Methods that previously returned `MBList<MBEquipmentRoster>` now return **a single resolved `Equipment` directly**. Gender + culture filtering is handled inside the model.

Confirmed-affected method (from TAOM grep):
- `EquipmentSelectionModel.GetEquipmentRostersForInitialChildrenGeneration(Hero)` — return type changed.

Other `EquipmentSelectionModel` methods likely affected (verify in S0 decompile):
- `GetEquipmentRostersForHeroComeOfAge` / similar age-event methods
- `GetEquipmentRostersForInitialPromotion` / similar status-change methods

### 4. Updated vanilla module XMLs

TaleWorlds updated their own data files with the new flags. When TAOM XSLT runs against these, any old-flag passthrough from XSLT will now produce stale data.

| Module | Files updated |
|---|---|
| **StoryMode** | `story_mode_characters.xml`, `story_mode_equipments.xml` |
| **SandBoxCore** | `obsolete_characters.xml`, `sandboxcore_equipment_sets.xml`, `spnpccharacters.xml` |
| **SandBox** | `Bandits.xml`, `caravans.xml`, `education_equipment_templates.xml`, `lords.xml`, `obsolete_characters.xml`, `sandbox_equipment_sets.xml`, `spspecialcharacters.xml` |
| **NavalDLC** | `naval_characters.xml`, `naval_education_equipment_templates.xml`, `naval_equipment_sets.xml`, `naval_lords.xml` (N/A for TAOM) |

### 5. Heroes & equipment behavior (v1.4.3)

These rely on the new template flag system:
- Kingdom ruler change → new ruler swaps to ruler-tier equipment; old ruler reverts to standard lord equipment
- Companions promoted to lord → culture-appropriate lord equipment (battle + civilian)
- Marriage cutscenes + aging events → correct cultural equipment for couples + children
- Coming-of-age / teen / birth events → correct equipment set (fixes "naked" appearance bug)
- Heirs + newly-promoted clan leaders → correct culture equipment (was: wrong culture / fallback)

### 6. `OnRulingClanChanged` parameter flip

The `Clan` argument used to mean **new ruler**. It now means **old ruler**.

This is a silent semantic change. Subscribers reading the argument as "new ruler" now get wrong behavior.

**TAOM verification:** grep confirmed no direct `OnRulingClanChanged` subscribers in TAOM. But `Patch24_BannerDriftGuard` (patches `Clan.UpdateBannerColorsAccordingToKingdom`) and `Patch12_WarOfTheRing` operate in adjacent territory — audit both in S4.

## Migration checklist (per TaleWorlds dev guidance)

1. ☐ Replace removed `EquipmentFlags` values with new flag combinations.
2. ☐ Replace `civilian="true"` on `<EquipmentSet>` with `equipmentType="Civilian"`.
   - ⚠️ Only on `<EquipmentSet>` elements. Other elements that happen to have `civilian="true"` may or may not be relevant; inspect case by case.
3. ☐ Remove `civilianTemplate` / `battleTemplate` attributes on character XMLs (TAOM has none — verified).
4. ☐ Ensure every main culture provides at least one equipment roster for each of:
   - `IsLordTemplate` (battle, male)
   - `IsLordTemplate | IsChildEquipmentTemplate` (civilian, male child)
   - `IsLordTemplate | IsTeenagerEquipmentTemplate` (civilian, male teen)
   - `IsKingdomRulerTemplate` (battle, male)
   - Plus `IsFemaleTemplate` variants of all four (battle and civilian — except child/teen which only need civilian).
5. ☐ Audit `OnRulingClanChanged` listeners — Clan parameter semantics flipped from new ruler to old ruler. TAOM has 0 direct subscribers; check Patch24/Patch12 indirect exposure.

## Tooling — to be written in S0

### `tools/migrate_equipment_type_1_4_3.py`

Mechanical XML migration. Pseudocode:

```python
for each XML file under Main/_Module/ModuleData/**:
    parse XML
    for each <EquipmentSet> element:
        if attribute civilian="true" exists:
            remove civilian="true"
            add equipmentType="Civilian"
        elif no equipmentType attribute and no civilian attribute:
            add equipmentType="Battle"  # explicit per migration checklist
    for each <EquipmentRoster> element:
        if no culture attribute and equipment items don't imply culture:
            warn: missing culture attribute
    write back
```

Flags:
- `--dry-run` — print diff, don't write
- `--apply` — write changes
- `--report-missing-culture` — list rosters lacking culture attribute

### `tools/audit_equipment_roster_coverage.py`

Validates the per-culture mandatory matrix above:

```python
for each TAOM custom culture:
    for each required (flags, equipmentType) combination:
        if no roster found:
            report MISSING: <culture>, <flags>, <equipmentType>
```

Output feeds **S5b** authoring queue.

### `tools/validate_equipment_flags_1_4_3.py`

Scans for removed flag names and reports occurrences with file:line.

## Risk inventory

| Risk | Likelihood | Mitigation |
|---|---|---|
| Mechanical replace hits wrong element (false positive on non-EquipmentSet) | Medium | Smart parser that filters by element, not text-substitution |
| Missing mandatory roster → naked NPC / fallback culture | High if not authored | S5b authoring; audit script as gate |
| Roster authored against wrong LOTRLOME item IDs → underwear bug | Medium | Re-run `tools/validate_gondor_refs.py` post-authoring (extend to all cultures) |
| ChildCreatorAdapter rewrite breaks `InitialChildGeneration` feature | High | TDD: failing test first, verify against actual 1.4.5 model behavior |
| `OnRulingClanChanged` indirect-via-Patch24 silent breakage | Medium | Manual audit + integration test of WotR transition |
| New `Stealth` equipment type tempts mid-migration adoption | Low (scope-cut) | Explicit out-of-scope in plan |

## Out of scope

- **Adopting `Stealth` equipment type for TAOM disguise system.** Even if we have an existing disguise feature, switching it to use the new enum value is a separate enhancement.
- **Restructuring duplicate battle+civilian equipment sets** (TaleWorlds devs explicitly noted this is a known pain point they're not solving in 1.4).
- **Opportunistically adopting `UseTeamColor` on horse armor**, `no_slim` on hand armors, `item_holsters.xml` XSLT merge — useful but separate enhancement issues.
