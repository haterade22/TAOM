# Bannerlord v1.5.4: impact on TAOM

**Date:** 2026-10-05 · **Branch:** `bannerlord-1.5.x` · **Engine:** client v1.5.4.123627
(`TaleWorlds.Native.dll` and the managed assemblies stamped 2026-10-05 08:12, Steam buildid 25653793),
Modding Kit v1.5.4.123627 (its `TaleWorlds.Native.dll` stamped 08:11, a few minutes ahead of the
client), Steam beta branch · **Issue:** #736 · **Predecessor:** [v1.5.3-impact.md](v1.5.3-impact.md).

## Bottom line

- **A fresh build needs no code change.** `dotnet build TAOM.Tests --no-incremental` against the
  installed v1.5.4 assemblies: 0 errors, and against BUTR's `1.5.4.123627-beta` reference assemblies
  (`-p:TaomGameRefs=RefAsm`, what CI builds): 0 errors. Final full suite, with the NativeSkinFixes
  removal below: 14,033 passed, 5 skipped, 1 failed (see "Gates"). The strict binding gate
  (`binding-gate.runsettings`, `TestCategory=BindingVerification`): 464 passed, 0 skipped, 0 failed.
- **A shipped binary is not compatible.** v1.5.4 replaced
  `TooltipProperty(string, string, int, bool, TooltipPropertyFlags)` with a twin that appends an
  optional `List<(string, bool)> traitLevels`. Source compiles against either, so no source or binding
  gate could see it, but a binary built against the old shape calls a member that no longer exists.
  Resolving every engine member reference of each release channel's `TAOM.dll` against the installed
  v1.5.4 assemblies (System.Reflection.Metadata, by name and full signature):
  - the testing channel's **v2.0.33** (built 2026-10-02): 1 unresolved of 2,940, that constructor,
    called on 21 tooltip sites (a 22nd call uses the `Color` overload, which v1.5.4 keeps). Players on v1.5.4 hit `MissingMethodException` there.
  - the dev install's **v2.0.34** build (2026-10-04 19:48): 0 unresolved of 2,981; its two
    `TooltipProperty` constructor references already carry six parameters.
  - a fresh build: 0 unresolved of 2,981 (the negative control).
  - patreon and public hold v2.0.29.5, the 1.4.8 line, which does not target 1.5.x.
  The six-parameter constructor appeared between the v2.0.33 and v2.0.34 builds, so the installed
  v1.5.3 most likely moved to a later 1.5.3 build (v1.5.4 code checks for `v1.5.3.123225`) after the
  2026-09-15 decompile of `v1.5.3.122374` that served as this bump's baseline. Testers on v1.5.4 need
  a build newer than v2.0.33.
- **The modding changes in the release notes do not touch TAOM.** No TAOM C# references
  `Kingdom.EncyclopediaTitle`, `GetFormalNameForKingdom`, `ChangeKingdomName` or
  `KingdomManager.CreateKingdom`, and no XML in any installed module, `TAOM_Map` and
  `LOTRLOME_Armory` included, carries `str_kingdom_formal_name`. (`Kingdom.Deserialize` already
  asserted on that id in v1.5.3, and already read `FormalName` from `title`; only the assert's line
  moved.) TAOM's `str_faction_formal_name_for_culture.*` and `str_faction_informal_name_for_culture.*`
  are a different id family; all six vanilla ids are still in `Native/ModuleData/module_strings.xml`,
  so `module_strings.xslt`'s drop templates still match.
- **One visible change for free.** Two vanilla dialog lines (`KINGDOM_FORMAL_NAME`, `SERVED_FACTION`
  in `LordConversationsCampaignBehavior`) now read `Kingdom.FormalName` instead of the culture's
  formal name. All 14 kingdoms in `taom_spkingdoms.xml` define a `title` ("Kingdom of Erebor",
  "Overlordship of Isengard"), and the 8 that reuse vanilla ids get theirs from `spkingdoms.xslt`, so
  lords now name TAOM's realms by their own titles. A player-founded kingdom is now "Kingdom of
  {founder clan}": v1.5.4's governor dialog stopped passing the chosen name, and TAOM has no
  kingdom-creation hook. Read from code, not yet seen in game.
- **Three TAOM comments described engine behaviour that changed;** all corrected, no code change
  (see the body diff).

The new start flow lives in `SandBox.ViewModelCollection`: `CampaignStartingOptionsVM` drops the

`SettlementNameplateItem{Large,Medium,Small}.xml` and `EncyclopediaHeroPage.xml`. The hero page clone

`PrefabCloneWidgetReferenceTests` passes against the v1.5.4 files and no nameplate widget class

## Decisions taken with this bump

- **Rebellion thresholds stay TAOM's** (maintainer, 2026-10-05): `revolt_tuning_config.json` keeps
  5/10 (high rebellion 17/24). The harsher low-security loyalty penalty that `CalculateLoyaltyChange`
  inherits from vanilla is accepted as is.
- **NativeSkinFixes removed** (maintainer, 2026-10-05: "not needed anymore"). It was parked and
  disabled at the wiring level since 2026-07-08, and v1.5.4's notes say the engine now fixes the
  covers_head plus full-glove hand bug. Its C# installer, the C++ hook project,
  `TAOM.NativeSkinFixes.dll`, `MinHook.x64.dll` and its license notice, the MCM toggle and its two
  strings, its tests and the CI static-CRT step are gone, and the stale copies in the dev install and
  the 1.5.x testing channel were backed up and deleted (patreon and public carry the 1.4.8 line and keep
  theirs); see [native-skin-fixes.md](../features/native-skin-fixes.md). The
  `bannerlord-1.4.5` line keeps it, parked. Its commit hook, `check-native-dll-crt.sh`, retires once
  the maintainer removes its `.claude/settings.json` entry.
