# Bannerlord v1.4.8 — TAOM Impact Analysis

**Engine bump: v1.4.7 → v1.4.8 (2026-08-10).** Steam updated the installed shipping client to v1.4.8 (base game) / War Sails v1.2.8 at 07:22–07:33, build `117131 → 119303`, Steam `buildid 24573425`. The same update shipped the public **War Sails Modding Kit**. This doc maps every v1.4.8 changelog line to the TAOM surface it could touch, with each verdict verified firsthand against a fresh v1.4.8 decompile diffed line-by-line against the preserved v1.4.7 baseline. Minor patch bump, no schema migration — see [`v1.4.x-taom-impact.md`](v1.4.x-taom-impact.md) for the full 1.3.15→1.4.5 matrix and [`v1.4.7-impact.md`](v1.4.7-impact.md) for the previous bump.

## Bottom line

- **No TAOM binding broke, and nothing needed fixing.** TAOM compiles against the v1.4.8 assemblies with **0 errors**; `BindingVerification` is **106/106** (194 Harmony targets, 46 GameModels, reflection sites); full suite **6311 passed / 0 failed / 2 skipped**.
- **The API surface TAOM touches did not move at all.** Regenerating the committed snapshot against v1.4.8 changed **only the version strings** — not one of the 194 patch-target or 46 GameModel override signatures differs from the v1.4.7 copy.
- **Blast radius: 8 of 56 base-bin assemblies changed**, none added or removed, and three of those eight differ only by the build number. `TaleWorlds.MountAndBlade` — the combat assembly — changed by **one line**. (Scope: that count is `bin\Win64_Shipping_Client` only. The module-bin assemblies were never in the decompile stack — see "The decompile stack had a 34-assembly hole".)
- **Zero vanilla `ModuleData` XML changed.** No file under `Native`/`SandBox`/`SandBoxCore`/`StoryMode`/`Multiplayer`/`CustomBattle` `ModuleData` was touched, so the 1.4.7 vanilla *data* baseline survived the update intact and every parity audit still has something to compare against.
- **Data/creature/scene parity clean** against v1.4.8: `audit_action_set_parity.py` 0 gaps + 0 orphans (exit 0), `validate_moduledata.py` PASS, `audit_battle_scenes.py` all 256 map-indices, `audit_scene_names.py` live scenes OK, `audit_mount_parity.py` every usage action bound and every gait clip tagged.
- **Two things are owed and are not code:** in-game control battles (below), and TAOM's shader caches, which are one format version behind (below).

### The decompile stack had a 34-assembly hole

Found while auditing this bump, not before it. `tools/decompile_bannerlord.ps1` only ever walked
`<GameBin>\Win64_Shipping_{Client,wEditor}`, and `tools/decompile_to_folder.ps1` pulled only the
*primary* DLL per module (`SandBox.dll`, `StoryMode.dll`). So **34 vanilla assemblies that ship
inside module bin folders were in no decompile artifact at all**:

`SandBox.View` · `SandBox.ViewModelCollection` · `SandBox.GauntletUI(+AutoGenerated ×2)` ·
`TaleWorlds.MountAndBlade.View` · `TaleWorlds.MountAndBlade.GauntletUI(+AutoGenerated ×2)` ·
`TaleWorlds.MountAndBlade.Platform.PC` · `StoryMode.{View,GauntletUI,ViewModelCollection,…}` ·
all 7 `NavalDLC.*` · all 6 `Multiplayer.*` · `CustomBattle`, `BirthAndDeath`, `FastMode`, `DOTS`

TAOM patches heavily into several of them — `AgentVisuals`, `CharacterTableau`,
`MobilePartyVisual`, `SPInventoryVM`, the tournament controllers all live there. **The
1.4.7 → 1.4.8 assembly diff therefore covered the base bin only.**

This is a one-way loss: Steam overwrites the install in place, so an assembly absent from the stack
when an update lands has no recoverable baseline afterwards. The 1.4.7 bytes for those 34 are gone.

Closed two ways:
- `decompile_bannerlord.ps1` gained a `_modules_build` pass over `Modules\*\bin\Win64_Shipping_Client`
  (125 managed DLLs decompiled; files named `<Module>__<Dll>.cs` because names collide across
  modules — `TaleWorlds.MountAndBlade.Multiplayer.dll` ships in both `CustomBattle\` and
  `Multiplayer\`). The next bump is diffable.
- For *this* bump, `~/.taom-src/v1.4.7/` supplied a partial recovery: 42 of its 475 cached types come
  from module DLLs, decompiled per-type from the 1.4.7 binaries by the same tool that reads 1.4.8 —
  so those diff apples-to-apples. That set is not arbitrary; it is every module-DLL type TAOM has
  ever had reason to look up, including `AgentVisuals`, `CharacterTableau`, `BasicCharacterTableau`,
  `TournamentBehavior`, `TournamentFightMissionController`, `SandBoxSaveHelper`, `MissionScreen`,
  `MissionAgentHandler` and the GameModel base `SandboxAgentStatCalculateModel`.
  **Result: 42 identical, 0 changed, 0 failed to compare.** Every module-DLL type TAOM has ever
  touched is byte-identical between v1.4.7 and v1.4.8.

What was never in doubt for these assemblies is the **signature** layer: `patch-targets.md` resolves
all 194 Harmony targets through Harmony's own resolution against the installed engine — including
targets inside `SandBox.View` and `MountAndBlade.View` — and regenerated byte-identical, with
`BindingVerification` 106/106. The hole was **body-level** diffing, which is exactly the class that
bit us at 1.4.7.

### The Modding Kit finally caught up

The `Win64_Shipping_wEditor` build had been stuck at **v1.4.5.114928** — three versions behind the shipping client — and 1.4.8 brought it to **v1.4.8.119303**, level for the first time. That is what the War Sails Modding Kit release means in practice: scene authoring, metamesh save, and terrain-shader compilation now run on the same engine the game does. The preserved baseline is therefore named `_editor_build_v1.4.5`, not `_v1.4.7`.

## Code changes made this bump

**None to `Main/`.** No binding broke, no signature moved, no patch needed re-authoring. The only code touched was the harness:

### `session-start.sh` — the drift guard failed on the event it exists for

This session's `SessionStart` hook printed **no** `GAME VERSION DRIFT` banner despite the game being v1.4.8 and the pin v1.4.7. It was not a race: the session transcript's birth time is `2026-08-10 08:20:07`, 47 minutes after the update finished at 07:33.

Root cause: `GAME_VERSION_XML="${BANNERLORD_GAME_DIR:-<literal>}/bin/..."`. The `:-` form substitutes the literal only when the variable is **unset or empty** — a variable that is *set but does not resolve in the hook's environment* sent the `-f` test straight to false and the whole block fell through in silence. `.claude/settings.json` does not define `BANNERLORD_GAME_DIR`, so the hook inherits whatever the harness process carries. Reproduced by exporting a bogus path: banner gone, no diagnostic.

Fixed by trying the env path, then **always** falling back to the known install, and printing an explicit `engine drift is UNCHECKED this session, not absent` line when neither resolves. Still fail-open — but no longer fail-*silent*, because silence from this guard reads as "no drift" when it means "never checked". All four paths verified (normal / bogus-env / no-install / non-startup source).

## Owed

### Shader caches are one format version behind (deferred by decision — [#448](https://github.com/haterade22/TAOM/issues/448))

Every `compressed_shader_cache.sack` the 1.4.8 update wrote carries format version `0x0783`. **Corrected 2026-08-10: the install holds 491 sacks, 487 of them `0x0783`** — the first survey scoped `find` to `Modules/` and missed the game-root `Shaders/D3D11/compressed_shader_cache.sack` (1.58 GB, also `0x0783`). All three TAOM-side sacks still carry `0x0782`:

| Module | Size | Version |
|---|---|---|
| `TAOM/Shaders/D3D11/` | 36 B (empty) | `0x0782` |
| `TAOM_Map/Shaders/D3D11/` | 49.8 MB | `0x0782` |
| `LOTRLOME_Armory/Shaders/D3D11/` | 108.7 MB | `0x0782` |

~158 MB of precompiled cache written under v1.4.7. Whether v1.4.8 ignores it, accepts it, or routes it into the new corrupted-cache fallback is **unverified**. Deferred deliberately; tracked as **#448** with three candidate paths (probe whether `0x0782` still loads · regenerate via the in-game walk · adopt the 1.4.8 publish pipeline, which now compiles terrain shaders).

### The Modding Kit jump and native-crash triage

**Corrected 2026-08-10 after fact-check — an earlier revision of this section overstated the blast
radius twice.** The accurate position:

`tools/native_crash_triage.py:37` defaults `--dll` to the **shipping client**
`TaleWorlds.Native.dll`, and `.claude/skills/native-crash-triage/SKILL.md:55` scopes the editor
binary narrowly — *"Editor crashes: pass `--dll` pointing at the `Win64_Shipping_wEditor`
`TaleWorlds.Native.dll`."* So the default triage path was never on the wEditor image, and the earlier
claim that "every offset previously derived through that skill was against a 1.4.5 image" was wrong.
What is true: **offsets derived for *editor* crashes** came off a binary that sat at `v1.4.5.114928`
until 07:25 today and is now `v1.4.8.119303`, having moved with no signal.

The second overstatement: local native images **do** survive. Two are on disk —
`E:\BannerlordBackup\1.3.15\bin\Win64_Shipping_Client\TaleWorlds.Native.dll` and
`E:\LOTRAOMAssets\native_dll_snapshots\TaleWorlds.Native.CURRENT_2026-06-30_1746.dll`. Neither is
v1.4.7, so the open report at `crashz/report.json` (`v1.4.7.117484`) still has no matching local
image, but "no native image survives locally" was false.

The durable lesson stands and is cheap: **copy both `bin/Win64_Shipping_{Client,wEditor}/TaleWorlds.Native.dll`
aside on every bump.** Nothing archives native modules — the decompile stack only *lists* them in
`_native_dlls.txt` — and Steam overwrites in place.

`engine-bump/SKILL.md:17` already warns "the wEditor build updates on its OWN Steam schedule — check
its DLL dates separately." That step was not run this session; the jump was found afterwards, by
diffing. Two other wEditor-dependent workflows moved under us: the sprite pipeline
(`.claude/rules/gui-ui.md:38` runs `TaleWorlds.TwoDimension.SpriteSheetGenerator.exe`, whose assembly
moved 106 lines) and `Main/SceneScripts/` (`Main/TAOM.csproj` mirrors the deployed client build into
`bin/Win64_Shipping_wEditor`, so TAOM.dll loads under the editor).
