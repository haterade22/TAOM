# Recipe: retiring content

## What this file is

The recipe for taking something out: a troop, an item and the art behind it, a lord, a clan, or a
vanilla entity you never wanted. Removing is the operation TAOM has got wrong most often, because a
deletion is invisible where you make it and shows up somewhere else, days later, as a naked troop or
a blank icon. Read this before you delete a line, not after.

## What a save actually holds

Whether a deletion is safe turns on one question: does the save file carry that entity's state, or is
it re-read from XML on every load? `AutoGeneratedSaveManager.cs` answers it by listing every member
the save writer touches for each type.

<!-- engine-ref type="TaleWorlds.CampaignSystem.AutoGeneratedSaveManager" file="Campaign/TaleWorlds.CampaignSystem/TaleWorlds.CampaignSystem/AutoGeneratedSaveManager.cs" lines="160-368" -->
<!-- measured: rg -c "\b<Type>\.AutoGeneratedGetMemberValue" over both AutoGeneratedSaveManager.cs files 2026-09-05 -->

| Entity | Engine class | Members the save writes | What that means for deleting |
|---|---|---|---|
| Troop | `CharacterObject` | 2 (`_heroObject`, `_originCharacter`, `CharacterObject.cs:20-24`) | level, skills, equipment and name come from XML every load |
| Item | `ItemObject` | 0 | every stat comes from XML every load |
| Culture | `CultureObject` | 0 | same |
| Party template | `PartyTemplateObject` | 0 | same |
| Kingdom | `Kingdom` | 27 | the live kingdom is inside the save |
| Settlement | `Settlement` | 28 | the live settlement is inside the save |
| Clan | `Clan` | 40 | the live clan is inside the save |
| Hero | `Hero` | 58 | the live hero is inside the save |

Each also carries its own id: `MBObjectBase.StringId` is `[SaveableProperty(1)]`
(`MBObjectBase.cs:11-12`), so an old save names the ids it was created with whatever the XML says now.
**Changing numbers on a troop or an item is therefore free on an existing save** (this is why
[Troops](troops.md) allows tier shifts across one), and **changing an id never is**.

Counting `[SaveableField]` on the class is a different check and can undercount, because Bannerlord
persists some members that carry no attribute at all. `Hero.Culture` and `Settlement.Culture` are both
bare `public CultureObject Culture;` fields and only the first is in the save: `Settlement.cs:961`
re-reads settlement culture from XML on every load. The reverse claim shipped into four documents
before anyone checked
([state-lifecycle-save.md](../reviews/lessons/state-lifecycle-save.md), the `Save-compat:` lesson).

## Three ways to remove something

| Strategy | What you do | Old saves | Use it when |
|---|---|---|---|
| **Orphan** | leave the entry, remove every path that reaches it (`<upgrade_target>`, party-template stack, recruitment pool) | survive intact | the default for a troop. `.claude/rules/troops.md:148-150` states it as a rule: never delete a troop, orphan it |
| **Obsolete stub** | strip the entry to a shell and mark it, keeping the id resolvable | survive; the entity stops taking part in anything | vanilla's own answer, below. TAOM has never used it: `is_obsolete` appears 0 times in `Main/_Module/ModuleData` |
| **Delete** | remove the entry and sweep every reference | break where the save names the id | you accept it and say so. `docs/features/gondor-armor-revamp.md:112` deleted 5 Lossarnach troops on the note that pre-1.0 saves are not preserved |

Pick one before editing and put the choice in the commit message. The failure mode is picking none,
deleting half, and leaving a file that reads as intentional.

## Worked example

### Vanilla's obsolete stub

<!-- example file="SandBoxCore/ModuleData/obsolete_characters.xml" id="huskarl_swordsman" -->

```xml
	<NPCCharacter
		id="huskarl_swordsman"
		default_group="Infantry"
		level="26"
		name="{=jFQPRvLg}Huscarl Swordsman"
		occupation="Soldier"
		culture="Culture.sturgia"
		is_hidden_encyclopedia="true"
		skill_template="SkillSet.infantry_heavyinfantry_level26_template_skills"
		is_obsolete="true">
```

This file lives in the game install, not the repo; a module reinstall reverts hand edits, so land a
repo-side validator gate with any fix. It is registered like any other troop file, as
`<XmlName id="NPCCharacters" path="obsolete_characters" />` in `SandBoxCore/SubModule.xml:78`, and it
exists to keep retired ids resolvable for saves that still name them. 39 entries, 30 flagged.

The three things to change when copying the pattern:

1. **`id`** must match the retired troop's id character for character. That is the whole point.
2. **`is_obsolete="true"`** is read once (`BasicCharacterObject.cs:336`) and used in exactly one place:
   `Hero.cs:1537` skips a hero's re-registration into its clan, settlement and companion lists on load.
   On a plain troop the flag changes nothing by itself, so the stub works by what it omits: an empty
   `<upgrade_targets>` and no culture binding mean nothing recruits or upgrades into it.
3. **`is_hidden_encyclopedia="true"`** keeps the shell out of the troop tree the player browses.

### The XSLT strip, in two shapes

A vanilla entity is removed by matching it with an empty template, so the identity transform never
copies it forward. Narrow (five named ids) and wide (every element of a type):

<!-- excerpt file="Main/_Module/ModuleData/spclans.xslt" -->

```xml
  <xsl:template match="Faction[@id='sea_raiders']"/>
  <xsl:template match="Faction[@id='mountain_bandits']"/>
  <xsl:template match="Faction[@id='forest_bandits']"/>
  <xsl:template match="Faction[@id='desert_bandits']"/>
  <xsl:template match="Faction[@id='steppe_bandits']"/>
```

<!-- excerpt file="TAOM_Map/ModuleData/settlements.xslt" -->

```xml
	<!-- Remove all vanilla Settlement elements -->
	<xsl:template match="Settlement"/>
```

That second stylesheet is 15 lines and removes 494 vanilla settlements, because the merge applies each
module's stylesheet to the document accumulated so far and only then merges that module's own file
(`MBObjectManager.cs:966-980`). TAOM_Map then supplies its own 988.

### The reference sweep, as a script

Deleting the entry is the small half. `tools/cleanup_deleted_troops_212.py` is the pattern for the
other half: 29 ids, and three files that name a troop and none of which is the troop file.

<!-- excerpt file="tools/cleanup_deleted_troops_212.py" -->

```python
TARGETS = {
    "taom_partyTemplates": "Main/_Module/ModuleData/taom_partyTemplates.xml",
    "troop_weights":       "Main/_Module/ModuleData/TroopWeights/troop_weights.xml",
    "resource_costs":      "Main/_Module/ModuleData/special_resources/troop_resource_costs.xml",
}
```

36 files under `Main/_Module/ModuleData` name a troop through the `NPCCharacter.` prefix, and more name
one as a bare id with no prefix at all. Grep for the bare id too, never only the prefixed form.

## Recipes

### Retire a troop

1. Decide orphan or delete from the table above, and write the choice into the commit message.
2. In the culture's file under `Main/_Module/ModuleData/troops/`, remove every
   `<upgrade_target id="NPCCharacter.<id>" />` pointing at the troop. Do this even when orphaning: it
   is the step that takes the troop out of play.
3. Sweep the three satellite files in the block above. The stale `<PartyTemplateStack>` row is the one
   that hurts, because a party template is what vanilla `SpawnLordParty` walks.
4. Sweep the code and the bare-id configs. `Main/Features/TroopProgression/VolunteerRecruitmentService.cs`
   and `Main/_Module/ModuleData/settlement_guards/settlement_guards_config.xml` name troop ids
   directly, and the generator that produced the troop recreates it on its next run unless you remove
   its definition there too (`docs/features/gondor-armor-revamp.md:118-121`).
5. If you deleted, add the stub from the worked example to keep the id resolvable, or accept that those
   saves break and say so.

Check: `python tools/validate_moduledata.py --code BROKEN_TROOP_REF --code BROKEN_PARTY_TEMPLATE_REF`
Takes effect: full game restart
Code: Code changes required in `Main/Features/TroopProgression/VolunteerRecruitmentService.cs` when the troop is named there

### Retire an item and its mesh

1. **Find the consumers before deleting anything.** `python tools/audit_item_refs.py --show-locations`
   lists every `Item.<id>` reference resolving to nothing, and
   `python tools/audit_deleted_mesh_impact.py` joins a deleted mesh through its item to its consumers
   across five reference shapes (`tools/audit_deleted_mesh_impact.py:38-46`): the `Item.` attribute, the
   `<EquipmentSet>` roster hop, culture reward lists, four bare-id configs TAOM parses in C# rather than
   through the engine resolver, and refs authored inside XSLT that exist in no `.xml` file.
2. An `ORPHAN` verdict is not the same as unreferenced. That tool matches `Item.` references and roster
   hops, and a crafting piece is named by neither: `<UsablePiece piece_id=>` and `<Piece id=>` are their
   own shapes. Six Easterling pieces read `ORPHAN` while one was a career start's weapon
   (`docs/features/armoury-mesh-cleanup.md:176-184`).
3. Re-point every surviving consumer onto replacement art before removing the definition.
   `tools/apply_dead_mesh_item_swaps.py` is the pattern: previews by default, writes only with
   `--write`, and keeps three mechanisms apart, an `Item.` reference swap, a `mesh=` re-point that
   leaves stats alone, and a whole-definition delete.
4. Only then delete the `<Item>` definition, in **both** Armory copies. The item folders live in the
   game install: `LOTRLOME_Armory/ModuleData/LOTRLOME_items/gondor/head_armors.xml` and its siblings.
5. Run both gates. Neither sees the other's half: `validate_mesh_refs.py` walks item XML and resolves
   meshes, so an item deleted outright is invisible to it, while `validate_moduledata.py` resolves
   `Item.` references, so an item whose art vanished still resolves clean
   ([the 2026-09-01 RCA](../reviews/rca-armoury-keyforce-cleanup-2026-09-01.md): one green gate hid
   212 of 275 breakages).

Check: `python tools/validate_moduledata.py --code BROKEN_ITEM_REF` and `python tools/validate_mesh_refs.py --no-rgl-log`
Takes effect: full game restart
Code: No code changes needed

### Retire a lord or a clan

1. A lord is two entries: an `<NPCCharacter>` in `Main/_Module/ModuleData/characters/lords.xml` (1,184
   of them) and a `<Hero>` in `characters/heroes.xml` (1,001) whose `faction="Faction.<clan>"` binds it
   to a clan in `characters/clans.xml` (145). Removing one and not the other leaves a half-entity.
2. Both are save-bound (58 and 40 members in the table above), so the deletion never reaches a running
   campaign. Treat every lord and clan removal as new campaigns only.
3. Before removing a clan, check what it holds. Vanilla `SpawnLordParty` runs an unguarded
   `Settlement.All.First(x => x.Culture == hero.Culture)` on the daily clan tick, so stranding a
   culture with no settlement is a crash with no TAOM frame
   ([lord-spawn-guard.md](../features/lord-spawn-guard.md), line 24).
4. Sweep the id out of `lords.xslt` and `heroes.xslt` too. Those stylesheets author lord data that
   exists in no `.xml` file, so a grep of the XML alone misses them.

Check: `python tools/validate_moduledata.py --code LANDLESS_CULTURE --code UNKNOWN_CULTURE`
Takes effect: new campaign only
Code: No code changes needed

### Strip a vanilla entity with XSLT

1. Add an empty template matching the entity to that file's stylesheet: narrow
   (`match="Faction[@id='sea_raiders']"`) for five things, wide (`match="Settlement"`) for all of them.
2. Write the reason in a comment above the templates. `spclans.xslt` records that vanilla's
   `BanditSpawnCampaignBehavior` indexes a hideout dictionary by clan culture with a hard indexer, so
   leaving those five clans in with no hideouts of their culture is a new-game crash. Later that
   comment is the only thing saying why the strip cannot be reverted.
3. Check the strip by hand. No validator models XSLT: of the 16 stylesheets across the three modules,
   exactly one is ever opened by any validator, `TAOM_Map/ModuleData/settlements.xslt`, and only for a
   single yes or no question ([tools/README.md](../../tools/README.md), the XSLT note). Transform the
   vanilla file yourself and count what came out.
4. Grep before adding a strip block. The five bandit templates in `spclans.xslt` are already present
   twice, at lines 27 to 31 and again at 1160 to 1164, comment and all.

Check: `python tools/validate_moduledata.py`
Takes effect: new campaign only for save-bound entities (clans, kingdoms, heroes, settlements), full game restart otherwise
Code: No code changes needed

### Never delete a settlement

Not on a live map. Three reasons stack:

1. A settlement carries 28 saved members, so an existing campaign holds its own copy and the XML
   deletion does not reach it. You get divergence, not removal.
2. A culture left holding zero settlements crashes the daily clan tick.
   `Patch65_LandlessCultureSpawnGuard` guards the symptom, not the cause.
3. The file you would edit is probably the wrong one. `TAOM_Map/ModuleData/settlements.xml` is live and
   holds 988 entries; the repo's `Main/_Module/ModuleData/settlements.xml` holds 863 and is loaded by
   nothing, because `Main/_Module/SubModule.xml` declares no `Settlements` XmlName at all.

Retarget instead: change its culture, owner or type and leave the id in place. See
[Settlements](settlements.md).

Check: `python tools/validate_moduledata.py --code LANDLESS_CULTURE`
Takes effect: new campaign only
Code: No code changes needed

## Gotchas: what fails silently and what crashes

- **A missing item id in an equipment slot is silent.** `Equipment.DeserializeNode` looks the item up
  with `GetObject<ItemObject>`, which returns null, and `IsItemFitsToSlot` returns `true` for a null
  item by design, so the slot takes an empty element and the troop spawns without that piece. No log
  line, no assert (`Equipment.cs:204-222`, `Equipment.cs:445-450`).
- **A missing id anywhere else is worse than null: it is a hollow object.**
  `ReadObjectReferenceFromXml` never returns null for an unknown id. It calls `GetPresumedObject`,
  which creates and registers an empty instance with `IsReady = false` (`MBObjectManager.cs:716-736`,
  `MBObjectManager.cs:1497-1515`). Every campaign type registers with auto-create on by default
  (`MBObjectManager.cs:376`, `Campaign.cs:1537`), so an `<upgrade_target>` naming a deleted troop
  (`CharacterObject.cs:565`) yields a real object with no stats rather than an error.
- **A duplicate id merges, it does not shadow, so a backup file must never end in `.xml`.** Files under
  one `XmlName` are merged before any object is built, keyed on the schema's unique attributes, and a
  later element with the same key merges attribute by attribute into the earlier one
  (`MBObjectManager.cs:846-867`). A folder-registered path globs `*.xml` in that folder
  (`MBObjectManager.cs:894-910`), and the Armory registers 18 folders holding 101 XML files beside 3
  single-file paths. The 10 sidecars living there put the date after the extension
  (`body_armors.xml.bak-deadmesh-20260901130757`), which is what keeps them out of the glob. Sweep them
  before a release: `pwsh tools/sweep_module_backups.ps1`
  ([module-backup-sweep.md](../reference/module-backup-sweep.md)).
- **One green gate is not a clean run.** The Armory is untracked, so the commit hook gating staged
  `Main/_Module/ModuleData/**/*.xml` never fires on an armour edit. Run those checks by hand or they do
  not run ([the RCA](../reviews/rca-armoury-keyforce-cleanup-2026-09-01.md), finding 2).
- **Deleted art and art that never existed need different remedies.** 24 Gondor sword meshes read as
  deleted by a cleanup; the base commit showed only four had ever shipped, so a restore would have run
  clean and changed nothing
  ([rca-armoury-dead-mesh-wave2](../reviews/rca-armoury-dead-mesh-wave2-2026-09-01.md)).
- **Delete on positive proof, never on a failure to find proof.** A sweep that reads "I could not
  resolve this" as "this is unused" behaves identically on a healthy install and destroys a broken one
  ([state-lifecycle-save.md](../reviews/lessons/state-lifecycle-save.md), the destructive-repair lesson).

## What nobody has written down yet

- **What a running campaign does when it loads a save naming a deleted troop or item id has never been
  tested here.** The pieces are known (the save carries the id, the registry no longer has it, the
  presumed-object path exists) but nobody has run the experiment. Start at `MBObjectBase.OnBeforeLoad`
  (`MBObjectBase.cs:63-76`) and `MBObjectManager.RegisterMBObjectWithoutInitialization`
  (`MBObjectManager.cs:190-199`), then make a save, delete an id, and load it.
- **What the validator does not check.** No numeric range checks, and only three schemas exist under
  `tools/schemas/`, so nothing gates `taom_partyTemplates.xml`, `troop_weights.xml` or the Armory item
  files for sane values. Its reach is uneven by module:
  [moduledata-validation.md](../features/moduledata-validation.md) and
  [tools/README.md](../../tools/README.md). A PASS means "no broken references in the roots it walks".
