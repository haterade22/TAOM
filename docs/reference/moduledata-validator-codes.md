# ModuleData validator codes

Every finding of `python tools/validate_moduledata.py`, the bug class behind it and how to repair it, plus
what the validator scans and the discipline for changing it. The short rule that loads with the data files
is `.claude/rules/moduledata-validation.md`; the design is [the feature doc](../features/moduledata-validation.md).

## Codes

| Code (severity) | Bug class it catches |
|---|---|
| `BROKEN_ITEM_REF` (error) | a `Item.X` ref to no defined item — the "underwear bug" (troop spawns naked) |
| `BROKEN_TROOP_REF` (error) | an `NPCCharacter.X` ref (upgrade_target, party-stack `troop=`, culture `basic_troop=`) to a deleted troop |
| `BROKEN_FACTION_REF` (error) | a `Faction.X` ref (settlement `owner=`, Hero `faction=`) to a clan no `<Faction id>` defines: `characters/clans.xml` plus vanilla `spclans.xml`, minus the bandit clans `spclans.xslt` strips. The settlement or hero loads ownerless. `Faction.neutral` (the engine's clanless value) is allowed. Skipped without the install; the `.xml` files only ([details](../features/moduledata-validation.md)) |
| `BROKEN_BODY_PROPERTY_REF` (error) | a `face_key_template` that names a `BodyProperty` nothing defines, so the character loads with a null face. Add the BodyProperty or repoint the template |
| `MISSING_EDUCATION_TEMPLATES` (error) | a main culture with no `child_education_templates_stage_2_page_0_branch_N_<culture>` character for some branch, so the age-8 child education hits a null tutor template and CTDs (#354). Add the missing templates to `taom_education_character_templates.xml` |
| `MISSING_HARNESS_FAMILY_TYPE` (error) | a `HorseHarness` item with no `<Armor family_type>`. It defaults to 0 (human), so the inventory refuses it on every mount. Set it to the mount's `Monster.family_type` (1 for horses) |
| `HARNESS_FAMILY_MISMATCH` (error) | a Horse and a HorseHarness in one equipment set whose family types differ. The engine silently unequips the harness on the next inventory transfer. Pair a harness of the mount's family |
| `UPGRADE_SKILL_REGRESSION` (error) | an upgrade edge whose target has a lower skill value than its source in any skill; an omitted `<skill>` reads as 0, so it counts as a drop. Militia to militia is exempt, keyed off what a culture binds, and an edge in `_RESPECIALIZATION_EXEMPT_EDGES` (`taom_schema.py`) is exempt on the skills it names. A side with a `skill_template` is judged on its effective skills: the SkillSet with the inline rows laid over it (`BasicCharacterObject.Deserialize` since v1.5.2), resolved through `sync_lord_inline_skills.effective_skills`. Without the install those edges are skipped and the CLI prints the skip; a SkillSet read that fails, or finds no vanilla SkillSet file in the install, is one ERROR (`(skill sets)`), and the two skill writers refuse the same root. Repair: `python tools/rebalance_troops.py --fix-monotonicity`; a templated target is repaired in its SkillSet, because the clamp refuses to write it |
| `BROKEN_ROSTER_REF` (error) | an `<EquipmentSet id>` that names no `<EquipmentRoster>`: the engine null-dereferences inside the NPCCharacters load, and its empty catch stops every character after it in the merged document from loading, with no crash at the typo. Rosters come from TAOM, vanilla, the Armory and TAOM_Map, minus any an xslt strips by id; refs come from the `.xml` files and TAOM's `.xslt` files (`lords.xslt` holds most). Skipped without the install |
| `BROKEN_SETTLEMENT_REF` (error) | a `Settlement.X` ref (a clan's or kingdom's home, a village's `bound`) to no settlement in the world the game builds: `TAOM_Map`'s rows, since its `settlements.xslt` strips vanilla's. TAOM's repo has no settlement file (the unloaded `settlements.xml` and `custom_settlements.xml` were removed on 2026-11-14). Skipped without the install. It reads the `.xml` files and TAOM's `.xslt` files, where `spclans.xslt` writes homes as element text. Fix the id, or add the settlement to the live map. `tools/check_release_pair.py` runs this code against a release channel |
| `TROOP_ID_REMOVED` (error) | a troop id listed in `tools/shipped_troop_ids.txt` (the newest release tag's ids) that no `troops/troops_*.xml` defines. A save holding it keeps a hollow `CharacterObject` whose null `UpgradeTargets` the engine's daily ticks read unguarded (#670). Restore the id and retire the troop by removing it from every `upgrade_targets`; or, for a break the maintainer accepted, add `id \| reason` under `[exceptions]` in the baseline. `/release` regenerates the file with `python tools/validate_moduledata.py --regenerate-shipped-troop-ids` |
| `UNKNOWN_CULTURE` (error) | a `culture="Culture.X"` that is not a real StringId (e.g. `rohan` instead of `vlandia`, `dale` instead of `sturgia`) |
| `LANDLESS_CULTURE` (error) | a culture on a `Lord`-occupation `NPCCharacter`, `<Faction>` or `<Kingdom>` that owns **no settlement** — vanilla `SpawnLordParty` ends with an unguarded `Settlement.All.First(x => x.Culture == hero.Culture)`, so its lords CTD the daily clan tick (#374). Known-landless cultures live in `_LANDLESS_BY_DESIGN` with a stated reason |
| `SETTLEMENT_ECONOMY_FLOOR` (error) | a settlement of a culture named in `tools/settlement_economy_floor.json` sits below that spec's town/castle/`hearth` floor in the **LIVE** `TAOM_Map` module. That module is unversioned, so a reinstall silently reverts the 2026-08-14 faction-economy pass and nothing else in the repo would notice. Also fires when the spec is missing, declares nothing, or names a culture that owns no settlement (a retag or typo leaves the gate covering nothing, which reads exactly like a clean run). Re-apply with `python tools/rebalance_settlement_prosperity.py --culture-floor-file tools/settlement_economy_floor.json --apply` |
| `MOUNTED_DWARF` (error) | a `race="dwarf"` `NPCCharacter` able to reach a `slot="Horse"` item that is **not** a dwarf mount (own inline roster, or a standalone roster it names), or tagged `default_group="Cavalry"`/`"HorseArcher"` while carrying none. The dwarf skeleton's rider bone is misaligned, so a mounted dwarf spawns inside the horse mesh. Nothing enforces this in battle: `Patch46_TournamentDwarfDismount` only strips every dwarf's horse in a tournament, dwarf mounts included. **Both halves are needed:** `CharacterObject.GetFormationClass()` ignores `default_group` when `IsHero` and reads `BattleEquipment` instead, so an enum-only check passes a lord who still spawns mounted. **The dwarf mounts are the carve-out** (`DWARF_MOUNT_IDS` in `tools/taom_schema.py`: the war ram, #515, and the WildMesh3D boars and goat, #794): a dwarf on one is legal and is genuinely Cavalry, so the group rule relaxes with it, but only for a character who actually carries one |
| `CREATURE_GEAR_OBTAINABLE` (error) | an item a `cave_troll` or `hill_troll` `NPCCharacter` can reach (inline rosters plus the standalone rosters it names), or one named in `_CREATURE_GEAR_EXTRA` (the unworn troll shield), that is merchandise in its XML, or a crafting piece of such a crafted weapon without `is_hidden="true"`. `is_merchandise="false"` alone keeps an item out of shops, workshops, loot and tournament prizes, and `is_hidden` alone keeps a piece out of the smithy; both live in the unversioned Armory. A run that finds no troll character, or a piece no file defines, is a finding; skipped without the install. Repair: `python tools/lock_creature_gear.py --apply` (`--modules` for a release channel; [troll-race.md](../features/troll-race.md)) |
| `MOUNT_WITHOUT_HARNESS` (error) | a `slot="Horse"` entry with no `slot="HorseHarness"` beside it in the same equipment set. **A harness is required, not optional.** It is not always armour: on some mounts it carries the rider's SEAT, and nothing in the XML distinguishes those, because where the saddle is modelled is a property of a mesh the validator cannot see. `sk_eb_goat_a`/`_b` are bare pelts and every ram saddle lives on one of the eight `sk_eb_goat_bard_*` harness meshes, so `ironpass_ram_herder` shipped four sets putting a dwarf on bare hide. Judged per equipment set, because the engine draws each slot from an independently chosen set, so filling three sets of four still spawns bare rams. Exemptions are named in `_HARNESSLESS_BY_DESIGN` with a reason each, in the `_BODYLESS_BY_DESIGN` style: currently the mumakil (a harness suppresses the Horse item's `<AdditionalMeshes>`, where its war-platform lives) and the spider rider (an OPEN GAP, no spider harness item has ever been authored) |
| `MISSING_BODY_ARMOUR` (error) | a troop in `troops_*.xml` whose **battle** sets never fill the `Body` slot, so it spawns bare-chested. No reference is broken and no mesh is missing, which is why every other gate passes it. The troops bare-chested on purpose live in `_BODYLESS_BY_DESIGN` with a reason (`dg_goblin_slave` and `hill_troll` have no Body item; the Uruk-hai champion and berserker wear a skirt there that leaves the torso bare); a test asserts those ids still exist, because an allowlist entry for a renamed troop rots silently. Found 2026-09-01: 15 of 16 Umbar troops in peasant rags with a green board |
| `ITEM_SLOT_REJECTED` (error) | an equipment row, battle or civilian, whose item type the engine will not put in that slot. `Equipment.DeserializeNode` assigns only when `IsItemFitsToSlot` passes, else it asserts and the slot stays empty, so the troop never wears the item. No ref is broken and the XSD types `slot` as a plain string, which is why nothing else caught the two Uruk troops shipping `BodyArmor` in `Cape` (#729). Reuses `audit_battle_equipment_memory.py`'s slot rule, rosters and troop-level overrides; every module's refusals are reported, and a module folder that is missing is a WARNING, not a pass |
| `SETTLEMENT_ASSIGNMENT_DRIFT` (error) | a town or castle pinned in `tools/settlement_assignments.json` whose owner or culture in the **LIVE** `TAOM_Map` differs from the pin, or a village bound to it with another culture: a reinstall or an older editor save reverted a deliberate reassignment. A missing or empty spec, an entry without a reason, or a pinned id that is not a fortification is also an error. Repair: `python tools/apply_settlement_assignments.py --apply` |
| `PRISON_SCENE_NOT_STEALTH` (error) | a settlement in the **LIVE** `TAOM_Map` whose `prison` Location names a scene with no `stealth_agent` or no `prison_break_reinforcement_point` entities. The 1.5.x prison break spawns its guards on the first and its reinforcements on the second; the pre-stealth `*_dungeon_a/_b` scenes have neither, so the guards have no stealth spawn points and the prison break is expected to fail (not verified in game). Orthanc and Orthanc Gate named `empire_dungeon_a` while the other 278 prisons used a `*_dungeon_stealth` scene (2026-11-13). A prison scene no module ships, or a missing live file, is a WARNING; a live file that does not parse, or one with no prison Location rows, is an ERROR (nothing was checked). Skipped without the install. `tools/check_release_pair.py` runs the same check on a release channel's `TAOM_Map`, since a repair to one install reaches players only through a package that carries it. Repair: run `python tools/remap_stale_scene_names.py --dry-run`, then with `--apply` (a backup is made); the finding names the tool only when the scene is a key of its `REMAP` table, otherwise point the prison at a `*_dungeon_stealth` scene |
| `UPGRADE_TIER_COLLAPSE` (error) | an upgrade edge whose target does not reach a higher tier than its source. Vanilla `DefaultPartyTroopUpgradeModel.GetXpCostForUpgrade` sums a per-tier table over `for (i = source.Tier + 1; i <= target.Tier; i++)`, so such an edge exits the loop immediately and the cost is **0**. `CampaignUIHelper.GetTroopXPTooltip` then evaluates `troop.Xp % cost` unguarded, which is a hard CTD on a party-screen hover (bundle a7dc3a20, #537); `PartyUpgraderCampaignBehavior` reads the same zero as "free" and promotes the whole stack for gold alone; `PartyBase.OnXpChanged` clamps roster XP to `Number * maxCost` and wipes it every tick. Tier is `clamp(ceil((level - 5) / 5), 0, MaxCharacterTier)`, a pure function of `level=`, so this is a data defect. `TaomPartyTroopUpgradeModel.GetXpCostForUpgrade` floors the cost at runtime, so a new collapse is no longer a crash; this gate exists so it stays a decision someone made. Ten deliberate same-level laterals (the elf tier-10 capstone fan-outs, the two `chosen_of_tharzog` capstones, the uruk ranged branch, the Dol Guldur villager entry) live in `_LATERAL_BY_DESIGN` with a stated reason each |
| `UPGRADE_INDEX_EMPTY` (error) | the shared index behind `UPGRADE_SKILL_REGRESSION` and `UPGRADE_TIER_COLLAPSE` came back with no troops, or with none carrying a `level=`, so both gates checked nothing that run. Those two read `troops/troops_*.xml` and `characters/npcs_*.xml` literally and non-recursively, unlike every sibling pass which `rglob`s, so a renamed folder or a file moved one directory deeper empties them silently. Added with #537 because a gate that quietly checks nothing reads exactly like a clean run |
| `SKILL_TEMPLATE_MISMATCH` (error) | an inline `<skills>` row beside a `skill_template` that differs from the template's value, or a template with inline rows that names no SkillSet, in any XML or XSLT file of the repo module's ModuleData (the Armory and `TAOM_Map` are not scanned); a run that finds no templated character at all is an error too. Since v1.5.2 `BasicCharacterObject.Deserialize` lays the inline rows over a copy of the template, so a differing row changes the character while the SkillSet (the source of truth) and every tool reading it say otherwise; v1.4.8 discarded the rows. 64 lords in `lords.xml` and 19 in `lords.xslt` had drifted when the bump landed (`331032a1`). Detection is `tools/sync_lord_inline_skills.py`'s (vanilla SkillSets first, then TAOM's), so the fixer and the gate agree; skipped, never faked, without the install (the `spc_*` templates live in SandBox). Repair: `python tools/sync_lord_inline_skills.py --apply`. Replaced `SKILL_TEMPLATE_SHADOWS_SKILLS`, which refused any character declaring both (#626) |
| `INCONSISTENT_ARMOUR_SLOT` (warn) | an armour slot filled in some of a troop's battle sets and empty in others. The engine draws each slot from an **independently chosen** set (`.claude/rules/troops.md`), so this ships a combination nobody authored, and every UI surface renders set #1 and looks correct. 96 exist across 10 cultures, which is why it warns rather than blocks |
| `INCONSISTENT_WEAPON_SLOT` (warn) | a non-hero troop whose battle sets disagree on weapons: a launcher in a slot of some sets only, ammo (arrows or bolts) missing from a set or at two indices, or no weapon slot index filled in every set. Troop-level `<equipment>` rows count in every set. Slots draw independently (`.claude/rules/troops.md`), so this ships a bow with no arrows or an unarmed draw (#529). The launcher and ammo checks need the install |
| `TOWNSFOLK_WITHOUT_BATTLE_ROSTER` (warn) | a character in `characters/npcs_*.xml` whose inline equipment holds civilian rosters only, so the arena stands spawn it naked (#295). That comes from #295's in-game log; the spawner was not found in managed code ([details](../modding/equipment-rosters.md)). Repair: `python tools/add_townsfolk_battle_rosters.py --apply` |
| `TROOP_ITEM_ZERO_NOT_MAIN` (error) | a battle set of a troop in `troops/` whose Item0 is a shield or ammunition while the same set carries a weapon. Item0 is the weapon in hand at spawn (`Equipment.GetInitialWeaponIndicesToEquip`); the engine puts a shield in the off hand, so the fault is that the rule reads no main class from Item0. A thrown weapon in Item0 is allowed: it is a thrower's main weapon, as in vanilla's `hidden_hand` and `beni_zilal` troops (#343). No finding in today's data. Repair with `python tools/rebalance_troops.py --fix-purpose --apply`, which exchanges the two items' slots. Needs the install's item classes; heroes and `SKIP_TROOP_IDS` are not judged ([troop-skill-balance.md](../features/troop-skill-balance.md)) |
| `TROOP_MAIN_WEAPON_NOT_ITEM0` (warn) | a troop in `troops/troops_*.xml` or the Fords roster (`troop_purpose.EXTRA_TROOP_FILES`) that the main weapon rule would still change: a mounted Cavalry troop whose every battle set carries a polearm that can be couched, or a troop whose name or id says spear, pike, lance or halberd and that carries a polearm in every set, while a set opens with a one or two handed weapon in Item0. The engine wields the first weapon slot, so the polearm is the weapon in hand at spawn only if it is in Item0. The rule is `troop_purpose.main_weapon_slots`, the same call `python tools/rebalance_troops.py --main-weapon-slots` plans with; couchability comes from `taom_schema.couchable_item_ids` (priced usages of the Armory, vanilla and the placeholders), so a rider whose spear cannot be couched is not judged, and the check is skipped without the install. Repair with `python tools/rebalance_troops.py --main-weapon-slots --apply` ([troop-skill-balance.md](../features/troop-skill-balance.md)) |
| `TROOP_SKILL_KIT_MISMATCH` (warn) | a troop in `troops/` whose Item0 class (over its battle sets, as if Item0 were fixed) is not its top weapon skill, or whose carried class sits under a class of the same kind it does not carry (melee: OneHanded, TwoHanded, Polearm; launcher: Bow, Crossbow). Throwing is a main class when it opens the kit (a thrower), and competes only then; ties pass. The rule is `tools/troop_purpose.py` (#343). Same-kind cases repair with `python tools/rebalance_troops.py --fix-purpose --apply`. No tool repairs the reasons left, each named in its message: "launcher troop that does not open with its launcher" (a Ranged or HorseArcher troop with a launcher in every battle set whose set opens with something else; vanilla ships the layout, so a designer exchanges the slots by hand), "melee skill above the launcher's ladder cell" (a launcher troop whose ranged ladder cell sits under a melee skill) and "thrower below its melee skill" (`--fix-purpose` keeps Throwing's value on disk; the message says whether the troop is in `THROWN_PRIMARY_TROOP_IDS`, whose troops `rebalance_troops.py --apply` gives the main number). Warns until that count is zero (`TROOP_SKILL_KIT_MISMATCH_SEVERITY`). Needs the install |
| `UPGRADE_ARMOUR_REGRESSION` (warn) | an upgrade edge whose target totals **less armour** than its source (battle-set average over the five armour slots, unfilled = 0). The equipment half of the ladder rule: 62 edges shipped that way (#541), the Rhun ash capstones in light plate over heavy-plate parents the worst. Item values come from the install, so the check is skipped, never faked, without it; warns rather than errors because the Armory is unversioned. Repair with `tools/fix_upgrade_armour_regressions.py --apply`; militia-to-militia and the bare-chested-by-design troops' Body/Cape are exempt |
| `CROSS_CULTURE_ARMOUR_INVERSION` (warn) | a culture's ENGINE-tier cell (median armour total of its troops at `clamp(ceil((level - 5) / 5), 0, 10)`, every ITEM first scaled to the reference chest cap of the line it belongs to (`REFERENCE_CAP`, Gondor's cap `rebalance_armor.KINGDOM_CAPS['gondor']`, 46 on 2026-11-14; a test pins the two), because kingdoms differ in armour power by design since #583) sitting more than 20 points under what the other kingdoms field two tiers lower (median of their medians, at least three of them). The cross-kingdom half of the ladder rule (#581): the edge gate above never compares kingdoms, and the old curve had one row for L31 to L51, so Gondor's tier 9 (194) shipped under the field's tier 7 (220). Same pure function as the report's gate preview (`taom_schema.cross_culture_armour_inversions`); skipped without the install; `_ARMOUR_LADDER_EXEMPT` names the deliberate off-ladder kits with a reason each. What it finds now is a kingdom dressed below its own cap (a capstone in shared low-band kit): `python tools/analyze_kingdom_armour.py` for the picture, then a roster decision |
| `WORN_ARMOUR_CEILING` (warn now, error once every contributor has the rewritten Armory) | a troop whose battle sets can add up past `rebalance_armor.WORN_ARMOUR_CEILING` in any region (head 64, body 77, arm 69, leg 59: vanilla's best troop plus 10, #1271, 2026-11-14). The sum is over the five armour slots, each slot taken from the battle set that fills it most, because Equipment.GetRandomEquipmentElements re-rolls the set index per slot whenever the seed is not -1 and a troop spawn never passes -1 (v1.5.7 `TaleWorlds.Core.Equipment.cs:549-590`); a per-set sum misses what a real spawn reaches. The maintainer decided this is an error. **Transitional:** the live Armory is unversioned and the validator reads the copy installed on each machine. Before the apply of 2026-11-14 it held the pre-#1271 item values and 367 troops reached past the ceiling; the rewritten Armory leaves none, but a contributor who still has the old one would fail the commit hook on every ModuleData commit under an error. It ships as a warning. In its own change, once every contributor has the rewritten Armory, set `taom_schema.WORN_ARMOUR_CEILING_SEVERITY` to `Severity.ERROR` and add `--code WORN_ARMOUR_CEILING` to both hook lists, `.claude/hooks/check-moduledata-validation.sh` and `.githooks/pre-commit` (`CommitGateCoverageTests` fails until the first names the code, and `CodeList` in `tools/tests/test_githooks_pre_commit.py` fails until the second matches it), then drop this paragraph. That one constant also sets the severity of the `(tooling)` issue below, and the two must stay equal: the `(tooling)` issue means the ceiling was not checked, so left as a warning beside an error ceiling it would let a broken import pass the commit hook. `WORN_ARMOUR_FLOOR` stays a warning. Troop files only (`troops/troops_*.xml`); `_ARMOUR_LADDER_EXEMPT` troops and ids containing `troll` or `creature` are left out. Item stats come from the install, so the pass is skipped, and `validate_moduledata.py` says so, without it; a missing `rebalance_armor` module is one `(tooling)` issue, at the ceiling's severity, saying nothing was checked. The limits and the arithmetic are `rebalance_armor.worn_armour_extremes_per_slot` and `worn_armour_breaches`, the same calls as the "Worn floor and ceiling" section of `python tools/analyze_kingdom_armour.py`. Repair: swap the piece that adds most for a lower one in its line, or reprice the item with `python tools/rebalance_armor.py` (docs/features/armor-balance.md) |
| `ENLISTMENT_KIT_RANK_REGRESSION` (warn now, as `WORN_ARMOUR_CEILING`) | an enlistment kit (`equipmentsets/taom_enlistment_equipment.xml`) weaker than what the player drew before it. The player keeps every kit, so each is held against every kit the resolver issued at the tiers below it (`rank_chains` mirrors `EnlistmentRosterResolver`: culture, then default; requested assignment, then infantry; tier descending). Two reasons from `generate_enlistment_rosters.rank_regressions` (#1290): an armour total (head, body, arm and leg; no tolerance) under the highest of any earlier kit; in a category the kit holds, a best weapon more than 3% weaker than the best of that category in any earlier kit (`WEAPON_TOLERANCE`; melee by `melee_catalogue` damage per second, a launcher by damage; a longbow is a bow, a bastard sword one handed, a couchable spear a lance of its own category when a cavalry kit is judged and a spear in every other kit, and a polearm with a thrown usage is not compared). A category an earlier kit holds and the kit drops is no finding since 2026-11-15, because the player keeps the earlier kit; the dry run of `--repair-ranks` lists those. `(unresolved)` names a piece with no armour values or no price, `(weapons)` says the weapons could not be priced, `(tooling)` says the generator could not be imported or failed an assert at import. On the ModuleData of 12b21d5e3, `python tools/validate_moduledata.py --moduledata <that tree> --code ENLISTMENT_KIT_RANK_REGRESSION` printed 152 (2026-11-15); after the repair and the two rule changes of the same day (the lance category, dropped categories as information), `python tools/validate_moduledata.py --code ENLISTMENT_KIT_RANK_REGRESSION` prints `PASS: no validation issues found` (2026-11-15) ([enlistment.md](../features/enlistment.md#a-ranks-kit-is-never-weaker-than-the-kit-before-it-1290)). Armour and weapon values come from the install, so the pass is skipped without it. A warning while the Armory is unversioned: its severity is `taom_schema.ENLISTMENT_KIT_RANK_SEVERITY`, and making it an error also needs `--code ENLISTMENT_KIT_RANK_REGRESSION` in both hook lists, as for the ceiling. Repair: `python tools/generate_enlistment_rosters.py --repair-ranks`, read the plan, add `--apply`, then `python tools/promote_borrowed_cultures.py --only <c> --apply` for a promoted culture (the message names the source, or the `item_map` when the source kits hold); a default kit is a hand edit of `DEFAULT_ROSTER_ITEMS` and the file |
| `WORN_ARMOUR_FLOOR` (warn) | a medium, heavy or elite troop (`rebalance_armor.level_to_band`: levels 14 to 18, 19 to 30, 31 to 51) whose worst-case battle sets wear less head or body armour than `rebalance_armor.WORN_ARMOUR_FLOOR` (medium 8/8, heavy 20/20, elite 30/30). Under the floor a one-handed hit that the combat model clears for plain gear can kill: a helmetless elite archer in a light chest. Light troops have no floor. Slots are drawn per slot, as for the ceiling. A troop in `_BODYLESS_BY_DESIGN` keeps the head floor and is not held to the body floor. The same scope and skips as `WORN_ARMOUR_CEILING`. A warning because heavy and elite troops in shared light or medium pieces sit under it: 42 troops on 2026-11-14 against the Armory before the apply, 203 predicted by the dry run of the apply (which lowers the light and medium bands) and 196 measured after the write, before the generator band fix (183 on a copy once the fixed generators ran). The maintainer fixes those kits over time and then makes the floor an error. Repair: fill the slot in every battle set from the troop's kingdom kit at its band; `python tools/analyze_kingdom_armour.py` lists each troop |
| `LORD_ARMOUR_RANGE` (warn) | a generic lord template, a lord with a roster or override of his own (`is_hero="true"`, occupation Lord, in `characters/*.xml` or a `lords.xslt` template) or a fallback or ruler roster (`taom_<culture>_lord_battle_<sex>`, `taom_<culture>_ruler_battle_<sex>`) judged by the worst whole battle set, because a hero wears one set entire (`Hero.SetInitialValuesFromCharacter`). Every lord that generic templates alone dress wears the same sets, so the row is the template's: it names the template, counts its lords and lists the first six; the other lords and the rosters keep a row each. `floor:` names each part (head, body, arm, leg, summed over the five armour slots) where the worst set is short: under the culture's best elite-band troop (levels 31 to 51, of the lord's race when the culture has one) by more than 10 percent of that troop's value and by 3 points or more. `ceiling:` names each part where the best set passes that troop by more than 5. ## What actually gets scanned: three modules, not one

Two of TAOM's three data modules live in the game install, are unversioned, and are covered very
unevenly.

| Module | Cross-ref sweep | Schema checks (dup id, enum, civilian) | Commit hook fires? |
|---|---|---|---|
| TAOM: `Main/_Module/ModuleData` | yes, all 6 ref kinds | yes | yes |
| `<game>/Modules/LOTRLOME_Armory/ModuleData` | yes, all 6 ref kinds (`extra_ref_roots`) | no, by design | no |
| `<game>/Modules/TAOM_Map/ModuleData` | yes, all 6 ref kinds (added #462) | no | no |

The last column is not a detail. The hook matches on staged `Main/_Module/ModuleData/*.xml` or `*.xslt`
(the `HAS_MD` loop over `STAGED_LIST` in `check-moduledata-validation.sh`) and neither live module is in git, so editing them stages
nothing and gates nothing. Run `python tools/validate_moduledata.py` by hand after any edit there.

- **Editing TAOM_Map's `settlements.xml`?** Its `Culture.` refs are checked since #462, but
  only when you run the validator yourself: the file is not in git, so the commit hook never fires on
  it. That file is the sole input to `settled_cultures`, so a bad id there corrupts the
  `LANDLESS_CULTURE` verdict with no other diagnostic. Run `python tools/validate_moduledata.py`
  after any edit, or check a new id with `mcp__taom-moduledata__culture_exists` first.
- **Authoring into LOTRLOME_Armory?** Its refs are checked, its structure is not. Duplicate ids,
  enums, the civilian rule and `MOUNTED_DWARF` apply to repo files only, so a troop or an equipment
  roster authored there would be entirely unvalidated. Today it defines items and monsters and
  nothing else; keep it that way, or extend the schema passes first.
- **Touching any XSLT?** Run `python tools/check_external_xslt.py`. It is the only gate that reaches
  every stylesheet across the three modules: well-formedness, plus a compile when lxml is present. No
  pass interprets a stylesheet. The file map in `xslt.md` covers the common inputs. For
  `spcultures.xslt` run `CulturePartyTemplateTests`; everything else is a manual transform-and-diff.

The file and ref counts, the full matrix and the named gaps:
[docs/features/moduledata-validation.md](../features/moduledata-validation.md)
"Module coverage at a glance".

## Discipline

- **Schemas are the source of truth.** Field types, enums, cross-ref targets, and the civilian rule live in `tools/schemas/*.json` — add new fields/enums there, never hardcode them in Python.
- **When you add a NEW file that defines `<NPCCharacter>`** (a new wanderer/companion/template file), add its path to `taom_npccharacter.json` `applies_to`, or its duplicate-id + enum checks silently won't run (Codex review 2026-05-30 found 3 such files uncovered).
- **The `MOUNTED_DWARF` dwarf-mount allowlist has two edges worth knowing before you edit dwarf data.**
  It resolves **every** Horse-slot mount a dwarf can reach, inline equipment first and then every
  standalone `<EquipmentRoster>` he names, not just the first one found: with an allowlist in play a
  ram listed ahead of a horse would otherwise take the pass and hide the horse behind it. And the
  allowlist is matched against what the item-ref regex actually captured, which requires the `Item.`
  prefix (`_ITEM_REF_ATTR_RE`), so a Horse slot written `id="taom_war_ram_a"` without it is never
  allowlisted: it surfaces as `(unnamed mount)` and errors. The ids are pinned rather than
  prefix-matched, so a future mount has to be reviewed into `DWARF_MOUNT_IDS` on purpose
  instead of arriving by name alone.
- **This pass only sees data an `NPCCharacter` names, and that hole shipped a real bug.**
  `MOUNTED_DWARF` walks `NPCCharacter` definitions plus the rosters they reference. The career
  starting rosters in `equipmentsets/taom_career_starting_equipment.xml` are applied to the player at
  **runtime** by `CareerStartingEquipmentService.ApplyCareerStartingEquipment` (roster id built from
  culture + archetype + sex, then applied to the player hero) and are never named by any
  `NPCCharacter`, so the sweep cannot reach them. `player_career_erebor_cavalry_m`/`_f` sat there
  equipping `Item.saddle_horse`, a vanilla horse on a dwarf, and every validator run passed. It was
  found by hand during #515 and is now covered by shipped-data tests in
  `TAOM.Tests/Features/CharacterCreation/CareerCultureCoverageTests.cs`, not by this validator. Treat
  any other XML applied to a character at runtime as having the same blind spot.
- A `PreToolUse` hook (`check-moduledata-validation.sh`) auto-runs the **error**-severity checks on every Claude-driven commit that stages ModuleData XML or XSLT and blocks on failure. `.githooks/pre-commit` (switched on by `setup-dev-env.ps1` through `core.hooksPath`) runs the same `--code` set for every committer, terminal and IDE included; the two run side by side until the Claude gate is retired. It does NOT surface warnings, so run the tool yourself to see `MISSING_CIVILIAN_TYPE` / `INVALID_ENUM` / `DUPLICATE_ITEM_DEF` / `BROKEN_PARTY_TEMPLATE_REF` / `INCONSISTENT_ARMOUR_SLOT`. A validator that crashes exits 3, not Python's 1 for an uncaught exception (which would read as findings): the hook allows that commit and puts the traceback beside the tool result.
- **The hook enforces an explicit `--code` allowlist, not "all errors".** On 2026-09-01 four of the nine error codes were missing from that list and therefore could never block a commit, including one added the same day. The two lists live in different files and neither referred to the other, so nothing detected the drift. `CommitGateCoverageTests` in `tools/tests/test_validate_moduledata.py` is now the reference between them: **add an error code and you must add its `--code` line, or that test fails and names it.** It also fails on a `--code` naming a code the validator cannot emit, which is a silently dead gate line.
- **Until 2026-09-18 the validator did NOT enforce engine XSD required-attributes; `SCHEMA_INVALID` does now** (#621). `characters/clans.xml` still has **no TAOM schema** (`tools/schemas/` covers only equipmentsets / npccharacter / spcultures), so its cross-field rules stay unchecked, but a `<Faction>` (clan) missing a `Factions.xsd`-required attribute such as `initial_home_settlement` now fails `SCHEMA_INVALID` and the commit hook instead of surfacing only when the engine/editor loads the file. (RCA: `clan_umbar_3` shipped without its home settlement, fixed 2026-06-22. See [docs/features/moduledata-validation.md](../features/moduledata-validation.md) "Coverage boundary".) **That hole is now half of a known CTD, so treat it as load-bearing rather than cosmetic:** a faction with a null `InitialHomeSettlement` is exactly the first of the two faults behind #374, and the second (a lord whose culture owns no settlement) is now gated by `LANDLESS_CULTURE` above. Either alone is harmless; together they throw `InvalidOperationException` out of `Campaign.Tick`. Patch65 repairs the faction at runtime, but a clan shipped without `initial_home_settlement` is still a data defect, which `SCHEMA_INVALID` now catches before commit. (See [docs/features/lord-spawn-guard.md](../features/lord-spawn-guard.md).) The same hole is wider for **armory `action_sets.xml` structure**, which neither the validator nor the hook covers at all: the hook fires only on `Main/_Module/ModuleData/*.xml` and `*.xslt` (the `HAS_MD` loop over `STAGED_LIST` in `check-moduledata-validation.sh`), the live file lives in the game install, and the only copy in this repo, `docs/reference/lotrlome-armory-snapshot/action_sets.xml`, is re-snapshotted with no structural check. Gate it with `python tools/audit_action_set_parity.py` (defaults to the live install; pass `--live <path>` to audit the tracked snapshot), which exits non-zero on any root-level `<action>`: the game client loads such a file silently while the dedicated-server engine throws `KeyNotFoundException` at `/action_sets/action` and dies on boot, so a clean single-player session proves nothing. (2026-08-03: 168 orphaned elements from twelve self-closing tavern sets. See [docs/reference/armory-guide.md](armory-guide.md) "action_sets structure".)
- **The XSD layer has its own gate since 2026-09-18: `python tools/validate_xml_schemas.py`** (pass the files you touched, repo or live; each is validated under its own module; `--live` scans whole live modules). It uses the engine's own file-to-schema mapping and also runs inside `validate_moduledata.py` as `SCHEMA_INVALID` for the repo module, so the commit hook gates repo files; live-install files are gated only when you run it. A failure is strong evidence, not proof: an XSD can lag the code, so confirm against the element's deserializer before editing. It does not cover `project.mbproj` native data (`action_sets.xml` stays with `audit_action_set_parity.py`).
- **PASS ≠ in-game loaded.** The validator proves refs resolve on disk now, not that the engine loaded them: a new XML file added after launch is null in-engine until a full game restart. See [validation-and-testing.md](../modding/validation-and-testing.md) "Green validator, naked troop".

## Why the validator exists

These bug classes recur (the underwear bug, dup ids across Armory folders, dead troop refs after deletions, `rohan`-vs-`vlandia` typos) and each was previously caught, if at all, by a separate hand-run script. The validator makes them catchable in one pass. Full design: [docs/features/moduledata-validation.md](../features/moduledata-validation.md). Sibling data rules: [troops.md](../../.claude/rules/troops.md), [xml-data.md](../../.claude/rules/xml-data.md), [vanilla-data-comparison.md](../../.claude/rules/vanilla-data-comparison.md). Matcher-authoring lesson: [Bannerlord prefix-ref matchers must be attribute-agnostic](../reviews/lessons/xslt-moduledata.md).
