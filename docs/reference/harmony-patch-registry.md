# Harmony Patch Registry

Full per-category rationale, history, and RCA links for every TAOM Harmony patch — moved verbatim from CLAUDE.md's Harmony Patch Categories table (repo-reorg 2026-07-12) so the eager-loaded CLAUDE.md keeps only the thin routing table (category | feature | target | status). **Before editing any patch, read its section here** and the scoped rule [.claude/rules/harmony-patches.md](../../.claude/rules/harmony-patches.md) (loads automatically when a `Main/**/Hooks/**` file is opened). Most sections end with a `docs/features/<x>.md` pointer — that feature doc remains the deep-dive.

> **Ground truth is the code:** `grep -r 'HarmonyPatchCategory' Main/` enumerates every attribute-registered category — this registry is maintained by hand and can lag. Two caveats when reconciling: **manual patches carry no category attribute by design** (Patch28_SettlementGuards' two manual patches, Patch23_BannerColorPersistence's manual entries), and the Patch31_SmartCavalryAI / Patch35_CompanionTactics `Formation.SetMovementOrder` postfixes register under the shared `Patch_MissionTime_SetMovementOrder` category attribute, not their feature-numbered ones.

## Patch13_RaceAge

**Target:** `HeroCreator.DeliverOffSpring` (Transpiler)

Noise reduction, NOT a crash fix. Vanilla `DeliverOffSpring` carries a `Debug.SilentAssert(mother.Race == father.Race)`; in TAOM mixed-race couples are normal, so the assert fires on every cross-race birth — breaking an attached debugger via `Debugger.Break()` and spamming "Silent Assert Failed!" debug-log lines (ButterLib's wrapper only logs; harmless for players). The transpiler NOPs the entire assert sequence (args + call), matching the `SilentAssert` call by operand method name because `CallerXxx` default-parameter attributes can defeat `MethodInfo.Equals`. If either IL anchor is missing (already-NOPped by a prior application, or engine IL drift) it logs a warning and degrades to a no-op instead of throwing out of `PatchCategory` — this transpiler is explicitly non-idempotent, which is why the `OnGameInitializationFinished` patch batch is one-shot guarded (`_gameInitPatchesApplied` in `SubModule.cs`). Behavior is otherwise unchanged — the birth proceeds identically. Owning feature: RaceAge — see `docs/features/race-age-system.md`.

## Patch14_Execution

**Target:** `TraitLevelingHelper.OnBloodFeudStarted(Hero)` (Prefix, skip-original) + `ExecutionCampaignBehavior.GetBloodFeudStartRelationPenaltyToOtherClan(Hero, Clan)` (Postfix, `ref int __result`)

The alignment rule for executions: killing your enemy is not dishonourable, and only the victim's own side objects. **Re-homed at the v1.5.x bump.** v1.5.0 deleted vanilla's `ExecutionRelationModel` engine-wide (`TaomExecutionRelationModel` went with it, no base to override) and `TraitLevelingHelper.OnLordExecuted()`, the argument-less call that made the old ThreadLocal `ExecutionContext` snapshot and its `KillCharacterAction.ApplyInternal` prefix necessary; both are gone. The engine now splits execution fallout in two and only ONE half is touched. The feud itself (`OnBloodFeudStateChanged` setting the victim clan's relation to the minimum) is left alone; the loop over every other clan that follows calls the static penalty method per clan and applies any non-zero result, and that is the seam. Zero trips the engine's own `!= 0` guard, so it is no hit and no count in the summary notice. Patching the method rather than the loop keeps the pre-execution "this will hurt your relations with N clans" tooltip honest, because the same method feeds it. Both patches are thin: they convert the sealed heroes and clans to `ExecutionParticipant(kingdomId, cultureId)` at the boundary and delegate to `IOnExecutionAction`, whose relation half delegates to `IExecutionRelationService` (one owner of side resolution, cross-alignment zeroing and the 1.5x kinslaying multiplier). Deliberately no "unknown, defer to vanilla" early return: sides resolve by kingdom with a culture fallback, so a kingdom-less executor or a victim whose clan the kill just destroyed (`ApplyInternal` destroys it BEFORE dispatching `OnHeroKilled`) is placed on a side rather than handing the calculation back to vanilla's flat penalty. Vanilla only reaches the relation loop while the feud clan still has a kingdom, so the honor prefix is the only path that ever sees a null one. The static method is ALSO reached when an AI clan executes a member of the player's clan (`OnPlayerClanMemberExecuted`): vanilla starts the feud the other way round and runs the same loop against the player's relations, the signature carries no executor, and the rule judges the player's own executions, so the postfix leaves vanilla's number alone there (`IOnExecutionAction.IsPlayerTheBereaved`, the victim's clan being the player's clan). `Main/Features/Execution/`. See `docs/features/execution-alignment.md` if present, else `docs/migration/v1.5.2-impact.md`.

## Patch17_TroopWeight

**Targets (6 postfixes):** `PartyUpgraderCampaignBehavior.UpgradeReadyTroops` (enforcement: shed-on-upgrade) · `PartyVM.RefreshPartyInformation` · `CampaignUIHelper.GetMainPartyHealthTooltip` · `ClanPartyItemWithPartyVM.UpdateProperties` + `ClanPartyItemWithHeroVM.UpdateProperties` (v1.5.x: the base `ClanPartyItemVM.UpdateProperties` is abstract, so the patch names both overrides through `TargetMethods`) · `RecruitmentVM.RefreshPartyProperties` · `PartyCharacterVM.RefreshValues` (the last five are display-only)

**`PartyCharacterVM.RefreshValues` carries TWO TAOM postfixes in different categories.** `Patch35_CompanionTactics` (`Patch35_PartyCharacterVM_RefreshValues` → `RoleTooltipDecorator`) PREPENDS a `[ROLE] ` prefix to `PartyCharacterVM.Name`; `Patch17_TroopWeight` APPENDS a `×N` weight tag to the same property. They compose safely and **order-independently** precisely because one prepends and the other appends, and vanilla reassigns `Name` from the character at the top of every `RefreshValues` so neither can double-apply. In practice they do not even meet: the decorator only touches heroes, and heroes are unlisted in `troop_weights.xml` so they weigh 1.0 and get no tag. A third mutator of this property would need to re-derive that reasoning: the decorator's "strip a prior bracketed prefix" logic only strips a LEADING `[...]`, so it would silently eat nothing and compound instead.

**Do not re-add a patch on `CampaignUIHelper.GetPartyHealthTooltip(PartyBase)`.** One shipped into review on 2026-09-06 and was deleted: that method emits no `{=ZgYAGfbD}Land Troop Capacity` row (the row exists only in the parameterless main-party builder) and has no caller in any shipped v1.4.8 client assembly. It was recovered from the 2026-07-11 deletion set, where it had legitimately rewritten the *Battle Ready / Wounded* rows, recovering a target proves the method exists, not that it produces what a new hook consumes. RCA `docs/reviews/rca-troopweight-usage-frame-2026-09-06.md` finding 3.

**Usage frame, 2026-09-06.** Players reported that recruiting heavy troops *shrinks* the party size limit: the 2026-07-11 deflation below, read backwards. Enforcement is unchanged; the presentation moved to the other side of the fraction. Capacity readouts now show `weighted-used / true-base` (**19 / 20**) instead of `raw / deflated` (**10 / 11**), which is the same cap by `raw > deflated ⟺ weighted > base`, so every vanilla over-capacity warning flag flips at the identical moment and none of them were touched. `ApplyPartySizeWeightPenalty` takes `includeDescriptions` and skips the display path, removing the `Heavy troops −N` tooltip line (v1.4.8-verified safe: `PartyBase.PartySizeLimitExplainer` has only two consumers, both tooltips). All six display postfixes delegate to one `TroopWeightDisplayHook` singleton. **Headcounts still read RAW**, map nameplate, `GameMenuPartyItemVM.RefreshCounts`, battle, and specifically the `Battle Ready` / `Wounded` tooltip rows that sit beside the rewritten `{=ZgYAGfbD}Land Troop Capacity` row; weighting those is the phantom-wounded bug (RCA 2026-06-07), pinned by `DisplayHook_DoesNotRewriteHeadcountRows`. The header patch targets `PartyVM.RefreshPartyInformation` rather than the `private static PopulatePartyListLabel` that the 2026-07-11 deletion set had prefixed: that builder receives no party and also produces the **prisoner** headers, so weighting it would have weighted `Prisoners (0 / 15)` too. A postfix on the caller also suppresses no vanilla code, retiring that prefix's Cluster-A audit flag (`docs/audits/cluster-harmony-patches.md:49`).

Troop weight system, heavy troops cost more party-size budget. **Reworked 2026-07-11 (count→limit):** the "elite tax" is now a party-size-LIMIT *deflation* applied in `TaomPartySizeModel` (`ITroopWeightService.ApplyPartySizeWeightPenalty` subtracts `ceil(weighted)−raw` from the limit, clamped ≥1; pure `TroopWeightService.ComputeSizePenalty`), NOT a count-getter patch, so **every troop count reads RAW everywhere** (map nameplate, party screen, land-capacity, tooltips, menus, battle all agree) while the recruit cap still fills at the troop weight (the displayed limit honestly shrinks with elite stacks). The two `NumberOfAllMembers`/`NumberOfRegularMembers` getter patches, the 5 weighted-display hooks (phantom-wounded fix: now moot, nothing is weighted), the `WeightedCountCache`, and the `[CountFlicker]` diagnostic were all **REMOVED** (~26 files). That rework reduced this category to the **shed-on-upgrade** postfix alone (adapted to the deflated-limit frame); the 2026-09-06 usage-frame block above added five display postfixes back, so it now holds six. Ripples handled: `SpecialResources` battle-reward scaling preserved via an explicit weighted-count call; `SettlementFood`'s garrison-leak correction self-neutralizes (vanilla food now reads raw at source). Incidental side-effects of the old global getter weighting (e.g. elite parties moving slightly slower) are intentionally gone: the feature now affects only the size cap. Reworked because the map "200↔20" flicker (proved to be the vanilla army-sum, not the weighting) + "party shows 325 but 159 fight" reports were all the weighting making UI counts disagree with reality. **Scoped 2026-08-07:** the shed runs only on parties with a `LeaderHero`. Vanilla drives `UpgradeReadyTroops` from `DailyTickPartyEvent`, tickered over `MobileParty.All`, so it also reaches militia/garrison/villager/bandit parties and (via `MapEventEnded`) a settlement's own `PartyBase`, none of which have a size limit worth enforcing (`CalculateMobilePartyMemberSizeLimit` returns a flat 20-body placeholder without a leader; `GetPartyMemberSizeLimit` returns 0 for a settlement party). Without the guard it capped every settlement's militia at ~20 and undid `Patch39_BanditPartySize`. See `docs/features/troop-weight-system.md`.

## Patch25_LocalizationOverride

**Target:** `MBTextManager.GetLocalizedText` (Prefix, bound via `TargetMethod()`/`AccessTools.Method`)

English string overrides for vanilla `{=ID}` tokens. Vanilla `GetLocalizedText` short-circuits for English — it returns the inline text from the `{=ID}text` value and never consults `LocalizedTextManager` — so `module_strings.xml` entries that reuse vanilla `{=ID}` tokens are silently ignored. Unregistered ids fall through to vanilla. See `docs/features/localization-override.md`.

## Patch30_MixedFormations

**Thread (verified v1.4.8, #595):** the prefix runs on the TWParallel WORKER POOL for AI units
(`Agent.TickParallel` -> `HumanAIComponent.ParallelUpdateFormationMovement` -> `Agent.GetBaseFormationFrame`
-> `Formation.GetOrderPositionOfUnit`), on the async tick thread via `Formation.Tick`, and on the main thread
from `OrderController`. `FormationLayoutService._lock` is load-bearing; `ForgetAgent` evicts a deleted
agent's slot because the engine recycles the index.

**Target:** `Formation.GetOrderPositionOfUnit` (Prefix)

Mixed ranged/melee formation layout — the Prefix replaces a unit's vanilla order position with the plane position computed by `IFormationLayoutService.ComputeUnitPlanePosition(formation, agentIndex, agentIsRanged)`, grounded via `Scene.GetGroundHeightAtPosition` and validated through `Mission.IsFormationUnitPositionAvailable` before overriding `__result` (Codex review #35 HIGH: vanilla's Hold path routes through that availability check to keep units off non-navigable terrain — an unavailable candidate falls through to vanilla so the engine's own `unit.GetWorldPosition()` fallback applies). Any null/missing-value/exception path returns `true` (vanilla). HOT PATH — fires per-unit per-formation-position-recalculation (up to ~40,000×/frame worst case in 200-unit formations), so the service singleton is cached in a static field per the harmony-patches hot-path rule. See `docs/features/mixed-formations.md`.

**Fall-through cases (do not remove).** A blanket `return false` on a positioning Prefix is a silent monopoly on that engine decision — any other feature relying on the vanilla path breaks against it with no error. Patch30 therefore falls through for:
- **Non-field-battle missions** (`Mission.IsFieldBattle != true`) — siege, sally-out, hideout, naval, settlement.
- **Banner bearers** (`unit?.Banner != null`) — `BannerBearerLogic` places them via `SwitchUnitLocations` into the engine's dedicated `RelativeFormationPosition[6]` banner slots; overriding their order position scatters the standards through the ranks. Added 2026-07-16 (Codex review 74 MED) when BannerBearers first gave formations bearers for Patch30 to misplace. `Agent.Banner` is `Equipment?.GetBanner()` — one `_weaponSlots[4]` read, no loop or allocation, so the check is cheap enough for this hot path, and it sits *before* the IoC resolve. See `docs/features/banner-bearers.md` + `docs/reviews/rca-banner-bearers-2026-07-16.md`.

## Patch31_SmartCavalryAI

**Targets:** `Formation.SetMovementOrder(MovementOrder input)` (Prefix + Postfix) and, as `Patch31b_FormationSetTargetFormation`, `Formation.SetTargetFormation(Formation targetFormation)` (Postfix); both deferred, see `Patch_MissionTime_SetMovementOrder`. Harmony binds `input` and `targetFormation` by name; `SmartCavalryAIBindingTests` pins both names, the enum values (`Charge = 2`, `ChargeToTarget = 3`) and every engine member the bodies and their adapters read.

**Two seams because the player's targeted charge is two calls.** `OrderController.SetOrderWithFormation(Charge, target)` issues a plain Charge (Patch31 starts the cycle at the NEAREST enemy) and then `SetTargetFormation(target)` (Patch31b re-points the cycle at the formation the player chose; `OrderController.cs:812-817`). Every `SetMovementOrder` ends with `SetTargetFormation(null)` (`Formation.cs:714`), which pushes target index -1 to every rider, so `CavalryCommandAdapter.IssueChargeToTarget` re-sets the native target after its own order, exactly as vanilla does. `Formation.Tick` re-applies the retained `FacingOrder` through `SetPositioning` every tick (`Formation.cs:2311-2314`), so `ApplyChargeLine` installs `FacingOrderLookAtDirection` with every line or the facing lasts one tick. All three found by the Codex pass of 2026-09-13 (P1 each).

Hit-and-run state machine on player-commanded cavalry (#586, 2026-09-13): Forming (a Move into a line, never a Stop: `MovementOrderStop` is `StandGround`, under which each rider holds its OWN position and the arrangement is ignored, `Formation.cs:1262`) -> Charging (`ChargeToTarget`, direction frozen at line time) -> PassingThrough (Move to a reform point past the live enemy) -> Reforming -> Forming again at the nearest live enemy. Every hold state has a dwell budget; every give-up hands the formation back to a vanilla Charge. Feature doc: `docs/features/smart-cavalry-ai.md`.

**Player-commanded formations only.** The postfix bails when `Formation.IsAIControlled` is true (F6 delegation, an enlisted battle, a dead player, and an emptied player formation, which vanilla `Formation.RemoveUnit` flips to AI control for good) and cancels any cycle such a formation still has. `FormationAI.TickOccasionally` issues the AI's movement order only when `IsAIControlled` (`FormationAI.cs:284-290`; there is no `SetCurrentOrder`), so a non-charge order on a player-commanded formation is the player's, and it cancels the cycle so the newer order stands, whether or not the toggle is on. Only STARTING a cycle needs the feature enabled. A player Move landing within 1 cm of the machine's own Move point reads as a re-issue; a click does not do that.

**The prefix exists to tell a re-issue from a new order.** `BannerBearerLogic.FormationBannerController.RepositionFormation` re-applies the formation's current order whenever a bearer dies (`BannerBearerLogic.cs:157`); `Formation.CopyOrdersFrom` and `DeploymentHandler` have the same shape. The prefix captures the previous order as `__state`; the postfix skips the cancel when `MovementOrder.AreOrdersPracticallySame(previous, input, isAIControlled: true)` (same kind, and for a Move within 1 m). Without it a bearer death mid-line-up silently ended the cycle.

**One engine path re-enters outside the recursion guard, by design.** `Formation.Tick`'s substitute loop (`Formation.cs:2291-2295`) issues a plain Charge when a `ChargeToTarget` target empties. That is a charge order on a mid-cycle formation, so it lands in the service's "charge now" path, the same nearest-enemy re-target `UpdateCharging` performs; the two are idempotent. Documented so nobody "fixes" the double path.

**Toggle off mid-cycle.** `ICavalryChargeService.HasActiveCycles` keeps `SmartCavalryAIMissionBehavior.OnMissionTick` running while a cycle exists; the service hands it back to a vanilla Charge on the next tick, then the early return resumes. Without it the riders sat on a Move nobody lifted.

**Open-field-only (do not remove).** This is an open-field line charge and must never manipulate formations outside a field battle. `CavalryChargeService.HandleChargeOrder`/`.Tick` bail unless `IBattlefieldQueryAdapter.IsFieldBattle` (engine `Mission.IsFieldBattle` — true ONLY for `MissionTeamAIType == FieldBattle`), so no native `Formation.SetPositioning`/`SetMovementOrder` is issued in a siege / sally-out / hideout / naval / settlement mission. That native re-entry, while the engine is still finalizing siege deployment, is the suspected path behind the Grymmclúd siege CTD (#349).

**The service gate alone is NOT sufficient — gate the tick too.** `SmartCavalryAIMissionBehavior.OnMissionTick` also calls `ApplyCollisionAvoidance`, which writes `agent.SetMovementDirection` per mounted unit per frame **bypassing `ICavalryChargeService` entirely**; with `AvoidFriendlies` (default `true`) the feature kept manipulating cavalry every frame in a siege even with the service gated. The same gate therefore sits at the top of `OnMissionTick` (which also skips the per-formation adapter build). **Target:** `Agent.CheckToDropFlaggedItem` (public, **Prefix skip-original + Finalizer**)

| When | Victim | Null |
|---|---|---|
| 2026-06-17 (crash report, warg-vs-warg) | read as a non-vanilla **mount** | `Equipment[wieldedIndex].Item` |
| 2026-08-10 (live debugger, warg battle) | **not a mount** — `IsHuman=true`, `IsMount=false`, `State=Active`, `Health=13`, no rider/mount, flags carry `CanWieldWeapon`, **`Character == null`** | `Equipment` itself (a not-yet-built agent has not reached `InitializeMissionEquipment`), making the **indexer** the throw |

**The null-`Equipment` window is SPAWN-time, not teardown, and `HasBeenBuilt` does not bound it.** `Equipment` is assigned exactly once, by `InitializeMissionEquipment` from `Agent.Build` (Agent.cs:5174), and `Agent.Clear` (:5194) zeroes every native pointer *without* nulling `Equipment`. It checks `Equipment == null` *first*, which also avoids reads vanilla would do: the wielded-index getters are unsafe raw pointer dereferences (`AgentHelper.GetPrimaryWieldedItemIndex`), so skipping them on a half-built agent is strictly safer than vanilla, not merely equivalent. **Finalizer is KEPT** as backstop — Harmony 2.4.2 opens its exception block before the prefix chain, so the generated try/catch genuinely wraps Prefix + original + postfix, and it still covers an unanticipated NRE shape. Its reach is exactly that and no more: it swallows ONLY `NullReferenceException`. AVs are catchable in this process (launcher config sets `legacyCorruptedStateExceptionsPolicy` — see Patch62), but the filter deliberately rethrows them: an AV should reach the crash reporter, not be silently absorbed. ## Patch71_HeroResetEquipmentsGuard

**Target:** `Hero.ResetEquipments()` (public, Prefix)

**Feature:** FieldCommission, `Main/Features/FieldCommission/Hooks/Patch71_HeroResetEquipmentsGuard.cs`. **Status:** ACTIVE.

Null-guards vanilla's `Hero.ResetEquipments`, which clones three equipments straight off `Hero.Template` with no checks: `_battleEquipment = Template.FirstBattleEquipment.Clone()`, then civilian, then stealth. **`RemoveCompanionAction.ApplyInternal` is its only caller anywhere in the campaign assemblies**, and reaches it only on `RemoveCompanionDetail.Fire` when `hero.IsWanderer`, so the blast radius is exactly the fire-a-companion path.

**Why TAOM hits it and vanilla does not.** A FieldCommission-promoted companion is created by `HeroCreator.CreateSpecialHero(troop, ...)`, which goes through `CreateHero(useCharacterAsTemplate: true)`, so `Hero.Template` (`=> CharacterObject.OriginalCharacter`) is the line troop rather than a wanderer template. On a non-hero `CharacterObject`, `FirstCivilianEquipment` falls through to `AllEquipments.FirstOrDefaultQ(e => e.IsCivilian)` and returns null for the 743 of 895 TAOM troop blocks that declare no civilian roster. `null.Clone()` is the NRE reported in #486. Native `spnpccharacters.xml` wanderers always declare a civilian set, which is why vanilla never reaches it. The throw lands after the companion is already de-clanned, de-partied and made a fugitive, and before `OnCompanionRemoved` dispatches, so a player who hits it should reload rather than play on.

**The stealth line fails the same way, one culture class over.** `CharacterObject.FirstStealthEquipment` on a non-hero is `Culture.DefaultStealthEquipmentRoster.AllEquipments.First()`, also unguarded. TAOM's eight `is_bandit="true"` cultures declare no stealth roster, and neither do vanilla's six, so this is guarded in code rather than papered over in `taom_spcultures.xml`. Hero *creation* survives the same gap because `Hero.SetInitialValuesFromCharacter` reaches stealth gear through `CharacterObject.StealthEquipments`, which guards on `Culture.DefaultBattleEquipmentRoster != null` and falls back to `neutral_culture`.

**Contract.** The prefix returns `true` untouched whenever the template supplies all three slots, so a vanilla-shaped hero still gets the engine's own reset and behaviour changes only in the cases that throw today. Otherwise it fills each slot in place via `Equipment.FillFrom` (which copies all 12 slots into the existing object, so references other code holds to the hero's equipment stay valid), falling back to the troop's own battle kit, and returns `false`.

**A fault returns `false` too, which is the one place this patch departs from the house "defer to vanilla on error" pattern, deliberately.** Everywhere else that fallback is safe because vanilla is a working default. Here it is not: by the time `ResetEquipments` runs, `ApplyInternal` has already de-clanned, de-partied and made the hero a fugitive, so handing control back re-raises the NRE and strands the campaign in exactly the torn state this patch exists to prevent. Skipping instead leaves the hero in the kit they are wearing, which is what the `None` branch already chooses for an unfillable slot. That makes the prefix total, which is why there is no Finalizer: a Finalizer could only suppress the engine's torn write (line 1 assigned, lines 2 and 3 stale), never repair it.

**Two traps the implementation exists to avoid, both worth knowing before editing it:**

- `Hero.BattleEquipment`, `CivilianEquipment` and `StealthEquipment` are `_field ?? Campaign.Current.Dead*/DefaultStealthEquipment`. Those three are **campaign-wide singletons** loaded once from the `default_*_equipment_roster*` objects, so `FillFrom` through a getter whose backing field is null does not equip the hero: it rewrites a shared object every consumer reads. The patch skips any slot whose target is `ReferenceEquals` to the matching singleton. The getters also never return null, so a `?.` there guards nothing.
- `FillFrom(source, useSourceEquipmentType)` copies the source's `EquipmentType` onto the target when the flag is true. On a battle fallback that retypes the hero's civilian kit `EquipmentType.Battle`, so the flag is passed false for every fallback fill. `HeroCommissionAdapter.CreateCompanionFromTroop` had the same defect at creation time and was fixed in the same commit.

A fault is logged at **ERROR with the full exception dump**, matching `Patch69_TournamentEndGuard`, because reaching this catch means something other than the known #486 shape went wrong and there would otherwise be nothing to root-cause from. The catch is deliberately broad (`Exception`, not the proven `NullReferenceException`) where Patch65 and Patch69 narrow theirs: those two wrap calls whose failure is contained, so swallowing broadly would hide unrelated bugs, whereas here ANY escaping exception reproduces the torn campaign state the patch exists to prevent.

**No other installed module patches this method** (re-verified independently on the second pass by scanning every module DLL). That is a point-in-time fact rather than an invariant: a future third-party POSTFIX would still run even when this prefix returns `false`, and would see equipment the original never assigned.

**One accepted behavioural difference from vanilla, currently unreachable.** Because the patch fills through the public getters rather than assigning the private backing properties, a hero whose backing field is null gets that slot SKIPPED (the getter would hand back the shared singleton), where vanilla would have assigned a fresh clone. `Hero.OnDeath` is the only thing that nulls those fields and a dead hero cannot be fired, so this cannot be reached by the FieldCommission population. It is recorded rather than fixed because closing it needs reflection onto private members, which costs a permanent binding surface across every engine bump for a case that cannot currently occur.

Decision logic lives in `Main/Features/FieldCommission/Domain/EquipmentResetPlan.cs` as a pure boolean helper so it is unit-testable without a running campaign (`EquipmentResetPlanTests`, an exhaustive eight-row truth table); the patch does every `Equipment` dereference at the boundary. `Fill` is `internal` so `Patch71FillTests` can pin the singleton guard and the equipment-type flag directly, which works because `Equipment` is constructible without a campaign. Bindings are drift-guarded in `FieldCommissionBindingTests`, including `MBEquipmentRoster.EmptyEquipment` (losing it would turn `ResolveStealth`'s `.First()` into a throw path). `ResetForUnload()` is wired into `SubModule.OnSubModuleUnloaded` alongside its siblings so the cached logger does not survive into a disposed container. RCA: [rca-field-commission-reset-equipments-2026-08-20.md](../reviews/rca-field-commission-reset-equipments-2026-08-20.md). See [field-commission.md](../features/field-commission.md).

Narrows the AI's random partner-clan draw to alignment-compatible clans. **This patch does NOT block anything.** The Free/Evil marriage block lives in `TaomMarriageModel.IsCoupleSuitableForMarriage`, which is the chokepoint every path funnels through. Mutating the existing instruction rather than replacing it preserves any labels attached to it. `Clan.All` appears on exactly ONE source line in the whole class, so the anchor is unambiguous; `MarriageAlignmentBindingTests` pins both that count and the `Ldarg_1` assumption (instance method, first parameter `Clan`) against the installed engine.

Cross-alignment marriages stay blocked in that case; only the steering is lost. `CandidateClansFor` additionally returns `Clan.All` unchanged on four degenerate paths (null clan, toggles off, Neutral considering culture, any exception) and on an empty filtered pool. An empty pool matters because `MBRandom.RandomInt(0)` returns 0 and the indexer would then throw. There is deliberately no `Campaign.Current` guard: `Clan.All` IS `Campaign.Current.Clans` and vanilla reads it unconditionally at the same point, so a successful read is itself the proof.

**Pool cache** lives in `MarriageClanPoolCache`, keyed on the considering clan's culture and stamped by `MarriageClanPoolStamp` on `Campaign.UniqueGameId` plus clan count plus campaign day. The id is a STRING, not the `Campaign` object, so a finished campaign's object graph is not pinned alive by a static field (`plans/001-cross-campaign-singleton-resets.md`). Clan culture is only ever assigned at clan CREATION, which moves the count, so the count is what covers culture churn; this is NOT the CultureConversion feature, which converts settlement cultures. The stamp is a pure class with its own tests because it is the only real decision here. The helper runs twice per lord per day, so the `IMarriageAlignmentService` resolve is cached too.

Applied from `SubModule.cs` in `OnSubModuleLoad` alongside `Patch59_CaravanTrade`, the nearest precedent (also a private `CampaignBehavior` method). Once per process, which is what a transpiler wants. See `docs/features/marriage-alignment.md`.

## Patch99_XmlMergeFastPath

**Target:** `TaleWorlds.ObjectSystem.MBObjectManager.CreateMergedXmlFile(List<Tuple<string, string>> toBeMerged, List<string> xsltList, bool skipValidation)` (prefix at `Priority.Last` that may skip the original; `void` finalizer). Module-XML merge fast path (plan 042, 2026-10-03). The engine's merge loop converts the whole document merged so far between `XmlDocument` and `XDocument` for every file and compiles every XSLT on every call, so a type's merge grows with the square of its size: about 28 s of a new campaign's 50.2 s loading screen and 14 s of a custom battle's load (rgl logs, 2026-10-02). The finalizer is `void`, so it never replaces the engine's exception, and Harmony keeps `rethrow` only while every finalizer on the method is void. **PatchShield: plan 040 puts `CreateMergedXmlFile` on `PatchShieldPolicy.ExcludedTargetMethods` and merges before this plan, so this patch adds no entry of its own and must not ship without 040's** (feature doc, "Shipping order").
