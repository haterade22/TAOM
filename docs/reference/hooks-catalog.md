> **`jq` is not on PATH in this Git Bash install** (verified 2026-08-20). A git gate reads its command through `taom_hook_command` (`_pybin.sh`), which runs Python first and jq only when there is no Python (`validate-push.sh` has no jq path: with no Python it asks on a force marker, #680); any other hook that parses stdin JSON must not depend on jq alone, or it is silently inert: a fail-open hook that never runs looks exactly like a hook with nothing to report. The grep+sed fallback truncates a value at the first escaped quote and leaves Windows backslashes doubled, so the fallback must be Python.

| `validate-push.sh` | PreToolUse (Bash, PowerShell) | Hard-blocks (exit 2) a force push (`--force`, `-f`, `--force-with-lease`, `--force-if-includes`, a `+` refspec) to master, main, `bannerlord-1.5.x` or `bannerlord-1.4.5`, named rather than `bannerlord-*` (maintainer decision D30); the hook's `PROTECTED` array is the only list, and the judge takes it as arguments. An unforced delete of a trunk (`--delete`, `:branch`) is not refused. **Every matching branch and option prefixes (#689):** it also refuses a forced push of every branch the remote also has, which git 2.55 runs as a forced update of every matching branch, both trunks included: the refspec `:` with a force flag, `+:`, and a forced push with no refspec under `push.default=matching`, set by `-c push.default=matching` between `git` and `push` (the key in any case; git refuses the glued `-cpush.default=...`) or by git's own config, read with `git config --get push.default` in the hook's directory at most once a run and only for a forced push with no refspec. git reads an unambiguous prefix of a long option as that option (`--force-w` runs as `--force-with-lease` and force-updates the trunk it names; `--mir` and `--m` run as `--mirror`, and `--al` and `--b` as `--all` and `--branches`, which reach both trunks with a force), so the judge compares a long option's name before any `=`, from 3 characters, as a prefix of a force option, of `--mirror`, of `--all` or `--branches`, and (since the #680 review) of a value option, on top of the words the old value table took for one; `--f` and `--forc`, which git refuses as ambiguous, count as force, which only refuses what git refuses. A `--force-if-includes` prefix counts as force too, a deliberate over-block: `--force-i` alone is no forced push, since git rejects a non-fast-forward. **One Python run reads and judges the push (#680):** `_shellwords.py verdict <protected...>` splits the command (`push_candidates`) and `_pushjudge.py` judges each candidate line holding `push`, in the reader's order and each once, until one refuses, and prints one line (`block<TAB>target`, `warn<TAB>target` or `allow`); the hook keeps the exit-2 message and the warning. The bash judge that ran here until #680 cost about 25 microseconds a word, so under load a trunk force push carrying 250 KB of quoted text holding `push` outran the 5 s registration it then had and ran unjudged (idle, 400 KB took 4.9 s and 800 KB 6 to 9.7 s). It was deleted, not kept as a fallback; `_pushjudge.py` ports it reading every word as bash did (split at space, tab and newline only, git recognised after lowering A-Z only, ASCII fd digits), and `tools/tests/test_pushjudge.py` pins each trap (`PINS`) and every 7c command of 143f0fa8 with the target bash named (`SEVEN_C`); the #689 rows and the rows run on a `push.default=matching` checkout have tables of their own (`ISSUE_689`, `PushDefaultTests`), as do the value options read by the prefix rule (`VALUE_PREFIXES`). One designed difference: a pattern refspec holding `?`, `[`, `]`, `\`, `(`, `)` or `\|` beside `*` is read as matching every protected name and names the first; git refuses such a refspec, so this can only refuse more. **Deadline:** the judge gets what is left of 3.0 s from the hook's first command (`EPOCHREALTIME`, capped at 3.0 s because the wall clock can be set back; a fixed 2.5 s in a bash older than 5.0) under `timeout -k 0.3`, so an overrun, or less than 0.3 s left after a slow `_pybin.sh` probe, answers `ask` under `hookSpecificOutput` after about 3.3 s instead of being killed, which fails open. The registration is 10 s (5 s until the #680 review, raised by maintainer decision), so it is only a backstop; `tools/test_hooks.sh` 7i holds each long push and each overrun to 4 s. An ask prompts even in bypass mode, so an unattended agent waits on it (`harness-facts.md`). **No verdict** (no Python, a payload the reader cannot parse, which it answers `unread`, or a judge that failed, rc 127 included, or printed something else): the raw payload decides, `ask` when it holds a force marker (`-[^[:space:]-]*f`, `--m`, which takes in `--mirror` and each prefix of it, `+` or a `\u` escape; the scan is linear, about 85 ms a MB) and allow with a stderr note otherwise. That scan reads the payload from its `"tool_input":` key on, looked for in the first 2 KB (the #680 review saw Claude Code 2.1.241 put it at offset 444 to 449; past 2 KB, or with the key written with a `\u` escape, it reads the whole payload, which only asks more, and a search of the whole payload for the key was quadratic in its offset, 17.7 s for a key after 256 KB): the session id and transcript path before that key hold a UUID that usually contains a dash, hex digits and an `f`, and while the scan read the whole payload most pushes asked in this state, a plain one included (16 of 20 harness-shaped payloads in a probe; `tools/test_hooks.sh` 7e now sends a plain push in such a payload and expects it allowed). **What it judges** (plan 011, plan 027 and their reviews): every command of a multi-line command, joining a line continued with `\` or a PowerShell backtick (D38) and splitting each line at `;`, `&` and `\|`, so a tail such as `2>&1 \| tail -5` cannot hide the push; every refspec, not only the last; `--all` with a force flag, and `--mirror`. The candidate lines are the command read as POSIX-shell text and the raw command, each cut at those characters everywhere; the POSIX text split outside quotes only, so a separator inside a quoted value (`git -C "E:/R&D" push`, `-o "a;b"`) does not cut `git` from `push`, and each such segment again with its argument boundaries kept; and the raw command split outside quotes with the tool's own escape, so reading PowerShell never loses a push the raw text showed (a comma argument list such as `Start-Process git -ArgumentList 'push','--force',...`, `& ("git") push`, a refspec in parentheses). The quote-blind split drops a `#` comment from a segment only where no quote (ASCII, typographic or backtick) comes anywhere before it in the command, so a quoted ` #` never hides the push, even where that split cuts inside the quoted value (convergence of plan 027). Neither split is safe alone: an apostrophe in a heredoc line (`Don't push`) opens a quote that never closes and glues the later lines into one segment, so the push is anchored on the first `push` token with a `git` token before it (plan 011 final convergence). The same glue can refuse a later, unrelated command after such a line; that over-block stays, on the safe side. The current branch is asked once per run and each distinct line is judged once, so 100 push lines stay cheap; a refspec glued to a redirection (`bannerlord-1.5.x>/dev/null`) still counts. ## Git hooks (every committer)

The hooks above run only for the commands Claude runs. The repository's own git hooks live in the
tracked folder `.githooks/`, which `core.hooksPath` names (set once per clone with
`git config core.hooksPath .githooks`; a worktree whose branch predates the folder runs no hook).

| Hook | What it does |
|---|---|
| `commit-msg` | Runs `tools/check_commit_msg.py` on every commit message, terminal and IDE commits included: the `<type>[(scope)]: vX.Y.Z - <description>` subject with the `<Version>` of the tree being committed, at most 72 characters, and no AI attribution line. A `fixup!`, `squash!` or `amend!` subject passes. Refuses with exit 1 and names each problem; fails open, saying so, when Python or the checker is missing. Tests: `tools/tests/test_check_commit_msg.py`. |

## Responding to a hook

Every gate and banner states what to do in its own message (ADR-011), so follow the message; nothing
here restates it. What reaches Claude: SessionStart stdout, a PreToolUse `deny` reason, exit-2
stderr, and a Stop hook's JSON `{"decision":"block","reason":...}`. Claude answers that reason in
one more response; the next Stop payload carries `stop_hook_active: true`, and every TAOM Stop
hook stays silent then (though it still clears its marker). In a headless or SDK run, that extra
response replaces the run's final message (plan 011; unverified live). An `ask` reason goes to the user. Plain stdout from Stop, PreCompact and
PostCompact hooks, and stderr from a hook that exits 0, go to the debug log only. A PreToolUse gate prints its decision
under `hookSpecificOutput`; Claude Code ignores a top-level `permissionDecision`, which left nine
gates inert until #647 (`harness-facts.md` "PreToolUse output contract", `tools/test_hooks.sh` 5c).

Skill-inline (not in `.claude/hooks/`): `check-freeze.sh` — PreToolUse (Edit|Write) declared in the `/freeze` + `/investigate` SKILL.md frontmatter; blocks edits outside the frozen directory while one of those skills is active. Fires only during skill invocation (`harness-facts.md` "Hook lifecycle").
