# The Long Defeat

## Overview

A planned campaign-free survival mode on the siege maps: you defend Helm's Deep (Minas Tirith is a later fortress) against wave after wave, and you spend gold between waves. **Phase 1 is on trunk, and no person has played a full run yet.** Unattended runs clear 4 waves. In the newest one, wave 5 had 2 attackers left when Mike closed the game. It is a main menu option ("The Long Defeat", hidden when no fortress loads and on a dedicated server) with Helm's Deep as its one fortress: ten authored waves, then the last wave scaled by count, a purse, a shop between waves, a horn for bonus gold, a keep point (see Notes for Phase 1), and a stalemate rule. `taom.ld_start` and the `TAOM_LONGDEFEAT_AUTORUN` environment variable start the same path without the prompt. The Phase 0 spike (below) proved the engine assumptions on 2026-11-03: an unattended run cleared three waves at Helm's Deep with every spike line present. The plan Phase 1 was built from is [long-defeat/phase1-plan.md](long-defeat/phase1-plan.md). Phase 2 adds the seeded roguelite layer (endless scale, affixes, boons, classes, commanders, the Cavalry sally); it is on trunk, and unattended runs proved most of it in game on 2026-11-05 (see "Phase 2" and "How to verify in game"). Phase 3 adds the fortifications the lord buys between waves (the gate, field care, the Elven Volley, the high towers' archers and volley); its Slices 1 to 8 are on trunk and none of it has been played (see "Phase 3: fortifications"). The plan and the phases are in [#1079](https://github.com/haterade22/TAOM/issues/1079).

## Why This Exists

- **Vanilla behavior:** a siege is one battle, with one spawn logic that owns every troop from the start.
- **TAOM requirement:** waves without end, under vanilla's siege AI and engines, with no scripted AI. Fords of War scripts its own AI; a siege should not have to rewrite ladders, towers, rams and wall defence.
- **Without the spike:** Phase 1 would build a mode on engine assumptions that nobody has tested. The first review of the spike already disproved one of them (below).

## Architecture

### What the mission leaves out of vanilla's list

`LongDefeatMissionLauncher.CreateBehaviors` copies vanilla's custom siege list (`BannerlordMissions.OpenSiegeMissionWithDeployment`) and leaves these out: the spawn logic and handler, the reinforcement controller, `BattleEndLogic`, the two deployment behaviors, `BattlePowerCalculationLogic`, `GeneralsAndCaptainsAssignmentLogic`, and the observer, agent, banner, victory and highlight logics. The director spawns every agent from the mission tick.

Two engine paths read what is left out. [The lifecycle doc](../reference/engine/mission-and-missionbehavior-lifecycle.md) has the mechanism and the line numbers.

| Engine path | What the mission does |
|---|---|
| `TeamQuerySystem` reads `IBattlePowerCalculationLogic` with no null check | `LongDefeatMissionLogic` implements it and returns a large constant |
| `GeneralsAndCaptainsAssignmentLogic` asks a model that reads the spawn logic | It stays out. `AssignPlayerRoleInTeamMissionController` sets the order owner, and the director makes the player the general: the `general` check reads both |

### How a soldier gets a place

Soldiers spawn with no position, and the deployment plan gives each formation its place. `Boot` gives `DefaultMissionDeploymentPlan` the troop counts and calls `MakeDefaultDeploymentPlans`. The garrison and each wave then call `Formation.BeginSpawn` and `Mission.SetFormationPositioningFromDeploymentPlan`, and each soldier asks `GetAgentBuildDataToSpawnTroop` with no position. A later batch or a bought pack skips the placing (`SetFormationPositioningFromDeploymentPlan`) but still calls `Formation.BeginSpawn` (`LongDefeatDirector.SpawnBatch`, `LongDefeatBattlefieldAdapter.BeginBatch`), which vanilla does not do for a formation that already has a place (`MissionBattleSideSpawnContext.cs:369`). Two parts are not vanilla's path: each wave places its formations again, and a wave's batch stays open across several ticks. Vanilla's reader of `IsSpawning` is in the class this mission leaves out (`:403`).

**What keeps a soldier on the right floor:**

- The layout offers only slots that native `BatchFormationUnitPositions` accepts, spreading out from the frame (`Formation.cs:669-671`, `LineFormation.cs:495-497`). A slot needs a navmesh face, in a siege the frame's face group digit, and a height near its neighbours. That list comes from the native pseudo-C.
- A slot with no navmesh goes back toward the frame (`Mission.cs:3983-3985`).
- When the slots run out, every remaining soldier stands on the frame point (`Mission.cs:3992-3995`).
- `IMBAgent.SetInitialFrame` then takes the height. It casts a ray down from 1.5 m above the given height, falls back to the terrain height, and uses 0 if every try misses. The fixed path still goes through this step, but its input is now an accepted slot.

**Never compute a place by hand on a scene with floors.** The first version laid its own grid around the frame, in the manner of Fords of War's spawn block. On the first run at Helm's Deep, 64 of the 101 defenders stood below the wall line, with a median height of 0.0 against a frame at 26.5, and 3 died from the fall. Whether 0.0 came from a collider, from the terrain or from a miss was not traced.

**The read-back:** the spike's `[S1] spawn level` printed each class with its frame, `far`, `off the navmesh`, `on the frame point` and a `z` spread. Phase 1 writes `[LongDefeat] spawn level ok: <side> <class> N of M, far F, off the navmesh O, on the frame point P` when a batch closes, summed across the ticks it spans, for defenders and attackers alike. It says `ok` when every soldier is within 10 m of the height of that class's recorded point, or the scene's frame, and on a navmesh, and `WRONG` otherwise. The unattended judge needs an `ok` line for each side and fails on `spawn level WRONG`. **`ok` does not mean on the walls.** The tolerance cannot separate a terrace at 26.5 from a gate at 20.5.

**The pile:** the Helm's Deep terrace runs out of slots, so the engine stands the rest of the foot on one point: 41 of 68 in a garrison of 100, 64 of 115 in a garrison of 170 (the slots grow with the batch's planned shape, from 27 to 51). The spike's `[S1] spawn pile` line named this when more than 6 of a class stood within 1 m of the frame point (a shield wall at spacing 0 can put 5 healthy soldiers there). A pile failed nothing, and they spread out by themselves: by t 30 s all 101 stood high. It looks wrong to a person, so Phase 1 musters in timed batches (`[LongDefeat][Muster] batch`), each judged by the `muster` check. **`ok` for that check means that no more than half the batch stands on the frame point, or no more than 6 if that is the larger number**, with no soldier far or off the navmesh and at most 6 overlapping an earlier batch. A timed-batch garrison harmed nothing in run `20261104-033424`: `high` read 183 of 185 at about t 50 to 55, and 185 of 185 at t 60. Reinforcements can pile on their own frame too (the spike read 24 of 24 in wave 2 and 2 of 16 in wave 3), because a reinforcing batch keeps the live formation's shape.

**A stacked muster batch is under investigation.** One unattended run at a triple garrison put a whole muster batch of 20 militia on the muster point itself, and two more runs with the same timing did not repeat it. The likely cause is that the formation layout found no place for the new soldier and the engine put him on the formation's order position, but that is not proven, so nothing is fixed. Commit `7f7adc225` adds a diagnostic: a batch that stacks (more soldiers on the point than the `muster` check allows) writes one `[LongDefeat][Muster] stacked batch` warning. It repeats the engine's place lookup for the next soldier and logs whether the layout gave a place (`layout_place`), whether that place has a navmesh (`place_navmesh`), the formation's real file count against the smallest count the layout allows (`files`, `min_files`), its `width`, `interval`, `diameter`, arrangement and order, its `units`, `spacing` and AI control, and how far its order position stands from the muster point (`order_to_muster`). A small pack placed beside the point writes nothing. The line has not fired in game yet.

**A healthy Helm's Deep:** the defender archers' frame stands at height 1.5, so the spike's `[S1] after initial spawn` read `high` of 68 of 101, with a `z` minimum near 1.3. That is the scene's frame and not the fault repeating. The spike's `[S1] frames` line printed all six frames; Phase 1 has no such line.

### How a wave ends

No wave retreats, so a wave ends when no attacker stands, and that does not happen by itself. Only `BattleEndLogic` ends a vanilla siege, the player's exit aside: on a depleted side, or a side wholly running away (`BattleEndLogic.cs:198-222, 279-361`). Kills, a morale rout, the power retreat and the sally lead there. This mode leaves that logic out. On the first unattended run the last 7 attackers, then 6, and the last 31 defenders stood apart from t 420 s to the limit at t 1,500 s.

**The hidden gate at Helm's Deep:** the scene holds a hidden inner gate at height 32.5 (`aserai_castle_gate_inner_l1 visible="false"`). The 2026-11-06 rework in the Kit dropped it, and Mike put it back at (137.5, 185.8, 32.7); the runs below read the old one at (133.4, 180.7, 32.5). Without an inner gate the engine would throw: `BehaviorAssaultWalls.cs:122-174` reads `InnerGate` with no null check once the outer gate is open, and `MovementOrder.cs:902` does so on a defenders' charge. So `LongDefeatHelmsDeepGateTests` reads the live scene for one visible outer gate and at least one inner gate, with a gate entity's own tags replacing its prefab's, as vanilla scenes use them. The engine takes it as `InnerGate` with no visibility check (`TeamAISiegeComponent.cs:54-57`), and a hidden gate never ticks, so it never opens (`CastleGate.cs:619-622`). The Middle lane then stays closed (`SiegeLane.cs:355-364`), and attackers on the gate lane go to that gate and stay in `AttackEntity` (`BehaviorAssaultWalls.cs:161-166`). In all three runs the first attacker at height 32 or more appeared 20 s after the outer gate fell. Defenders hold their lane place on plain Move orders, and they hunt only with over 30 attackers inside (`TacticDefendCastle.cs:975`). Constant team power turns off the retreat and the sally, which are the other ways out. So `Boot` breaks any hidden gate and logs `[LongDefeat][Boot] hidden gate at (...): broken` (or `NOT broken`), then `hidden gates broken N`. It is not removed, because a null `InnerGate` throws in `BehaviorAssaultWalls`. **A campaign siege on this scene meets the same hidden gate**, and nobody has checked what it does there. **Breaking it works** (spike run `20261103-235325`, build `985b0d54e`, defaults): `[S1] hidden gate at (133.4, 180.7, 32.5): broken`, and `Middle open True` once the outer gate falls. Waves 1 and 2 of 110 cleared at 349 s and 669 s with no `stale` line, against 465 s and 840 s before. Wave 3 went quiet with 44 attackers left, and the charge ended it at 1,254 s, with no soldier felled by rule. The same rework left the right wall's breach child without its `WallSegment` script, so the base game's siege set-up threw at every start on the scene and the first run on it stalled in wave 1; the scene was fixed on 2026-11-10 and `tools/check_siege_wall_scripts.py` gates it ([RCA](../reviews/rca-helms-deep-siege-wall-2026-11-10.md)).

`WatchStalemate` was the spike's rule for every other stand-off. Phase 1 carries it as `Domain/StalemateRule.cs`, with its thresholds in `waves.json` and its lines tagged `[LongDefeat][Wave]`.

**The last few defenders lose the run (Mike, 2026-11-04).** When the rule below reaches no result, and `stragglerCount` (5) or fewer defenders stand, fewer than the attackers, the run ends as `DefendersDead`, with the panel's "The garrison has fallen". Any larger stand-off stays a stalemate. The first `--speed 10` run needed this: it ended on 89 attackers against 1 defender they did not reach. This loss skips the `stale` check, because the run did end, so the `[Check]` line and the `[End]` line name who stood. `reason=lost_defenders` alone no longer proves that no defender stood. Nobody has played what a living person sees here: Escape can dismiss the end panel, as on the other ends.

**The last few fall first (Mike, 2026-11-04).** When `stragglerCount` (5) or fewer attackers stand, fewer than the defenders, they fall after `stragglerSeconds` (60 s) with no charge, so the defenders stay on the walls. A death on either side does not restart that clock. Before this, 8 of the 15 cleared waves in four runs waited 110 s or more on their last 1 or 2 attackers, and Mike closed a run at the end of wave 5 because 2 attackers stood far outside the walls, near (274, 266) and (288, 257), and nothing moved. Nobody has traced why such a soldier stays out. A felled soldier pays no bounty. Larger stand-offs take the longer path:

1. With half the wave down and no loss on either side for 60 s, or no loss for 180 s at any count, `[LongDefeat][Wave] N stale: both teams charge` is written (the spike's `[S2] wave N stale` also printed the attackers' places and each formation's behavior, which Phase 1 does not), and both teams change to vanilla's `TacticCharge`. That tactic only weights `BehaviorCharge`, which returns 0 until the walls test passes (`BehaviorCharge.cs:169-201`), so it moves soldiers on some lanes and not on others, and a formation under a player's orders does not move at all.
2. After 90 s more with no loss, `[LongDefeat][Wave] N stragglers fall: ...` is written and they fall (`Mission.KillAgentCheat`; the spike printed their places under `[S2] wave N: nobody reached the last M attackers`). One soldier can stand for good: in wave 2 of the passing run the last attacker never left the spawn area, at (260.2, 305.9, -0.8). Only stragglers fall: at most a tenth of the wave, and fewer than the defenders. Otherwise no wave clears, because a clear must be earned: at Minas Tirith the first form of this rule felled 35 attackers with 2 defenders left. That end is now a loss, and only a larger stand-off is a `stalemate`. The judge's result counts the waves that ended by this rule.
3. At the wave's clear, the defenders get a new `TacticDefendCastle`, and they start the next wave out of place: `high` read 46 at the start of wave 3, and 163 of 170 about 15 s later. The next wave's new `TacticBreachWalls` comes when its first batch is out (`RefreshAttackerTactic` in `Domain/SurvivalRun.cs`), so the attackers stay on `TacticCharge` until then.

The rule fired in waves 2 and 3 of the passing run. A wave of 110 lost its last soldier at about 840 s and 1,380 s of mission time, 90 s and 128 s after the `stale` line. Soldiers can still flee on low morale, and Phase 1 closes that. The state lines of the four runs count none, and one `OnAgentPanicked` warning fired at Minas Tirith.

### The terrain shader dialog at Helm's Deep

A Helm's Deep load can stop at a native dialog: `Error compiling shader file: $BASE/Shaders/Sources/pbr_terrain.rs` (and `pbr_terrain_gbuffer.rs`), X4008 at `terrain_pixel_functions.rsh:818`, raised to an error by X3129. **Press Cancel.** The mission then loads in seconds. Retry compiles the same source (native `FUN_1800934e0` returns to `D3DCompileFromFile`), and Cancel returns a null blob. Two native flags skip the dialog, and nobody has read what sets them. The dialog holds the game, and nobody is there in an unattended run, so `tools/run_long_defeat.py` presses Cancel by itself and logs that in `runner_log.txt`. Left open for 304 s, the dialog made the load stall watchdog (removed 2026-11-12) write a `[CrashReport]` block, which failed the judge; with the watchdog gone it only stalls the run.

Open: Mike's by-hand launches at 17:26 and 17:28 loaded in under 10 s and show no sign of this dialog, and all three unattended launches at this fortress met it. The runner's `shader cache list differs` does not explain that, because it is on all four runs, and Minas Tirith had no dialog. Phase 1 stands in for the cached-variant or guarded-copy ask with one sentence in the setup prompt ("If a shader error window appears while the fortress loads, press Cancel"), which replaces that ask only on Mike's word, and does not touch `Shaders/`, which belongs to the install. **Decision for Mike, open:** build a scene shader sack for Helm's Deep in the Kit. It would live in the unversioned `TAOM_Map`, so a reinstall reverts it, and the same dialog already threatens a Custom Battle siege at this scene.

### Decisions from the spike

The first two still hold in Phase 1. The other three describe the spike's runner, which went with the spike: Phase 1 has no refill and no in-mission tests.

- **Power never orders a retreat.** The constant keeps both power ratios near 1, so `TacticBreachWalls` never takes its one-way retreat on power, and `TacticDefendCastle` never sallies on it. No wave retreats in this mode (Mike, 2026-11-03). The constant closes only the team retreat: a soldier can still flee on low morale, so Phase 1 adds attackers to `TaomCustomBattleMoraleModel.CanPanicDueToMorale`, and its state lines count anyone who flees. `FellFoesAdapter.SendOff` calls `Retreat` directly, and the `no-rout` check fails if a soldier it sends off is counted.
- **Waves are larger than 100.** At 100 attackers or fewer, `TacticBreachWalls` stops using its machines. The spike's by-hand default was a wave of 120 and a garrison of 100, and its unattended default was 110 and 170, because 100 defenders held on one run and all died on the other, with about 45 attackers left. Phase 1's balance is under "The first balance" below.
- **Each wave got a new tactic.** The first spawn batch latches a shock assault and clears `ForcedUse` on the engines. The runner set `ForcedUse` back and added a new `TacticBreachWalls` when the wave's queue emptied.
- **The garrison refilled between waves,** so a later wave's evidence did not depend on the first wave's losses.
- **All in-mission tests ran after wave 1:** S5, S7, then S4. Every later wave then met the repaired gate.

A third table holds waves 3, 4 and 5 at 120, 125 and 130 attackers, with level 21 troops first at wave 5, and bounties 1.5 times higher. The old top mix stays at wave 10. **The rest rule:** nothing heals a surviving soldier in a mission, so I suspected that wounds caused the growing losses. At each clear, every standing defender now regains `rules.restShare` of the health they are missing (`waves.json`, 0 to 1, shipped 0.5, and 0 turns it off). `[LongDefeat][Wave] N rest: defenders C, mean health B% to A%` measures the wound: A is read back from the engine. The mean covers survivors, counts a fleeing soldier, and can read high while the front rank is badly hurt. The planned Field care can sell more healing on top of this. Damage to the gate and to shields also carries over, and the rule does not touch them (`Agent.RestoreShieldHitPoints` has no caller).

**Wounds are not the main cause.** Run `20261104-071020` (clean build `34541922c`, on engine changeset 125270) measured it: survivors' mean health was already 84% to 91% before each rest, and 92% to 95% after. Its defenders lost per wave were 32, 42, 91, 36, then 140 at wave 5, which reached 2 attackers and 48 defenders when Mike closed the game. The same table lost 18, 77, 151, 98 in the run before, so one run cannot separate the rule from chance. Why losses swing this much between runs, and why attackers climb in numbers in some waves and not others, is still open. The rule costs little and stays for now, and Mike can set `restShare` to 0.

The towers stay at the wall after wave 1, and Phase 1 has no gate repair, so from wave 2 attackers reached high ground 55 to 70 s after the wave began, against about 150 s in wave 1. A wave took 5.5 to 11 minutes, and five waves took at most 2,427 live seconds, under the wrapper's 3,600 s live limit.

## Configuration

No MCM. Six JSON files under `Main/_Module/ModuleData/long_defeat/` hold the content, and each bad value costs one logged warning and falls back to its default: `fortresses.json` (scene, cultures, garrison, keep point), `waves.json` (the `rules` numbers, bounties, wave rosters) and `shop.json` (offers and starting gold), then `affixes.json`, `boons.json` and `classes.json`, each described under "Phase 2" below. The files are read once per game process, so an edit needs a full game restart, not a new run. An unattended run takes an arm file of `key=value` lines named by `TAOM_LONGDEFEAT_AUTORUN`: `fortress`, `waves`, `out` (required, absolute), `quit`, `live_limit_seconds`, `wall_limit_seconds`, `screenshots`, `garrison_scale`, `expect`, `speed` (1, 2, 4 or 10), and the Phase 2 keys `seed`, `start_wave`, `start_rerolls` and `class`, and the Phase 3 key `start_gold`. Player-facing text is the `TAOM_LD_*` rows of `taom_module_strings.xml`; the 12 language files carry the English seed until #763.

**The run report** (`long_defeat_report_*.json`, beside the log) also carries what a leaderboard checks: `schema`, `build`, `balance` (a hash of the six JSON files with line endings normalized), `cheatMode`, `mods` (ids with versions), `autoplay`, `garrisonScale`, `targetWaves`, `maxSpeed` (the highest mission speed set in the run), `startedUtc` and `endedUtc`. It holds no player name. The board itself is not built: [leaderboard-plan.md](long-defeat/leaderboard-plan.md), #1080.

## Phase 2

Phase 2 ([phase2-plan.md](long-defeat/phase2-plan.md)) layers a seeded roguelite run over Phase 1's survival run: an endless scale past the authored waves, affixes on the attackers, boons the lord picks, four classes, enemy commanders with summons, and a Cavalry sally. It was built in eleven slices and pushed to trunk. Unattended runs on 2026-11-05 passed the troop and class boons, the reroll, the captain and the lieutenant with his summons, all three foot classes, the Cavalry class without a sally point, and the Hammer, Winged Terror and Morgul Blades affixes. Still owed: the sally itself (no point is recorded yet), the kill owner after the player's death, and a person's play. "How to verify in game" lists the check for each mechanic. Its content is in `affixes.json`, `boons.json` and `classes.json`, plus new blocks in `waves.json` (`scaling`, `tiers`, `commanders`) and `fortresses.json` (`sally`, `towers`, `volley`). Every check named below is a `[Check] id=taom.long-defeat.<name>` line with a row in `tools/ingame_checks/1079.toml`, and `tools/run_long_defeat.py` judges it. **Still open:** no sally point is recorded yet (Mike records one on 2026-11-06, see "The Cavalry sally"), and a stacked muster batch is under investigation (see "The pile").

### The seeded run and the report (Slice 1)

- **Report schema 2.** Schema 1's fields keep their names and meaning. Schema 2 adds `seed`, `class`, `startWave`, `startRerolls`, `boons`, `rerolls`, `poison`, per wave `affixes`, `healthFactor`, `damageFactor`, the summon counts and `commander`, and `gold.commander` and `gold.boon`. `balance` hashes six files, the three Phase 1 files plus `affixes.json`, `boons.json` and `classes.json` (a missing file joins as empty text), so the hash differs from any Phase 1 build's.
- **`RunRandom`** is the SplitMix64 every roll draws from, with its vectors pinned in `RunRandomTests` and in `test_run_long_defeat.py`. `RunOptions` gains `Seed` (the start time's ticks when none is armed, taken in `BuildPlan`), `StartWave` and `StartRerolls`.
- **Arm keys** added to the Configuration list: `seed` (0 to 2^53-1; a negative or larger value is refused, because the cap keeps every digit for a JavaScript reader of the report, and a clock seed is masked into it), `start_wave` (1 to 100: the run begins at that wave number, while `waves` still counts clears), `start_rerolls` (0 to 3) and `class`.
- **Wrapper flags:** `--seed`, `--start-wave`, `--start-rerolls` (armed as 1 unless given), `--class` (`all` gives each run the next class) and `--deep` (`--start-wave 12 --waves 4`, judged by its own list and allowed to end lost). The judge refuses a report that is not schema 2 or that does not echo the armed seed, start wave and rerolls, and fails on any `owner_missing` above 0.
- **Blow owner gate:** `LongDefeatBlowOwnerTests` fails when anything outside `ApplyPoison` and `Fell` kills an agent, or when a blow takes owner -1 (see "Poison and the kill owner").

### The endless scale (Slice 2)

A wave past the authored list takes a health factor and a damage factor, each `min(maxFactor, 1 + perWave * extra)` with `extra` the waves past the list (shipped: 5% and 3% a wave, capped at 3). Every `tierEveryWaves` (3) extra waves, each row of its mix moves one link along the roster's `tiers` chain. Rows that land on one troop merge their weights, a chain stops at its end, and the count line is unchanged.

- **Helm's Deep's chain** runs fighter and militia spearman to warrior to spearman to veteran spearman to veteran pikeman; swordman to infantry to veteran infantry; and skirmisher to arbalest to crossbowman to veteran crossbowman. Only the last authored wave's mix is stepped (spearman, infantry, berserker, crossbowman), so just four links can fire with the shipped waves (spearman, infantry, crossbowman and, at two steps, veteran spearman). The links from militia spearman, fighter, warrior, swordman, skirmisher and arbalest are parsed and checked but no wave reaches them. `bounties` gains the four veteran troops (15, 20, 20, 20).
- **Config:** `waves.json` takes `healthPerWave`, `damagePerWave`, `maxFactor` (1 to 10) and `tierEveryWaves` (1 to 50) in a roster's `scaling`, and a `tiers` block beside it. A bad number keeps its default with one warning. A tier link that is not a troop id, points at its own troop, joins two classes the roster's waves show or closes a cycle is skipped, and a target with no bounty pays 0 with one warning. The launcher's troop check reads `RunPlanTroops.AllTroopIds`, so a missing tier target refuses the launch instead of spawning nothing.
- **Health** is written after each attacker spawns (`BaseHealthLimit`, `HealthLimit` and `Health`, in `LongDefeatBattlefieldAdapter.SpawnBatch`, from `SoldierBatch.HealthFactor`).
- **Damage** is published by `LongDefeatEffectsAdapter` with the effect that starts the wave, before any soldier of it spawns. `LongDefeatCombatHooks.Amplify` applies it to attackers' blows from `TaomCustomBattleDamageModel.ApplyDamageAmplifications`. The hook is inert unless the Long Defeat mission is armed, so Fords of War and every other Custom Battle pass through, and a fall is not a blow (the engine names the faller as its own attacker), so a scaled attacker's fall damage is untouched. The model also runs for a soldier's blow on the gate, a wall section or a shield, which take the factor too; the ram damages the gate directly and does not. Whether that is wanted is open (phase2-plan.md, Slice 13). Defenders are never scaled.
- **Report and check:** `waves[].healthFactor` and `damageFactor` carry the values (1 inside the authored list). `scale` (key `w=<N>`) is written once per scaled wave, at its clear or at the run's end inside it. A sampled attacker's health limit over its character maximum must equal the health factor within 1% at spawn and again late in the wave; its troop must be one of the wave's stepped mix; a damage factor above 1 must have raised at least one attacker blow (a defender's boon blow is not counted); and the engine's standing count must never exceed the room the previous tick spawned into. The sample is a standing attacker that is not running away, so a runner left from the wave before is never read. The judge requires the line from any report with a wave row whose health or damage factor is above 1. The numbers are first guesses (assumptions A9 and A15 of the plan).

### Affixes (Slices 3, 8 and 9)

**The roll.** From wave 5 a wave carries affixes: one from wave 5, two from 10, three from 15 (`affixes.json` `schedule`). The roll is a partial Fisher-Yates over `AffixPlan.Pool`, drawn from `RunRandom` stream 1 at `(wave, 0)`, so one seed gives one roll, a shorter roll is a prefix of a longer one, and the HUD's preview of the next wave cannot differ from the wave. The roll is taken when the wave's horn sounds. The eight ids are `lash, drums, eye, discipline, hide, hammer, terror, blades`, and all eight are in the pool (`AFFIX_POOL` in `tools/run_long_defeat.py` follows, and a test pins both to the same list). `AffixPlan` holds the schedule, each power's numbers and the names of the fortress's attacker culture (`names.isengard` and `names.mordor` ship; at Helm's Deep `blades` is named Fouled Blades). A bad number keeps its default with one warning, and a culture with no name table shows power ids with one warning. Adding a power to the pool changes every roll, so each slice that did so (the pool grew from five to seven to eight) re-pinned the rolls and the in-game seeds. At wave 5 seed 0 now rolls `eye`, 1 `hide`, 2 `lash`, 3 `blades`, 5 `discipline`, 7 `terror`, 9 `hammer` and 15 `drums`.

**The stat powers and `hide`.**

- `lash` (swing speed, attack eagerness), `drums` (move speed, acceleration), `eye` (aim error, draw, reload and missile speed) and `discipline` (block and parry) fold into one `RaceAbilityEffects` record built fresh for each wave (`RunModifiers.StatTable`) and published with the wave's start effect, before any attacker spawns.
- `LongDefeatStatHooks.UpdateStats` runs after the race abilities' post-pass in `TaomCustomBattleAgentStatCalculateModel.UpdateAgentStats` and applies the record through `RaceAbilityStatApplier`, so a percentage multiplies what the engine just derived and never compounds. A horse takes its rider's record (only its mount speed, which the record copies from move speed); a riderless horse takes nothing.
- `hide` raises the four armour values of a human attacker by its percent in `InitializeAgentStats`, because the engine writes armour once, at spawn. Null build data (`SpawnMonster`), a horse and a defender pass through.
- Both hooks are inert unless the Long Defeat mission is armed. `LongDefeatHookState` holds the one armed mission and the one published `LdStatTable` that the stat and combat hooks both read, and the attackers' damage factor lives in `LdStatTable.AttackerDamage` alone.
- Not built: `RefreshStats` for the affixes (nothing stands when a wave starts, so it matters only for the war cry and the boons).

**`hammer` (Hammer of the Underworld).** `RunModifiers.EngineHitPoints` is `1 + engineHitPointsPercent / 100` in a hammer wave and 1 in every other. At each wave start the effects adapter writes `MaxHitPoint` of every live ram and siege tower to the vanilla value of the engine's type (`SiegeEngineType.BaseHitPoints`, the number the deployment sets) times that factor, and the current hit points by the same ratio. A damaged engine keeps its share, a destroyed one stays destroyed (no `Reset`), and factor 1 restores the vanilla value after a hammer wave. The write comes with the wave's stat publish, before any attacker spawns. The factor multiplies the engines' vanilla hit points and nothing else: the endless health factor is the attackers' soldiers' health limit and the endless damage factor their blows, which reach the gate, the walls and the shields through the damage model but not the ram, so neither feeds the hammer or is fed by it.

**`terror` (Winged Terror).** It pulses on the run's clock: every `pulseSeconds` of a terror wave's fighting, once per tick however long the tick, `LdMoralePulse.Apply` lowers each standing human defender within `radius` of a standing attacker by `amount`, never below `floor` (35), and leaves one at or under the floor alone, so routs do not cascade. Distance is measured across the ground, so a defender on a wall is reached from its foot. The attackers are only read for their positions, and the lord is never a target (a lord played by a human has no morale component and answers -1, but an autoplayed one is handed to the AI and gets one, so the pulse leaves out the main agent). The pulse reads the attackers' positions once into an array, counts the defenders drained and the ones left more than 0.001 below the floor (`pushed_below`) inside the call, and times itself. The first three pulses of each wave log `[LongDefeat][Terror] pulse n= ms=`, and any slow one too.

**`blades` (Morgul Blades).** See "Poison and the kill owner" below.

**The HUD and the report.** The strip names the running wave's affixes at once, and between waves the next wave's with, past the authored list, its attackers' health and damage (read from the wave plan; the view builds that preview only between waves). The report's `waves[].affixes` carries the power ids.

**Checks.**

- `affix` (key `w=<N>`) is written when a wave with affixes starts: the count matches the schedule (with `affixCount` boon cuts applied, see Boons), the powers are distinct and known, and each has a name in the culture's table.
- `affix-effect` (key `power=<id>`) has a verdict per power. For the stat powers and `hide` it is written when the wave's first batch has closed: one standing human attacker with no live race ability and no hero aura (#1127, `RaceAbilityHooks.HasLiveEffects`) is read back against the stat model's own answer for the same agent with the affixes left out (a thread-local bypass of the hook; armour against the spawn equipment's sums), within 1%. A sample that could not show the effect (an unarmoured soldier) is a skip, and no standing plain attacker is a fail with `reason=no-sample`. The director reads one soldier once per wave and judges each stat power on that sample. A wave whose only powers are `hammer`, `terror` or `blades` reads no soldier, because those have no stat expectations.
- `hammer` is written when the wave starts and passes when every live engine holds the vanilla value times the factor within 1% (the gate's state is logged beside it and judges nothing, and is read from every mission object because a destroyed gate leaves the active list, `Mission.cs:3060`; no live engine, or a factor of 1, is a skip).
- `terror` is written when the wave clears or the run ends in it. It passes on at least one pulse that drained someone, fails on any `pushed_below` or a pulse that took 16 ms or more, and skips when the wave had no pulse or none drained anyone.
- `blades` is described under poison.
- **The judge** replays each wave row's affixes from the report's seed (`affix_roll`, pinned against `AffixPlanTests`) and reads `affixes.json`'s schedule by the game's own rules (a missing file rolls nothing, a bad schedule is the shipped one). It requires `affix` from a run that cleared 5 waves or whose report shows a wave with affixes (the plan says 4 clears, which would fail a `--waves 4` run that never starts wave 5), and an `affix-effect` pass or skip line from a run whose report shows any power.

### Boons (Slices 4 and 6)

**Picks and rerolls.** A clear that brings `WavesCleared` to a multiple of 3 owes a pick, and one that brings it to a multiple of 5 earns a reroll into a bank of 3. A reroll lost to the cap is not counted as earned; `StartRerolls` seeds the bank and counts as earned, so the bank is always earned minus used. One offer is open at a time and stays open into later intermissions. A pick or a reroll is made between waves only, and the panel never opens by itself for one (a notice and the hint line announce it). A boon lasts until the run ends.

**The offer.** Three cards drawn from `RunRandom` stream 2 at `(pick, draw)`, with the first pick numbered 1 and the first draw 0. Each card is `Below(total weight)` walked over the eligible rows in file order, 10 a row and `legendWeight` (shipped 1) for a Legend row, taken and removed. A reroll discards the offer and draws again with the next draw index, leaving out the three cards just shown unless fewer than 3 others are eligible. A boon owned is never offered again; fewer than 3 eligible rows offer what is left, and none lapses the pick with a log line. A class row is offered only to a run of that class (`SurvivalRun` builds its `BoonDeck` with `plan.Options.ClassId ?? ""`), and a troop category's rows only while the fortress's garrison or shop holds a troop of that group (`RunPlanTroops.DefenderGroups`, static data, so the replay sees it). A troop's group comes from its character, the engine's flags read once from the XML `default_group` by the launcher (`LongDefeatTroopGroups`, into `RunPlan.TroopGroups`): mounted is cavalry, else ranged is archers, else infantry. So the King's Knights on the Helm's Deep shop list, bought to fight on foot, are cavalry.

**`boons.json`** ships 34 rows (counted from the file): 5 war chest, 5 fortress, 3 Legend (`the_long_silence` among them, see Commanders), 12 class rows (three for each of the four classes) and 9 troop rows (three for each category: infantry, archers, cavalry). Names and texts are TAOM's own. Drawbacks carry their own line of text (a `drawbackText` key the plan did not list, so no cost is hidden).

**The effect vocabulary** is closed; the reader skips any other key or an out-of-range value with one warning, and a boon left with no effect or a drawback with no text is skipped.

- War chest and fortress keys: `bountyPercent`, `waveBonusPercent`, `earlyGoldPercent`, `pricePercent`, `gold` (paid once at the pick), `garrisonCap`, `intermissionSeconds`, `restShare`, `keepHoldPercent`, `packBonus` and `affixCount` (negative only; never a drawback, as `gold` is never one).
- Ten targeted keys, each with a `target` (`infantry`, `archers`, `cavalry` or `player`, in an effect and in a drawback; a targeted key without a valid target is skipped with one warning): `swingSpeedPercent`, `moveSpeedPercent`, `drawSpeedPercent`, `reloadSpeedPercent`, `blockPercent`, `parryPercent`, `aimErrorPercent`, `damagePercent`, `damageTakenPercent` and `healthPercent`.
- Commander boon key `commanderCooldownPercent` (see Commanders).

**Every number a boon changes is recomputed from the boons owned** (`RunModifiers.Rules`, `Gold`, `AffixCut`), so a second boon never applies the first twice.

- The war chest keys become four factors (a sum of percents, never below 0, rounded half away from zero where they meet gold). The horn's factor scales both its rate and its cap. A price factor and `packBonus` rewrite the shop's offers (the view shows what a buy costs and the pack the player gets).
- The fortress keys change the run's effective rules with floors (garrison 1, intermission and keep hold 5 s, rest share 0 to 1). An intermission boon acts from the next clear.
- `affixCount` cuts the affixes of the wave that begins after the pick: the wave carries the first `max(0, scheduled + cut)` of its roll, so the HUD's next-wave line shows the cut list.
- The stat keys fold into one `RaceAbilityEffects` record per target in the published `LdStatTable` (percents sum within a target; the cavalry and player records copy move speed into mount speed). `LongDefeatStatHooks.UpdateStats` writes the record of the group a defender's character puts it in; the lord's body takes the `player` record only, whoever he was.
- `damagePercent` and `damageTakenPercent` are two factors per target that `LongDefeatCombatHooks.Amplify` and `Reduce` apply from `TaomCustomBattleDamageModel` (a horse takes its rider's, and `Reduce` wraps the Fords call).
- A health boon multiplies the health limit of those standing by that boon's own factor (`ScaleHealth`, keeping each soldier's health share), and every defender batch spawned later takes the product of the boons' factors for its group, so a second health boon never applies the first again. The lord's health is only ever set outright to the combined factor, at the pick too, so a body adopted in the same tick cannot take the pick twice.
- A pick tells the director what to do on the next tick: publish the new table, refresh the driven properties of the groups whose stat keys changed (`RefreshStats`, which logs `[LongDefeat][Boon] refresh <group> n= ms=`), then scale health, all before anything spawns. A body that becomes the lord's (the start, a respawn, a soldier taken over after his death) is refreshed and has its health limit set outright to the player's factor (`AdoptIfNew`), because the controller setter calls no stat update (`Agent.cs:1233-1290`). The lord's own spawn takes the same path, so `SpawnPlayer` carries no factor.
- Not built: spreading a large refresh over ticks (the `refresh` line measures it; risk 11 of the plan), and any read of a damage-only boon (it acts at the blow).

**The panel and the bot.** The panel gets a pick group above the shop (three `LongDefeatBoonVM` cards, a reroll button with its count), and the end panel lists the boons taken and opens with "Class: ...". The HUD strip names the class after the wave ("Wave 3, Archer"). The unattended bot answers an open pick first: a reroll when one is banked and every card has a drawback, else the first card without a drawback, else the first card. It also spends the first banked reroll it ever holds on the first offer, which is how a 5-wave run proves a reroll at clear 3 (the plan's rule alone would reroll only on three drawbacks).

**Checks.**

- `boon` (key `p<N>`) is written when a card is taken: the last draw showed 3 distinct cards (or all that were eligible), the taken one among them, and every number a boon changes reads back as the shipped value changed by the boons owned, recomputed in the check apart from `RunModifiers`. For a boon with a stat or health key the line ends with `read=pass`, `read=skip` (no soldier of the target stood) or `read=fail`: a soldier of the target, read right after the refresh, holds its health limit at the combined factor and each driven property at its baseline (the stat model with the hooks inert) changed by the summed percent. A rider's horse is read too: its `MountSpeed` against the stat model's answer for the horse, when a horse stands under the soldier. The first pack of that group spawned after the pick is read the same way as its own `boon` line (key `p<N>-<group>`, `read=spawned`).
- `reroll` (key `p<N>`) is written for each reroll: the bank fell by one, there are new distinct cards, and none of the cards just shown when 3 or more others were eligible.
- The horn's `early-start` check follows the factor in force.
- **The report** lists each pick (`pick`, `wave`, every draw in `offered`, `taken`, `takenBeforeWave`), `rerolls` and `gold.boon`.
- **The judge** replays the boons from the report's seed over the shipped `boons.json` (`boon_cards`, pinned against `BoonDeckTests` and `LongDefeatShippedConfigTests`), including the class and troop rows (`troop_groups` reads `fords_troops.xml`, `boon_eligible`, pinned against the C# deck for an archer at Helm's Deep). It checks the rerolls add up, keys the affix cut on the wave a boon was taken before (`affix_cut`), requires the `read=` token on the pick line of a taken boon with a stat or health key (`read_owed_picks`), requires `boon` from a run that cleared more than 3 waves or took a pick (a `--waves 3` run ends at the clear that opens the pick, so the bot never sees an intermission to take it in), and requires `reroll` from one that banked a reroll at its first pick or spent one.
- `docs/reference/provenance-register.md` records the design reference (a comparison-only row, status uncleared), and the reviewer compares the names and texts in `boons.json` against that page.

### The lord's class (Slices 5 and 11)

**Classes.** The lord plays one of four classes from `long_defeat/classes.json`: Sword and Board, Two Handed Infantry, Archer and Cavalry (`mounted: true`). A class is a kit per defender culture (Helm's Deep's defenders are `vlandia`, which is Rohan), written with the XML slot names `Item0` to `Item3`, `Head`, `Body`, `Leg`, `Gloves`, `Cape`, `Horse` and `HorseHarness`; an empty string clears a slot, and a class with no kit for the fortress's culture is not offered there. The foot kits give weapons only, so the lord's armour stays his own. The class question's description says the Cavalry kit also sets the armour and the horse.

**The spawn.** At the start and at every respawn the adapter copies the lord's first battle set, overwrites the kit's slots and hands that set to the engine as the spawn's equipment override, which `Mission.DecideAgentSpawnEquipment` reads before anything else. A foot class always clears both horse slots and spawns with `NoHorses(true)`; the spawn clears `NoHorses` only through the kit (`.NoHorses(!mounted)`). `spawnWithHorse` stays false on purpose, because true would read a mount key from the lord's own Horse slot (`Mission.cs:4500-4503`) instead of the kit's. A null key still builds the horse, and the visual picks a random coat (`MountVisualCreator.cs:41-46`), so a remount shows a new coat (plan risk 8 is closed). A slot is mapped through `Equipment.GetEquipmentIndexFromOldEquipmentIndexName` and checked with `Equipment.IsItemFitsToSlot` (a horse must also be rideable, in `BuildKit`). An unknown item or a misfit leaves the lord's own item in that slot with one warning, so the `class` check fails instead of the run quietly playing another kit. A player troop with no battle set starts from an empty one, because spawned without the override the engine would throw for a hero (`FirstBattleEquipment.Clone()` on null) or give any other troop an empty set. The adapter reads the kit back once, in the frame of the spawn, and keeps those facts rather than the `Agent`, whose slot the engine recycles. A soldier's body taken over after the lord dies keeps its own gear.

**Own-gear rule.** Every kit item is carried by a Rohan troop in `fords_troops.xml`, with one named exception that `LongDefeatShippedConfigTests.OwnGearExceptions` lists with its source: the two-handed class swings the Armory axe `wm_rohan_ws_axe_2h_a01` (`LOTRLOME_items/LOTRAOM_weapons.xml`), because no Rohan troop carries a two-handed sword, axe or mace (decision D5, taken on Mike's standing word).

**Cavalry.** Its kit is one Rohan rider troop's gear, the East Emnet Eorlingas Lancer: spear `wm_rohan_ws_spear_a03`, shield `wm_rohan_shield_a02_ggw`, sword `wm_rohan_ws_sword_a01`, the five armour pieces, and `t3_empire_horse` with `rohan_horse_armor_one`, with the fourth weapon slot cleared. Every id exists in the Armory or SandBoxCore, and `LongDefeatShippedConfigTests` pins that the kit is that troop's own. Not built: an `Item4` slot (no Fords troop carries one, and a test says so). Its three class boons are:

- Gallop of the Eorlingas: move speed +15 percent on the player record, which `ApplyMount` carries to the horse through `MountSpeedPercent` and `RiderAgent`. The `boon` check reads `MountSpeed` on the lord's horse while he has one; with none standing it drops that reading and still writes `read=pass`.
- Spear of Eorl: +25 percent damage, -10 percent swing speed and -10 percent draw speed. The kit's spear has only thrust attacks, which run on `ThrustOrRangedReadySpeedMultiplier`, a separate property from the swing one.
- Oath of Eorl: +35 percent health.

A cavalry troop boon such as Fleet Horses of the Mark still reads `skip` in a Cavalry run, because the mounted lord is the player record and the bot buys no rider.

**Choosing a class.** The setup prompt asks a second question after the fortress, "Choose your class", with one row per class: the row shows the class name, and its kit text shows when the row is hovered, because the engine's row is a fixed 65 px button that a two-line text overflowed. Cancel at either question starts nothing, and a fortress that offers no class starts at once. `taom.ld_start <fortress> [waves] [class]` takes the class as a third word (or as the second when there is no wave count). The arm key `class` reaches `RunOptions.ClassId` through `ToSetup`. `LongDefeatConfigCatalog.BuildPlan` resolves it: the class asked for when the fortress offers it, else the bot's draw `RunRandom.For(seed, 3, 0, 0).Below(classes on offer)` for an unattended run, else the first class on offer for a person. A class asked for and not on offer costs one warning and takes that default. The resolved id is written back into the options, so the report's `class` names the class that was played (empty only when none is on offer), and `RunPlan.Loadout` carries the kit. With four classes the bot's unarmed draw is `Below(4)`; seeds 0 to 7 draw sword_and_board, archer, cavalry, archer, two_handed, cavalry, archer, archer (pinned in `ClassPlanTests` and `test_run_long_defeat.py`).

**The check.** `class` (manifest row `taom.long-defeat.class`, key the mission id, or `<mission>-d<N>` at a respawn) is written after each spawn of the lord: every kit slot read back from his spawn equipment holds the item the kit names (an empty slot reads back empty), the engine refused no slot, he did not fall back to his own gear, and he sits a horse only when the class rides. It is required of every run (`absence = "fail"` once the boot passed).

**The wrapper.** It reads `CLASSES` from `classes.json` and a test pins it to the file. `--class` takes only those ids or `all`, which gives each of `--runs` the next class (`--runs 4` plays all four). The judge expects the class each run armed, set per run in `arm_text_for` so `--class all` is compared run by run, or, when none is armed, the bot's draw replayed from the report's seed (`bot_class`, pinned against `ClassPlanTests`). It also fails a report whose class is not on offer and a run with no `class` pass line.

### Commanders and summons (Slice 7)

- **Who and when.** Every fourth wave brings an enemy commander, from the roster's `commanders` block in `waves.json`: Lugdush (`lord_I3_1`, captain, wave 4), Ugluk (`lord_I1_1`, lieutenant, 8) and Lurtz (`lord_I4_1`, general, 12 and after). A rank sets its own health factor (2x, 3x, 4x, decision D11), written after spawn and multiplied with the endless factor, a bounty paid into `gold.commander` on a kill (none for a felled commander) and its abilities. The HUD strip shows his rank and next ability, not his name, because the data carries none.
- **The general grows.** From wave 16 he returns stronger: `steps = min(maxSteps, max(0, wave / every - validRanks))` adds 25 percent health, shortens each cooldown by 10 percent (never under 5 s, and a war cry's never under its duration plus 5 s) and adds 5 soldiers to each summon per step, so waves 4, 8 and 12 are at full strength.
- **Spawn.** He is queued at the head of the attacker queue when the wave's first batch closes, spawns as the next soldier, takes a slot of live room like anyone and is outside the roster count. The engine marks a hero unique at his spawn (`Mission.cs:4517-4523`) and dresses him in his first battle set rather than a random one (`Mission.cs:4284-4287`, `:4108`). The warg in that set is cleared like any horse (`:4468`, `:4109-4112`), so he fights on foot, and the other managed differences are cosmetic (his banner moves from the extra weapon slot to the formation, `:4122-4134`, and the face cache and random colours are off).
- **Abilities** run on a `CommanderClock` started when the director tells the run he is up: at most one use per tick, and a permanent stop when he is killed, felled or leaves the field (soldiers already summoned still come). `War Cry` (first at 20 s, then every 60 s, for 15 s) adds 15 percent swing and 10 percent move speed to every attacker's stat record, published and refreshed on the standing attackers at its start and end. `Summon` (30 s, then every 120 s) queues 20 Uruk-hai veterans at the head of the queue, so they spawn as live room allows. The Legend row `the_long_silence` (`commanderCooldownPercent` 50) stretches every cooldown.
- **Felling.** A felled soldier is first brought to at most 1000 health, because `KillAgentCheat` inflicts a flat 2000 (`Mission.cs:6228`) and `Agent.HandleBlow` kills only when the health left is under 1 (`Agent.cs:5529`); a commander of wave 36 or later stands above 2000 and would otherwise survive the fell.
- **Stalemate rule.** The wave size it uses counts the summons queued, and the straggler share the `wave` check allows is `stragglerShare * (count + summoned)`.
- **The role registry.** `LongDefeatAgentRegistry` replaces the shared fell counter. `Fell` marks each soldier before it kills him and `AttackerDown(troop, role, felled)` books the removal by what it was, so roster kills plus roster felled equals the roster count, and summon kills plus felled equals the summons queued (leaderboard rules 5 and 17).
- **Checks.** `commander` (key `w<N>`) and `summon` (key `w<N>s<k>`) are written at the clear. The report adds the summon counts, `waves[].commander` and `gold.commander`; the judge replays rules 16 and 17 (`commander_problem`).
- **Left for the first run:** whether native code treats a hero spawned mid-wave as a soldier (risk 1; `[LongDefeat][Commander]` logs his position, formation, behavior and `unique=` every 5 s), whether the summons arrive in time (risk 16, `spawned_at`) and whether the shop bot lives long enough to prove each mechanic (risk 10).

### Poison and the kill owner (Slice 9)

**Fouled Blades.** In a `blades` wave an attacker's hit on a defender poisons him.

- `LongDefeatMissionLogic.OnScoreHit`, which carries the engine's own `isBlocked` and `damagedHp`, forwards a hit only while the director's volatile `WantsHits` is set and only when it has an affector that is not the victim, was not blocked, took some health and left the victim standing (`LongDefeatHitFilter`; a mount's blow is its rider's). `HandleBlow` writes the health and raises the hit before it calls `Die`, so a victim read under 1 health is a killing blow and no dose reaches him.
- The director turns the two agents into registry keys on the calling thread (an attacker is registered at his spawn, a defender at his first hit, and every removal evicts its agent and carries its key), then parks the dose on the main thread through `RunOrDefer`.
- `SurvivalRun` holds Fords' pure `PoisonRules` in an `LdPoisonBook`: one dose per victim, 2 health a second for 6 seconds (`affixes.json`), the hitter owns the dose, and doses are counted apart from hits because `PoisonRules.Totals` counts every apply. A key the registry forgot drops the dose and any later hit naming it. Ticks go out in `RunEffects.PoisonTicks` while an attacker stands, and the wave's end takes the doses with it.
- Poison writes health directly, so the wave damage factor and the `damageTakenPercent` boons, which scale the blows the engine owns, do not reach it.

**Who owns a killing tick.** Fords' recipe is not copied as it is, because it sends owner -1 when the shooter has gone and `Agent.Die` then swaps in a last hitter whose index may belong to another agent. A tick that would kill needs a living owner chosen by `PoisonOwner.Choose`: the poisoner while the registry holds him and he is active, else the commander, else any attacker standing. With none the tick is withheld and the victim keeps 1 health. The victim and the owner are read again at the call, for `IsActive()` and for being the current occupant of their slot (a deleted agent answers `IsActive()` for the slot's next tenant). An owner found not live is counted as `owner_missing` and kills nothing.

**`Fell`.** It no longer leaves a felled straggler's death to `KillAgentCheat`, whose owner is `MainAgent ?? victim` (`Mission.cs:6220-6221`). While the player's body stands it still calls it. Otherwise it builds the same blunt 2000 blow owned by a standing defender (decision D13), so a `--lose` run that fells with the player dead gives `CustomBattleMoraleModel` a real affector; with no defender standing nobody is felled. The soldier is still marked before the kill and brought under 1000 health first, so the blow is lethal at any limit. `LongDefeatBlowOwnerTests` pins both members' source.

**Neither `hammer` nor `terror` kills anything**, so the blow-owner gate has nothing new to allow for them.

**Check and report.** The `blades` verdict of `affix-effect` is written when the wave ends (`power=blades w= doses= hits= damage= owner_missing= withheld=`) and fails above 0 `owner_missing`. It skips when no hit landed (`reason=no-hit`) or no dose took a point of health (`reason=no-damage`). `[LongDefeat][Blades]` tick lines show the first three ticks of a wave and any that killed, were withheld or went to a substitute owner. The report's `poison` object carries the run's totals, and the wrapper also fails any `owner_missing=` token in the log and the report's `poison.ownerMissing`.

## The opening split (Mike, 2026-11-12, #1128)

Mike asked for the defenders to start each wave in four groups: the infantry split between the wall and the gate, and the archers between the lower wall, where the siege towers come, and the high walls. A fortress row turns it on with a `split` block in `fortresses.json`, `{"wallFoot": 0.7, "lowArchers": 0.7}`: the share of the infantry that goes to the wall and the share of the archers that goes to the lower wall, each from 0.05 to 0.95. Helm's Deep ships 70/30 for both (Mike's call). A row with no block plays as before, and a bad block is one warning and no split.

**Why vanilla needs help.** Two unattended runs at Helm's Deep on 2026-11-12 showed that the siege tactic already spreads the archers over three archer positions, but keeps the infantry in one body: the boot line read `formations=0:21,1:50`, and after the tactic ran `0:125,1:27,2:17,3:16`. Before any lane is active, `TacticDefendCastle` defends only the lanes that hold a gate (TacticDefendCastle.cs:1005-1016) and consolidates its melee formations to that lane count, so every soldier on foot goes to the gate.

**How it works.** In each calm (the preparation and every intermission), once the garrison or a pack has finished its muster, `LongDefeatBattlefieldAdapter.SplitDefenders` puts every standing defender on foot, except the player, a mounted soldier and a post archer, into four formations: the wall group (formation 5), the gate group (0), the lower archers (1) and the high archers (3). Each group gets the soldiers nearest its place. The places come from the scene's own siege objects, never from recorded points:

- **Gate:** the first visible gate's middle position.
- **Wall:** the wall segments on the lanes that are not the gate's lane. With two or more, the line spans the two farthest apart (at most 60 m); with one, that segment. A midpoint with no navmesh falls back to the nearest segment.
- **Archers:** the defender archer positions below and at or above the wall line (the wall's height less 3 m), each the one nearest the wall place.

Each group is taken off AI control and ordered with the shapes of vanilla's ready order: a move, a facing and a line of the place's width for the infantry (BehaviorDefendCastleKeyPosition), and a move with Scatter, fire at will and a wide form for the archers (BehaviorShootFromCastleWalls). Vanilla also holds a wait position before contact and forms a shield wall later; the split does neither. Scatter joins every defender archer point within 40 m of the order position on each ground axis, at any height (the `strategic_archer_point` prefab sets `_distanceToCheck` 40 and `_ignoreHeight`). A formation off AI control keeps its units through the tactic's consolidation, though it can gain some. A place with no navmesh, or outside the boundary, is no place. The groups stand until the director hands them back, or until the engine does: the stalemate charge (`OrderCharge`), a new body for the lord (`AdoptMain`) and the fall of the lord's body (`Mission.OnAgentRemoved` calls `Team.DelegateCommandToAI`) each give every formation to the AI. After a new body or the lord's fall, and after a pack musters during a hold, the director splits again on the next tick. A split again keeps every soldier the hold placed in the same group, and the others (a pack's soldiers) fill the group below its share, nearest its place first.

**The release.** The director reads the defense level of each siege lane (`SiegeLane.GetDefenseState`: 0 empty, 1 token, 2 full) at the hold and every tick of the wave. At the first lane that rises above its level at the hold, it hands each group back to the AI and the tactic defends from where they stand. A group whose movement order the player changed stays with the player; a facing, firing or arrangement order alone does not keep it. A split again inside a hold keeps the hold's levels, so a lane that rose before it still counts. A wave that clears with no contact, or a run that ends during a hold, also hands the groups back; the next calm splits afresh.

**The check.** `taom.long-defeat.split` is written at the release, key `w<N>`. It passes when each group holds soldiers and its median ground distance to its place is within 25 m for the infantry and 40 m for the archers. A skip names its reason: `short-hold` (under 20 s), `engine-took` (no group was still off AI control), `charge`, `no-contact`, `run-ended` or `no-groups`. A scene that gives no place for a pair fails with `reason=no-places`; the other pair is still split and held. `tools/run_long_defeat.py` owes one split pass for a fortress row with a `split` block once the log shows a split was made and a wave cleared; a skip does not pay it. The `[LongDefeat][Split]` lines give each group's size and place at each split, and its median and the count on the walls at each wave start.

**Not proven yet.** The design depends on three things only a run can show: whether a lane rises early (a tower pushed to the wall is already Used), whether held Scatter archers climb to the wall points, and whether the wall midpoint has a navmesh. The first in-game run answers all three from its `[Split]` lines. The check judges the ground distance only: the `_high` counts are logged, not judged, so whether a pass should also need the high archers and the wall group on the walls is still Mike's call. The tests are `DefenderSplitTests`, `LongDefeatSplitReaderTests`, `LongDefeatSplitChecksTests`, `LongDefeatDirectorSplitTests` and the split cases of `test_run_long_defeat.py`.

## Decisions for the later phases

Mike decided these on 2026-11-03. The full text is in [the #1079 design comment](https://github.com/haterade22/TAOM/issues/1079#issuecomment-6617849770).

- **No wave retreats.** A wave ends when every attacker is dead.
- **General:** the player leads the defenders, and a bought hero takes over while the player is down.
- **Commanders:** waves 4, 8 and 12 and on bring a captain, a lieutenant, then a general, with abilities on a cooldown. Every faction's waves, commanders and summons use its own troops.
- **Classes:** Sword and Board, Two Handed Infantry, Archer, Cavalry. Each has a start kit from the faction's own gear and its own boon pool. Cavalry is a sally force from a recorded point outside the walls, because a vanilla siege spawns everyone on foot (S9).
- **Boons:** pick 1 of 3 after every 3 cleared waves (Mike moved this from 5 on 2026-11-04). A boon lasts until the run ends. This is an assumption Mike may correct. The design reference is a comparison only, and its provenance row lands with the first commit that builds boons.
- **Affixes:** named powers on the attackers, rolled for each wave: 1 from wave 5, 2 from wave 10, 3 from wave 15.
- **Endless scale:** a wave cannot exceed the battle size, so each wave also raises health and damage, and the troop tiers rise.
- **Leaderboard:** players submit the run report through a Discord command, a bot checks it and updates the board, and a top 10 entry also needs a clip. Mike accepted this on 2026-11-04. The plan is [leaderboard-plan.md](long-defeat/leaderboard-plan.md), and Luiz has the brief for the bot.
- **Phase 4 (planned):** the armoury, the engineer's yard, gear that lasts the run, and the death rule (take over a soldier, rise at the keep at the next clear) are planned in [phase4-plan.md](long-defeat/phase4-plan.md), with open questions OQ8 to OQ20 taken at their recommended answers unless Mike changes them. Slice 1 (config and plan, pure) is built; nothing else is.

A charge can send a formation to a closed inner gate (`BehaviorCharge.cs:25-31`). With the hidden gate broken at `Boot` and repairs limited to visible gates, that needs a `[LongDefeat][Boot] hidden gate ... NOT broken` line, or a scene with a visible inner gate that a repair closes.
- **Muster place (Mike, 2026-11-04):** without a recorded point, the garrison's foot spawn at the scene's foot frame (166.4, 191.2, 26.5), its archers at (208.9, 137.8, 1.5), and bought packs at the reinforcement frames (138.4, 159.5, 32.5) and (141.1, 162.9, 32.5), a terrace where Mike saw them stuck. Helm's Deep now ships points Mike recorded, in the open ground behind the Deeping Wall: foot (186.9, 141.2, 3.7), archers (197.7, 151.6, 1.7). On the scene before the 2026-11-06 rework, the navmesh joined them to the walls with the gate closed, so soldiers reached their posts: `high` read 153 of 168 before the gate broke in run `20261104-135653`, the one run on them, which cleared one wave and was closed by hand. A point with no navmesh writes a failed `muster` check. `fortresses.json` takes an optional `muster` block with a `foot` and an `archers` point, each `x`, `y`, `z`, `fx`, `fy` (the look is normalized; a length outside 0.5 to 1.5 is refused). With no block, or no point for a class, spawning is exactly what it was. With a point, the director calls `SetMusterFrame` for each defender batch of that class right after the batch opens. The adapter checks the point has a navmesh, then calls `Formation.SetPositioning` with it and spawns the batch with `AgentBuildData.SpawnsIntoOwnFormation(true)`, so the engine takes the next free native slot of the formation around the point (`Mission.cs:3950-3953`, `:4243-4247`). It runs for every batch, not only the first, because the formation's order position follows the AI and a later batch would otherwise spawn wherever the AI last sent it. The spawn level read-back (`far`, `off the navmesh`, `on the frame point`) then judges against the recorded point. A point with no navmesh costs one `[LongDefeat][Muster]` warning per class and that class keeps the scene frame. A bad value reverts the whole `muster` block with one warning naming it. Attackers never use it, and the player's lord spawns as before. A player's Advance order with no enemy alive keeps a bought pack's place, so that formation walks to the point until the next wave. Nobody has seen this in game, and restoring the place was left out as a guard for a rare case.
  - **To record:** in a Long Defeat mission, stand on the spot facing the way the line should face and run `taom.ld_record muster_foot`, then the same for `taom.ld_record muster_archers`. Run `taom.ld_export` to write the block next to `long_defeat_records.jsonl` and paste its `muster` object into the fortress's entry in `fortresses.json`. A `[LongDefeat][Muster] batch ...` line with `on_point` and `overlap` shows how the batches landed.
- **Morale hold:** `LongDefeatMorale.HoldsAttacker` keeps attackers from fleeing on low morale. The morale model asks it only below morale 0.01, from agent threads, so each true answer bumps the any-thread counter `taom.long-defeat.morale-hold`; a run that shows the counter above 0 proves the clause fired. A story mission (#1105) hosts the same run in a campaign and bumps the same counter, so in a session that also ran a story mission the counter does not prove a Long Defeat run.
- **End panel in an unattended run:** the driver waits 2 s of wall time after the result (`EndPanelSeconds`) before it leaves, so the panel's 0.25 s refresh opens it and `[LongDefeat][Hud] end panel open` is written.
- **Keys and photo mode:** `B` (shop) and `H` (horn) are free for this mission. The Escape menu offers Photo Mode and no Long Defeat view can close it again, so `LongDefeatHudView.IsPhotoModeAllowed` returns false and the item stays disabled.
- **Speed (1x, 2x, 4x, 10x; key `M`, four buttons in the shop panel, arm key `speed`, launcher `--speed`):** the rule is Fords' pure `FordsGameSpeed` wrapped in `LongDefeatSpeedFrame` (which differs at 10x with a person driving, below), driven by `Main/Adapters/LongDefeatMissionSpeed.cs` (a `[LongDefeat][Speed] speed=N mt=` line on each change). The speed lives in `LongDefeatSession`, not in the run, so a wave or an intermission never changes it, and the next `Fill` (a new run) resets it to 1x. The adapter stops fast forward and the fixed step when the view finalizes. Only fast forward stops at `Mission.MissionEnded` (`Mission.cs:3728`); the fixed step takes one tick more. `LongDefeatSession.Speed` reads 1 once the run has a result, so a fight with no rules does not run at 10x behind the end panel, and `MaxSpeed` keeps its value.
  - **What 10x does** (installed v1.5.6, `MissionState.cs:171-197`): with `IsFastForward` set, `TickMission` computes `num2 = num * 9` and runs `TickMissionAux(0.1f, 0.1f, updateCamera: false, asyncAITick: false)` until `num2` is spent, then `TickMissionAux(num, realDt, updateCamera: true, asyncAITick: false)` once. So `Agent.Tick`, `Team.Tick` and every `OnMissionTick` run on the main thread in steps of at most 0.1 s, nine frames' worth plus the frame itself (`Agent.TickParallel` still goes through `TWParallel.For`), and the camera updates only in the last step with the real frame time. `Mission.cs:3728` clears `IsFastForward` once the mission has ended, and `TakeControlOfAgent` clears it (`Mission.cs:6409`); the adapter sets it again every frame. 2x and 4x set `FixedDeltaTimeMode` to the frame's time times the speed, capped at 0.1 s (`MissionState.cs:155-158`), so one slow frame slows the run.
  - **Player input and camera at 10x:** the camera and the mouse look are tied to the real frame time (`updateCamera` is true only in the last step). The main agent's input handler is `MissionMainAgentController.OnPreMissionTick`, which `Mission.OnPreTick` calls (`Mission.cs:3540`). Native `IMBMission.Tick` (0x5B0410) calls the managed `Mission_OnPreTick` on every call, so under fast forward `ControlTick` runs once per step and reads each frame's key presses once per step: a tap would repeat nine extra times. So 10x with a person driving a live main agent uses a fixed step of `min(realDt * 10, 0.1)` instead of fast forward (`LongDefeatSpeedFrame`, chosen each frame by `LongDefeatMissionSpeed` from `MainAgent.IsActive()` and `IsPlayerControlled`); a dead player and an AI-driven main agent keep engine fast forward. The fixed step reaches a true 10x only at 100 fps or more: at 60 fps it is 0.1 s a frame, about 6x. How a fight feels at 10x is unverified, and nothing here has run in game.
  - **Seconds:** the director adds each `OnMissionTick` dt, so a wave's `seconds` and the live-limit seconds are mission time: 10x does not scale them (a wave takes about the same mission seconds and a tenth of the wall time), only the larger steps change how the fight plays out. The HUD notice timer and the panel refresh use the real frame time. Above 1x the frame mean and max on the `[State]` line are mission dt, not real frames (use `[MissionPerf]` for real frames), and a dt cap of 1/15 s is seen in the logs. The report's `maxSpeed` records the highest speed set in the run, because the sum of the rows' `seconds` can then exceed `endedUtc - startedUtc` ([leaderboard-plan.md](long-defeat/leaderboard-plan.md) rule 13).
  - **The shop panel does not pause or change the speed:** it is a focus layer with no `PauseGameEngine` call, so the speed stays as set while it is open and the wave timer keeps running at that speed. The Escape menu registers an active-state disable request (`MissionGauntletEscapeMenuBase.cs:73-74`), so `GameStateManager.OnTick` calls `OnIdleTick` and `TickMission` does not run; `IsFastForward` stays set meanwhile.
  - **Why `M`:** not `T`. `GauntletChatLogView` is a global layer; its `MissionScreen.TryUpdateChatLogLayerParameters` hands it the scene layer's input (`MissionScreen.cs:3283-3290`), it registers `ChatLogHotKeyCategory` there, and a release of game key 6 (`InputKey.T`, `ChatLogHotKeyCategory.cs:53`) starts the chat box (`GauntletChatLogView.cs:215-218`) and takes the keyboard. `M` is in none of the eight categories that reach the scene layer (`Generic`, `GenericPanelGameKeyCategory`, `GenericCampaignPanelsGameKeyCategory`, `ScoreboardHotKeyCategory`, `CombatHotKeyCategory`, `Cheats`, `MissionOrderHotkeyCategory`, `ChatLogHotKeyCategory`): grep of each category's `InputKey` names in the v1.5.6 decompile, only these files read. TAOM's other `M` is Realm Borders on the campaign map and Fords' own view. Ctrl and Alt leave it to the game. `M` works with a panel open, because `CanUse(M)` returns `IsKeysAllowed` on the focused layer, so the panel host reads it from the panel layer's own input; the four buttons are the other way.
  - **A caution about `H`:** `ScoreboardHotKeyCategory` binds `ToggleHud` to `H` and `ToggleFastForward` to `F`, and `CheatsHotKeyCategory` uses `H` with modifiers. This mission's view list has no scoreboard view, so no reader was found, but the claim above that `H` is free rests on that absence.
- **Terrain after Cancel:** the terrain renders after a Cancel on the shader dialog (screenshots in `E:\Temp\long-defeat-runs\20261104-033424`). The scene has a strong teal cast, which Mike is to judge.
- **Trolls and repaired gates:** `CreatureSiegeRules` latches a gate as destroyed for good, so a troll would treat a repaired gate as open. Clear the track on a repair, or stand the role down in this mission.
- **The Nine:** `DreadMissionGate` admits only Fords by name, so the Nine project no dread here.
- **The buy point:** `DeploymentHandler` is absent, but the adapter disables every defender deployment point at boot (the adapter's disable loop, the job of `SiegeDeploymentHandler.RemoveDeploymentPoints`), so no placeholder should show. Nobody has looked in game.
