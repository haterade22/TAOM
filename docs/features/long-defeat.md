# The Long Defeat

## Overview

A planned campaign-free survival mode on the siege maps: you defend Helm's Deep (Minas Tirith is a later fortress) against wave after wave, and you spend gold between waves. **Phase 1 is on trunk, and no person has played a full run yet.** Unattended runs clear 4 waves. In the newest one, wave 5 had 2 attackers left when Mike closed the game. It is a main menu option ("The Long Defeat", hidden when no fortress loads and on a dedicated server) with Helm's Deep as its one fortress: ten authored waves, then the last wave scaled by count, a purse, a shop between waves, a horn for bonus gold, a keep point (see Notes for Phase 1), and a stalemate rule. `taom.ld_start` and the `TAOM_LONGDEFEAT_AUTORUN` environment variable start the same path without the prompt. The Phase 0 spike (below) proved the engine assumptions on 2026-11-03: an unattended run cleared three waves at Helm's Deep with every spike line present. The plan Phase 1 was built from is [long-defeat/phase1-plan.md](long-defeat/phase1-plan.md). The plan and the phases are in [#1079](https://github.com/haterade22/TAOM/issues/1079).

## Why This Exists

- **Vanilla behavior:** a siege is one battle, with one spawn logic that owns every troop from the start.
- **TAOM requirement:** waves without end, under vanilla's siege AI and engines, with no scripted AI. Fords of War scripts its own AI; a siege should not have to rewrite ladders, towers, rams and wall defence.
- **Without the spike:** Phase 1 would build a mode on engine assumptions that nobody has tested. The first review of the spike already disproved one of them (below).

## Architecture

### What the mission leaves out of vanilla's list

`LongDefeatMissionLauncher.CreateBehaviors` copies vanilla's custom siege list (`BannerlordMissions.OpenSiegeMissionWithDeployment`) and leaves these out: the spawn logic and handler, the reinforcement controller, `BattleEndLogic`, the two deployment behaviors, `BattlePowerCalculationLogic`, `GeneralsAndCaptainsAssignmentLogic`, and the observer, agent, banner, victory and highlight logics. The director spawns every agent from the mission tick.

Two engine paths read what is left out. [The lifecycle doc](../reference/engine/mission-and-missionbehavior-lifecycle.md) has the mechanism and the line numbers.

| Engine path | What the mission does |
|---|---|
| `TeamQuerySystem` reads `IBattlePowerCalculationLogic` with no null check | `LongDefeatMissionLogic` implements it and returns a large constant |
| `GeneralsAndCaptainsAssignmentLogic` asks a model that reads the spawn logic | It stays out. `AssignPlayerRoleInTeamMissionController` sets the order owner, and the director makes the player the general: the `general` check reads both |

### How a soldier gets a place

Soldiers spawn with no position, and the deployment plan gives each formation its place. `Boot` gives `DefaultMissionDeploymentPlan` the troop counts and calls `MakeDefaultDeploymentPlans`. The garrison and each wave then call `Formation.BeginSpawn` and `Mission.SetFormationPositioningFromDeploymentPlan`, and each soldier asks `GetAgentBuildDataToSpawnTroop` with no position. A later batch or a bought pack skips the placing (`SetFormationPositioningFromDeploymentPlan`) but still calls `Formation.BeginSpawn` (`LongDefeatDirector.SpawnBatch`, `LongDefeatBattlefieldAdapter.BeginBatch`), which vanilla does not do for a formation that already has a place (`MissionBattleSideSpawnContext.cs:369`). Two parts are not vanilla's path: each wave places its formations again, and a wave's batch stays open across several ticks. Vanilla's reader of `IsSpawning` is in the class this mission leaves out (`:403`).

**What keeps a soldier on the right floor:**

- The layout offers only slots that native `BatchFormationUnitPositions` accepts, spreading out from the frame (`Formation.cs:669-671`, `LineFormation.cs:495-497`). A slot needs a navmesh face, in a siege the frame's face group digit, and a height near its neighbours. That list comes from the native pseudo-C.
- A slot with no navmesh goes back toward the frame (`Mission.cs:3983-3985`).
- When the slots run out, every remaining soldier stands on the frame point (`Mission.cs:3992-3995`).
- `IMBAgent.SetInitialFrame` then takes the height. It casts a ray down from 1.5 m above the given height, falls back to the terrain height, and uses 0 if every try misses. The fixed path still goes through this step, but its input is now an accepted slot.

**Never compute a place by hand on a scene with floors.** The first version laid its own grid around the frame, in the manner of Fords of War's spawn block. On the first run at Helm's Deep, 64 of the 101 defenders stood below the wall line, with a median height of 0.0 against a frame at 26.5, and 3 died from the fall. Whether 0.0 came from a collider, from the terrain or from a miss was not traced.

**The read-back:** the spike's `[S1] spawn level` printed each class with its frame, `far`, `off the navmesh`, `on the frame point` and a `z` spread. Phase 1 writes `[LongDefeat] spawn level ok: <side> <class> N of M, far F, off the navmesh O, on the frame point P` when a batch closes, summed across the ticks it spans, for defenders and attackers alike. It says `ok` when every soldier is within 10 m of the height of that class's recorded point, or the scene's frame, and on a navmesh, and `WRONG` otherwise. The unattended judge needs an `ok` line for each side and fails on `spawn level WRONG`. **`ok` does not mean on the walls.** The tolerance cannot separate a terrace at 26.5 from a gate at 20.5.

**The pile:** the Helm's Deep terrace runs out of slots, so the engine stands the rest of the foot on one point: 41 of 68 in a garrison of 100, 64 of 115 in a garrison of 170 (the slots grow with the batch's planned shape, from 27 to 51). The spike's `[S1] spawn pile` line named this when more than 6 of a class stood within 1 m of the frame point (a shield wall at spacing 0 can put 5 healthy soldiers there). A pile failed nothing, and they spread out by themselves: by t 30 s all 101 stood high. It looks wrong to a person, so Phase 1 musters in timed batches (`[LongDefeat][Muster] batch`), each judged by the `muster` check. **`ok` for that check means that no more than half the batch stands on the frame point, or no more than 6 if that is the larger number**, with no soldier far or off the navmesh and at most 6 overlapping an earlier batch. A timed-batch garrison harmed nothing in run `20261104-033424`: `high` read 183 of 185 at about t 50 to 55, and 185 of 185 at t 60. Reinforcements can pile on their own frame too (the spike read 24 of 24 in wave 2 and 2 of 16 in wave 3), because a reinforcing batch keeps the live formation's shape.

**A healthy Helm's Deep:** the defender archers' frame stands at height 1.5, so the spike's `[S1] after initial spawn` read `high` of 68 of 101, with a `z` minimum near 1.3. That is the scene's frame and not the fault repeating. The spike's `[S1] frames` line printed all six frames; Phase 1 has no such line.

### How a wave ends

No wave retreats, so a wave ends when no attacker stands, and that does not happen by itself. Only `BattleEndLogic` ends a vanilla siege, the player's exit aside: on a depleted side, or a side wholly running away (`BattleEndLogic.cs:198-222, 279-361`). Kills, a morale rout, the power retreat and the sally lead there. This mode leaves that logic out. On the first unattended run the last 7 attackers, then 6, and the last 31 defenders stood apart from t 420 s to the limit at t 1,500 s.

**The hidden gate at Helm's Deep:** the scene holds a hidden inner gate at height 32.5 (`aserai_castle_gate_inner_l1 visible="false"`, `scene.xscene:5971`). The engine takes it as `InnerGate` with no visibility check (`TeamAISiegeComponent.cs:54-57`), and a hidden gate never ticks, so it never opens (`CastleGate.cs:619-622`). The Middle lane then stays closed (`SiegeLane.cs:355-364`), and attackers on the gate lane go to that gate and stay in `AttackEntity` (`BehaviorAssaultWalls.cs:161-166`). In all three runs the first attacker at height 32 or more appeared 20 s after the outer gate fell. Defenders hold their lane place on plain Move orders, and they hunt only with over 30 attackers inside (`TacticDefendCastle.cs:975`). Constant team power turns off the retreat and the sally, which are the other ways out. So `Boot` breaks any hidden gate and logs `[LongDefeat][Boot] hidden gate at (...): broken` (or `NOT broken`), then `hidden gates broken N`. It is not removed, because a null `InnerGate` throws in `BehaviorAssaultWalls`. **A campaign siege on this scene meets the same hidden gate**, and nobody has checked what it does there. **Breaking it works** (spike run `20261103-235325`, build `985b0d54e`, defaults): `[S1] hidden gate at (133.4, 180.7, 32.5): broken`, and `Middle open True` once the outer gate falls. Waves 1 and 2 of 110 cleared at 349 s and 669 s with no `stale` line, against 465 s and 840 s before. Wave 3 went quiet with 44 attackers left, and the charge ended it at 1,254 s, with no soldier felled by rule.

`WatchStalemate` was the spike's rule for every other stand-off. Phase 1 carries it as `Domain/StalemateRule.cs`, with its thresholds in `waves.json` and its lines tagged `[LongDefeat][Wave]`.

**The last few defenders lose the run (Mike, 2026-11-04).** When the rule below reaches no result, and `stragglerCount` (5) or fewer defenders stand, fewer than the attackers, the run ends as `DefendersDead`, with the panel's "The garrison has fallen". Any larger stand-off stays a stalemate. The first `--speed 10` run needed this: it ended on 89 attackers against 1 defender they did not reach. This loss skips the `stale` check, because the run did end, so the `[Check]` line and the `[End]` line name who stood. `reason=lost_defenders` alone no longer proves that no defender stood. Nobody has played what a living person sees here: Escape can dismiss the end panel, as on the other ends.

**The last few fall first (Mike, 2026-11-04).** When `stragglerCount` (5) or fewer attackers stand, fewer than the defenders, they fall after `stragglerSeconds` (60 s) with no charge, so the defenders stay on the walls. A death on either side does not restart that clock. Before this, 8 of the 15 cleared waves in four runs waited 110 s or more on their last 1 or 2 attackers, and Mike closed a run at the end of wave 5 because 2 attackers stood far outside the walls, near (274, 266) and (288, 257), and nothing moved. Nobody has traced why such a soldier stays out. A felled soldier pays no bounty. Larger stand-offs take the longer path:

1. With half the wave down and no loss on either side for 60 s, or no loss for 180 s at any count, `[LongDefeat][Wave] N stale: both teams charge` is written (the spike's `[S2] wave N stale` also printed the attackers' places and each formation's behavior, which Phase 1 does not), and both teams change to vanilla's `TacticCharge`. That tactic only weights `BehaviorCharge`, which returns 0 until the walls test passes (`BehaviorCharge.cs:169-201`), so it moves soldiers on some lanes and not on others, and a formation under a player's orders does not move at all.
2. After 90 s more with no loss, `[LongDefeat][Wave] N stragglers fall: ...` is written and they fall (`Mission.KillAgentCheat`; the spike printed their places under `[S2] wave N: nobody reached the last M attackers`). One soldier can stand for good: in wave 2 of the passing run the last attacker never left the spawn area, at (260.2, 305.9, -0.8). Only stragglers fall: at most a tenth of the wave, and fewer than the defenders. Otherwise no wave clears, because a clear must be earned: at Minas Tirith the first form of this rule felled 35 attackers with 2 defenders left. That end is now a loss, and only a larger stand-off is a `stalemate`. The judge's result counts the waves that ended by this rule.
3. At the wave's clear, the defenders get a new `TacticDefendCastle`, and they start the next wave out of place: `high` read 46 at the start of wave 3, and 163 of 170 about 15 s later. The next wave's new `TacticBreachWalls` comes when its first batch is out (`RefreshAttackerTactic` in `Domain/SurvivalRun.cs`), so the attackers stay on `TacticCharge` until then.

The rule fired in waves 2 and 3 of the passing run. A wave of 110 lost its last soldier at about 840 s and 1,380 s of mission time, 90 s and 128 s after the `stale` line. Soldiers can still flee on low morale, and Phase 1 closes that. The state lines of the four runs count none, and one `OnAgentPanicked` warning fired at Minas Tirith.

### The terrain shader dialog at Helm's Deep

A Helm's Deep load can stop at a native dialog: `Error compiling shader file: $BASE/Shaders/Sources/pbr_terrain.rs` (and `pbr_terrain_gbuffer.rs`), X4008 at `terrain_pixel_functions.rsh:818`, raised to an error by X3129. **Press Cancel.** The mission then loads in seconds. Retry compiles the same source (native `FUN_1800934e0` returns to `D3DCompileFromFile`), and Cancel returns a null blob. Two native flags skip the dialog, and nobody has read what sets them. The dialog holds the game, and nobody is there in an unattended run, so `tools/run_long_defeat.py` presses Cancel by itself and logs that in `runner_log.txt`. Left open for 304 s, the dialog makes `BattleLoadStallWatchdog` write a `[CrashReport]` block, which fails the judge.

Open: Mike's by-hand launches at 17:26 and 17:28 loaded in under 10 s and show no sign of this dialog, and all three unattended launches at this fortress met it. The runner's `shader cache list differs` does not explain that, because it is on all four runs, and Minas Tirith had no dialog. Phase 1 stands in for the cached-variant or guarded-copy ask with one sentence in the setup prompt ("If a shader error window appears while the fortress loads, press Cancel"), which replaces that ask only on Mike's word, and does not touch `Shaders/`, which belongs to the install. **Decision for Mike, open:** build a scene shader sack for Helm's Deep in the Kit. It would live in the unversioned `TAOM_Map`, so a reinstall reverts it, and the same dialog already threatens a Custom Battle siege at this scene.

### Decisions from the spike

The first two still hold in Phase 1. The other three describe the spike's runner, which went with the spike: Phase 1 has no refill and no in-mission tests.

- **Power never orders a retreat.** The constant keeps both power ratios near 1, so `TacticBreachWalls` never takes its one-way retreat on power, and `TacticDefendCastle` never sallies on it. No wave retreats in this mode (Mike, 2026-11-03). The constant closes only the team retreat: a soldier can still flee on low morale, so Phase 1 adds attackers to `TaomCustomBattleMoraleModel.CanPanicDueToMorale`, and its state lines count anyone who flees. `FellFoesAdapter.SendOff` calls `Retreat` directly, and the `no-rout` check fails if a soldier it sends off is counted.
- **Waves are larger than 100.** At 100 attackers or fewer, `TacticBreachWalls` stops using its machines. The spike's by-hand default was a wave of 120 and a garrison of 100, and its unattended default was 110 and 170, because 100 defenders held on one run and all died on the other, with about 45 attackers left. Phase 1's balance is under "The first balance" below.
- **Each wave got a new tactic.** The first spawn batch latches a shock assault and clears `ForcedUse` on the engines. The runner set `ForcedUse` back and added a new `TacticBreachWalls` when the wave's queue emptied.
- **The garrison refilled between waves,** so a later wave's evidence did not depend on the first wave's losses.
- **All in-mission tests ran after wave 1:** S5, S7, then S4. Every later wave then met the repaired gate.

**The rest rule:** nothing heals a surviving soldier in a mission, so I suspected that wounds caused the growing losses. **Wounds are not the main cause.** Run `20261104-071020` (clean build `34541922c`, on engine changeset 125270) measured it: survivors' mean health was already 84% to 91% before each rest, and 92% to 95% after. The same table lost 18, 77, 151, 98 in the run before, so one run cannot separate the rule from chance. Why losses swing this much between runs, and why attackers climb in numbers in some waves and not others, is still open. The rule costs little and stays for now, and Mike can set `restShare` to 0.

The towers stay at the wall after wave 1, and Phase 1 has no gate repair, so from wave 2 attackers reached high ground 55 to 70 s after the wave began, against about 150 s in wave 1. A wave took 5.5 to 11 minutes, and five waves took at most 2,427 live seconds, under the wrapper's 3,600 s live limit.

## Configuration

No MCM. Three JSON files under `Main/_Module/ModuleData/long_defeat/` hold the content, and each bad value costs one logged warning and falls back to its default: `fortresses.json` (scene, cultures, garrison, keep point), `waves.json` (the `rules` numbers, bounties, wave rosters) and `shop.json` (offers and starting gold). The files are read once per game process, so an edit needs a full game restart, not a new run. An unattended run takes an arm file of `key=value` lines named by `TAOM_LONGDEFEAT_AUTORUN`: `fortress`, `waves`, `out` (required, absolute), `quit`, `live_limit_seconds`, `wall_limit_seconds`, `screenshots`, `garrison_scale`, `expect`, `speed` (1, 2, 4 or 10). Player-facing text is the `TAOM_LD_*` rows of `taom_module_strings.xml`; the 12 language files carry the English seed until #763.

**The run report** (`long_defeat_report_*.json`, beside the log) also carries what a leaderboard checks: `schema`, `build`, `balance` (a hash of the six JSON files with line endings normalized), `cheatMode`, `mods` (ids with versions), `autoplay`, `garrisonScale`, `targetWaves`, `maxSpeed` (the highest mission speed set in the run), `startedUtc` and `endedUtc`. It holds no player name. The board itself is not built: [leaderboard-plan.md](long-defeat/leaderboard-plan.md), #1080.

**Phase 2, Slice 1 (foundations, [phase2-plan.md](long-defeat/phase2-plan.md)):** the report is schema 2. Schema 1's fields keep their names and meaning, and it adds `seed`, `class`, `startWave`, `startRerolls`, `boons`, `rerolls`, `poison`, per wave `affixes`, `healthFactor`, `damageFactor`, the summon counts and `commander`, and `gold.commander` and `gold.boon`. Only `seed`, `startWave` and `startRerolls` carry values yet; the others sit at their empty value until the slice that fills them. `balance` now hashes six files, the three above plus `affixes.json`, `boons.json` and `classes.json` (a missing file joins as empty text), so the hash differs from any Phase 1 build's. `RunRandom` is the SplitMix64 every later roll draws from, with its vectors pinned in `RunRandomTests` and in `test_run_long_defeat.py`. `RunOptions` gains `Seed` (the start time's ticks when none is armed, taken in `BuildPlan`), `StartWave` and `StartRerolls`. The arm file gains `seed` (0 to 2^53-1, a negative or larger value refused: the cap keeps every digit for a JavaScript reader of the report, and a clock seed is masked into it), `start_wave` (1 to 100: the run begins at that wave number, while `waves` still counts clears), `start_rerolls` (0 to 3) and `class` (read and echoed, with no effect before the class slice). The wrapper gains `--seed`, `--start-wave`, `--start-rerolls` (armed as 1 unless given), `--class` (`all` gives each run the next class) and `--deep` (`--start-wave 12 --waves 4`, judged by its own list and allowed to end lost). Its judge refuses a report that is not schema 2 or that does not echo the armed seed, start wave and rerolls, and fails on any `owner_missing` above 0. `LongDefeatBlowOwnerTests` fails when anything outside `ApplyPoison` and `Fell` kills an agent, or when a blow takes owner -1. It does not make `Fell` safe yet: `KillAgentCheat` still uses `MainAgent ?? victim` as the owner, and Slice 9 gives `Fell` a standing defender and pins that. Nothing here is played in game yet: the check is `--start-wave 3 --waves 1`, with the report reading schema 2, the seed and start wave 3.

**Phase 2, Slice 2 (the endless scale):** a wave past the authored list takes a health factor and a damage factor, each `min(maxFactor, 1 + perWave * extra)` with `extra` the waves past the list (shipped: 5% and 3% a wave, capped at 3), and every `tierEveryWaves` (3) extra waves each row of its mix moves one link along the roster's `tiers` chain. Rows that land on one troop merge their weights, a chain stops at its end, and the count line is unchanged. Helm's Deep's chain runs fighter and militia spearman to warrior to spearman to veteran spearman to veteran pikeman, swordman to infantry to veteran infantry, and skirmisher to arbalest to crossbowman to veteran crossbowman. Only the last authored wave's mix is stepped (spearman, infantry, berserker, crossbowman), so just four links can fire with the shipped waves (spearman, infantry, crossbowman and, at two steps, veteran spearman); the links from militia spearman, fighter, warrior, swordman, skirmisher and arbalest are parsed and checked but no wave reaches them; `bounties` gains the four veteran troops (15, 20, 20, 20). `waves.json` takes `healthPerWave`, `damagePerWave`, `maxFactor` (1 to 10) and `tierEveryWaves` (1 to 50) in a roster's `scaling` and a `tiers` block beside it. A bad number keeps its default with one warning. A tier link that is not a troop id, points at its own troop, joins two classes the roster's waves show or closes a cycle is skipped, and a target with no bounty pays 0 with one warning. The health factor is written after each attacker spawns (`BaseHealthLimit`, `HealthLimit` and `Health`, in `LongDefeatBattlefieldAdapter.SpawnBatch`, from `SoldierBatch.HealthFactor`). The damage factor is published by the new `LongDefeatEffectsAdapter` with the effect that starts the wave, before any soldier of it spawns, and `LongDefeatCombatHooks.Amplify` applies it to attackers' blows from `TaomCustomBattleDamageModel.ApplyDamageAmplifications`; the hook is inert unless the Long Defeat mission is armed, so Fords of War and every other Custom Battle pass through, and a fall is not a blow (the engine names the faller as its own attacker), so a scaled attacker's fall damage is untouched. The model also runs for a soldier's blow on the gate, a wall section or a shield, which take the factor too; the ram damages the gate directly and does not. Whether that is wanted is open (phase2-plan.md, Slice 13). Defenders are never scaled yet. The launcher's troop check now reads `RunPlanTroops.AllTroopIds`, so a missing tier target refuses the launch instead of spawning nothing. The report's `waves[].healthFactor` and `damageFactor` carry the values (1 inside the authored list). `[Check] id=taom.long-defeat.scale` (manifest row `taom.long-defeat.scale`, key `w=<N>`) is written once per scaled wave, at its clear or at the run's end inside it: a sampled attacker's health limit over its character maximum must equal the health factor within 1% at spawn and again late in the wave, its troop must be one of the wave's stepped mix, a damage factor above 1 must have raised at least one blow, and the engine's standing count must never exceed the room the previous tick spawned into. The sample is a standing attacker that is not running away, so a runner left from the wave before is never read. The wrapper's judge requires that line from any report with a wave row whose health or damage factor is above 1. The numbers are first guesses (assumptions A9 and A15 of the plan). Not played yet: the check is `python tools/run_long_defeat.py --start-wave 12 --waves 2`, with `scale` passing from a roster sample; wave 13 is the first to step a troop, since the steps are `extra / 3`, so a run that ends at wave 11 or 12 proves the factors only.

## How to verify in game

**Preconditions:** a build that holds Phase 1, and the main menu with no game loaded.

1. Click "The Long Defeat", read the prompt (it names the best run and the shader sentence) and pick Helm's Deep. Or, with cheat mode on, enter `taom.ld_start helms`; the reply starts with `Starting The Long Defeat at helms`. If a shader error window appears while the fortress loads, press Cancel.
2. In the newest `taom_debug_*.log`, `[Check] id=taom.long-defeat.boot` must say `result=pass` with `friendly=false`, and `general` must pass. Any `spawn level WRONG` line is a failure.
3. Watch the garrison muster in batches (`[LongDefeat][Muster]` lines, then `[Check] id=taom.long-defeat.muster`). The HUD strip shows the wave, the timer, gold and both head counts. `B` opens the shop, `H` sounds the horn for bonus gold, and the order bar moves formations. Tab does nothing. `M` steps the speed (1x, 2x, 4x, 10x, then 1x), and the strip's last item shows it.
4. Each cleared wave writes `[Check] id=taom.long-defeat.wave`. The run ends by a result panel with its Leave button, which returns to the main menu, and writes `end` and `best-run` lines.
5. Speed (not yet played): press `M` three times. The strip reads `Speed: 2x`, `4x`, `10x`, and each press writes `[LongDefeat][Speed] speed=N mt=...`. At 10x the soldiers should move about ten times faster while the camera and the mouse look still follow your frame. Between waves open the shop with `B`: the Game speed row has four buttons, the current one lit, and a click sets that speed (press `M` with the shop open too). Start a wave and check the speed holds. Close the mission and start a new run: it begins at 1x. The report's `maxSpeed` is the highest speed you used.
6. The fixed step at 10x (not yet played): with a live player at 10x, press use on a siege engine, crouch, switch weapons and tap a movement key once each. Every tap must act once: one mount of the engine, one crouch toggle, one weapon switch, one step. Engine fast forward would repeat each. Then die at 10x: the strip stays at 10x and the game runs in fast forward until the respawn.

**Unattended:** `python tools/run_long_defeat.py --waves 5`, under the gate in [unattended-game-runs.md](../reference/unattended-game-runs.md); `--lose` runs the loss case, `--runs 3` repeats it and `--speed 10` plays at ten times the speed from the first frame (the report names it as `maxSpeed`, the wrapper fails the run unless that equals the flag, and the log's `[LongDefeat][Speed]` lines record it). The shop bot and an AI-driven main agent play. Exit 0 needs the done reason, the report, no `spawn level WRONG`, no failed check of this feature, a `[BuildStamp]` that starts with this tree's HEAD, a pass line for every required check, a read-back line for each side, as many `wave` pass lines as waves cleared, and no crash block. The Phase 0 recipes were run with `tools/run_long_defeat_spike.py`, which is gone: read it from commit 985b0d54e.

An unreachable step is reported with the command tried and the unmet precondition. Never mark it verified through another path.

## Decisions for the later phases

Mike decided these on 2026-11-03. The full text is in [the #1079 design comment](https://github.com/haterade22/TAOM/issues/1079#issuecomment-6617849770).

- **No wave retreats.** A wave ends when every attacker is dead.
- **General:** the player leads the defenders, and a bought hero takes over while the player is down.
- **Commanders:** waves 4, 8 and 12 and on bring a captain, a lieutenant, then a general, with abilities on a cooldown. Every faction's waves, commanders and summons use its own troops.
- **Classes:** Sword and Board, Two Handed Infantry, Archer, Cavalry. Each has a start kit from the faction's own gear and its own boon pool. Cavalry is a sally force from a recorded point outside the walls, because a vanilla siege spawns everyone on foot (S9).
- **Boons:** pick 1 of 3 after every 3 cleared waves (Mike moved this from 5 on 2026-11-04). A boon lasts until the run ends. This is an assumption Mike may correct. The design reference is a comparison only, and its provenance row lands with the first commit that builds boons.
- **Affixes:** named powers on the attackers, rolled for each wave: 1 from wave 5, 2 from wave 10, 3 from wave 15.
- **Endless scale:** a wave cannot exceed the battle size, so each wave also raises health and damage, and the troop tiers rise.
- **Leaderboard:** players submit the run report through a Discord command, a bot checks it and updates the board, and a top 10 entry also needs a clip. Mike accepted this on 2026-11-04. The plan is [leaderboard-plan.md](long-defeat/leaderboard-plan.md), and Luiz has the brief for the bot.

- **The stalemate rule:** Phase 1 carried `WatchStalemate` into the domain, with its thresholds in JSON. `KillAgentCheat` credits the kill to the main agent, or with none to the victim's last hitter (`Mission.cs:6220`, `Agent.cs:4689-4693`). Phase 1 keeps `KillAgentCheat` (the adapter calls it); `Agent.Die` (`Agent.cs:4678`), which credits no main agent, is the spike's suggestion and was not taken. With the hidden gate broken at `Boot` and repairs limited to visible gates, that needs a `[LongDefeat][Boot] hidden gate ... NOT broken` line, or a scene with a visible inner gate that a repair closes.
- **Muster place (Mike, 2026-11-04):** without a recorded point, the garrison's foot spawn at the scene's foot frame (166.4, 191.2, 26.5), its archers at (208.9, 137.8, 1.5), and bought packs at the reinforcement frames (138.4, 159.5, 32.5) and (141.1, 162.9, 32.5), a terrace where Mike saw them stuck. Helm's Deep now ships points Mike recorded, in the open ground behind the Deeping Wall: foot (186.9, 141.2, 3.7), archers (197.7, 151.6, 1.7). The navmesh joins them to the walls with the gate closed, so soldiers reach their posts: `high` read 153 of 168 before the gate broke in run `20261104-135653`, the one run on them, which cleared one wave and was closed by hand. A point with no navmesh writes a failed `muster` check. `fortresses.json` takes an optional `muster` block with a `foot` and an `archers` point, each `x`, `y`, `z`, `fx`, `fy` (the look is normalized; a length outside 0.5 to 1.5 is refused). With no block, or no point for a class, spawning is exactly what it was. With a point, the director calls `SetMusterFrame` for each defender batch of that class right after the batch opens. The adapter checks the point has a navmesh, then calls `Formation.SetPositioning` with it and spawns the batch with `AgentBuildData.SpawnsIntoOwnFormation(true)`, so the engine takes the next free native slot of the formation around the point (`Mission.cs:3950-3953`, `:4243-4247`). It runs for every batch, not only the first, because the formation's order position follows the AI and a later batch would otherwise spawn wherever the AI last sent it. The spawn level read-back (`far`, `off the navmesh`, `on the frame point`) then judges against the recorded point. A point with no navmesh costs one `[LongDefeat][Muster]` warning per class and that class keeps the scene frame. A bad value reverts the whole `muster` block with one warning naming it. Attackers never use it, and the player's lord spawns as before. A player's Advance order with no enemy alive keeps a bought pack's place, so that formation walks to the point until the next wave. Nobody has seen this in game, and restoring the place was left out as a guard for a rare case.
  - **To record:** in a Long Defeat mission, stand on the spot facing the way the line should face and run `taom.ld_record muster_foot`, then the same for `taom.ld_record muster_archers`. Run `taom.ld_export` to write the block next to `long_defeat_records.jsonl` and paste its `muster` object into the fortress's entry in `fortresses.json`. A `[LongDefeat][Muster] batch ...` line with `on_point` and `overlap` shows how the batches landed.
- **Morale hold:** `LongDefeatMorale.HoldsAttacker` keeps attackers from fleeing on low morale. The morale model asks it only below morale 0.01, from agent threads, so each true answer bumps the any-thread counter `taom.long-defeat.morale-hold`; a run that shows the counter above 0 proves the clause fired.
- **End panel in an unattended run:** the driver waits 2 s of wall time after the result (`EndPanelSeconds`) before it leaves, so the panel's 0.25 s refresh opens it and `[LongDefeat][Hud] end panel open` is written.
- **Keys and photo mode:** `B` (shop) and `H` (horn) are free for this mission. The Escape menu offers Photo Mode and no Long Defeat view can close it again, so `LongDefeatHudView.IsPhotoModeAllowed` returns false and the item stays disabled.
- **Speed (1x, 2x, 4x, 10x; key `M`, four buttons in the shop panel, arm key `speed`, launcher `--speed`):** the rule is Fords' pure `FordsGameSpeed` wrapped in `LongDefeatSpeedFrame` (which differs at 10x with a person driving, below), driven by `Main/Adapters/LongDefeatMissionSpeed.cs` (a `[LongDefeat][Speed] speed=N mt=` line on each change). The speed lives in `LongDefeatSession`, not in the run, so a wave or an intermission never changes it, and the next `Fill` (a new run) resets it to 1x. The adapter stops fast forward and the fixed step when the view finalizes. Only fast forward stops at `Mission.MissionEnded` (`Mission.cs:3728`); the fixed step takes one tick more. `LongDefeatSession.Speed` reads 1 once the run has a result, so a fight with no rules does not run at 10x behind the end panel, and `MaxSpeed` keeps its value.
  - **What 10x does** (installed v1.5.6, `MissionState.cs:171-197`): with `IsFastForward` set, `TickMission` computes `num2 = num * 9` and runs `TickMissionAux(0.1f, 0.1f, updateCamera: false, asyncAITick: false)` until `num2` is spent, then `TickMissionAux(num, realDt, updateCamera: true, asyncAITick: false)` once. So `Agent.Tick`, `Team.Tick` and every `OnMissionTick` run on the main thread in steps of at most 0.1 s, nine frames' worth plus the frame itself (`Agent.TickParallel` still goes through `TWParallel.For`), and the camera updates only in the last step with the real frame time. `Mission.cs:3728` clears `IsFastForward` once the mission has ended, and `TakeControlOfAgent` clears it (`Mission.cs:6409`); the adapter sets it again every frame. 2x and 4x set `FixedDeltaTimeMode` to the frame's time times the speed, capped at 0.1 s (`MissionState.cs:155-158`), so one slow frame slows the run.
  - **Player input and camera at 10x:** the camera and the mouse look are tied to the real frame time (`updateCamera` is true only in the last step). The main agent's input handler is `MissionMainAgentController.OnPreMissionTick`, which `Mission.OnPreTick` calls (`Mission.cs:3540`). Native `IMBMission.Tick` (0x5B0410) calls the managed `Mission_OnPreTick` on every call, so under fast forward `ControlTick` runs once per step and reads each frame's key presses once per step: a tap would repeat nine extra times. So 10x with a person driving a live main agent uses a fixed step of `min(realDt * 10, 0.1)` instead of fast forward (`LongDefeatSpeedFrame`, chosen each frame by `LongDefeatMissionSpeed` from `MainAgent.IsActive()` and `IsPlayerControlled`); a dead player and an AI-driven main agent keep engine fast forward. The fixed step reaches a true 10x only at 100 fps or more: at 60 fps it is 0.1 s a frame, about 6x. How a fight feels at 10x is unverified, and nothing here has run in game.
  - **Seconds:** the director adds each `OnMissionTick` dt, so a wave's `seconds` and the live-limit seconds are mission time: 10x does not scale them (a wave takes about the same mission seconds and a tenth of the wall time), only the larger steps change how the fight plays out. The HUD notice timer and the panel refresh use the real frame time. Above 1x the frame mean and max on the `[State]` line are mission dt, not real frames (use `[MissionPerf]` for real frames), and a dt cap of 1/15 s is seen in the logs. The report's `maxSpeed` records the highest speed set in the run, because the sum of the rows' `seconds` can then exceed `endedUtc - startedUtc` ([leaderboard-plan.md](long-defeat/leaderboard-plan.md) rule 13).
  - **The shop panel does not pause or change the speed:** it is a focus layer with no `PauseGameEngine` call, so the speed stays as set while it is open and the wave timer keeps running at that speed. The Escape menu registers an active-state disable request (`MissionGauntletEscapeMenuBase.cs:73-74`), so `GameStateManager.OnTick` calls `OnIdleTick` and `TickMission` does not run; `IsFastForward` stays set meanwhile.
  - **Why `M`:** not `T`. `GauntletChatLogView` is a global layer; its `MissionScreen.TryUpdateChatLogLayerParameters` hands it the scene layer's input (`MissionScreen.cs:3283-3290`), it registers `ChatLogHotKeyCategory` there, and a release of game key 6 (`InputKey.T`, `ChatLogHotKeyCategory.cs:53`) starts the chat box (`GauntletChatLogView.cs:215-218`) and takes the keyboard. `M` is in none of the eight categories that reach the scene layer (`Generic`, `GenericPanelGameKeyCategory`, `GenericCampaignPanelsGameKeyCategory`, `ScoreboardHotKeyCategory`, `CombatHotKeyCategory`, `Cheats`, `MissionOrderHotkeyCategory`, `ChatLogHotKeyCategory`): grep of each category's `InputKey` names in the v1.5.6 decompile, only these files read. TAOM's other `M` is Realm Borders on the campaign map and Fords' own view. Ctrl and Alt leave it to the game. `M` works with a panel open, because `CanUse(M)` returns `IsKeysAllowed` on the focused layer, so the panel host reads it from the panel layer's own input; the four buttons are the other way.
  - **A caution about `H`:** `ScoreboardHotKeyCategory` binds `ToggleHud` to `H` and `ToggleFastForward` to `F`, and `CheatsHotKeyCategory` uses `H` with modifiers. This mission's view list has no scoreboard view, so no reader was found, but the claim above that `H` is free rests on that absence.
- **Terrain after Cancel:** the terrain renders after a Cancel on the shader dialog (screenshots in `E:\Temp\long-defeat-runs\20261104-033424`). The scene has a strong teal cast, which Mike is to judge.
- **Trolls and repaired gates:** `CreatureSiegeRules` latches a gate as destroyed for good, so a troll would treat a repaired gate as open. Clear the track on a repair, or stand the role down in this mission.
- **The Nine:** `DreadMissionGate` admits only Fords by name, so the Nine project no dread here.
- **The buy point:** `DeploymentHandler` is absent, but the adapter disables every defender deployment point at boot (the adapter's disable loop, the job of `SiegeDeploymentHandler.RemoveDeploymentPoints`), so no placeholder should show. Nobody has looked in game.
