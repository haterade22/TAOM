# The Long Defeat

## Overview

A planned campaign-free survival mode on the siege maps: you defend Helm's Deep or Minas Tirith against wave after wave, and you spend gold between waves. **Phase 1 is on trunk, and no person has played a full run yet.** Unattended runs clear 4 waves. In the newest one, wave 5 had 2 attackers left when Mike closed the game. It is a main menu option ("The Long Defeat", hidden when no fortress loads and on a dedicated server) with two fortresses, Helm's Deep and Minas Tirith (built as data, not yet played). Each has ten authored waves, then the last wave scaled by count, a purse, a shop between waves, a horn for bonus gold, a keep point (see Notes for Phase 1), and a stalemate rule. `taom.ld_start` and the `TAOM_LONGDEFEAT_AUTORUN` environment variable start the same path without the prompt. The Phase 0 spike (below) proved the engine assumptions on 2026-11-03: an unattended run cleared three waves at Helm's Deep with every spike line present. The plan Phase 1 was built from is [long-defeat/phase1-plan.md](long-defeat/phase1-plan.md). Phase 2 adds the seeded roguelite layer (endless scale, affixes, boons, classes, commanders, the Cavalry sally); it is on trunk, and unattended runs proved most of it in game on 2026-11-05 (see "Phase 2" and "How to verify in game"). Phase 3 adds the fortifications the lord buys between waves (the gate, field care, the Elven Volley, the high towers' archers and volley); its Slices 1 to 8 are on trunk and none of it has been played (see "Phase 3: fortifications"). The plan and the phases are in [#1079](https://github.com/haterade22/TAOM/issues/1079).

## Why This Exists

- **Vanilla behavior:** a siege is one battle, with one spawn logic that owns every troop from the start.
- **TAOM requirement:** waves without end, under vanilla's siege AI and engines, with no scripted AI. Fords of War scripts its own AI; a siege should not have to rewrite ladders, towers, rams and wall defence.
- **Without the spike:** Phase 1 would build a mode on engine assumptions that nobody has tested. The first review of the spike already disproved one of them (below).

## Architecture

### What the mission leaves out of vanilla's list

`LongDefeatMissionLauncher.CreateBehaviors` copies vanilla's custom siege list (`BannerlordMissions.OpenSiegeMissionWithDeployment`) and leaves these out: the spawn logic and handler, the reinforcement controller, `BattleEndLogic`, the two deployment behaviors, `BattlePowerCalculationLogic`, `GeneralsAndCaptainsAssignmentLogic`, and the observer, agent, banner, victory and highlight logics. The director spawns every agent from the mission tick.

Two engine paths read what is left out. [The lifecycle doc](../reference/engine/mission-and-missionbehavior-lifecycle.md) has the mechanism and the line numbers.

| Engine path | What the mission does |
|---|---|
| `TeamQuerySystem` reads `IBattlePowerCalculationLogic` with no null check | `LongDefeatMissionLogic` implements it and returns a large constant |
| `GeneralsAndCaptainsAssignmentLogic` asks a model that reads the spawn logic | It stays out. `AssignPlayerRoleInTeamMissionController` sets the order owner, and the director makes the player the general: the `general` check reads both |

### How a soldier gets a place

Soldiers spawn with no position, and the deployment plan gives each formation its place. `Boot` gives `DefaultMissionDeploymentPlan` the troop counts and calls `MakeDefaultDeploymentPlans`. The garrison and each wave then call `Formation.BeginSpawn` and `Mission.SetFormationPositioningFromDeploymentPlan`, and each soldier asks `GetAgentBuildDataToSpawnTroop` with no position. A later batch or a bought pack skips the placing (`SetFormationPositioningFromDeploymentPlan`) but still calls `Formation.BeginSpawn` (`LongDefeatDirector.SpawnBatch`, `LongDefeatBattlefieldAdapter.BeginBatch`), which vanilla does not do for a formation that already has a place (`MissionBattleSideSpawnContext.cs:369`). Two parts are not vanilla's path: each wave places its formations again, and a wave's batch stays open across several ticks. Vanilla's reader of `IsSpawning` is in the class this mission leaves out (`:403`).

**What keeps a soldier on the right floor:**

- The layout offers only slots that native `BatchFormationUnitPositions` accepts, spreading out from the frame (`Formation.cs:669-671`, `LineFormation.cs:495-497`). A slot needs a navmesh face, in a siege the frame's face group digit, and a height near its neighbours. That list comes from the native pseudo-C.
- A slot with no navmesh goes back toward the frame (`Mission.cs:3983-3985`).
- When the slots run out, every remaining soldier stands on the frame point (`Mission.cs:3992-3995`).
- `IMBAgent.SetInitialFrame` then takes the height. It casts a ray down from 1.5 m above the given height, falls back to the terrain height, and uses 0 if every try misses. The fixed path still goes through this step, but its input is now an accepted slot.

**Never compute a place by hand on a scene with floors.** The first version laid its own grid around the frame, in the manner of Fords of War's spawn block. On the first run at Helm's Deep, 64 of the 101 defenders stood below the wall line, with a median height of 0.0 against a frame at 26.5, and 3 died from the fall. Whether 0.0 came from a collider, from the terrain or from a miss was not traced.

**The read-back:** the spike's `[S1] spawn level` printed each class with its frame, `far`, `off the navmesh`, `on the frame point` and a `z` spread. Phase 1 writes `[LongDefeat] spawn level ok: <side> <class> N of M, far F, off the navmesh O, on the frame point P` when a batch closes, summed across the ticks it spans, for defenders and attackers alike. It says `ok` when every soldier is within 10 m of the height of that class's recorded point, or the scene's frame, and on a navmesh, and `WRONG` otherwise. The unattended judge needs an `ok` line for each side and fails on `spawn level WRONG`. **`ok` does not mean on the walls.** The tolerance cannot separate a terrace at 26.5 from a gate at 20.5.

**The pile:** the Helm's Deep terrace runs out of slots, so the engine stands the rest of the foot on one point: 41 of 68 in a garrison of 100, 64 of 115 in a garrison of 170 (the slots grow with the batch's planned shape, from 27 to 51). The spike's `[S1] spawn pile` line named this when more than 6 of a class stood within 1 m of the frame point (a shield wall at spacing 0 can put 5 healthy soldiers there). A pile failed nothing, and they spread out by themselves: by t 30 s all 101 stood high. It looks wrong to a person, so Phase 1 musters in timed batches (`[LongDefeat][Muster] batch`), each judged by the `muster` check. **`ok` for that check means that no more than half the batch stands on the frame point, or no more than 6 if that is the larger number**, with no soldier far or off the navmesh and at most 6 overlapping an earlier batch. A timed-batch garrison harmed nothing in run `20261104-033424`: `high` read 183 of 185 at about t 50 to 55, and 185 of 185 at t 60. Reinforcements can pile on their own frame too (the spike read 24 of 24 in wave 2 and 2 of 16 in wave 3), because a reinforcing batch keeps the live formation's shape.

**A stacked muster batch is under investigation.** One unattended run at a triple garrison put a whole muster batch of 20 militia on the muster point itself, and two more runs with the same timing did not repeat it. The likely cause is that the formation layout found no place for the new soldier and the engine put him on the formation's order position, but that is not proven, so nothing is fixed. Commit `7f7adc225` adds a diagnostic: a batch that stacks (more soldiers on the point than the `muster` check allows) writes one `[LongDefeat][Muster] stacked batch` warning. It repeats the engine's place lookup for the next soldier and logs whether the layout gave a place (`layout_place`), whether that place has a navmesh (`place_navmesh`), the formation's real file count against the smallest count the layout allows (`files`, `min_files`), its `width`, `interval`, `diameter`, arrangement and order, its `units`, `spacing` and AI control, and how far its order position stands from the muster point (`order_to_muster`). A small pack placed beside the point writes nothing. The line has not fired in game yet.

**A healthy Helm's Deep:** the defender archers' frame stands at height 1.5, so the spike's `[S1] after initial spawn` read `high` of 68 of 101, with a `z` minimum near 1.3. That is the scene's frame and not the fault repeating. The spike's `[S1] frames` line printed all six frames; Phase 1 has no such line.

### How a wave ends

No wave retreats, so a wave ends when no attacker stands, and that does not happen by itself. Only `BattleEndLogic` ends a vanilla siege, the player's exit aside: on a depleted side, or a side wholly running away (`BattleEndLogic.cs:198-222, 279-361`). Kills, a morale rout, the power retreat and the sally lead there. This mode leaves that logic out. On the first unattended run the last 7 attackers, then 6, and the last 31 defenders stood apart from t 420 s to the limit at t 1,500 s.

**The hidden gate at Helm's Deep:** since 2026-11-18 the scene has one visible inner gate, `empire_castle_gate_inner_l3` at (167.9, 220.1, 20.7), just inside the outer gate, and no hidden one: Mike added the gate in the Kit, and the hidden gate was removed from the live scene, because the engine takes the first registered `inner_gate` with no visibility check and every gate joins the Middle lane, which stays shut while any of them is closed (`TeamAISiegeComponent.cs:57`, `SiegeLane.cs:352-364`). `LongDefeatHelmsDeepGateTests` requires exactly one inner gate, visible. The boot now logs `gates 2 visible` and `hidden 0`, a level or a repair acts on both gates (keys `g0.` and `g1.`), the `gate-attacked` watch reads and samples only the gates the repair touched, and a troll strikes the inner gate once the outer one falls. The prefab's navmesh ids (462 and 467) named no face in the scene's navmesh, so the shut inner door blocked no path. On 2026-11-18 the four door faces (3607, 3608 and their second-layer twins 7237, 7238) were set to id 521 in `navmesh.bin` and the gate's `NavigationMeshId` to 521, as vanilla does with this prefab. The id ends in 1, so the faces stay inside the castle (`SiegeQuerySystem.cs:184`). The gate has no swing faces, because the face behind it spans the passage. The outer gate's `NavigationMeshIdToDisableOnOpen` went from 502 (no face) to 501, its four side strips, and its second-layer door face 7233 got id 500. Run `20261118-133313` (build `2ea2401bc`) loaded the scene and cleared 3 waves, and the attackers broke both gates in wave 2. `LongDefeatHelmsDeepGateTests` requires the 521. The rest of this paragraph is the history of the hidden gate. Until then the scene held a hidden inner gate at height 32.5 (`aserai_castle_gate_inner_l1 visible="false"`). The 2026-11-06 rework in the Kit dropped it, and Mike put it back at (137.5, 185.8, 32.7); the runs below read the old one at (133.4, 180.7, 32.5). Without an inner gate the engine would throw: `BehaviorAssaultWalls.cs:122-174` reads `InnerGate` with no null check once the outer gate is open, and `MovementOrder.cs:902` does so on a defenders' charge. So `LongDefeatHelmsDeepGateTests` read the live scene for one visible outer gate and at least one inner gate, with a gate entity's own tags replacing its prefab's, as vanilla scenes use them. The engine takes it as `InnerGate` with no visibility check (`TeamAISiegeComponent.cs:54-57`), and a hidden gate never ticks, so it never opens (`CastleGate.cs:619-622`). The Middle lane then stays closed (`SiegeLane.cs:355-364`), and attackers on the gate lane go to that gate and stay in `AttackEntity` (`BehaviorAssaultWalls.cs:161-166`). In all three runs the first attacker at height 32 or more appeared 20 s after the outer gate fell. Defenders hold their lane place on plain Move orders, and they hunt only with over 30 attackers inside (`TacticDefendCastle.cs:975`). Constant team power turns off the retreat and the sally, which are the other ways out. So `Boot` breaks any hidden gate and logs `[LongDefeat][Boot] hidden gate at (...): broken` (or `NOT broken`), then `hidden gates broken N`. It is not removed, because a null `InnerGate` throws in `BehaviorAssaultWalls`. Until 2026-11-18 a campaign siege on this scene met the same hidden gate, and nobody checked what it did there. **Breaking it works** (spike run `20261103-235325`, build `985b0d54e`, defaults): `[S1] hidden gate at (133.4, 180.7, 32.5): broken`, and `Middle open True` once the outer gate falls. Waves 1 and 2 of 110 cleared at 349 s and 669 s with no `stale` line, against 465 s and 840 s before. Wave 3 went quiet with 44 attackers left, and the charge ended it at 1,254 s, with no soldier felled by rule. The same rework left the right wall's breach child without its `WallSegment` script, so the base game's siege set-up threw at every start on the scene and the first run on it stalled in wave 1; the scene was fixed on 2026-11-10 and `tools/check_siege_wall_scripts.py` gates it ([RCA](../reviews/rca-helms-deep-siege-wall-2026-11-10.md)).

`WatchStalemate` was the spike's rule for every other stand-off. Phase 1 carries it as `Domain/StalemateRule.cs`, with its thresholds in `waves.json` and its lines tagged `[LongDefeat][Wave]`.

**The last few defenders lose the run (Mike, 2026-11-04).** When the rule below reaches no result, and `stragglerCount` (5) or fewer defenders stand, fewer than the attackers, the run ends as `DefendersDead`, with the panel's "The garrison has fallen". Any larger stand-off stays a stalemate. The first `--speed 10` run needed this: it ended on 89 attackers against 1 defender they did not reach. This loss skips the `stale` check, because the run did end, so the `[Check]` line and the `[End]` line name who stood. `reason=lost_defenders` alone no longer proves that no defender stood. Nobody has played what a living person sees here: Escape can dismiss the end panel, as on the other ends.

**The last few fall first (Mike, 2026-11-04).** When `stragglerCount` (5) or fewer attackers stand, fewer than the defenders, they fall after `stragglerSeconds` (60 s) with no charge, so the defenders stay on the walls. A death on either side does not restart that clock. Before this, 8 of the 15 cleared waves in four runs waited 110 s or more on their last 1 or 2 attackers, and Mike closed a run at the end of wave 5 because 2 attackers stood far outside the walls, near (274, 266) and (288, 257), and nothing moved. Nobody has traced why such a soldier stays out. A felled soldier pays no bounty. Larger stand-offs take the longer path:

1. With half the wave down and no loss on either side for 60 s, or no loss for 180 s at any count, `[LongDefeat][Wave] N stale: both teams charge` is written (the spike's `[S2] wave N stale` also printed the attackers' places and each formation's behavior, which Phase 1 does not), and both teams change to vanilla's `TacticCharge`. That tactic only weights `BehaviorCharge`, which returns 0 until the walls test passes (`BehaviorCharge.cs:169-201`), so it moves soldiers on some lanes and not on others, and a formation under a player's orders does not move at all.
2. After 90 s more with no loss, `[LongDefeat][Wave] N stragglers fall: ...` is written and they fall (`Mission.KillAgentCheat`; the spike printed their places under `[S2] wave N: nobody reached the last M attackers`). One soldier can stand for good: in wave 2 of the passing run the last attacker never left the spawn area, at (260.2, 305.9, -0.8). Only stragglers fall: at most a tenth of the wave, and fewer than the defenders. Otherwise no wave clears, because a clear must be earned: at Minas Tirith the first form of this rule felled 35 attackers with 2 defenders left. That end is now a loss, and only a larger stand-off is a `stalemate`. The judge's result counts the waves that ended by this rule.
3. At the wave's clear, the defenders get a new `TacticDefendCastle`, and they start the next wave out of place: `high` read 46 at the start of wave 3, and 163 of 170 about 15 s later. The next wave's new `TacticBreachWalls` comes when its first batch is out (`RefreshAttackerTactic` in `Domain/SurvivalRun.cs`), so the attackers stay on `TacticCharge` until then.

The rule fired in waves 2 and 3 of the passing run. A wave of 110 lost its last soldier at about 840 s and 1,380 s of mission time, 90 s and 128 s after the `stale` line. Soldiers can still flee on low morale, and Phase 1 closes that. The state lines of the four runs count none, and one `OnAgentPanicked` warning fired at Minas Tirith.

### The terrain shader dialog at Helm's Deep

A Helm's Deep load can stop at a native dialog: `Error compiling shader file: $BASE/Shaders/Sources/pbr_terrain.rs` (and `pbr_terrain_gbuffer.rs`), X4008 at `terrain_pixel_functions.rsh:818`, raised to an error by X3129. **Press Cancel.** The mission then loads in seconds. Retry compiles the same source (native `FUN_1800934e0` returns to `D3DCompileFromFile`), and Cancel returns a null blob. Two native flags skip the dialog, and nobody has read what sets them. The dialog holds the game, and nobody is there in an unattended run, so `tools/run_long_defeat.py` presses Cancel by itself and logs that in `runner_log.txt`. Left open for 304 s, the dialog made the load stall watchdog (removed 2026-11-12) write a `[CrashReport]` block, which failed the judge; with the watchdog gone it only stalls the run.

Open: Mike's by-hand launches at 17:26 and 17:28 loaded in under 10 s and show no sign of this dialog, and all three unattended launches at this fortress met it. The runner's `shader cache list differs` does not explain that, because it is on all four runs, and Minas Tirith had no dialog. Phase 1 stands in for the cached-variant or guarded-copy ask with one sentence in the setup prompt ("If a shader error window appears while the fortress loads, press Cancel"), which replaces that ask only on Mike's word, and does not touch `Shaders/`, which belongs to the install. **Decision for Mike, open:** build a scene shader sack for Helm's Deep in the Kit. It would live in the unversioned `TAOM_Map`, so a reinstall reverts it, and the same dialog already threatens a Custom Battle siege at this scene.

### Decisions from the spike

The first two still hold in Phase 1. The other three describe the spike's runner, which went with the spike: Phase 1 has no refill and no in-mission tests.

- **Power never orders a retreat.** The constant keeps both power ratios near 1, so `TacticBreachWalls` never takes its one-way retreat on power, and `TacticDefendCastle` never sallies on it. No wave retreats in this mode (Mike, 2026-11-03). The constant closes only the team retreat: a soldier can still flee on low morale, so Phase 1 adds attackers to `TaomCustomBattleMoraleModel.CanPanicDueToMorale`, and its state lines count anyone who flees. `FellFoesAdapter.SendOff` calls `Retreat` directly, and the `no-rout` check fails if a soldier it sends off is counted.
- **Waves are larger than 100.** At 100 attackers or fewer, `TacticBreachWalls` stops using its machines. The spike's by-hand default was a wave of 120 and a garrison of 100, and its unattended default was 110 and 170, because 100 defenders held on one run and all died on the other, with about 45 attackers left. Phase 1's balance is under "The first balance" below.
- **Each wave got a new tactic.** The first spawn batch latches a shock assault and clears `ForcedUse` on the engines. The runner set `ForcedUse` back and added a new `TacticBreachWalls` when the wave's queue emptied.
- **The garrison refilled between waves,** so a later wave's evidence did not depend on the first wave's losses.
- **All in-mission tests ran after wave 1:** S5, S7, then S4. Every later wave then met the repaired gate.

Why losses swing this much between runs, and why attackers climb in numbers in some waves and not others, is still open. The rule costs little and stays for now, and Mike can set `restShare` to 0.

The towers stay at the wall after wave 1, and Phase 1 has no gate repair, so from wave 2 attackers reached high ground 55 to 70 s after the wave began, against about 150 s in wave 1. ## Configuration

No MCM. Six JSON files under `Main/_Module/ModuleData/long_defeat/` hold the content, and each bad value costs one logged warning and falls back to its default: `fortresses.json` (scene, cultures, garrison, keep point), `waves.json` (the `rules` numbers, bounties, wave rosters) and `shop.json` (offers and starting gold), then `affixes.json`, `boons.json` and `classes.json`, each described under "Phase 2" below. The files are read once per game process, so an edit needs a full game restart, not a new run. An unattended run takes an arm file of `key=value` lines named by `TAOM_LONGDEFEAT_AUTORUN`: `fortress`, `waves`, `out` (required, absolute), `quit`, `live_limit_seconds`, `wall_limit_seconds`, `screenshots`, `garrison_scale`, `expect`, `speed` (1, 2, 4 or 10), and the Phase 2 keys `seed`, `start_wave`, `start_rerolls` and `class`, and the Phase 3 key `start_gold`. Player-facing text is the `TAOM_LD_*` rows of `taom_module_strings.xml`; the 12 language files carry the English seed until #763.

**The run report** (`long_defeat_report_*.json`, beside the log) also carries what a leaderboard checks: `schema`, `build`, `balance` (a hash of the six JSON files with line endings normalized), `cheatMode`, `mods` (ids with versions), `autoplay`, `garrisonScale`, `targetWaves`, `maxSpeed` (the highest mission speed set in the run), `startedUtc` and `endedUtc`. It holds no player name. The board itself is not built: [leaderboard-plan.md](long-defeat/leaderboard-plan.md), #1080.

## Phase 2

Phase 2 ([phase2-plan.md](long-defeat/phase2-plan.md)) layers a seeded roguelite run over Phase 1's survival run: an endless scale past the authored waves, affixes on the attackers, boons the lord picks, four classes, enemy commanders with summons, and a Cavalry sally. It was built in eleven slices and pushed to trunk. Unattended runs on 2026-11-05 passed the troop and class boons, the reroll, the captain and the lieutenant with his summons, all three foot classes, the Cavalry class without a sally point, and the Hammer, Winged Terror and Morgul Blades affixes. Still owed: the sally itself in game (the point was recorded on 2026-11-16), the kill owner after the player's death, and a person's play. "How to verify in game" lists the check for each mechanic. ### The seeded run and the report (Slice 1)

- **Report schema 2.** Schema 1's fields keep their names and meaning. Schema 2 adds `seed`, `class`, `startWave`, `startRerolls`, `boons`, `rerolls`, `poison`, per wave `affixes`, `healthFactor`, `damageFactor`, the summon counts and `commander`, and `gold.commander` and `gold.boon`. `balance` hashes six files, the three Phase 1 files plus `affixes.json`, `boons.json` and `classes.json` (a missing file joins as empty text), so the hash differs from any Phase 1 build's.
- **`RunRandom`** is the SplitMix64 every roll draws from, with its vectors pinned in `RunRandomTests` and in `test_run_long_defeat.py`. `RunOptions` gains `Seed` (the start time's ticks when none is armed, taken in `BuildPlan`), `StartWave` and `StartRerolls`.
- **Arm keys** added to the Configuration list: `seed` (0 to 2^53-1; a negative or larger value is refused, because the cap keeps every digit for a JavaScript reader of the report, and a clock seed is masked into it), `start_wave` (1 to 100: the run begins at that wave number, while `waves` still counts clears), `start_rerolls` (0 to 3) and `class`.
- **Wrapper flags:** `--seed`, `--start-wave`, `--start-rerolls` (armed as 1 unless given), `--class` (`all` gives each run the next class) and `--deep` (`--start-wave 12 --waves 4`, judged by its own list and allowed to end lost). The judge refuses a report that is not schema 2 or that does not echo the armed seed, start wave and rerolls, and fails on any `owner_missing` above 0.
- **Blow owner gate:** `LongDefeatBlowOwnerTests` fails when anything outside `ApplyPoison` and `Fell` kills an agent, or when a blow takes owner -1 (see "Poison and the kill owner").

### The endless scale (Slice 2)

A wave past the authored list takes a health factor and a damage factor, each `min(maxFactor, 1 + perWave * extra)` with `extra` the waves past the list (shipped: 5% and 3% a wave, capped at 3). Every `tierEveryWaves` (3) extra waves, each row of its mix moves one link along the roster's `tiers` chain. Rows that land on one troop merge their weights, a chain stops at its end, and the count line is unchanged.

- **Helm's Deep's chain** runs fighter and militia spearman to warrior to spearman to veteran spearman to veteran pikeman; swordman to infantry to veteran infantry; and skirmisher to arbalest to crossbowman to veteran crossbowman. Only the last authored wave's mix is stepped (spearman, infantry, berserker, crossbowman), so just four links can fire with the shipped waves (spearman, infantry, crossbowman and, at two steps, veteran spearman). The links from militia spearman, fighter, warrior, swordman, skirmisher and arbalest are parsed and checked but no wave reaches them. `bounties` gains the four veteran troops (15, 20, 20, 20).
- **Config:** `waves.json` takes `healthPerWave`, `damagePerWave`, `maxFactor` (1 to 10) and `tierEveryWaves` (1 to 50) in a roster's `scaling`, and a `tiers` block beside it. A bad number keeps its default with one warning. A tier link that is not a troop id, points at its own troop, joins two classes the roster's waves show or closes a cycle is skipped, and a target with no bounty pays 0 with one warning. The launcher's troop check reads `RunPlanTroops.AllTroopIds`, so a missing tier target refuses the launch instead of spawning nothing.
- **Health** is written after each attacker spawns (`BaseHealthLimit`, `HealthLimit` and `Health`, in `LongDefeatBattlefieldAdapter.SpawnBatch`, from `SoldierBatch.HealthFactor`).
- **Damage** is published by `LongDefeatEffectsAdapter` with the effect that starts the wave, before any soldier of it spawns. `LongDefeatCombatHooks.Amplify` applies it to attackers' blows from `TaomCustomBattleDamageModel.ApplyDamageAmplifications`. The hook is inert unless the Long Defeat mission is armed, so Fords of War and every other Custom Battle pass through, and a fall is not a blow (the engine names the faller as its own attacker), so a scaled attacker's fall damage is untouched. The model also runs for a soldier's blow on the gate, a wall section or a shield, which take the factor too; the ram damages the gate directly and does not. Whether that is wanted is open (phase2-plan.md, Slice 13). Defenders are never scaled.
- **Report and check:** `waves[].healthFactor` and `damageFactor` carry the values (1 inside the authored list). `scale` (key `w=<N>`) is written once per scaled wave, at its clear or at the run's end inside it. A sampled attacker's health limit over its character maximum must equal the health factor within 1% at spawn and again late in the wave; its troop must be one of the wave's stepped mix; a damage factor above 1 must have raised at least one attacker blow (a defender's boon blow is not counted); and the engine's standing count must never exceed the room the previous tick spawned into. The sample is a standing attacker that is not running away, so a runner left from the wave before is never read. The judge requires the line from any report with a wave row whose health or damage factor is above 1. The numbers are first guesses (assumptions A9 and A15 of the plan).

### Affixes (Slices 3, 8 and 9)

**The roll.** From wave 5 a wave carries affixes: one from wave 5, two from 10, three from 15 (`affixes.json` `schedule`). The roll is a partial Fisher-Yates over `AffixPlan.Pool`, drawn from `RunRandom` stream 1 at `(wave, 0)`, so one seed gives one roll, a shorter roll is a prefix of a longer one, and the HUD's preview of the next wave cannot differ from the wave. The roll is taken when the wave's horn sounds. The eight ids are `lash, drums, eye, discipline, hide, hammer, terror, blades`, and all eight are in the pool (`AFFIX_POOL` in `tools/run_long_defeat.py` follows, and a test pins both to the same list). `AffixPlan` holds the schedule, each power's numbers and the names of the fortress's attacker culture (`names.isengard` and `names.mordor` ship; at Helm's Deep `blades` is named Fouled Blades). A bad number keeps its default with one warning, and a culture with no name table shows power ids with one warning. Adding a power to the pool changes every roll, so each slice that did so (the pool grew from five to seven to eight) re-pinned the rolls and the in-game seeds. At wave 5 seed 0 now rolls `eye`, 1 `hide`, 2 `lash`, 3 `blades`, 5 `discipline`, 7 `terror`, 9 `hammer` and 15 `drums`.

**The stat powers and `hide`.**

- `lash` (swing speed, attack eagerness), `drums` (move speed, acceleration), `eye` (aim error, draw, reload and missile speed) and `discipline` (block and parry) fold into one `RaceAbilityEffects` record built fresh for each wave (`RunModifiers.StatTable`) and published with the wave's start effect, before any attacker spawns.
- `LongDefeatStatHooks.UpdateStats` runs after the race abilities' post-pass in `TaomCustomBattleAgentStatCalculateModel.UpdateAgentStats` and applies the record through `RaceAbilityStatApplier`, so a percentage multiplies what the engine just derived and never compounds. A horse takes its rider's record (only its mount speed, which the record copies from move speed); a riderless horse takes nothing.
- `hide` raises the four armour values of a human attacker by its percent in `InitializeAgentStats`, because the engine writes armour once, at spawn. Null build data (`SpawnMonster`), a horse and a defender pass through.
- Both hooks are inert unless the Long Defeat mission is armed. `LongDefeatHookState` holds the one armed mission and the one published `LdStatTable` that the stat and combat hooks both read, and the attackers' damage factor lives in `LdStatTable.AttackerDamage` alone.
- Not built: `RefreshStats` for the affixes (nothing stands when a wave starts, so it matters only for the war cry and the boons).

**`hammer` (Hammer of the Underworld).** `RunModifiers.EngineHitPoints` is `1 + engineHitPointsPercent / 100` in a hammer wave and 1 in every other. At each wave start the effects adapter writes `MaxHitPoint` of every live ram and siege tower to the vanilla value of the engine's type (`SiegeEngineType.BaseHitPoints`, the number the deployment sets) times that factor, and the current hit points by the same ratio. A damaged engine keeps its share. The Hammer calls no `Reset` itself: the wave start's restore (see "Engines come back each wave") brings a destroyed engine back first, at its full hit points, so the Hammer then writes it as an intact one. Factor 1 restores the vanilla value after a hammer wave. The write comes with the wave's stat publish, before any attacker spawns. The factor multiplies the engines' vanilla hit points and nothing else: the endless health factor is the attackers' soldiers' health limit and the endless damage factor their blows, which reach the gate, the walls and the shields through the damage model but not the ram, so neither feeds the hammer or is fed by it.

**`terror` (Winged Terror).** It pulses on the run's clock: every `pulseSeconds` of a terror wave's fighting, once per tick however long the tick, `LdMoralePulse.Apply` lowers each standing human defender within `radius` of a standing attacker by `amount`, never below `floor` (35), and leaves one at or under the floor alone, so routs do not cascade. Distance is measured across the ground, so a defender on a wall is reached from its foot. The attackers are only read for their positions, and the lord is never a target (a lord played by a human has no morale component and answers -1, but an autoplayed one is handed to the AI and gets one, so the pulse leaves out the main agent). The pulse reads the attackers' positions once into an array, counts the defenders drained and the ones left more than 0.001 below the floor (`pushed_below`) inside the call, and times itself. The first three pulses of each wave log `[LongDefeat][Terror] pulse n= ms=`, and any slow one too.

**`blades` (Morgul Blades).** See "Poison and the kill owner" below.

**The HUD and the report.** The strip names the running wave's affixes at once, and between waves the next wave's with, past the authored list, its attackers' health and damage (read from the wave plan; the view builds that preview only between waves). The report's `waves[].affixes` carries the power ids.

**Checks.**

- `affix` (key `w=<N>`) is written when a wave with affixes starts: the count matches the schedule (with `affixCount` boon cuts applied, see Boons), the powers are distinct and known, and each has a name in the culture's table.
- `affix-effect` (key `power=<id>`) has a verdict per power. For the stat powers and `hide` it is written when the wave's first batch has closed: one standing human attacker with no live race ability and no hero aura (#1127, `RaceAbilityHooks.HasLiveEffects`) is read back against the stat model's own answer for the same agent with the affixes left out (a thread-local bypass of the hook; armour against the spawn equipment's sums), within 1%. A sample that could not show the effect (an unarmoured soldier) is a skip, and no standing plain attacker is a fail with `reason=no-sample`. The director reads one soldier once per wave and judges each stat power on that sample. A wave whose only powers are `hammer`, `terror` or `blades` reads no soldier, because those have no stat expectations.
- `hammer` is written when the wave starts and passes when every live engine holds the vanilla value times the factor within 1% (the gate's state is logged beside it and judges nothing, and is read from every mission object because a destroyed gate leaves the active list, `Mission.cs:3060`; no live engine, or a factor of 1, is a skip).
- `terror` is written when the wave clears or the run ends in it. It passes on at least one pulse that drained someone, fails on any `pushed_below` or a pulse that took 16 ms or more, and skips when the wave had no pulse or none drained anyone.
- `blades` is described under poison.
- **The judge** replays each wave row's affixes from the report's seed (`affix_roll`, pinned against `AffixPlanTests`) and reads `affixes.json`'s schedule by the game's own rules (a missing file rolls nothing, a bad schedule is the shipped one). It requires `affix` from a run that cleared 5 waves or whose report shows a wave with affixes (the plan says 4 clears, which would fail a `--waves 4` run that never starts wave 5), and an `affix-effect` pass or skip line from a run whose report shows any power.

### Boons (Slices 4 and 6)

**Picks and rerolls.** A clear that brings `WavesCleared` to a multiple of 3 owes a pick, and one that brings it to a multiple of 5 earns a reroll into a bank of 3. A reroll lost to the cap is not counted as earned; `StartRerolls` seeds the bank and counts as earned, so the bank is always earned minus used. One offer is open at a time and stays open into later intermissions. A pick or a reroll is made between waves only, and the panel never opens by itself for one (a notice and the hint line announce it). A boon lasts until the run ends.

**The offer.** Three cards drawn from `RunRandom` stream 2 at `(pick, draw)`, with the first pick numbered 1 and the first draw 0. Each card is `Below(total weight)` walked over the eligible rows in file order, 10 a row and `legendWeight` (shipped 1) for a Legend row, taken and removed. A reroll discards the offer and draws again with the next draw index, leaving out the three cards just shown unless fewer than 3 others are eligible. A boon owned is never offered again; fewer than 3 eligible rows offer what is left, and none lapses the pick with a log line. A class row is offered only to a run of that class (`SurvivalRun` builds its `BoonDeck` with `plan.Options.ClassId ?? ""`), and a troop category's rows only while the fortress's garrison or shop holds a troop of that group (`RunPlanTroops.DefenderGroups`, static data, so the replay sees it). A troop's group comes from its character, the engine's flags read once from the XML `default_group` by the launcher (`LongDefeatTroopGroups`, into `RunPlan.TroopGroups`): mounted is cavalry, else ranged is archers, else infantry. So the King's Knights on the Helm's Deep shop list, bought to fight on foot, are cavalry.

**`boons.json`** ships 34 rows (counted from the file): 5 war chest, 5 fortress, 3 Legend (`the_long_silence` among them, see Commanders), 12 class rows (three for each of the four classes) and 9 troop rows (three for each category: infantry, archers, cavalry). Names and texts are TAOM's own. Drawbacks carry their own line of text (a `drawbackText` key the plan did not list, so no cost is hidden).

**The effect vocabulary** is closed; the reader skips any other key or an out-of-range value with one warning, and a boon left with no effect or a drawback with no text is skipped.

- War chest and fortress keys: `bountyPercent`, `waveBonusPercent`, `earlyGoldPercent`, `pricePercent`, `gold` (paid once at the pick), `garrisonCap`, `intermissionSeconds`, `restShare`, `keepHoldPercent`, `packBonus` and `affixCount` (negative only; never a drawback, as `gold` is never one).
- Ten targeted keys, each with a `target` (`infantry`, `archers`, `cavalry` or `player`, in an effect and in a drawback; a targeted key without a valid target is skipped with one warning): `swingSpeedPercent`, `moveSpeedPercent`, `drawSpeedPercent`, `reloadSpeedPercent`, `blockPercent`, `parryPercent`, `aimErrorPercent`, `damagePercent`, `damageTakenPercent` and `healthPercent`.
- Commander boon key `commanderCooldownPercent` (see Commanders).

**Every number a boon changes is recomputed from the boons owned** (`RunModifiers.Rules`, `Gold`, `AffixCut`), so a second boon never applies the first twice.

- The war chest keys become four factors (a sum of percents, never below 0, rounded half away from zero where they meet gold). The horn's factor scales both its rate and its cap. A price factor and `packBonus` rewrite the shop's offers (the view shows what a buy costs and the pack the player gets).
- The fortress keys change the run's effective rules with floors (garrison 1, intermission and keep hold 5 s, rest share 0 to 1). An intermission boon acts from the next clear.
- `affixCount` cuts the affixes of the wave that begins after the pick: the wave carries the first `max(0, scheduled + cut)` of its roll, so the HUD's next-wave line shows the cut list.
- The stat keys fold into one `RaceAbilityEffects` record per target in the published `LdStatTable` (percents sum within a target; the cavalry and player records copy move speed into mount speed). `LongDefeatStatHooks.UpdateStats` writes the record of the group a defender's character puts it in; the lord's body takes the `player` record only, whoever he was.
- `damagePercent` and `damageTakenPercent` are two factors per target that `LongDefeatCombatHooks.Amplify` and `Reduce` apply from `TaomCustomBattleDamageModel` (a horse takes its rider's, and `Reduce` wraps the Fords call).
- A health boon multiplies the health limit of those standing by that boon's own factor (`ScaleHealth`, keeping each soldier's health share), and every defender batch spawned later takes the product of the boons' factors for its group, so a second health boon never applies the first again. The lord's health is only ever set outright to the combined factor, at the pick too, so a body adopted in the same tick cannot take the pick twice.
- A pick tells the director what to do on the next tick: publish the new table, refresh the driven properties of the groups whose stat keys changed (`RefreshStats`, which logs `[LongDefeat][Boon] refresh <group> n= ms=`), then scale health, all before anything spawns. A body that becomes the lord's (the start, a respawn, a soldier taken over after his death) is refreshed and has its health limit set outright to the player's factor (`AdoptIfNew`), because the controller setter calls no stat update (`Agent.cs:1233-1290`). The lord's own spawn takes the same path, so `SpawnPlayer` carries no factor.
- Not built: spreading a large refresh over ticks (the `refresh` line measures it; risk 11 of the plan), and any read of a damage-only boon (it acts at the blow).

**The panel and the bot.** The panel gets a pick group above the shop (three `LongDefeatBoonVM` cards, a reroll button with its count), and the end panel lists the boons taken and opens with "Class: ...". The HUD strip names the class after the wave ("Wave 3, Archer"). The unattended bot answers an open pick first: a reroll when one is banked and every card has a drawback, else the first card without a drawback, else the first card. It also spends the first banked reroll it ever holds on the first offer, which is how a 5-wave run proves a reroll at clear 3 (the plan's rule alone would reroll only on three drawbacks).

**Checks.**

- `boon` (key `p<N>`) is written when a card is taken: the last draw showed 3 distinct cards (or all that were eligible), the taken one among them, and every number a boon changes reads back as the shipped value changed by the boons owned, recomputed in the check apart from `RunModifiers`. For a boon with a stat or health key the line ends with `read=pass`, `read=skip` (no soldier of the target stood) or `read=fail`: a soldier of the target, read right after the refresh, holds its health limit at the combined factor and each driven property at its baseline (the stat model with the hooks inert) changed by the summed percent. A rider's horse is read too: its `MountSpeed` against the stat model's answer for the horse, when a horse stands under the soldier. The first pack of that group spawned after the pick is read the same way as its own `boon` line (key `p<N>-<group>`, `read=spawned`).
- `reroll` (key `p<N>`) is written for each reroll: the bank fell by one, there are new distinct cards, and none of the cards just shown when 3 or more others were eligible.
- The horn's `early-start` check follows the factor in force.
- **The report** lists each pick (`pick`, `wave`, every draw in `offered`, `taken`, `takenBeforeWave`), `rerolls` and `gold.boon`.
- **The judge** replays the boons from the report's seed over the shipped `boons.json` (`boon_cards`, pinned against `BoonDeckTests` and `LongDefeatShippedConfigTests`), including the class and troop rows (`troop_groups` reads `fords_troops.xml`, `boon_eligible`, pinned against the C# deck for an archer at Helm's Deep). It checks the rerolls add up, keys the affix cut on the wave a boon was taken before (`affix_cut`), requires the `read=` token on the pick line of a taken boon with a stat or health key (`read_owed_picks`), requires `boon` from a run that cleared more than 3 waves or took a pick (a `--waves 3` run ends at the clear that opens the pick, so the bot never sees an intermission to take it in), and requires `reroll` from one that banked a reroll at its first pick or spent one.
- `docs/reference/provenance-register.md` records the design reference (a comparison-only row, status uncleared), and the reviewer compares the names and texts in `boons.json` against that page.

### The lord's class (Slices 5 and 11)

**Classes.** The lord plays one of four classes from `long_defeat/classes.json`: Sword and Board, Two Handed Infantry, Archer and Cavalry (`mounted: true`). A class is a kit per defender culture (Helm's Deep's defenders are `vlandia`, which is Rohan), written with the XML slot names `Item0` to `Item3`, `Head`, `Body`, `Leg`, `Gloves`, `Cape`, `Horse` and `HorseHarness`; an empty string clears a slot, and a class with no kit for the fortress's culture is not offered there. The foot kits give weapons only, so the lord's armour stays his own. The class question's description says the Cavalry kit also sets the armour and the horse.

**The spawn.** At the start and at every respawn the adapter copies the lord's first battle set, overwrites the kit's slots and hands that set to the engine as the spawn's equipment override, which `Mission.DecideAgentSpawnEquipment` reads before anything else. A foot class always clears both horse slots and spawns with `NoHorses(true)`; the spawn clears `NoHorses` only through the kit (`.NoHorses(!mounted)`). `spawnWithHorse` stays false on purpose, because true would read a mount key from the lord's own Horse slot (`Mission.cs:4500-4503`) instead of the kit's. A null key still builds the horse, and the visual picks a random coat (`MountVisualCreator.cs:41-46`), so a remount shows a new coat (plan risk 8 is closed). A slot is mapped through `Equipment.GetEquipmentIndexFromOldEquipmentIndexName` and checked with `Equipment.IsItemFitsToSlot` (a horse must also be rideable, in `BuildKit`). An unknown item or a misfit leaves the lord's own item in that slot with one warning, so the `class` check fails instead of the run quietly playing another kit. A player troop with no battle set starts from an empty one, because spawned without the override the engine would throw for a hero (`FirstBattleEquipment.Clone()` on null) or give any other troop an empty set. The adapter reads the kit back once, in the frame of the spawn, and keeps those facts rather than the `Agent`, whose slot the engine recycles. A soldier's body taken over after the lord dies keeps its own gear.

**Own-gear rule.** Every kit item is carried by a Rohan troop in `fords_troops.xml`, with one named exception that `LongDefeatShippedConfigTests.OwnGearExceptions` lists with its source: the two-handed class swings the Armory axe `wm_rohan_ws_axe_2h_a01` (`LOTRLOME_items/LOTRAOM_weapons.xml`), because no Rohan troop carries a two-handed sword, axe or mace (decision D5, taken on Mike's standing word).

**Cavalry.** Its kit is one Rohan rider troop's gear, the East Emnet Eorlingas Lancer: spear `wm_rohan_ws_spear_a03`, shield `wm_rohan_shield_a02_ggw`, sword `wm_rohan_ws_sword_a01`, the five armour pieces, and `t3_empire_horse` with `rohan_horse_armor_one`, with the fourth weapon slot cleared. Every id exists in the Armory or SandBoxCore, and `LongDefeatShippedConfigTests` pins that the kit is that troop's own. Not built: an `Item4` slot (no Fords troop carries one, and a test says so). Its three class boons are:

- Gallop of the Eorlingas: move speed +15 percent on the player record, which `ApplyMount` carries to the horse through `MountSpeedPercent` and `RiderAgent`. The `boon` check reads `MountSpeed` on the lord's horse while he has one; with none standing it drops that reading and still writes `read=pass`.
- Spear of Eorl: +25 percent damage, -10 percent swing speed and -10 percent draw speed. The kit's spear has only thrust attacks, which run on `ThrustOrRangedReadySpeedMultiplier`, a separate property from the swing one.
- Oath of Eorl: +35 percent health.

A cavalry troop boon such as Fleet Horses of the Mark still reads `skip` in a Cavalry run, because the mounted lord is the player record and the bot buys no rider.

**Choosing a class.** The setup prompt asks a second question after the fortress, "Choose your class", with one row per class: the row shows the class name, and its kit text shows when the row is hovered, because the engine's row is a fixed 65 px button that a two-line text overflowed. Cancel at either question starts nothing, and a fortress that offers no class starts at once. `taom.ld_start <fortress> [waves] [class]` takes the class as a third word (or as the second when there is no wave count). The arm key `class` reaches `RunOptions.ClassId` through `ToSetup`. `LongDefeatConfigCatalog.BuildPlan` resolves it: the class asked for when the fortress offers it, else the bot's draw `RunRandom.For(seed, 3, 0, 0).Below(classes on offer)` for an unattended run, else the first class on offer for a person. A class asked for and not on offer costs one warning and takes that default. The resolved id is written back into the options, so the report's `class` names the class that was played (empty only when none is on offer), and `RunPlan.Loadout` carries the kit. With four classes the bot's unarmed draw is `Below(4)`; seeds 0 to 7 draw sword_and_board, archer, cavalry, archer, two_handed, cavalry, archer, archer (pinned in `ClassPlanTests` and `test_run_long_defeat.py`).

**The check.** `class` (manifest row `taom.long-defeat.class`, key the mission id, or `<mission>-d<N>` at a respawn) is written after each spawn of the lord: every kit slot read back from his spawn equipment holds the item the kit names (an empty slot reads back empty), the engine refused no slot, he did not fall back to his own gear, and he sits a horse only when the class rides. It is required of every run (`absence = "fail"` once the boot passed).

**The wrapper.** It reads `CLASSES` from `classes.json` and a test pins it to the file. `--class` takes only those ids or `all`, which gives each of `--runs` the next class (`--runs 4` plays all four). The judge expects the class each run armed, set per run in `arm_text_for` so `--class all` is compared run by run, or, when none is armed, the bot's draw replayed from the report's seed (`bot_class`, pinned against `ClassPlanTests`). It also fails a report whose class is not on offer and a run with no `class` pass line.

### Commanders and summons (Slice 7)

- **Who and when.** Every fourth wave brings an enemy commander, from the roster's `commanders` block in `waves.json`: Lugdush (`lord_I3_1`, captain, wave 4), Ugluk (`lord_I1_1`, lieutenant, 8) and Lurtz (`lord_I4_1`, general, 12 and after). A rank sets its own health factor (2x, 3x, 4x, decision D11), written after spawn and multiplied with the endless factor, a bounty paid into `gold.commander` on a kill (none for a felled commander) and its abilities. The HUD strip shows his rank and next ability, not his name, because the data carries none.
- **The general grows.** From wave 16 he returns stronger: `steps = min(maxSteps, max(0, wave / every - validRanks))` adds 25 percent health, shortens each cooldown by 10 percent (never under 5 s, and a war cry's never under its duration plus 5 s) and adds 5 soldiers to each summon per step, so waves 4, 8 and 12 are at full strength.
- **Spawn.** He is queued at the head of the attacker queue when the wave's first batch closes, spawns as the next soldier, takes a slot of live room like anyone and is outside the roster count. The engine marks a hero unique at his spawn (`Mission.cs:4517-4523`) and dresses him in his first battle set rather than a random one (`Mission.cs:4284-4287`, `:4108`). The warg in that set is cleared like any horse (`:4468`, `:4109-4112`), so he fights on foot, and the other managed differences are cosmetic (his banner moves from the extra weapon slot to the formation, `:4122-4134`, and the face cache and random colours are off).
- **Abilities** run on a `CommanderClock` started when the director tells the run he is up: at most one use per tick, and a permanent stop when he is killed, felled or leaves the field (soldiers already summoned still come). `War Cry` (first at 20 s, then every 60 s, for 15 s) adds 15 percent swing and 10 percent move speed to every attacker's stat record, published and refreshed on the standing attackers at its start and end. `Summon` (30 s, then every 120 s) queues 20 Uruk-hai veterans at the head of the queue, so they spawn as live room allows. ### Poison and the kill owner (Slice 9)

**Fouled Blades.** In a `blades` wave an attacker's hit on a defender poisons him.

- `LongDefeatMissionLogic.OnScoreHit`, which carries the engine's own `isBlocked` and `damagedHp`, forwards a hit only while the director's volatile `WantsHits` is set and only when it has an affector that is not the victim, was not blocked, took some health and left the victim standing (`LongDefeatHitFilter`; a mount's blow is its rider's). `HandleBlow` writes the health and raises the hit before it calls `Die`, so a victim read under 1 health is a killing blow and no dose reaches him.
- The director turns the two agents into registry keys on the calling thread (an attacker is registered at his spawn, a defender at his first hit, and every removal evicts its agent and carries its key), then parks the dose on the main thread through `RunOrDefer`.
- `SurvivalRun` holds Fords' pure `PoisonRules` in an `LdPoisonBook`: one dose per victim, 2 health a second for 6 seconds (`affixes.json`), the hitter owns the dose, and doses are counted apart from hits because `PoisonRules.Totals` counts every apply. A key the registry forgot drops the dose and any later hit naming it. Ticks go out in `RunEffects.PoisonTicks` while an attacker stands, and the wave's end takes the doses with it.
- Poison writes health directly, so the wave damage factor and the `damageTakenPercent` boons, which scale the blows the engine owns, do not reach it.

**Who owns a killing tick.** Fords' recipe is not copied as it is, because it sends owner -1 when the shooter has gone and `Agent.Die` then swaps in a last hitter whose index may belong to another agent. A tick that would kill needs a living owner chosen by `PoisonOwner.Choose`: the poisoner while the registry holds him and he is active, else the commander, else any attacker standing. With none the tick is withheld and the victim keeps 1 health. The victim and the owner are read again at the call, for `IsActive()` and for being the current occupant of their slot (a deleted agent answers `IsActive()` for the slot's next tenant). An owner found not live is counted as `owner_missing` and kills nothing.

**`Fell`.** It no longer leaves a felled straggler's death to `KillAgentCheat`, whose owner is `MainAgent ?? victim` (`Mission.cs:6220-6221`). While the player's body stands it still calls it. Otherwise it builds the same blunt 2000 blow owned by a standing defender (decision D13), so a `--lose` run that fells with the player dead gives `CustomBattleMoraleModel` a real affector; with no defender standing nobody is felled. The soldier is still marked before the kill and brought under 1000 health first, so the blow is lethal at any limit. `LongDefeatBlowOwnerTests` pins both members' source.

**Neither `hammer` nor `terror` kills anything**, so the blow-owner gate has nothing new to allow for them.

**Check and report.** The `blades` verdict of `affix-effect` is written when the wave ends (`power=blades w= doses= hits= damage= owner_missing= withheld=`) and fails above 0 `owner_missing`. It skips when no hit landed (`reason=no-hit`) or no dose took a point of health (`reason=no-damage`). `[LongDefeat][Blades]` tick lines show the first three ticks of a wave and any that killed, were withheld or went to a substitute owner. The report's `poison` object carries the run's totals, and the wrapper also fails any `owner_missing=` token in the log and the report's `poison.ownerMissing`.

### The gates (Phase 3, Slice 5)

([phase3-plan.md](long-defeat/phase3-plan.md).) `FortOffer.Offered` now offers the gate's three levels with its repair, beside field care; the towers and the volley still answer `NotOffered`. A level (D18) sets each visible gate's `MaxHitPoint` to its vanilla maximum, read at the boot before any hit (15000 at Helm's Deep), times the level's factor, and keeps a standing gate's share of hit points less one point (`GateMath.KeepShare`), so the damage-state index the next hit computes can only stay or rise: a next hit that computes index 0 on a gate stored at 1 or more reads `_destructionStates[-1]` and throws, while a smaller fall only shows an earlier damage state (E9b). The order also reaches a lord whose body left with no death: under autoplay his body is AI-driven and can rout (the morale hold keeps attackers only), which removes it with no loss booked. The run reads that no lord stands and orders the rise, as the old respawn raised him. The report lists the take-overs and the rises.

Two clocks run in a wave. Under autoplay the run asks for a bot take-over (`RunEffects.TakeOverForBot`) 5 s after a fall, and again every 5 s while no body stands. In the wave `lord_falls` names, 20 s after its first batch is out, the run asks once for the lord to be felled (`RunEffects.FellLord`). Both clocks run as the last step of a tick and only while the wave still runs, so neither asks on the tick that cleared it, and each absence is counted from its own start, after a rout too. Slice 4 carries both out. A death is booked as forced only when the field reports that the body removed is the one its blow struck, so an ask nobody carried out marks no death.

The general's seat (`GeneralSeat.Choose`) is the player's body, his own or a taken one. While he has none it goes to the first standing hero in the shop's order, else to nobody, and the run hands it out (`RunEffects.General`) only when it changes. The first plan gave the seat to a bought Marshal; the shop's heroes (#1337) replaced him, and Mike's 2026-11-03 decision already said a bought hero takes the seat. In this mission the seat changes only how much its holder's fall or rout moves the defenders' morale (`Agent.GetBattleImportance` doubles for the general, and the morale model reads it at an incapacitation and at a panic). Slice 4 writes it to the engine.

### The death rule in the engine (Phase 4, Slice 4, spike S12)

([phase4-plan.md](long-defeat/phase4-plan.md).) The engine half. `ILongDefeatLordAdapter` is the field's part (`LongDefeatBattlefieldAdapter.Lord.cs`; the run host hands the director the field as its lord adapter too) and `LongDefeatDirector.Lord.cs` the director's. Every adapter call is made from the director's tick; a removal callback only notes the death. An agent is held by reference and tested for liveness before each use, never keyed by `Agent.Index`. A director with no lord adapter keeps the old respawn and serves none of this; only the director's tests build one.

**The rise.** At a clear the director serves the run's order. The place is the recorded keep (`at=recorded`), else the scene's keep frame (`scene`), and the home point for a mounted class (`home`). In a story mission where the player attacks, the keep is the enemy's, so the lord rises at the engine's own attacker frame and the place is booked `respawn`. At the boot the `fort-points` check also tests a recorded keep for a navmesh and the mission boundary when the player defends (`rise=recorded`); a keep that fails either fails the check, and the rise falls back to the scene's frame (`rise=scene-fallback`). The field finds the soldier the lord took (the live main agent that is not the body it spawned for the lord), hands him to the AI, then spawns the lord at the place in his class kit. That is the order of vanilla's own body swap (`Mission.cs:4736-4738`), and it keeps `Formation.HasPlayerControlledTroop` right when both stand in one formation: the plan's order (spawn, then hand back) left the flag false with the player in the formation. Handing a body to the AI never clears `Mission.MainAgent`, so the soldier stays the main agent until the new body, built with the `Player` controller, takes it. A refused spawn gives the soldier back to the player, fails `rise` with `reason=spawn-refused` and tells the run nothing, so the next clear orders the rise again. A soldier who is using a machine or a ladder is handed back all the same, and the line says `was_using=1`. The kit is the class kit; a bought gear set reaches the rise with Slice 5.

**The `rise` check** (key `w<N>`, the wave the rise precedes) is written on the tick after, once the new body was adopted. It passes when the main agent is the lord's own body, within 2 m on the ground and 3 m in height of the place (none to judge for `respawn`), driven by `Player` for a person and by `AI` under autoplay, no other body of the player's side is `Player`-controlled, and the general and the order owner are the lord. What became of the soldier is named and not judged: `handed_back=1`, `noop` (already AI-driven, as every body is under autoplay), `dead` or `none`. The `player-death` row of a fall now says how the next body came: `via=rise`, or `via=takeover by=person` or `by=bot`.

**The general's seat.** The director writes the seat on the tick the run hands it out (`SetGeneral`): the live main agent for the lord, the live hero with that id for a hero, and nobody otherwise. A hero is seated only on the player's own team, because a story mission's free heroes can stand with the other side. The engine never clears `Team.GeneralAgent` when its body is removed, so this write is what takes a dead lord out of the seat. The `general-down` check (key `d<N>`, the death's number) reads the seat on the tick after a fall: it passes for the hero the run chose (`want=`), and for nobody when the run chose nobody or the chosen hero no longer stands. It fails for the dead body (`seat=stale`), for another hero, and for an empty seat while the chosen hero stands by the director's own books (`stands=1`). When a body already stands at the read (a take-over came first), the line is a skip with `reason=has-main`.

**The bot's take-over.** Five seconds after a fall under autoplay, the field takes the soldier nearest to where the lord last stood, among those `Mission.CanTakeControlOfAgent` accepts (a human, active, non-hero agent of the player's team that uses no game object, at a quarter of his health or more, with no main agent standing), through `Mission.TakeControlOfAgent`. A posted tower archer is never taken: the posts' hold would pin the bot to the tower for the wave. The soldier's troop, formation and order are logged before the take and after the adoption.

**The forced fall.** In the `lord_falls` wave the field fells the lord's own body, which must be the standing main agent, with the blow `Fell` builds (`StrikeFelled` is now the one builder), owned by the nearest standing attacker who is not running away. With no such attacker nobody is felled and the line says so. The body is marked before the blow (`LongDefeatLordWatch.MarkForced`), its removal reports itself forced, and the run books that fact. A blow that leaves his health at 1 or more (an immortal body, a mission that disables dying) withdraws the mark. `KillAgentCheat` is never used: it would credit the kill to the lord himself.

**The run's end.** A `rise` or `general-down` read-back still owed when the run ends is written as a skip with `reason=run-ended`, so its row exists, and the field drops the lord's last position and the forced mark.

**The wrapper.** `LORD_FALLS_DELIVERED` is on. A run armed with `--lord-falls` fails unless it cleared that wave and the report lists a forced death in it: a lord who fell by himself first proves nothing about the option. The judge refuses a report in which a body fell in a wave the run cleared and went on from with no rise before the next wave, so a rise that comes a wave late fails. It owes one `rise` pass for each rise the report lists. It owes one `general-down` line for each death: a pass, or a skip with `reason=has-main`. A lost run owes none for a death in the wave it ended in, and in any other run one `run-ended` skip pays for a death in the last wave (a fall on the tick of the final clear). It owes a `player-death` pass when a take-over or a rise followed the first death. It owes a `sally-return` pass only when the run cleared a wave in which the rider did not fall in his own body: a rider who fell is not in his own body at the clear, the game writes that check as a skip (`reason=taken-over`), and he rises at home instead. Rule 25 also holds a rise at `home` to a mounted class, and to no other.

### Difficulty (Phase 5, Slice 6)

([phase5-plan.md](long-defeat/phase5-plan.md) D64.) The menu now asks fortress, then difficulty, then class. There are two difficulties, `normal` and `hard`. Normal plays exactly as before. Hard changes three things, all read from `waves.json` `rules.hard` (`factor` 1.25, `affixWavesEarlier` 2; a bad value keeps its default with one warning):

- **The wave count** is `min(1000, round(normal count * factor))`: the normal count after its own `maxCount` cap, rounded once, half away from zero. Waves 1 to 5 send 138, 150, 150, 156 and 163 instead of 110, 120, 120, 125 and 130. The cap of 300 becomes 375: from wave 20 on, hard sends 375 a wave where normal sends 300. The plan text said the count stays inside `maxCount`; with that cap kept, hard would equal normal from wave 20.
- **The growth of health and damage** per wave is multiplied by the factor (0.05 to 0.0625 and 0.03 to 0.0375), so wave 13 takes 1.1875 and 1.1125 where normal takes 1.15 and 1.09, and wave 20 takes 1.625 and 1.375 against 1.5 and 1.3. `maxFactor` and `tierEveryWaves` do not change, and the authored waves keep factor 1.
- **The affix schedule** starts 2 waves earlier: the stages at waves 5, 10 and 15 begin at 3, 8 and 13, and never before wave 1. The roll of a wave is the same as at normal.

`LongDefeatConfigCatalog.BuildPlan` is the one place that applies it: for a hard run it hands the plan `WavePlan.Harder(factor)` and `AffixPlan.Earlier(waves)`, and for a normal run it hands the fortress's own plan object. Both fortresses share the numbers. **The keep minimum rises with it.** `keepMinAttackers` is held above the straggler share (a tenth) of the smallest authored wave, so that a straggler group can never take the keep. Wave 1 sends 138 on hard, so a hard run's rules carry 14 at both fortresses where normal carries 12 (`WavePlan.SmallestAuthoredCount`, applied in `BuildPlan`). The wrapper does not replay the keep minimum.

**What changes for a normal run.** Besides the new report field, the `balance` hash changes once, because `waves.json` gained `rules.hard`, so every leaderboard board opens anew. The unattended plan's `Describe()` log line also gains ` difficulty=normal`. Nothing a normal run plays changes.

Hard pays about a quarter more bounty a wave, because more attackers die; the balance pass (Slice 10) may move that. Story Missions use `WavePlan` and `RunOptions` too and read the default, normal.

**Where it shows.** `RunOptions.Difficulty` is the option. The setup prompt shows each difficulty row with its own best run, through the same "best run" text as the fortress row. A fortress with no class starts as soon as the difficulty is picked, and Cancel at the difficulty starts nothing. The best run of a hard run is stored under `<fortress>:hard`; normal keeps the bare fortress id, so a stored file stays as it was. The report has `difficulty` (`normal` or `hard`) right after `class`, with no schema bump: a report without it reads as normal. `taom.ld_start <fortress> [waves] [class] [normal|hard]` takes the difficulty as the last word, and a hard start answers "Starting The Long Defeat at helms (hard), ...". A class whose id is `normal` or `hard` would be read as the difficulty; no shipped class has such an id. The autorun arm key is `difficulty`; an unknown value logs one warning naming it and plays normal. The co-op payload is version 2: a difficulty byte follows `lordFalls`, and a version 1 payload is refused.

**The wrapper.** `tools/run_long_defeat.py --difficulty hard` arms the key and holds the report to it (a report of an older build reads as normal, so a run armed with none must report normal). `wave_problem` replays leaderboard rule 5 at the report's difficulty: each row's kills plus felled is the count above and its two factors are the growth above. A row's shortfall (count minus kills plus felled) may not be negative, and the shortfalls together may not exceed the report's `fled`; both factors are checked on every row, also when attackers fled. A hard report must carry every field in every row and name a fortress the roster file knows. `affix_problem` replays the shifted schedule for a hard report. The numbers are pinned by `WavePlanTests`, `AffixPlanTests`, `LongDefeatShippedConfigTests.BuildPlan_Hard_ScalesTheShippedWavesAndSchedule` and `DifficultyTests` in `tools/tests/test_run_long_defeat.py`.

**Not played yet.** Both prompts, a hard run's counts in the game and the hard best-run row are owed an in-game check. The proof runs are `--difficulty hard --waves 5 --seed 7` at both fortresses (138, 150, 150, 156 and 163 attackers) and a `--deep` run on hard.

## The opening split (Mike, 2026-11-12, #1128)

Mike asked for the defenders to start each wave in four groups: the infantry split between the wall and the gate, and the archers between the lower wall, where the siege towers come, and the high walls. A fortress row turns it on with a `split` block in `fortresses.json`, `{"wallFoot": 0.7, "lowArchers": 0.7}`: the share of the infantry that goes to the wall and the share of the archers that goes to the lower wall, each from 0.05 to 0.95. Helm's Deep ships 70/30 for both (Mike's call). A row with no block plays as before, and a bad block is one warning and no split.

**Why vanilla needs help.** Two unattended runs at Helm's Deep on 2026-11-12 showed that the siege tactic already spreads the archers over three archer positions, but keeps the infantry in one body: the boot line read `formations=0:21,1:50`, and after the tactic ran `0:125,1:27,2:17,3:16`. Before any lane is active, `TacticDefendCastle` defends only the lanes that hold a gate (TacticDefendCastle.cs:1005-1016) and consolidates its melee formations to that lane count, so every soldier on foot goes to the gate.

**How it works.** In each calm (the preparation and every intermission), once the garrison or a pack has finished its muster, `LongDefeatBattlefieldAdapter.SplitDefenders` puts every standing defender on foot, except the player, a mounted soldier and a post archer, into four formations: the wall group (formation 5), the gate group (0), the lower archers (1) and the high archers (3). Each group gets the soldiers nearest its place. The places come from the scene's own siege objects, never from recorded points:

- **Gate:** the first visible gate's middle position.
- **Wall:** the wall segments on the lanes that are not the gate's lane. With two or more, the line spans the two farthest apart (at most 60 m); with one, that segment. A midpoint with no navmesh falls back to the nearest segment.
- **Archers:** the defender archer positions below and at or above the wall line (the wall's height less 3 m), each the one nearest the wall place.

Each group is taken off AI control and ordered with the shapes of vanilla's ready order: a move, a facing and a line of the place's width for the infantry (BehaviorDefendCastleKeyPosition), and a move with Scatter, fire at will and a wide form for the archers (BehaviorShootFromCastleWalls). Vanilla also holds a wait position before contact and forms a shield wall later; the split does neither. Scatter joins every defender archer point within 40 m of the order position on each ground axis, at any height (the `strategic_archer_point` prefab sets `_distanceToCheck` 40 and `_ignoreHeight`). A formation off AI control keeps its units through the tactic's consolidation, though it can gain some. A place with no navmesh, or outside the boundary, is no place. The groups stand until the director hands them back, or until the engine does: the stalemate charge (`OrderCharge`), a new body for the lord (`AdoptMain`) and the fall of the lord's body (`Mission.OnAgentRemoved` calls `Team.DelegateCommandToAI`) each give every formation to the AI. After a new body or the lord's fall, after a pack musters during a hold, and after an upgrade that replaced a soldier (a fade can empty a group, and `Formation.RemoveUnit` hands an emptied formation to the AI), the director splits again on the next tick. A split again keeps every soldier the hold placed in the same group, and the others (a pack's soldiers) fill the group below its share, nearest its place first.

**The release.** The director reads the siege AI's count of attackers at the walls (`SiegeQuerySystem`'s left, middle and right close attacker counts) on every tick of the wave. An attacker counts when it stands within 15 m of a side's defender origin and 3 m of its height, or in the side's region on an inside navmesh face (a face id that ends in 1, a docked siege tower's floors among them); the engine refreshes the counts every 5 s. With no `right_defender_origin` tag in the scene, as at Helm's Deep, the engine takes the right origin from the middle lane, so the right count holds the gate and the middle count only attackers on inside faces; the release does not care which count rises. A fresh split drops that cache (`SiegeQuerySystem.Expire`) before it reads the hold's counts: at a clear the cache can still hold the last wave's counts, which as a baseline hid the next wave's contact and, after a horn within 5 s, released the hold at once. At the first count that rises above its value at the hold, it hands each group back to the AI and the tactic defends from where they stand. The first build read each lane's defense level (`SiegeLane.GetDefenseState`) instead, and the first game run (2026-11-13) showed it is no contact: `SiegeLane.DetermineLaneState` raises a closed lane from empty to token as soon as an attacker formation takes one of its siege engines (`SiegeWeapon.IsUsed`), before the engine moves, and from token to full when 30 attackers are also in the side's region; a ladder, or an engine that finished its action, also lifts a closed lane to token, or to full with those 30 attackers, so both waves released within a second of their start, and the gate group, 102 m of path from the keep yard, was still 55 m to 64 m from the gate. A group whose movement order the player changed stays with the player; a facing, firing or arrangement order alone does not keep it. A split again inside a hold keeps the hold's counts, so a count that rose before it still counts. A wave that clears with no contact, or a run that ends during a hold, also hands the groups back; the next calm splits afresh.

**The check.** `taom.long-defeat.split` is written at the release, key `w<N>`. It passes when each group holds soldiers and its median ground distance to its place is within 25 m for the infantry and 40 m for the archers. A skip names its reason: `short-hold` (under 20 s), `engine-took` (no group was still off AI control), `charge`, `no-contact`, `run-ended` or `no-groups`. A scene that gives no place for a pair fails with `reason=no-places`; the other pair is still split and held. `tools/run_long_defeat.py` owes one split pass for a fortress row with a `split` block once the log shows a split was made and a wave cleared; a skip does not pay it. The `[LongDefeat][Split]` lines give each group's size and place at each split, and its median and the count on the walls at each wave start.

**In game (2026-11-13, trunk 4cafca4ab plus the close-attacker release).** Both waves passed: contact came 219 s into the hold in wave 1 and 47 s into wave 2; every group stood at its place (wall 4.6 m and 4.7 m, gate 2.8 m and 2.6 m, lower archers 22.8 m and 25.4 m, high archers 21.1 m and 20.4 m) with `kept=0`; all 87 and 90 of the wall group and all high archers stood at or above the wall line. The wall group reached its place (the log does not say whether that place was the wall midpoint or the nearest wall segment), and the held Scatter archers climb to the wall points. The run itself failed on two older defects: a soldier off the navmesh at the garrison muster (#1142), and a field-care purchase the check could not judge (#1143). The check judges the ground distance only: the `_high` counts are logged, not judged, so whether a pass should also need the high archers and the wall group on the walls is still Mike's call. The tests are `DefenderSplitTests`, `LongDefeatSplitReaderTests`, `LongDefeatSplitChecksTests`, `LongDefeatDirectorSplitTests` and the split cases of `test_run_long_defeat.py`.

## Engines come back each wave (#1160)

Players reported that a siege tower or a ram they destroyed never came back, so the later waves had no engine on that side. The boot deploys the engines once (`DeployEngines`), and nothing undid a destroy. The destroy path (`DestructableComponent.OnHit` calls `Mission.OnObjectDisabled`) disables the machine and turns its faces off: `UsableMachine.Disable` stops its users, removes its detachment, turns its standing points off and takes it off the active mission objects. Each tick, `SiegeLane.RefreshLane` then drops the disabled weapon from its lane.

**How it works.** At each wave start, before the Hammer writes the engines' hit points and before any attacker spawns, `LongDefeatBattlefieldAdapter.RestoreEngines` takes each ram and tower that the boot deployed and that is destroyed, and brings it back in six steps:

1. `DestructableComponent.Reset()` shows the intact entity again and sets the hit points to the maximum the Hammer last wrote.
2. `SetAbilityOfFaces(true)` on the destructible undoes the destroy's `SetAbilityOfFaces(false)`. Vanilla's ram and tower prefabs give the destructible no navmesh (`NavMeshPrefabName` is empty), so both calls do nothing there; the machine's own faces come back in step 3, through `SetEnabled`.
3. The type's own mission reset, `SiegeTower.OnMissionReset` or `BatteringRam.OnMissionReset`. Both are `protected internal`, so the adapter calls them by reflection, and the reflection-site gate pins both. `UsableMachine.OnMissionReset` enables the machine, which puts it back on the active list and turns its faces on (`MissionObject.SetEnabled`), and resets each component: the movement component resets its path tracker and moves the engine to the start of its path. The tower's reset also closes its gate and turns its gate navmesh off.
4. A tower whose reset ran is set back to its boot state where the reset leaves it different. Vanilla runs this reset only after it removes every agent (`Mission.ResetMissionObjects`), so it never meets these two. The reset's `SetEnabled` calls the tower's `SetAbilityOfFaces(true)` override, which turns on every ladder queue and its face (SiegeTower.cs:514-535), while the boot keeps them off until the tower arrives (:759-763, :211-215): the restore turns each one off again. A tower that reached the wall before it fell keeps its upper wait point (`ActiveWaitStandingPoint = WaitStandingPoints[1]`, :208), which nothing sets back: the restore sets the lower one, `WaitStandingPoints[0]`, as the boot does (UsableMachine.cs:400). Both members are private or protected, so the adapter reads them by reflection, and the reflection-site gate pins them.
5. The engine goes back into the siege lane of its own side (`TeamAISiegeComponent.SiegeLanes`, matched on `WeaponSide`). The first formation that joins it makes its detachment again (`Formation.JoinDetachment`, Formation.cs:2517-2521).
6. Once every engine is back, each attacker formation's `BehaviorUseSiegeMachines` builds its engine list again through the public `OnValidBehaviorSideChanged`. The behavior builds that list once, when the formation gets its first soldier, and drops a destroyed engine on its next occasional tick; the formations last across waves, so without this a formation that was pushing an engine when a player destroyed it in the middle of a wave would not follow it again. The log line is `[LongDefeat][Engines] N attacker formation(s) listed their siege engines again`.

The tower's reset also shows the breakable wall it targets as broken, which no fall of a tower does, so the restore reads both states of every breakable wall first and writes them back after. A ram whose gate is already down comes back too, but has nothing to strike until a repair closes the gate.

**Known limits.**

- A tower's fall shows every scene entity tagged `barrier` (`SiegeTower.OnDestroyed`), and the reset does not hide them; they hide again when a tower opens its gate at the wall (`GateState.Open`, SiegeTower.cs:1007).
- An engine's arrival turns off its `NavMeshIdToDisableOnDestination` face (`SetDestinationNavMeshIdState`, SiegeTower.cs:199, BatteringRam.cs:165), and the reset writes the arrival flag directly, so it does not turn that face on again. Every Native ram and tower prefab sets the id to -1 and the Helm's Deep scene sets none, so nothing changes today. A fortress whose engines set one needs that face turned on in the restore.
- The reset carries the engine from the wall to the start of its path in one `SetGlobalFrame` call while soldiers are alive nearby. What the native side does with a jump that long is UNVERIFIED (not decompiled), so the in-game check watches for it.
- A story mission hosts the same director in a campaign siege (`StoryMissionLauncher`). Every story row authors one wave, so the restore can run only at wave 1's start, where nothing is destroyed yet. It becomes live behaviour once a story row has a second wave.

**The checks.** Both use the key `w<N>` of the wave whose start restored an engine.

- `taom.long-defeat.engine-restore` is written at that wave start, only when an engine came back or the restore met a problem. Each engine reads `<kind><index>=ok`, or the faults it still has, joined by commas: `destroyed`, `disabled`, `hp` (below its maximum), `moved` (1 m or more along its path), `lane`, and for a tower `ladders` (a ladder queue still on) or `wait` (its wait point is not the lower one). A reset that was not found or that threw adds `problem=` and fails the check. The `moved` fault reads the path tracker, which the reset zeroes wherever the entity really stands, so only the in-game check proves where the engine stands.
- `taom.long-defeat.engine-use` is written at that wave's clear, or at the end of a run inside the wave. Each engine reads `used` (5 m or more along its path), `arrived`, `fell` (destroyed again after 5 m), each with its metres, or `idle`, or `gone`. Two words count for nothing: `fell-early` (destroyed again before 5 m, which shows nothing about the attackers' use) and `done` (a ram whose gate was already down at the restore). A wave of only those is a skip with `reason=unjudged`. When the run ends inside the wave, an idle engine makes a skip with `reason=run-ended`, not a fail. The manifest reads a session whose only `engine-use` lines are skips as NOT REACHED.

**The test option.** The bot never attacks an engine, so an unattended run exercises the restore with `--break-engines N` (arm key `break_engines`, `RunOptions.BreakEnginesAtClear`, echoed as the report's `breakEngines`). At clear N, and only when a wave follows it, the director destroys every standing ram and tower with one hit from the scene's ram, as `TryBreak` breaks the hidden gate. The hit is owned by the player's body or a standing defender, the owner `Fell` picks: a tower's fall kills whoever stands on it, and vanilla's morale model reads the killer's formation with no null test, so a hit with no owner would end in a null dereference. With no defender standing, nothing is broken. The wrapper refuses an N at or past `--waves`, and once the report cleared a wave past N (a lost run included) it owes a pass of each check that names the wave after the break, `w=<startWave + N>`; a skip, or a pass of another wave, does not pay it. The proof run is `--waves 2 --garrison-scale 1.3 --start-gold 5000 --break-engines 1`: in wave 1 the ram breaks the gate, and the start gold makes the bot repair it, so the ram has a gate to strike again in wave 2. The `[LongDefeat][Engines]` lines give each restore, the relist, each use and the break.

The break comes at a clear, when no attacker formation has soldiers, and `Team.Tick` ticks only formations that have them (Team.cs:616-621). So the unattended run never drops an engine from a formation's own list, and it does not cover a player's destroy in the middle of a wave, which does (step 6). That case needs a played check (`tools/ingame_checks/1160.toml`, `[[human]]`). Not played.

The tests are `LongDefeatEngineChecksTests`, `LongDefeatDirectorEngineTests`, the `break_engines` cases of `LongDefeatAutorunPlanTests`, `Build_TheBreakEnginesClearIsEchoed_AndNoneIsNull`, `TheEngineRestoreMembers_StillResolve` in `LongDefeatBindingTests`, the five reflection-site rows, the restore's source pins in `LongDefeatFortWiringTests`, and `BreakEnginesTests` and `EngineManifestTests` in `test_run_long_defeat.py`.

## Upgrade the soldiers you have (#1161)

Players asked to upgrade the soldiers they already have in the shop, one step at a time up their troop line. The Long Defeat troops are `fow_*` copies, and `fords_troops.xml` gives them no upgrade targets, so the steps come from data: each shop in `shop.json` lists `upgrades` rows, `{from, to, price, name}`, with the price for one soldier. The Rohan shop follows TAOM's own tree in `troops/troops_rohan.xml`, which loads in a Custom Game too, so a line climbs past the `fow_*` copies into the campaign troops (`LongDefeatShippedConfigTests` pins each step to that tree, one level up, in the defender culture, from a troop the run can have):

| Line | Steps, with the price for one soldier |
|---|---|
| Westfold | Militia to Axemen (15); Axemen to Veteran Axemen (25) or to Heavy Axemen (25); Veteran Axemen to Helmingas Axemen (40); Heavy Axemen to Helmingas Heavy Axemen (40) |
| Eastfold | Yeomen to Bowmen (15); Bowmen to Veteran Bowmen (25) |
| Edoras | King's Knights to the King's Royal Guard (60); Royal Guard to the Riders of Rohan (90) |

The prices are first numbers; play decides them. Also open for play: whether a buy takes every soldier of a troop that the gold pays for (as now) or one pack at a time.

Step 8 is a sidegrade, kept on purpose (2026-11-13 review). The King's Royal Guard has 15 less Polearm and 5 less One Handed than the King's Knight, but 5 more levels, 20 more Athletics and better head and arm armour. Steps 8 and 9 stay apart because each step must be one level up the campaign tree (`LongDefeatShippedConfigTests`). To undo it, merge steps 8 and 9 and relax that test to "a path of the campaign tree".

**How it works.**

1. `UpgradesReader` keeps each step under the id `from>to`. A bad row, a repeated step or a step that would close a loop is skipped with one warning, so every line ends.
2. Between waves the director reads the standing defenders by troop (`TickStanding`): on the first tick, every 0.5 s, and after a spawn. An order moves its own counts from the old troop to the new one. A wave forgets that read, because soldiers die in it.
3. A buy (`SurvivalRun.TryUpgrade`) takes every standing soldier of the step's troop that no order has taken yet and that the gold pays for, and spends the gold at once. An upgrade takes no boon price factor. The order is booked for the wave after the calm in which it was bought. No upgrade is sold while the garrison musters (#1388): `SurvivalRun.Mustering` is true until the last muster batch has spawned, `TryUpgrade` returns `NotOpen` and the shop lists no upgrade row, so a click in the first seconds cannot take only the first batch of 20. With the shipped muster (batches of 20, 4 s apart) the rows open about 16 s into the preparation at the default garrison scale and about 24 s at scale 1.3.
4. An open order holds the next wave for a tick, as a fortification effect does: a buy on the last tick of a calm, or just before the horn, runs before the wave's first batch. The order reads the new troop's health factor when it goes out, not when it was bought, so a boon picked after the buy counts.
5. On the next tick, `LongDefeatBattlefieldAdapter.ReplaceDefenders` replaces each soldier: it reads his share of health, fades him out at once with his mount left in place (`FadeOut(true, false)`; only soldiers on foot are chosen), spawns the new troop on foot at his place, facing and formation, scales the new soldier's health and writes the share back. The native fade sets the state to Routed and reports the removal before it returns (`python tools/native_decompile.py --engine-method IMBAgent.FadeOut`); the run and the morale logic count a fade as no loss. A new soldier counts as replaced only when he is active, and as read back only when he stands within 1 m of the old place. Mounted soldiers, runners, heroes, engine crews, tower posts, the player and the lord are never upgraded. A post archer is excluded by the `_postedByAgent` registry, wherever he stands; the filter does not test the posts formation index (#1401), because in a cavalry run the tactic's own split puts 21 ordinary skirmishers into index 4 (run 20261116-024002: `ordered=65 found=44`, then eight `none-found` skips). A spawn that throws ends the run on a fault, as a pack spawn does.
6. An upgrade that replaced a soldier tells the split that the engine took its groups (`NoteEngineTookSplit`): `Formation.RemoveUnit` hands an emptied formation to the AI (Formation.cs:2376-2379), so a held split is made again.
7. `CompleteUpgrade(order, replaced, found)` books one `upgrade` purchase with its `count`, the soldiers replaced, and pays back the gold of the rest. It books the old troop's standing count as `found - replaced`, so soldiers the field could not reach are not sold again (#1388).

The shop lists the steps under the packs, under "Upgrade your soldiers": one row for each step whose troop has a soldier standing, with how many stand and how many the gold pays for. The bot buys the first step the gold reaches, after its packs and fortifications. The run report adds the `upgrades` sink and the `upgrade` purchase kind with its `count`. The run judge checks a purchase's base against its `shop.json` step and its price against base times count. It owes each purchase its own pass line, matched by wave, step and count, also in a lost run. The check key is `<mission>u<N>`, the mission's Nth upgrade order. The review and its fixes: [rca-ld-shop-upgrades-2026-11-13.md](../reviews/rca-ld-shop-upgrades-2026-11-13.md). The English text is registered; the language rows wait for the project lead's pass (backlog #1129). Not played.

**What a click says (#1388).** A row reads "Upgrades N of M for G gold" (key `TAOM_LD_Hud_UpgradeDeal`): N is the soldiers the gold pays for, M the soldiers of that troop that stand, G is N times the price each; the price line "{PRICE} gold each" stays. Before this change the row read "M standing, gold for N" and never said the total. A buy sets a notice on the run's view (`UpgradeNotice`, with a serial), and the HUD says each serial once: "{STEP}: {COUNT} upgraded, {LEFT} left." (`TAOM_LD_Notice_UpgradeBought`). A refund, when an order replaced fewer soldiers than it bought, says "{STEP}: {COUNT} could not be upgraded, {GOLD} gold paid back." (`TAOM_LD_Notice_UpgradeRefund`). The notice names the step label, not the troops, because the troop names carry a faction tag and are singular. A row the gold pays nothing for is disabled and keeps the older line "M standing, gold for 0" (`TAOM_LD_Hud_UpgradeDetail`), so no key is retired. The three new keys wait for the language pass. The client check `taom.long-defeat.upgrade-notice` is written once per notice the HUD said. `tools/ingame_checks/1388.toml` judges the notice (the run keeps one notice slot and the HUD reads it every 0.25 s, so the row proves at least one Bought notice in a run, not one per buy) and the order of the buys against the last muster batch (`upgrade-after-muster`; `upgrade-bought-after-muster` needs a buy between the last batch and the first wave); `tools/ingame_checks/1401.toml` judges that a cavalry run's skirmisher order finds and replaces all 65 (50 archers at garrison scale 1.3; the row is bound to that scale). The row text and the refund text are proven by unit tests and human rows, not by a log, because the bot never opens the panel and a normal run no longer makes a short order; a refund row that stays unreached by design would keep the issue from ever reading PASS.

## Heroes at the shop (#1337)

The shop sells Aragorn, Legolas and Gimli (#1325). Each is cheap, lasts until he falls, and is for sale again after that.

**The characters.** `characters/taom_mission_heroes.xml` holds `taom_hero_aragorn`, `taom_hero_legolas` and `taom_hero_gimli`, loaded for Campaign, CampaignStoryMode and CustomGame (#1335; the campaign for #1366, below). In a Custom Game `is_hero` makes the engine refuse a take-over (`Mission.CanTakeControlOfAgent`) and makes the shop's upgrade filter skip them; in a campaign `IsHero` reads false, so a take-over is possible ([hero-abilities.md](hero-abilities.md), Traps); `is_obsolete` keeps them out of the Custom Battle pickers. None has a horse: the engine reads a formation as mounted once a tenth or more of it rides (`Formation.CalculateHasSignificantNumberOfMounted`), and one rider would be a third of the heroes' group. Aragorn carries his sword and no bow, so that the AI keeps him in the melee line. Legolas has his bow in the first slot, with two quivers and his sword. The engine wields the first weapon slot at the spawn (`Mission.SpawnTroopWithAgentBuildData` runs `agent.WieldInitialWeapons`), so the adapter draws no weapon. Gimli carries `sm_dwarf_erebor_axe_2h_c`, "[Erebor] Two-Handed Axe V" (#1373). Against Dain's axe, his kit until #1373, the swing damage rises from 88 to 140 (`tools/melee_catalogue.py`) and the swing is slower (65 to 58). The Erebor blade has none of the flags `CanCrushThrough`, `CanKnockDown`, `CanDismount`, `CanHook` and `CanPenetrateShield`, which Dain's blade has (`LOTRLOME_crafting_pieces.xml`: `sm_dwarf_erebor_axe_blade_2h_c` lists `BonusAgainstShield`, `CanBePickedUpFromCorpse` and `Civilian`). The trade: with the Erebor axe Gimli hits harder (swing 140 against 88) and slower. In the Long Defeat (the Custom Battle damage model, which reads the weapon's `CanCrushThrough` flag for an overhead swing, `CustomAgentApplyDamageModel.cs:123`) he loses the overhead crush-through Dain's axe had. In a campaign mission (the story mission, the campaign companion) the engine's rule never reads that flag (`SandboxAgentApplyDamageModel.DecideCrushedThrough`, lines 470-487 of the `taom-src` source), so nothing is lost there. TAOM's own crush-through rule (`CrushThroughService`) is asked before the engine's rule in both damage models and reads no weapon flag, so the axe changes nothing in it. The other flags of Dain's blade (`CanKnockDown`, `CanDismount`, `CanHook`, `CanPenetrateShield`) are gone in every mode. An option the maintainer can take with one key is `"forceCrushThrough": true` in the `selfEffects` of `gimli_baruk_khazad`, which makes every swing of the 12 s rage break a block unless the defender's own ability holds against a crush (`RaceAbilityService.CrushVerdict`; a new buff, not a replacement). His signature strike rings are a fraction of the hit's damage, so they rise with the swing. The campaign companion `named_companion_gimli` carries the axe in a new campaign only: a Hero's equipment is saved (`Hero.cs:212-213`) and the companions are equipped once at a new game. The three community dwarves keep Dain's axe. `python tools/validate_moduledata.py` warns `MELEE_BLOW_CEILING` for this axe (swing 140 above 123.2, the tier limit of the troops that carry it), on trunk too because Iron Pass troops carry the axe. The blade is not in `hero_blades`, as troop items share it. The ladder's repair (`tools/restat_melee_blades.py`) does not change it today: the blade backs a one-handed and a two-handed axe, and the tool's report lists it among 7 such blades that it does not price by tier, so the swing stays 140 and the warning stays until those blades are cloned. Aragorn's `strider_sword` has two usages, a one-handed bastard sword mode whose usage set needs a shield (`requires_shield` in Native's `item_usage_sets.xml`) and a two-handed mode. He carries no shield and should fight two-handed; the engine changes the usage index on its own (`Agent.OnWeaponUsageIndexChange` writes `Equipment.SetUsageIndexOfSlot`), so the spawn does not prove the mode, and the hunters line below names it. Legolas keeps `wm_mirkwood_bow_a01`, the best of the Armory's four Mirkwood bows: damage 86 (`wm_mirkwood_bow_a04` has the same), with the highest accuracy (98) and missile speed (99) of the four.

**The data.** A shop in `shop.json` lists its heroes: `id`, `troop`, `price` (1 to 100,000), an optional `healthFactor` (1 to 10; 1 when absent), `name` and `text`. `HeroesReader` skips a bad row with one warning; an id must be a set id (lowercase letters, digits and underscores), troops are compared without case, and a repeated id or troop keeps the first. The Rohan shop sells Aragorn for 350 gold and Legolas and Gimli for 300 each, at eight times a soldier's health (800; #1438 raised both from 300 gold, 250 and three times, after the balance tally). `ShippedMissionHeroesTests` holds the rule "no hero costs more than the dearest pack"; the numbers are the maintainer's to tune.

**The rules** (`SurvivalRun.Heroes.cs`):

1. A hero is sold between waves only, and one of each at a time: a hero who is bought, or stands on the field, answers `Alive`.
2. He takes one place under the garrison cap, from the buy until he leaves the field.
3. His price takes the boons' price factor, as a pack's does, and is spent at the buy. The purchase is booked as kind `hero` in the sink `heroes`.
4. He spawns on the next tick. If the field cannot spawn him, the gold is paid back and the purchase is dropped, so the purchases still sum to the sink.
5. When he leaves the field he is for sale again at once. A fall is also a defender's loss; a rout is not.
6. No boon draws for a hero: he belongs to no defender group (`RunPlanTroops.DefenderTroopIds` leaves him out, and the launch's existence check, `AllTroopIds`, includes him). A health boon never rescales him: the effects adapter skips `IsHero` bodies, so his health is always his shop factor. The stat and damage boons of his arm reach him at hit time as they reach any defender.

**The field** (`LongDefeatBattlefieldAdapter.Heroes.cs`, `LongDefeatDirector.Heroes.cs`). The director spawns each bought hero after the lord and the batches of that tick, at the plan's home place: the recorded foot muster, else the keep. With no place it refuses, because the engine would lay the body out from a deployment plan nobody built for his formation. Heroes bought in one calm spawn on the same point: three game runs spawned the three on one point without a problem, side offsets would get no navmesh test, and the Move order below walks the group away at once. The adapter puts him in the heroes' own formation, index 7 (`HeroGroup.FormationIndex`), which the mode uses for nothing else, so the order bar shows the three as group 8. Nothing on screen names it "The Three Hunters": that is this document's name for group 8. The formation is positioned at the place before its first spawn, as the mounted lord's is. The adapter scales the health limit by the shop's factor and holds the body by reference. A removal of a held body is reported as `LdRemovalKind.Hero` with the shop id. The opening split leaves a held hero out of its groups.

**The standing order at the wall.** When a spawn finds the formation AI controlled (its first use, or after a hand-back), the adapter takes it off AI control and orders a Move to the heroes' place, facing the place's direction, in a line of the wide form that fires at will. The place is one wall lane's own place, the lane nearest the heroes' spawn place (`WallLanes`, `NearestLane`): there the lane's defenders stand and the attackers come over the wall. With no wall lane it is the outer gate (`GatePlace`), else the hero's own spawn place when it has a navmesh inside the boundary; it is found once per mission. With no place the group gets Stop. The order sets the arrangement, the firing and the form each time, because the formation keeps what a siege behaviour gave it while the AI held it (a shield wall and a lane's width), and it sets no custom width, because a lane's width is for a line of forty. It sets no side: the side steers only the AI's behaviours, and the tactic names a lane's defender by it. A Move is always applicable, so it lasts through a calm. The first design ordered a charge, which was wrong for two reasons. Heroes are sold between waves only, and a charge with no enemy standing is not applicable, so `Formation.Tick` replaces it with its substitute, Stop, within a frame (`MovementOrder.IsApplicable`, `MovementOrder.GetSubstituteOrder`). And a charge that stays live inside the walls sends the group to a gate to get out (`MovementOrder.TickOccasionally`). Run 20261115-195135 showed the first: Aragorn and Gimli made no kill in three waves, and Legolas made 17, shooting from where he stood. The second design put the place at the middle between the wall's lanes, where the opening split's wall line stands; the review moved it to a lane, because a melee soldier does not seek an enemy 20 m away. The heroes hold that one lane; the player sends them elsewhere with order key 8. Legolas stands with the other two at the wall lane (#1438). A first design held him on the high archer place nearest the outer gate, which at Helm's Deep is the only high archer place (155.5, 206.2, 29.7); from there the engine gave him no target, and he shot 0 arrows in five waves (runs 20261117-190319, 20261117-195226, 20261117-201252), while the same hold at the wall lane shot 88 arrows in two waves (20261117-202809). In the stalemate charge every defender charges, and so do the heroes (attackers stand then, so the charge stays applicable); when the tactic comes back they take the wall order again before its first tick.

**The hold and the repair.** With the player as general, a formation off AI control is not AI-owned, so the siege tactic's transfers out of it are refused. The first build asked for the engine's flag instead (`SetControlledByAI(true, enforceNotSplittableByAI: true)`), but the engine ignores that call on a formation that is already AI controlled, and `AdoptMain` hands every formation to the AI. Run 20261115-181243 showed the result: the three had left formation 7 (`in_group=0` at every wave clear; the review traced them to the foot formation), and they had 3 of the run's 347 kills. A formation off AI control can still gain soldiers: consolidation ranks it first as a target, the castle defence moves units into it, and an empty formation 7 is a split target. Three hand-backs make it AI controlled again: the lord's fall (the engine's own: `Mission.OnAgentRemoved` calls `Team.DelegateCommandToAI`), a new body for the lord (TAOM's `AdoptMain`) and the stalemate charge (TAOM's `OrderCharge`). So the director calls `HoldHunters` each tick while a hero it spawned stands. When the group is off AI control, holds exactly the live held heroes and each of them is in it, the hold only reads. Otherwise it repairs the group: every soldier who is not a live held hero goes out (a ranged soldier to the archers' formation, any other to the foot formation), every live hero outside it is put back (a routing hero is left alone, as the split leaves a routing soldier), and a group the AI holds again gets the wall order. A spawn runs the same steps: the strangers go out before the spawn, and the heroes go back and the order is given after it. An order the player gives to group 8 stands until a hand-back; after one, the group gets the wall order again. The player's own "delegate to AI" for group 8 is undone on the next tick, because the siege tactic would merge the three into the foot formation, as in run 20261115-181243. The director logs every regain (`[Hero] the heroes' group was taken back from the AI`) and the first five membership repairs (`[Hero] the heroes' group repaired:`); later repairs show only in the running totals of the `hunters` line. The held bodies are a copy-on-write array: the spawn, the removal (treated as callable from any thread, the repo's rule) and the clear replace it under a lock, and the readers take it without one, so a tick's hold allocates nothing. Run 20261115-195135 proved that the group holds (`in_group=3 units=3 held=1` in three waves). Run 20261115-210056, on commit a5f607f41, proved the wall order. At each wave clear the standing heroes were in the group and near the lane (`near=3`, then 2, then 1, each equal to `standing`). Legolas had 24 kills at the second clear and Gimli 20 at the third. Aragorn fell twice and Legolas once, each with a `hero-fall` line, and Aragorn was bought again in the calm between, with a second `hero` line. The one hand-back, at the lord's fall, was retaken with nobody moved (`retaken=1 moved_out=0 moved_back=0`). Aragorn made no kill before his first fall: at three times a soldier's health a hero at a ladder's top can die within a wave, which is a number for the maintainer and for the abilities phase.

**The bot, the report and the judge.** The shop bot buys the first hero that is for sale, that the gold reaches and that the cap has room for, once no pack fits and no fortification is wanted, and before any upgrade. So a default run spends its first gold on soldiers as before, and a run with gold to spare fields the heroes. The report's `gold.spentOn` has `heroes` and its purchases have kind `hero` with the hero's id. `tools/run_long_defeat.py` replays a hero purchase at the shop's price through the price factor, and owes a `hero` pass line for each one. A run that cleared a wave a hero was bought before also owes one `hunters` line, a pass or a skip (`owed_hunters_lines`); it reads the cleared wave numbers from the report's wave rows, because `wavesCleared` counts clears from the start wave.

**The checks.** `taom.long-defeat.hero` (key `<mission>h<N>`) is written on the tick after a buy: it passes when the body is a hero to the engine (a Custom Game body, `is_hero=1 campaign=0`) or a campaign character with no Hero behind it (`is_hero=0 campaign=1`, #1366; the line reads `campaign=` right after `is_hero=`), has no mount, stands in formation 7, has its health limit scaled by the shop's factor, the formation is off AI control after the spawn (`held=1`) and it holds no soldier who is not a held hero (`strangers=0`). It names the formation's movement order (`order=`, `Move` after the wall order) and the item in his hand. `taom.long-defeat.hero-fall` is written when a held hero leaves the field, with `cause=killed` or `cause=fled`. `taom.long-defeat.hunters` (key `<mission>hw<wave>`) is written at each wave clear of a mission that spawned a hero. It reads `standing`, `in_group` (the standing heroes in formation 7), `units` (the soldiers formation 7 holds), `held` (1 when it is off AI control), `order` (its movement order), `own` (1 when that order is a Move within 2 m of the heroes' place, the field's own order), `settled` (the whole seconds since the field gave that order), `near` (the standing heroes within 20 m of the place on the ground and 4 m in height, so a hero at the foot of the wall does not count), the kills and health per hero, `weapons=<id>:<weapon class>,...` (#1373: the class of the weapon each standing hero holds in its current usage, read from `agent.WieldedWeapon.CurrentUsageItem`, `none` when nothing is wielded; for example `weapons=aragorn:TwoHandedSword,gimli:TwoHandedAxe,legolas:Bow`), and the director's running totals for the mission: `retaken` (regains), `moved_out` and `moved_back`. It passes only when `in_group` equals `standing`, `units` equals `in_group`, `held=1`, and, once the field's own order has stood 60 seconds (`own=1`, `settled` 60 or more), `near` equals `standing`. So in an unattended run, where nobody orders group 8, a hero who never reached the wall lane fails the line; a player's own order is never judged, and neither are heroes still on their way after a hand-back. With no place for the heroes (no wall lane, no gate, no usable spawn place) the order is Stop and `near` is never judged. The director runs the hold just before it reads, so a transfer in the frame of the clear is repaired first and shows in the totals. `kills` is the engine's `KillCount`, which also counts knock-outs; it and the totals are reported, never judged. `weapons` is information only and never changes the verdict. With no hero standing the line is skipped. Manifest: `tools/ingame_checks/1337.toml`, which accepts the line with and without `weapons=`. `tools/ingame_checks/1373.toml` pins Gimli's spawn line to `wielded=sm_dwarf_erebor_axe_2h_c` and gives each hero his own weapon row (a fallen hero is not in the list): `aragorn:TwoHandedSword` (a `aragorn:OneHandedSword` fails the row), `gimli:TwoHandedAxe` and `legolas:Bow`, for this mode and for the story mission.

**Free heroes in a story mission (#1366).** `RunPlan.FreeHeroes` lists heroes who stand from the first tick with no purchase: `SurvivalRun.Begin` queues each as pending (one place under the garrison cap), the director spawns them after the lord is adopted, and a fallen one is not for sale because `TryBuyHero` knows only the shop's heroes. The Long Defeat's own plan leaves the list empty. The story mission's `helms_deep_defend` fills it ([story-missions.md](story-missions.md), "The free heroes"). The log texts of a failed spawn and of a leave are worded for both a bought and a free hero. `SpawnHero` now passes the character's first battle set as the spawn kit (the engine fixes equipment only for `IsHero`); in a Custom Game that clones the set the engine already took, but no unattended Long Defeat run has been made since the change, so `python tools/run_long_defeat.py --waves 3 --garrison-scale 1.3 --start-gold 5000` is owed.

Aragorn's and Gimli's timed abilities and killing blows are built (#1359), and Legolas's ranged kit (#1361, Phase 5 of #1325): [hero-abilities.md](hero-abilities.md). His extra arrows are `AddCustomMissile` arrows like the Elven Volley's, but of their own item, so the volley's hit filter and posts counter never count them. **Not built yet.** The always-on strip with their health and kills. The fallback that puts Aragorn and Gimli in the foot formation and Legolas with the archers: it is built only if a run in the game shows that group 8 cannot be ordered or that the siege tactic merges it. The dev command `taom.ld_hero` of #1335: the shop bot buys the heroes in a run with `--start-gold`, and a person buys them at the shop, so no command is needed to field them. A post that moves with the fight (the heroes hold one lane today) belongs to the abilities phase. Unproven in game: the heroes' part in the stalemate charge and the membership repair. ## Co-op through a Coop session (#1280)

Players asked to defend a fortress together. With BannerlordCoop loaded, the main menu shows a second option, "The Long Defeat (co-op)", under the solo one. It is hidden on a dedicated server, without Coop, and when no fortress loads. One player hosts: the same setup questions as a solo run, then Coop starts a session with TAOM's run inside it. The others join by the host's address and port. TAOM ships no Coop code: it calls Coop's session API (Bannerlord-Coop-Team/BannerlordCoop#4691, draft PR #4694) through `TAOM.CoopCompat`, which Garrett agreed to on 2026-11-14.

**How it works.**

1. A host's setup becomes a payload: a version byte, the fortress id and every `RunOptions` field (`LongDefeatSessionPayload`, at most Coop's 8,192 bytes). Coop hands the same payload to every member. A member whose TAOM reads another payload version is refused with a notice; the payload carries no hash of the `long_defeat` data, so every member must install the same TAOM.
2. Each member opens the same mission from that payload, with Coop's session behaviours added to TAOM's own (`LongDefeatCoopMission.Compose`). Coop's spawn gate turns on when TAOM asks for those behaviours, before the mission opens.
3. Coop elects the host: the first member whose mission is ready. TAOM decides its role on Coop's host change, never on "I hosted", so the player who pressed Host can be a follower.
4. Until the election, nothing starts. With no host in 60 s, the run ends with the fault `NoHost`.
5. The host runs the whole director: the garrison, the waves, the shop and the HUD. A follower boots the scene and spawns only its own lord, on foot even with a mounted class. It has no HUD and no shop.
6. The speed stays at 1x, because a host at 4x and a follower at 1x play two different fights. Only the host may take a soldier after the lord falls.
7. In a session, Coop adds a defender ally team for the other players' lords, and the engine would put TAOM's plain troops there too (`Mission.cs:5229-5233`). So every TAOM spawn names its team. A death or a hit on the ally team is no garrison loss and takes no poison. A solo run is unchanged, because there the engine already picks the same team.
8. When the host's mission ends, by any exit, the host sends `CoopCompatLdRunEnded` (session, host epoch, reason, wave, waves cleared, kills) over Coop's session channel, then closes the session. Each follower shows the result, and Coop ends its mission.
9. If the host leaves and Coop makes a follower the host, that follower closes the session, shows "The host left" and ends its game. A director handoff is a later slice.

Not built ([#1292](https://github.com/haterade22/TAOM/issues/1292)): the director handoff, a follower's shop and HUD, the wave messages, a mounted follower, a won or lost end notice, and whether a co-op run counts in the solo best runs. The session code builds only against a Coop with the session API (`Missions.Sessions.dll` in `CoopBinDir`); against an older Coop, `TAOM.CoopCompat` builds a stub, logs "sessions off" and the co-op option stays hidden. The English text is registered; the language rows wait for the project lead's pass. Not played: a two-client run is owed.

- **Multiplayer (research only, 2026-11-12; nothing built):** players want to defend together, and later to fight each other with one side attacking. BannerlordCoop cannot carry the mode as it ships: a co-op siege starts from a campaign map event (`CoopSiegeBattleLauncher.OpenCoopSiegeBattle` returns null without one, `source/Missions/Battles/CoopSiegeBattleLauncher.cs:59-63` in the local clone), and a client reaches a mission only from the campaign state, after it loads the server's save (`doc/ClientAndConnectionStates.md`). Its code is source-available since 2026-06-17, so TAOM may not copy or adapt it without the maintainers' written permission ([co-op interop](coop-interop.md#bannerlordcoop-versions-and-the-bannerlord-they-need)); the route through Coop is a campaign-free session built in Coop as a contribution, which needs their agreement (given on 2026-11-14, next bullet). The route TAOM owns is native multiplayer: a module adds a game mode with `Module.AddMultiplayerGameMode` (`Module.cs:1722`) and its own network messages with `DefineGameNetworkMessageTypeForMod` (`GameNetwork.cs:1497`). Its first risk is the siege AI: vanilla's multiplayer siege mission (`MultiplayerMissions.OpenSiegeMission`) adds neither `MissionCombatantsLogic` nor `MissionSiegeEnginesLogic`, so a dedicated-server spike must show the siege team AI running before any build. Three parts do not carry over as they are: the speed controls (one player cannot change the time for everyone), the takeover of a soldier after the lord falls (the engine's respawn instead), and the shop, armoury and yard (requests a client sends and the server checks).
- **Multiplayer through Coop (agreed 2026-11-14):** Garrett, BannerlordCoop's owner, agreed on Discord to option A of TAOM's request: the campaign-free session is built inside Coop as a contribution, Coop owns that code under its license, and TAOM ships no Coop code and starts a session through Coop's public seam. Option B (Coop's mission code inside TAOM) was not granted, so TAOM must not copy or adapt Coop code. Coop work: Epic Bannerlord-Coop-Team/BannerlordCoop#4691, one PR into `bannerlord-1.5.x`. ## Decisions for the later phases

Phase 5 (Minas Tirith: Gondor against Mordor) follows [phase5-plan.md](long-defeat/phase5-plan.md). Slices 1 to 4 are built as data and not yet played ("Phase 5: Minas Tirith" above); the plan's own decisions D51, D53, D54 and D60 were taken at their recommendations and each is one data row to undo.

Mike decided these on 2026-11-03. The full text is in [the #1079 design comment](https://github.com/haterade22/TAOM/issues/1079#issuecomment-6617849770).

- **No wave retreats.** A wave ends when every attacker is dead.
- **General:** the player leads the defenders, and a bought hero takes over while the player is down.
- **Commanders:** waves 4, 8 and 12 and on bring a captain, a lieutenant, then a general, with abilities on a cooldown. Every faction's waves, commanders and summons use its own troops.
- **Classes:** Sword and Board, Two Handed Infantry, Archer, Cavalry. Each has a start kit from the faction's own gear and its own boon pool. Cavalry is a sally force from a recorded point outside the walls, because a vanilla siege spawns everyone on foot (S9).
- **Boons:** pick 1 of 3 after every 3 cleared waves (Mike moved this from 5 on 2026-11-04). A boon lasts until the run ends. This is an assumption Mike may correct. The design reference is a comparison only, and its provenance row lands with the first commit that builds boons.
- **Affixes:** named powers on the attackers, rolled for each wave: 1 from wave 5, 2 from wave 10, 3 from wave 15.
- **Endless scale:** a wave cannot exceed the battle size, so each wave also raises health and damage, and the troop tiers rise.
- **Leaderboard:** players submit the run report through a Discord command, a bot checks it and updates the board, and a top 10 entry also needs a clip. Mike accepted this on 2026-11-04. The plan is [leaderboard-plan.md](long-defeat/leaderboard-plan.md), and Luiz has the brief for the bot.
- **Phase 4 (planned):** the armoury, the engineer's yard, gear that lasts the run, and the death rule (take over a soldier, rise at the keep at the next clear) are planned in [phase4-plan.md](long-defeat/phase4-plan.md), with open questions OQ8 to OQ20 taken at their recommended answers unless Mike changes them. Slices 1 to 3 (config, the buys and the bot, the death rule; all pure) are built; the engine halves are not.

With no block, or no point for a class, spawning is exactly what it was. With a point, the director calls `SetMusterFrame` for each defender batch of that class right after the batch opens. Attackers never use it, and the player's lord spawns as before. A player's Advance order with no enemy alive keeps a bought pack's place, so that formation walks to the point until the next wave. Nobody has seen this in game, and restoring the place was left out as a guard for a rare case.

The speed lives in `LongDefeatSession`, not in the run, so a wave or an intermission never changes it, and the next `Fill` (a new run) resets it to 1x. Only fast forward stops at `Mission.MissionEnded` (`Mission.cs:3728`); the fixed step takes one tick more. `LongDefeatSession.Speed` reads 1 once the run has a result, so a fight with no rules does not run at 10x behind the end panel, and `MaxSpeed` keeps its value.
  - **What 10x does** (installed v1.5.6, `MissionState.cs:171-197`): with `IsFastForward` set, `TickMission` computes `num2 = num * 9` and runs `TickMissionAux(0.1f, 0.1f, updateCamera: false, asyncAITick: false)` until `num2` is spent, then `TickMissionAux(num, realDt, updateCamera: true, asyncAITick: false)` once.   - **Player input and camera at 10x:** the camera and the mouse look are tied to the real frame time (`updateCamera` is true only in the last step). The main agent's input handler is `MissionMainAgentController.OnPreMissionTick`, which `Mission.OnPreTick` calls (`Mission.cs:3540`). Native `IMBMission.Tick` (0x5B0410) calls the managed `Mission_OnPreTick` on every call, so under fast forward `ControlTick` runs once per step and reads each frame's key presses once per step: a tap would repeat nine extra times. So 10x with a person driving a live main agent uses a fixed step of `min(realDt * 10, 0.1)` instead of fast forward (`LongDefeatSpeedFrame`, chosen each frame by `LongDefeatMissionSpeed` from `MainAgent.IsActive()` and `IsPlayerControlled`); a dead player and an AI-driven main agent keep engine fast forward. The fixed step reaches a true 10x only at 100 fps or more: at 60 fps it is 0.1 s a frame, about 6x. How a fight feels at 10x is unverified, and nothing here has run in game.
  - **Seconds:** the director adds each `OnMissionTick` dt, so a wave's `seconds` and the live-limit seconds are mission time: 10x does not scale them (a wave takes about the same mission seconds and a tenth of the wall time), only the larger steps change how the fight plays out. The HUD notice timer and the panel refresh use the real frame time. Above 1x the frame mean and max on the `[State]` line are mission dt, not real frames (use `[MissionPerf]` for real frames), and a dt cap of 1/15 s is seen in the logs. The report's `maxSpeed` records the highest speed set in the run, because the sum of the rows' `seconds` can then exceed `endedUtc - startedUtc` ([leaderboard-plan.md](long-defeat/leaderboard-plan.md) rule 13).
  - **The shop panel does not pause or change the speed:** it is a focus layer with no `PauseGameEngine` call, so the speed stays as set while it is open and the wave timer keeps running at that speed. The Escape menu registers an active-state disable request (`MissionGauntletEscapeMenuBase.cs:73-74`), so `GameStateManager.OnTick` calls `OnIdleTick` and `TickMission` does not run; `IsFastForward` stays set meanwhile.
  - **Why `M`:** not `T`. `GauntletChatLogView` is a global layer; its `MissionScreen.TryUpdateChatLogLayerParameters` hands it the scene layer's input (`MissionScreen.cs:3283-3290`), it registers `ChatLogHotKeyCategory` there, and a release of game key 6 (`InputKey.T`, `ChatLogHotKeyCategory.cs:53`) starts the chat box (`GauntletChatLogView.cs:215-218`) and takes the keyboard. `M` is in none of the eight categories that reach the scene layer (`Generic`, `GenericPanelGameKeyCategory`, `GenericCampaignPanelsGameKeyCategory`, `ScoreboardHotKeyCategory`, `CombatHotKeyCategory`, `Cheats`, `MissionOrderHotkeyCategory`, `ChatLogHotKeyCategory`): grep of each category's `InputKey` names in the v1.5.6 decompile, only these files read. TAOM's other `M` is Realm Borders on the campaign map and Fords' own view. Ctrl and Alt leave it to the game. `M` works with a panel open, because `CanUse(M)` returns `IsKeysAllowed` on the focused layer, so the panel host reads it from the panel layer's own input; the four buttons are the other way.
  - **A caution about `H`:** `ScoreboardHotKeyCategory` binds `ToggleHud` to `H` and `ToggleFastForward` to `F`, and `CheatsHotKeyCategory` uses `H` with modifiers. This mission's view list has no scoreboard view, so no reader was found, but the claim above that `H` is free rests on that absence.
