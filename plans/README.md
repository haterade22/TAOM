### Rules for this programme

- **The integrator owns this file.** Executors never edit `plans/README.md` on a WP branch: every branch shares it,
  so row edits collide at merge. An executor reports its status, commit hashes and measured counts (tests, data,
  hooks, tool tests) in its hand-off, and the integrator records them after the merge. The integrator is the
  maintainer or a session the maintainer names. WP101 is the one exception: its Part C runs in the main checkout and
  writes its own row and the first integrator record.
- **One worktree per WP**, created from the main checkout:
  `git worktree add C:\Users\mikew\source\repos\taom-port\<id> -b port148/<id>-<slug> bannerlord-1.4.5`.
  At most four executors at once, plus the integrator. Never two builds in one worktree.
- **Never `./build.ps1`; every build and test carries `-p:DisableModuleCopy=true -p:ModuleId=`.** On 1.4.x
  `Main/TAOM.csproj` does not gate its CopyModule target on DisableModuleCopy, so a build without `-p:ModuleId=`
  deploys into the game install.
- **Executors commit on their WP branch only.** They never push, merge, tag, open a PR or create an issue.
- **Maintainer-only steps** appear in each plan as explicit steps with the exact diff or action: edits to
  `.claude/settings.json`, `.claude/settings.local.json`, `Directory.Build.props` and `docs/adrs/`; push, tag,
  release, `gh issue create`; anything that spends money (Codex runs, `tools/translate_with_claude.py`); and every
  in-game check.
- **GitHub issues.** Plans name the new work that needs an issue. Executors never create one: the integrator creates
  or names it before handing out the WP, and gives the executor the number.
- **A conditional on a WP in the same wave** needs a dependency edge or a named integrator action. Lanes cut their
  branches in parallel, so "if WP x merged first" reads the executor's base, not the eventual merge order.
- **`docs/reference/taleworlds-api-snapshot/patch-targets.md` is regenerated by WP137.** Nobody keeps it current before
  that: a plan's hand edit or regeneration of it is harmless, and a missing row is expected until WP137 merges.
- **A plan's Status block is authoritative** for its Depends on. `_audit/.../data/wp_map.json` was the planning input
  and is not kept in step.
- **Every commit subject carries `v2.0.28`** until the first 1.4.x release commit, which is v2.4.0 (D8). A ported
  commit's body is written for 1.4.x readers and ends with one `Ported-from: <40-hex sha>` trailer per included
  1.5.x commit.

### How to run it

1. WP101 runs first. Part A is a maintainer step: refresh the laptop's `LOTRLOME_Armory` (D20). Part B fast-forwards
   to origin and merges the public #697 troop tree. Part C commits these plans, this index and the planning record,
   so every later worktree carries them. Until then the plans exist only as untracked files in the main checkout.
2. Wave 0 then runs in two lanes: harness 102 then 103, and code 104 then 105. WP103 makes the git safety hooks
   real; today nine of them print a decision format Claude Code ignores. Wave 1's parallel sessions start only once
   wave 0 is merged.
3. Waves 1 to 5 follow in order. Inside a wave, lanes run in parallel worktrees, and a WP starts only when every WP
   in its "Depends on" cell is DONE.
4. Hand an executor one plan: "Execute `plans/<id>-<slug>.md`." Each plan is self-contained: current state with
   excerpts, the per-port procedure, the commit template, verify commands with expected results, STOP conditions and
   done criteria. A plan split into Parts can go to one session per Part.
5. The integrator merges each finished WP branch into `bannerlord-1.4.5` in table order, which satisfies every
   "Depends on" edge, runs the full build and test after each merge, records the result under "Integrator record"
   and commits this file: later plans read their prerequisites from the committed copy.
