### FREEZE-THREADING-01: the mission tick handshake turns any stuck agent tick, or any escaped mission-tick exception, into a permanent freeze (P1, latent; mechanism CONFIRMED in the v1.4.8 dump)

**Engine mechanism (v1.4.8 dump, `MountAndBlade/TaleWorlds.MountAndBlade/TaleWorlds.MountAndBlade/`):**
- `MissionState.TickMissionAux` calls the native `Mission.Tick(dt)` and then the managed `Mission.OnTick(...)` (MissionState.cs:212-218).
- `Mission.OnTick` sets `tickCompleted = false` (Mission.cs:3740), runs every `MissionBehavior.OnMissionTick` (3741-3744), and only at the end starts the asynchronous agent tick with `TickAgentsAndTeamsAsync` (3768-3775).
- `TickAgentsAndTeamsImp` runs `TWParallel.For(... AgentTickMT)` (Agent.TickParallel), then `Agent.Tick` for every agent, then `Team.Tick` for every team, and only then `tickCompleted = true` (3601-3613), followed by `AfterAsyncTickTick` (3614-3617).
- The next frame's `[MBCallback] OnPreTick` calls `WaitTickCompletion()` first (3529-3537), which is `while (!tickCompleted) Thread.Sleep(1);` with no timeout (3585-3591).

So the main thread sleeps in a 1 ms loop forever when the agent tick never reaches line 3613 of the previous frame. The window stays on its last frame, FMOD's own threads keep playing the loaded combat and ambient loops, the managed heap stops moving, and CPU use is low. That matches the player report "the game suddenly freezes ... combat sounds continue ... Task Manager looks normal".

**Three ways the 1.4.x line can leave `tickCompleted` false (working tree c5b84fb41; no file below is among the 52 drifted files):**
1. **A TAOM handler on the agent tick that spins or blocks.** Anything reached from `Agent.Tick` (every `AgentComponent.OnTick`, `TickAsAI`), `Team.Tick` (TeamAI, tactics, `Formation.SetMovementOrder`), or a native callback raised inside that window. A `Dictionary` corrupted by a concurrent writer can loop forever in a lookup. See FREEZE-THREADING-03 for the writers.
2. **An exception inside the agent tick, swallowed.** `Native2ManagedPatcher` puts a finalizer on every static method of every `*CallbacksGenerated` type (Native2ManagedPatcher.cs:72-81; E3 line 4 and E4 line 4: "attached 247 Finalizer(s)"). That includes `CoreCallbacksGenerated.Mission_TickAgentsAndTeams` (dump CoreCallbacksGenerated.cs:936-940). The bridge always swallows: `HandleAndSwallow` returns null, "swallow, game keeps ticking" (CrashReportPatchHelper.cs:21-23, 49; Native2ManagedPatcher.cs:121-122). `TickAgentsAndTeamsImp` is left before line 3613, so the next `OnPreTick` waits forever. Without TAOM's finalizer the exception would reach native instead (UNVERIFIED what native does with it: likely a crash).
3. **An exception escaping any `MissionBehavior.OnMissionTick` override** (vanilla, TAOM or a third-party mod such as BetterTime). It unwinds out of `Mission.OnTick` after line 3740 and before line 3768, through `MissionState.OnTick`, `GameStateManager.OnTick` (GameStateManager.cs:193-207, no catch), `Game.OnTick` (Game.cs:332-336: `GameStateManager.OnTick` is outside the try that guards GameHandlers), `GameManagerBase.OnTick` (GameManagerBase.cs:104-114, no catch) to `Module.OnApplicationTick` (Module.cs:463-519), where TAOM's `ModuleOnApplicationTickFinalizer` swallows (Patch37_CrashReport.cs:54-61). No agent tick was started, so the next frame hangs. `MissionBehaviorOnMissionTickFinalizer` (Patch37_CrashReport.cs:104-111) patches only the empty base `MissionBehavior.OnMissionTick`; Harmony does not reach overrides, so it guards nothing.

**What the logs say.** Routes 2 and 3 always write a `[CrashReport]` block (or a "bundle suppressed" line) to taom_debug.log before the silence (CrashReportService.cs:110-114, 129). E3 and E4 have none (grep of both logs), and the 1.5.x RCA for #634 records "no exception and no crash report". So these three player freezes were not routes 2 or 3. Route 1, or a native-side stall, remains open. E3's own freeze happened before the agent tick ever started (see FREEZE-THREADING-02).

**What a player log would show for each route:** routes 2 and 3 leave `[CrashReport] ... @ TaleWorlds.AutoGenerated.<callback>` or `@ TaleWorlds.MountAndBlade.Module.OnApplicationTick` followed by only `[MemSample]` lines with a flat `heapMB`. Route 1 leaves only the flat-heap `[MemSample]` tail.

**1.5.x status.** Recognised, not fixed:
- `rca-coop-safety-nets-2026-10-21.md` finding 1 (on origin/bannerlord-1.5.x) traces exactly route 3: "the next catcher was Patch37 on `Module.OnApplicationTick`, which swallows after the tick window has been left in a state that hangs the next frame". bd1ac8292 reverted two co-op rethrows for that reason.
- `Dependencies/Foundation/PatchShieldPolicy.cs:171-185` on 1.5.x: "A throw in OnTick after it clears tickCompleted and before the agent tick sets it again, swallowed by any catcher above it, still hangs the next WaitTickCompletion, and no entry here prevents that ... left to the PatchShield follow-up plan."
- Plan 006 on 1.5.x (42624b95b, 8e6b0935c, 8c84fa20e, 9e8c99bdb) cut the Native2Managed finalizers to a 16-name allowlist (`Native2ManagedTargets.cs` on 1.5.x, lines 28-61). `Mission_TickAgentsAndTeams` and `Mission_OnPreTick` are not on it, so route 2 no longer becomes a freeze on 1.5.x. Route 3 is still there.
- f75288ebf (#634) adds Patch91 and `MissionTickStallWatchdog`, which would photograph route 1 as a `[MissionStall]` stack.

**Fix direction (1.4.x).**
- (a) Port plan 006's allowlist (with its off-main-thread marking, FREEZE-THREADING-05), which removes route 2.
- (b) NEW, nothing on 1.5.x does this: a `Mission.OnTick` Harmony finalizer, plus one on `Mission.TickAgentsAndTeamsImp`. When the method exits by exception, it sets the private `tickCompleted` back to `true` (cached `AccessTools.FieldRefAccess<Mission,bool>("tickCompleted")`), then lets the exception continue to Patch37 so it is still reported. That turns a permanent freeze into one skipped agent tick plus a crash report. Pin it with a binding test on the field name and on the three Mission.cs line facts above.
- (c) Every TAOM `OnMissionTick` override must catch its own exceptions. Audit owed: list the overrides without a try/catch.

**Verify.** Unit-test the finalizer with a fake that throws, and assert that `tickCompleted` is restored. In game (laptop, v1.4.8): use a dev console command that makes a TAOM behaviour throw once from `OnMissionTick` mid-battle. Before the fix the game freezes with audio playing and a `[CrashReport]` block; after the fix there is one bundle and the battle keeps running.

### FREEZE-THREADING-02: the Harad first-battle freeze (E3) is a main-thread stall inside the render-ready wait, before any mission or agent tick runs; no TAOM thread hazard can be involved (P1 by player impact; mechanism partly CONFIRMED, cause UNVERIFIED)

**Evidence.**
- E3 lines 217-223. `FinishMissionLoadingDone` at +7909 ms, then `WaitingForRender waitedMs=1 shaders=2720` (20:02:48) and `waitedMs=2259 shaders=2697` (20:02:50). After that there is no TAOM line except `[MemSample]` until the log ends at 20:04:22, and `heapMB` stays fixed at 466.
- The `WaitingForRender` line comes from a postfix on every `MissionState.OnTick` frame while `FirstMissionTickAfterLoading` is still true (MissionState_OnTick_RenderWait_Patch.cs:52-76), throttled to 1 per 1000 ms (BattleLoadDiagnosticsService.cs:37, 285-301). Silence therefore means the main thread completed no frame at all. The second line came 2259 ms after the first, so even the frame before the silence lasted over a second.
- `[MemSample]` keeps writing because it runs on a thread-pool `Timer` (MemoryPressureSampler.cs:51-55), not on the game thread.
- In v1.4.8, `MissionState.OnTick` calls `TickMission` only once `Handler.RenderIsReady()` is true (MissionState.cs:110-113), and `TickMissionAux` calls `Mission.OnTick` only after `_missionTickCount > 2` (MissionState.cs:212-218). So in this window no `Mission.OnTick`, no `OnPreTick`/`WaitTickCompletion` and no asynchronous agent tick has run. FREEZE-THREADING-01 and -03 cannot apply to E3.

**Same shape, one that recovered.** E4's first tournament (arena_aserai_a, 559 agents) logged `waitedMs=1 shaders=1569` at 20:21:20 (E4:2125). The next line is `waitedMs=68290 shaders=0` at 20:22:29 (E4:2131), so the main thread completed no frame for 68 s. Then the 1 Hz lines resumed and the mission reached `BattlePlayable` (E4:2151-2153). E4's last load (arena_empire_a, `shaders=806`, E4:5138) went silent the same way for at least 205 s (until the log ends at 20:51:51) without recovering, while `sysCommitUsedMB` rose from 24700 to 26625 and `availPhysMB` fell to 1929.

**Most likely cause (UNVERIFIED).** The engine compiling the scene's shaders, with the main thread unable to finish a frame until they are done. At E4's observed rate (1569 in about 68 s), E3's 2697 shaders need about 2 minutes. The player killed the game 92 s after the last line, and had killed the previous session on the same scene too (E3:17, stale inflight marker for battle_terrain_031). E4's last load does not fit that rate (806 shaders, over 205 s): either memory pressure slowed the compile, or it is a genuine wedge. 1.5.x has seen the same shape: 89374fc4f's message cites a 2026-10-18 bundle that fell from 3128 to 3066 shaders and then logged nothing for about 290 s, and concludes that "the log alone cannot separate a slow compile from a main-thread wedge".

**Diagnostic gap on 1.4.x.**
- `BattleLoadStallWatchdog` fires at 300 s by default (BattleLoadDiagnosticsSettings.cs:36). E3 ran 96 s and E4's last load 208 s past window open, so no `STILL LOADING` marker was written.
- When the watchdog does fire, it records the phase and the shader count, not the main thread's stack (BattleLoadStallWatchdog.cs:180-201).
- Its `Decide` does treat a count unchanged for 60 s as a wedge (BattleLoadStallWatchdog.cs:33, 115-127), so a stuck main thread cannot defer it forever. That part is correct.
- f75288ebf's Patch91 frame probe arms inside `MissionState.TickMissionAux`, which never runs in this window, so the 1.5.x `[MissionStall]` watchdog is blind here too.

**What would verify it.** The player's `rgl_log` for the E3 session: `compile_shader` lines continuing up to 20:04:22 mean a slow compile, and no engine lines mean a wedge. Better still, a full process dump taken while frozen (Task Manager > Details > Bannerlord.exe > Create dump file), opened in WinDbg with SOS (`~*e !clrstack`, plus `k` on the main thread for native frames).

**Fix direction.** Shader warm-up and cache policy belong to the shader/load lens (ShaderPrecompilation, Patch21). Within this lens:
- (a) the main-thread heartbeat in FREEZE-THREADING-06, which covers this window;
- (b) port the triage tool fix 89374fc4f and its follow-up 1581d4d0a (`tools/triage_battle_load.py` exists on 1.4.x and differs from 89374fc4f's parent by 2 lines);
- (c) a lower default for `StallWatchdogSeconds`, or a separate early "no frame for N s" marker: players gave up after 1.5 to 3.5 minutes in E3 and E4;
- (d) release-note text telling players that a first battle on a cold shader cache can sit on the loading screen for minutes.

**1.5.x commits:** 89374fc4f and 1581d4d0a (triage only). There is no fix for the stall itself on 1.5.x in this lens.

### FREEZE-THREADING-04: a throw anywhere in mission start makes the mission reload every frame, an infinite loading screen (P1 for load hangs; mechanism CONFIRMED in the v1.4.8 dump)

**Mechanism.**
1. `MissionState.TickLoading` calls `LoadMission()` whenever `!_missionInitializing`, and `FinishMissionLoading()` once loading has finished (MissionState.cs:221-232).
2. `FinishMissionLoading` clears `_missionInitializing` as its first statement (MissionState.cs:335) and then runs `Mission.AfterStart()` (:345). `AfterStart` sets `CurrentState = Continuing` only as its last statement (Mission.cs:3835), after six loops over submodules, behaviours and mission objects (Mission.cs:3805-3830).
3. A throw from any of those loops unwinds out of `MissionState.OnTick` to Patch37's `ModuleOnApplicationTickFinalizer`, which swallows it (FREEZE-THREADING-01, route 3).
4. On the next frame the state is still `Initializing` and `_missionInitializing` is false, so `LoadMission()` runs `Mission.Initialize()` again (MissionState.cs:235-245). This repeats on every frame: the player sees an endless loading screen. Without the swallow it would be a crash.

**TAOM exposure on 1.4.x.** `SubModule.OnMissionBehaviorInitialize` adds 25 behaviours through the local function `AddTaomBehavior` with no per-behaviour catch (SubModule.cs:1757-1910; `AddTaomBehavior` at :1782-1787). A throwing constructor or registration falls straight into this loop. E3 and E4 each passed through it once (`TaomBehaviorsDone count=25`, E3:215), so it is not the cause of these sessions. It is one route to the maintainer's "many infinite loading screens".

**1.5.x.** ecaa67d26 (#775) adds `MissionStartGuard` (Patch103): a transpiler on `Mission.AfterStart` that wraps those six call sites (`MissionStartGuardSwaps.cs` on 1.5.x), logs the type and module that threw, shows one message and lets the mission start. The same commit closes the BattleLoad window in a `finally` when TAOM's own setup throws.

**Port notes.** All six call sites exist once each in the v1.4.8 body (Mission.cs:3807, 3811, 3815, 3819, 3825, 3829). The transpiler's `CallSwap` type comes from the 1.5.x-only `MissionPerf` feature, and the module registers through the 1.5.x `Main/Composition/FeatureModules.cs`, so it must be adapted, not cherry-picked. Take only the MissionStartGuard hunks of ecaa67d26; the same commit also carries SkeletonBuffer, NameplateCull and MapViewRelease. Its `MissionStartGuardBindingTests` read the real IL, so they have to pass against the installed v1.4.8.

**Verify.** The binding test, plus an in-game run with a dev trigger that throws from one TAOM `AfterStart`: before the fix the loading screen never ends; after it there is one message and the battle starts.

### FREEZE-THREADING-05: a crash captured on a worker or timer thread runs the Mission and Campaign collectors and opens the UI inquiry from that thread (P2; CONFIRMED in code)

**Evidence (1.4.x working tree).**
- `CrashReportService.HandleException` skips the Mission and Campaign collectors and the inquiry only when `ex.Data["TAOM.CrashReport.OffMainThread"]` is true (CrashReportService.cs:117-146, 161-171, 190-203). Only `AppDomainExceptionHook` sets that key (AppDomainExceptionHook.cs:42, 66-68).
- The Native2Managed bridge, which catches exceptions in native callbacks raised off-thread (`Mission_TickAgentsAndTeams`, `Mission_OnAgentShootMissile`, `Mission_OnAgentRemoved` and the rest), passes no tag (Native2ManagedPatcher.cs:121-122).
- `BattleLoadStallWatchdog` calls `HandleException` from its thread-pool timer (BattleLoadStallWatchdog.cs:185-201), also untagged.
- In both cases the service runs `_campaign.Collect()` and `_mission.Collect()` against live engine state, and then `CrashNotifier.Notify` → `InformationManager.ShowInquiry` (CrashNotifier.cs:17-31), which builds Gauntlet UI on a thread that is not the UI thread.

**Impact.** This matters only after something has already thrown off-thread, or after the watchdog fires. A UI inquiry built from a worker while the main thread ticks the screen stack can corrupt it or crash natively (UNVERIFIED which). It also adds work on the thread the main thread may be waiting for (FREEZE-THREADING-01).

**1.5.x.**
- 8e6b0935c (plan 006, D43) marks bridge captures made off the main thread.
- 8c84fa20e turns the verdict into a `HandleException` parameter, because `Exception.Data` is read-only for preallocated OOM and stack-overflow exceptions, and adds `AppDomainExceptionHook.IsOffMainThread`.
- 9e8c99bdb (convergence) records that the watchdog is still the open exception on 1.5.x.
- 42624b95b and 8e6b0935c (D47) cut the bridge to the 16-name allowlist, which also removes route 2 of FREEZE-THREADING-01.
- Plan 007 (e9b28e2a per the 1.5.x plans index) is the complementary PatchShield change (perf).

**Port notes.** These four commits change `CrashReportService`, `ICrashReportService`, `AppDomainExceptionHook`, `CrashReportPatchHelper`, `Native2ManagedPatcher` and a new `Native2ManagedTargets`. The allowlist names must be re-verified against the installed v1.4.8 `CoreCallbacksGenerated` and `EngineCallbacksGenerated`; the 1.5.x tests pin them by literal name. Extend the tag to the watchdog's call (new on both lines).

**Verify.** The 1.5.x tests (`Native2ManagedBridgeTests`, `AppDomainExceptionHookTests`, `CrashReportPatchHelperTests`, `Native2ManagedTargetsTests`), plus a binding check of the allowlist on v1.4.8.

**Proposal (NEW on both lines, built on f75288ebf's parts):**
1. **Heartbeat.** A prefix on `TaleWorlds.DotNet.Managed.ApplicationTick`, which native calls once per frame in every game state, stamps a volatile frame counter and a UTC timestamp. Patch37 already targets this method with its finalizer (Patch37_CrashReport.cs:36-43).
2. **Breadcrumbs.** Enter/exit stamps from f75288ebf's two probes (`TickMissionAux`, `TickAgentsAndTeamsImp`), plus `BattleLoadRenderWaitProbe` (already on 1.4.x), plus an enter/exit bracket on `ScreenManager.Tick`. Volatile writes only.
3. **Watchdog.** A 1 s thread-pool timer. When the heartbeat is older than 10 s, write one `[Freeze]` ERROR at 10/20/40/80 s with:
   - which brackets are in flight and since when;
   - the last published shader count and its age;
   - the memory tokens;
   - the managed stacks of the main thread and of the agent-tick thread if it is in flight (`ThreadStackCapture` from f75288ebf; the same code is inline in 1.4.x `ExitStallSampler`).
   It never calls an engine API, and it stands down while `ExitStallSampler` owns the exit window.
4. **Optional self-dump** at 60 s, MCM toggle: `MiniDumpWriteDump` from dbghelp on the own process, into the Logs folder. The native RIPs then classify the freeze without a debugger:
   - any thread at `TaleWorlds.Native.dll+0x88730`, `+0x88744`, `+0x89977` or `+0x89990` (the v1.4.8 skeleton-buffer spin loops, FREEZE-THREADING-07);
   - the main thread in `Mission.WaitTickCompletion` while another thread spins in `Dictionary` (FREEZE-THREADING-01 and -03);
   - the main thread in native code under the render wait (FREEZE-THREADING-02).

**Risks.** `Thread.Suspend` can deadlock if the suspended thread holds a lock that the stack walk needs (the loader lock during JIT, for example); f75288ebf's `ThreadStackCapture` documents the mid-GC case. Mitigations: sample only a thread silent for at least 10 s, never allocate or log between Suspend and Resume, and take at most one sample per threshold. A full dump of a 10 GB process is large, so offer `MiniDumpWithThreadInfo` plus `MiniDumpWithIndirectlyReferencedMemory` as the default.

**Today, with no code change.** Ask a frozen player for a Task Manager dump (Details > Bannerlord.exe > Create dump file) plus taom_debug.log and the rgl_log. In WinDbg: `.loadby sos clr`, `~*e !clrstack`, and `~*k` for native frames. Check the RIPs listed above.

### FREEZE-THREADING-07: the engine's per-frame skeleton buffers have no bounds check, and the same code is in v1.4.8: a crowded frame freezes the battle for good, with audio playing and nothing logged (P1; engine code CONFIRMED identical in v1.4.8, freeze threshold UNVERIFIED on 1.4.8)

**1.5.x lead (re-checked here).**
- ecaa67d26 (#776) and the 1.5.x engine doc `docs/reference/engine/mission-frame-threads-and-native-costs.md` section 10 describe two per-frame pools in `TaleWorlds.Native.dll`: 65,536 and 262,144 entries. Each skeleton drawn reserves entries with one `lock xadd`, and nothing compares the block index with 32. One reservation past the end overwrites the "block ready" bytes, and threads waiting on them spin forever (`movzx eax, byte [rbx]; test al, al; jnz`).
- The doc says: "The battle stands still and the function logs nothing: a hang, not a crash."
- Measured on v1.5.4 by an outside source cited there (yotthani): about 2,340 human skeletons in view fill pool 1. 1,501 agents ran; 1,751 hung in 1 of 3 runs; 2,001 hung in 3 of 3. A siege adds about 200 skeletons, close melee near the camera 300 to 450, and every horse, warg and creature mount fills pool 2.

**Verified this session on the installed v1.4.8 `TaleWorlds.Native.dll`** (14,185,944 bytes; read-only Python scan of `.text`, VA 0x1000):
- Each of the four 1.5.x signatures (`SkeletonBufferSignature.cs` on 1.5.x) matches exactly once: watch load at RVA 0x88681, pool-2 load at 0x88475, pool-1 guard site at 0x886B4, pool-2 guard site at 0x898F0. Both loads read the same global, 0xD96D18.
- The resolver's link check holds: a `call` 0x29 after the pool-2 load (RVA 0x8849E) targets 0x898D0, 0x20 before the pool-2 site. Those are the v1.5.4 distances.
- The function layout is the same as v1.5.4: watch to guard is 0x33 bytes on both, pool-2 load to watch 0x20C on both, pool-2 load to pool-2 site 0x147B on both.
- The four spin loops sit at the v1.5.4 relative offsets: `0f b6 03 84 c0 75 f9` at 0x88730, 0x88744 and 0x89977, and `0f b6 0b 84 c9 75 f9` at 0x89990.

So v1.4.8 carries the same unchecked reservation and the same spin. What remains UNVERIFIED on 1.4.8 is the threshold, and whether the post-site code differs anywhere the patterns do not cover (no disassembler run here).

**Why this fits the reports.**
- The symptom is exactly "freezes and stays that way, combat sounds continue, Task Manager looks normal" (fact 3).
- c17541f2c (#701, 1.5.x) records that "Players on 1.4.8 and 2.0.x reported mid-battle freezes that stopped when they lowered the vanilla Number of Ragdolls and Number of Corpses options". Corpses are drawn skeletons, and on Unlimited the engine keeps up to 1,021 bodies.
- That matches the maintainer's history of ragdoll and corpse causes (fact 11).
- TAOM 1.4.x does not raise the battle size (no `BattleSize` code in Main/), so reaching the limit takes the vanilla maximum plus corpses, sieges, close melee or TAOM's creature crews.
- E3 and E4's battles (about 300 agents) are far below the limit, so this is not the Harad player's freeze.

**Fix (port).**
- (a) The SkeletonBuffer guard and watch from ecaa67d26. The guard rewrites 13 bytes per pool in memory only after an exact single-match byte check, and gives an overflowing skeleton its pool's first slots (wrong bones for a frame instead of a permanent hang).
- (b) BattleCorpses from c17541f2c: fade bodies 60 s after they settle, keep at most 25 per battle (never raising the player's option), and offer once to lower Number of Ragdolls to 5 and Number of Corpses to Low.

**Port notes.**
- Both features sit on 1.5.x-only plumbing: `TaomFeatureModule`/`OnPhase(MainMenu)` from `Main/Composition` (plan 018), and `ClipBudgetSignature` from `MissionPerf.AnimMemory`. Adapt them, do not cherry-pick.
- Add a v1.4.8 row to `SkeletonBufferInstalledBinaryTests.KnownBuilds`: (14185944, "v1.4.8", 0x88681, 0xD96D18, 0x886B4, 0x88475, 0x898F0), from the scan above.
- The guard is TAOM's first write to engine code, so the maintainer must decide whether to accept it on 1.4.x.

**Verify.** `SkeletonBufferInstalledBinaryTests` on the laptop (read-only against the installed DLL). In game: a vanilla-maximum siege with Unlimited corpses, watching the mission-end `[SkeletonBuffer]` peak line. A dump of any frozen battle whose thread RIPs fall in the spin ranges above settles it.

### FREEZE-THREADING-09: `BehaviorTree.RunTree` walks nodes in an uncapped loop on the main thread (P3 hardening; no reachable spin found)

**Evidence.** `RunTree` loops `CurrentNode = CurrentNode.HandleExecute()` until a node asks to leave the tree or the walk returns to the root (BehaviorTreesCore.cs:53-80). It runs from `BehaviorTreeMissionLogic.OnMissionTick` (BehaviorTreeMissionLogic.cs:118-135) on the main thread.

**What I checked.** I traced `Selector` and `Sequence` (BehaviorTreesNodes.cs:121-330). Every branch that returns `this` either sets `WaitingForEvent` or `IsWaitingASingleTime`, or clears `_lastChild` first. The `BTTask` branch that returns `this` without either is dead code, because only `BTControlNode` overrides `Decorator` (BehaviorTreesNodes.cs:40). I found no spin, but nothing bounds the loop if a future node or listener leaves an unexpected state; `Selector`'s `default` branch already logs "this should never happen".

**Fix (NEW; 1.5.x `RunTree` is identical).** Cap node transitions per `RunTree` call (for example 1,000). On hitting the cap, log once per tree type and set `IsRunning = false`, the same as the existing exception path.

**Verify.** A unit test with a two-node cycle stub that would spin without the cap.

## Checked and ruled out

- **Locks shared between the main thread and the workers (question 4).** No deadlock found.
  - Patch30 runs on the TWParallel workers, allocates a `FormationAdapter` per call and takes `FormationLayoutService._lock` (Patch30_FormationGetOrderPositionOfUnit.cs:28-46; FormationLayoutService.cs:65-100). The main thread takes the same lock only from `OnMissionTick`, and the handshake keeps that window apart from the agent tick.
  - Inside the lock there are only dictionary operations, slot arithmetic and read-only `formation.Units` walks; nothing waits on the pool.
  - `CavalryChargeService` issues an order inside its lock (CavalryChargeService.cs, the lock at about :152-177). That re-enters the same reentrant `Monitor` on the same thread, and the order call does not wait on another thread.
  - 13f34c1cb (plan 032, #714) is a contention and allocation port for the perf lens, not a freeze fix.
- **Blocking waits in TAOM code.** None on a mission path. The only `Thread.Sleep` calls are the FileLogger writer's idle loop (FileLogger.cs:134-139) and a bounded 3 × 250 ms retry on `GetBattleSceneIndexMap` (MBMapScene_GetBattleSceneIndexMap_Patch.cs:31-67). Every TAOM `while` loop is bounded (BFS with a visited set and a depth cap, TroopUpgradeGraph.cs:30-55; queue drains; exception unwrapping), except `RunTree` (FREEZE-THREADING-09).
- **FileLogger** writes and flushes INFO, WARNING and ERROR on the calling thread under `_writeLock` (FileLogger.cs:57-71). That is a cost on hot paths (BattleLoad writes one INFO line per agent phase: its sequence number reached 1640 for the 533-agent arena_empire_a tournament load in E4, line 5138), not a deadlock: nothing holds another lock while waiting on it. This belongs to the load-time lens.
- **Co-op rethrows (bd1ac8292).** Not applicable. The rethrows it reverts came from 6ce20f6ed, which is not on the 1.4.x line, and the 1.4.x `SaveShieldPolicy` keeps swallowing MISSION-INIT faults in every mode (SaveShieldPolicy.cs:30-36). One edge: with the triage flag `saveshield-swallow-disabled.flag` set, a mission-init fault rethrown from inside `OnMissionTick` lands on route 3 of FREEZE-THREADING-01.
- **PatchShield on 1.4.x** swallows only missing-API exceptions, at the innermost patched method (PatchShield.cs:11-18), so it is harmless to the handshake, with one exception. `Patch35_Mission_OnTick` (an empty postfix, Patch35_Mission_OnTick.cs:15-35) makes PatchShield wrap `Mission.OnTick` from the second game start in a process: pass 2 runs in Dependencies' `OnGameInitializationFinished`, before TAOM applies Patch35 at SubModule.cs:1575. A foreign mod's `MissingMethodException` thrown from `OnMissionTick` is then swallowed at `Mission.OnTick`: route 3 again. Deleting the empty postfix removes that and its per-frame shield cost.
- **The E3 `[BuildStamp] MISMATCH`** changes no Dependencies code. 0c3234375 is an ancestor of c5b84fb41, and `git diff 0c3234375 c5b84fb41 -- Dependencies/` is empty.
- **E4's three `[ERROR]` off-thread lines** are the #595 tripwire reporting callbacks that `BehaviorTreeMissionLogic` then parked. On 1.4.x they reach no unsynchronised TAOM writer (FREEZE-THREADING-03).

## Summary

**Answers to the five questions.**
1. *Off-thread callbacks in v1.4.8.*
   - Managed-provable on the async agent tick: every `AgentComponent.OnTick` and `TickAsAI` (Agent.cs:4746-4779); `CommonAIComponent` → `Mission.OnAgentPanicked` (CommonAIComponent.cs:119-135); `HumanAIComponent` → `Mission.OnObjectUsed` / `OnObjectStoppedBeingUsed` (HumanAIComponent.cs:210-264; Agent.cs:4006, 4199); `Team.Tick` → TeamAI → formation orders.
   - On the worker pool: `OnTickParallel` and `Formation.GetOrderPositionOfUnit` (Mission.cs:3593-3604; NativeParallelDriver.cs:55-84).
   - Native-raised, thread chosen by native: `OnAgentShootMissile`, `OnDismount`/`OnMount`, `OnAgentAlarmedStateChanged`, `OnAgentRemoved` (observed in E4:2265-2266 and 2986, and in #634).
2. *TAOM handlers off the main thread and their shared state.* The eight rows of FREEZE-THREADING-03. Dictionary writers are BTML `trees` plus the `_scheduled` list, MountDespawn `_pending` and `_deathTimes`, and FieldCommission `_battleKills`. The List writers are CareerPerk `_activeContexts` and the SpatialGrid cells. The UI call is `DisplayMessage`. Already locked: `AgentAdapterCache`, `FormationLayoutService`, `TroopStanceManager`, `CavalryChargeService`, `CareerAbilityBuffTracker`.
3. *Port candidates.*
   - f75288ebf (#634) ports with adaptation: drop the SignatureStrikes hunk; `SubModule.cs` and the bookkeeping files conflict.
   - Follow-ups: efe326242, e5f644da4, b8b144635, fe8f30c7a.
   - Plan 006: 42624b95b, 8e6b0935c, 8c84fa20e, 9e8c99bdb.
   - Triage: 89374fc4f, 1581d4d0a.
   - ecaa67d26 (MissionStartGuard and SkeletonBuffer, adapted).
   - c17541f2c (BattleCorpses, adapted).
   - a913629cd (stuck battles, adapted), plus shipping 1b00d1acd publicly.
   - Not applicable: bd1ac8292. Perf only: 13f34c1cb.
4. *Other freeze mechanisms.*
   - The `tickCompleted` handshake turns swallowed exceptions into permanent freezes (01).
   - A mission-start throw reloads the mission every frame (04).
   - Skeleton-buffer overflow is a native spin, present in v1.4.8 (07).
   - Stuck map battles (08).
   - Uncapped BT loop (09).
   - No lock deadlock found.
5. *Diagnostic.* 1.4.x has only the load watchdog (300 s, no stack) and the tournament-exit stack sampler. 1.5.x adds `[MissionStall]` (f75288ebf), which is blind to the render wait. The proposal in FREEZE-THREADING-06 is a heartbeat on `Managed.ApplicationTick`, with stack capture at 10/20/40/80 s and an optional self-dump classified by the v1.4.8 RVAs recorded here.

**Ranking by player impact.**
1. FREEZE-THREADING-07: skeleton buffers, a permanent battle freeze with audio playing. v1.4.8 code is proven identical, and 1.4.8 players' freezes went away with fewer corpses and ragdolls (#701).
2. FREEZE-THREADING-02: the Harad player's actual freeze, a main-thread stall in the render wait (probably shader compilation) that no 1.4.x diagnostic can explain.
3. FREEZE-THREADING-03: unsynchronised engine-callback writers, the #634 battle freeze on this exact line.
4. FREEZE-THREADING-01: handshake hazard.
5. FREEZE-THREADING-04: infinite reload on a mission-start throw.
6. FREEZE-THREADING-06: freeze diagnostics.
7. FREEZE-THREADING-05: off-thread crash capture.
8. FREEZE-THREADING-08: stuck map battles.
9. FREEZE-THREADING-09: uncapped BT loop.

**Most important conclusion.** The Harad first-battle freeze is not a TAOM threading bug. It happens before the agent tick exists, which leaves a shader compile or a native wedge. The mid-battle "frozen with sound" reports, by contrast, have two concrete mechanisms on the 1.4.x line that 1.5.x has already fixed or instrumented: the unguarded native skeleton buffers (ecaa67d26 plus c17541f2c) and the off-thread callback writers (f75288ebf). Both are worth porting first, together with a heartbeat that names the stuck frame in the next player log.
