### [PERF-L4-01] Stop paying about 31 s of every game boot for 247 Native2Managed finalizers

- **Evidence**: `Main/SubModule.cs:194-210` (`git show b2e387db`; `AttachAll` at `:203`) applies `Patch37_CrashReport`, subscribes the AppDomain hook, then calls `Native2ManagedPatcher.AttachAll(_harmony)` when `EnableNativeToManagedCapture` (default true, `Main/Features/CrashReport/CrashReportSettings.cs:32`).
- **Evidence**: `Main/Features/CrashReport/Hooks/Native2ManagedPatcher.cs:72-87` calls `harmony.Patch(m, finalizer: ...)` once per static method of every `*CallbacksGenerated` type in three AutoGenerated DLLs. The desktop log records the count: `[CrashReport] Native2Managed: attached 247 Finalizer(s)` on every launch.
- **Evidence (measured)**: the gap between the line before this block (`[SaveDefiners] ... no base-id collisions`, log line 4) and `Native2Managed: attached 247` is **29 to 33 s on 25 of 25 launches** that have both lines (for example `taom_debug_2026-09-23_12-43-26.log` 12:43:27 to 12:43:59; `..._13-05-00.log` 13:05:00 to 13:05:33). The matching rgl log (`rgl_log_42764.txt:694-696`) shows the engine's whole module-load window as 12:43:25.6 to 12:44:12.2 (46.5 s), so this one block is about two thirds of it.
- **Attribution (bounded, not isolated)**: the block also holds `Patch37_CrashReport` (9 classes), one MCM `CrashReportSettings.Instance` read and `AppDomainExceptionHook.Subscribe()`. The same boot applies about 50 patch classes (Patch18, 19, 58, 83, 61 x4 categories, 89 x4, 90, 62, 79, 0; counted with `git grep -c 'HarmonyPatchCategory("<name>")'`) between 12:44:02 and 12:44:09, about 140 ms per patch. At that rate 256 patches predict about 33 s, so the 247 finalizers are the bulk. A second data point agrees: nine `[TableauDiag] PatchCategory '...' applied OK` lines (about a dozen classes) land between 13:51:41 and 13:51:42 in `taom_debug_2026-09-23_13-43-40.log`, i.e. under about 100 ms a patch. A Stopwatch around `AttachAll` would settle it (UNMEASURED directly).
- **Whole-boot context**: TAOM's first log line is 12:43:27 and the rgl log is silent from 12:43:25.6 until the engine's `Adding trace listener` at 12:44:12.2 (`rgl_log_42764.txt:694-695`); inside that window TAOM logs `CastleRecruitment ... gate swapped` at 12:44:11. So TAOM's `OnSubModuleLoad` is about 45 of the 46.5 s module-load window: about 32 s in this block, 3 s in UIExtender registration (12:43:59 to 12:44:02) and about 9 s for the remaining patch categories and config loads. No `gap > 1.5 s` exists in the rgl log between 12:44:12 and 12:44:51 (awk over the timestamps), so the rest of the boot is the engine's.
- **Value delivered**: none observed. `grep -l "AutoGenerated.<callback>" taom_debug_*.log` (the bridge's origin string, `Native2ManagedPatcher.cs:122`) finds 0 of 30 logs, and no doc cites a capture from it.
- **Stale claim**: `Native2ManagedPatcher.cs:16` and `docs/features/crash-report.md:278` say finalizers "cost ~0 unless an exception is thrown". Harmony's documented finalizer semantics run it on every call (with `__exception == null`; UNVERIFIED against the Harmony build the game loads), and the patched method becomes a non-inlinable replacement wrapped in try/catch either way. The null path in `CrashReportPatchHelper.HandleAndSwallow` (`Main/Features/CrashReport/Hooks/CrashReportPatchHelper.cs:31`) is cheap, so the runtime cost is small; the boot cost is not.
- **Frequency**: once per process start, every player, every launch.
- **Impact**: about 30 s added to every boot; at a player's typical 2 to 4 launches a day that is minutes a day for a capture path that has produced no line in five days of logs.
- **Effort**: S (default the MCM toggle off, or replace the reflection sweep with an allowlist of the few callbacks worth guarding; add a Stopwatch line so the cost stays visible).
- **Risk**: LOW. Losing the sweep loses a diagnostic that has not fired; the nine named Patch37 finalizers stay. MCM json2 persists old defaults, so a default flip needs a renamed setting (trap index "Persisted MCM defaults").
- **Confidence**: HIGH that the block costs about 32 s per boot (25 of 25 logs); MED that the finalizers are the dominant part (rate-based attribution).
- **Fix sketch**: rename the setting (for example `EnableNativeToManagedCaptureV2`, default false) so existing json2 files do not pin true, keep the code for opt-in debugging, and log `AttachAll` elapsed ms. If a subset is wanted, patch an explicit list (the `ScriptComponentBehavior`, `Agent` and `Mission` callbacks) instead of every generated method.
- **Delta**: pre-existing (the patcher dates from the May 2026 crash-report feature, CHANGELOG-2026-H1 lines 5514-5548), but the measurement is new.
- **P1**: no.
- **Plan candidate**: yes. The largest measured cost in this lane, an S fix, and a clean verification story (the log gap).

### [PERF-L4-02] Stop the per-frame stack-walk and flushed log line from the loading-window trace

- **Evidence**: `Main/Features/MapLoadDiagnostics/Hooks/LoadingWindow_Transitions_Patch.cs:30-35` postfixes `LoadingWindow.DisableGlobalLoadingWindow` with `MapLoadTracer.TraceWithCallers("LOADING-WINDOW lowered")`. Its own doc comment (`:17-18`) says these "fire a handful of times per session, not per frame".
- **Evidence**: `Main/Features/MapLoadDiagnostics/MapLoadTracer.cs:62-82` builds `new StackTrace()`, calls `GetFrame(i).GetMethod()` for up to 12 frames and formats a string; `:52` writes it with `LogInfo`, which is durable (`Main/Core/Logging/FileLogger.cs:85`: `Enqueue("INFO", message, durable: true)`), so every line takes `_writeLock`, `WriteLine` and `Flush()` on the game thread (`FileLogger.cs` `Drain`, lines 99-125 of the file).
- **Evidence (measured)**: `taom_debug_2026-09-23_13-43-40.log` is 83,803,347 bytes and 265,061 lines, of which 262,831 (99.2%) are `[MapLoad] #N ... LOADING-WINDOW lowered` (`grep -c`). 140,047 of them name the caller `GauntletPartyScreen.OnFrameTick`, 121,359 `MBInitialScreenBase.OnFrameTick`, 248 `BodyGeneratorView.OnTick`. Per-minute counts are flat at about 21,530 (`awk` on the minute field, 13:45 to 13:49), i.e. about 360 lines a second: one per rendered frame while the party screen or main menu is open. Other logs: 18,477 lines (`..._12-43-26.log`), 4,343 (`..._09-22_16-00-17.log`).
- **Frequency**: every frame on the main menu, the party screen and character creation (the engine lowers the window from those screens' `OnFrameTick` unconditionally).
- **Per-call cost shape**: one managed stack walk with reflection on 12 frames, about 3 string allocations, `DateTime.Now` formatting, a lock, a file write and a `Flush` syscall. Per-frame time UNMEASURED; a Stopwatch around `TraceWithCallers` (or comparing `[MapLoad]` heartbeat fps with the patch on and off) would measure it.
- **Impact**: a 35-minute session wrote 84 MB of log, the crash bundle zips that file (`Main/Features/CrashReport/CrashReportService.cs:97` "re-zipping an ever-growing taom_debug.log"; log path wired at `CrashReportIoC.cs:48`), and the durable flush puts disk I/O on the UI thread every frame the party screen is open. The trace's diagnostic value (who raises the window and whether the lower comes back) needs only the transitions, not the steady-state lowers.
- **Effort**: S.
- **Risk**: LOW. Diagnostic only.
- **Confidence**: HIGH on frequency and volume (log-measured); MED on frame-time impact (UNMEASURED).
- **Fix sketch**: in the Disable postfix, trace only when the window was actually up (read `LoadingWindow.IsLoadingWindowActive`, a public static in v1.5.3 `TaleWorlds.Engine.LoadingWindow.cs:5` that `DisableGlobalLoadingWindow` itself tests at `:35`, in a prefix into `__state`, or keep a static "last raised" flag set by the Enable postfix), so the steady-state no-op lowers log nothing. Optionally route the tracer through `LogDebug` (queued, not flushed).
- **Delta**: introduced (`502f7cde`, 2026-09-14, v2.0.28).
- **P1**: no.
- **Plan candidate**: yes. One-line guard, measurable by log size.

### [PERF-L4-03] Make the warg bone check reject far targets before it builds native wrappers for them

- **Evidence**: `Main/Adapters/AgentAdapter.cs:207-227` (`CustomAttack`) captures EVERY active agent within `WargConfig.TargetDetectionRange` (20 m, `Main/Features/Warg/WargConfig.cs:35`) as a bone-check target, allies included (the team test lives only in the hit callback, `Main/Features/Warg/WargAttackService.cs:43-45`). The warg is the only producer (`git grep "\.CustomAttack("` finds one caller, `WargAttackService.cs:151`).
- **Evidence**: `Main/Features/AdvancedCombat/BoneCheckDuringAnimation.cs:31-58` runs every frame of the attack window. Per frame it reads `_agent.AgentVisuals` and `GetSkeleton()` (`:39-41`), then `BoneCheck.CheckBoneCollision` (`Main/Features/AdvancedCombat/BoneCheck.cs:53-127`) reads the attacker's visuals and skeleton AGAIN (`:61-68`), allocates a `List<(sbyte, Vec3)>` (`:76`), and for EACH target calls `IsActive()`, `IsFadingOut()`, `AgentVisuals`, `GetSkeleton()` and `GetGlobalFrame()` (`:92-116`) before the only distance gate, which sits inside `FindBoneInRange` (`:132`; `_maxRangeForCheck` = max(20, r^2 x 20) = 20 m^2, about 4.5 m).
- **Engine cost of each call (v1.5.3 decompile)**: `AgentAdapter.AgentVisuals` allocates a new `AgentVisualsAdapter` per read (`Main/Adapters/AgentAdapter.cs:36-38`). `MBAgentVisuals.GetSkeleton()` marshals a NEW `Skeleton` on every call (`ManagedCallbacks.ScriptingInterfaceOfIMBAgentVisuals.cs:776-786`), and `NativeObject.Construct` (`TaleWorlds.DotNet.NativeObject.cs:32-43`) makes a native `IncreaseReferenceCount`, takes a process-wide lock, allocates a keeper and a strong `GCHandle.Alloc(this)` held for 10 ticks; the object has a finalizer (`:45-51`) that makes a second native call. `AgentAdapter.IsActive()` calls `AgentSlotIdentity.IsCurrentOccupant` (`Main/Features/AdvancedCombat/AgentSlotIdentity.cs:19-26`), a native `Mission.FindAgentWithIndex` (`TaleWorlds.MountAndBlade.Mission.cs:2164-2171`); `IsFadingOut` is native (`TaleWorlds.MountAndBlade.Agent.cs:3338-3341`). Targets inside 4.5 m then cost one native `GetBoneEntitialFrameWithIndex` per target bone (about 30 for a human; `TaleWorlds.Core.HumanBone` has 30 members) times 10 attacker bones of distance math.
- **Frequency**: per active warg attack, per frame, for 0.5 to 0.9 of the attack clip (`WargAttackService.cs:134-148`). The tree sleeps `SleepAfterAttack` = 3 s after each attack (`WargBehaviorTree.cs:89`, `WargConfig.cs:36`), so roughly a quarter of engaged wargs hold a live bone check at any moment (duty cycle inferred from the tree, UNMEASURED).
- **Scale estimate**: a 1,000-agent battle with 80 warg riders engaged, 20 concurrent attacks, 60 agents inside 20 m of each warg: per frame about 20 x (2 + 60) = 1,240 `Skeleton` wrappers (1,240 GCHandles, lock acquisitions and finalizable objects), about 20 x 60 x 5 = 6,000 native calls before any distance test, plus about 20 x 8 x 30 = 4,800 bone-frame calls for targets actually within 4.5 m. At 60 fps that is about 74,000 finalizable objects a second through the finalizer thread. Frame time UNMEASURED; `[MissionPerf]` heartbeat fps in a warg-heavy custom battle with and without the reorder would measure it.
- **Impact**: the cost sits in the heaviest phase of a creature battle, grows with (wargs attacking) x (crowd density), and the finalizer and GCHandle churn surfaces as GC pauses rather than on a TAOM stack, so a profiler would not easily attribute it.
- **Effort**: S to M.
- **Risk**: LOW to MED. Hit detection is hand-tuned (#219); the reorder must not change which targets can be hit. Keep the per-target liveness checks; only move them after a cheap `Position` distance reject.
- **Confidence**: HIGH on the per-call mechanism (engine and TAOM source read); MED on the scale numbers (densities and duty cycle are estimates).
- **Fix sketch**: in `CustomAttack`, drop same-team targets at capture (keep enemy mounts, whose team comes from the rider, per `HandleWargTargetHit`). In `BoneCheckDuringAnimation.Tick`, fetch the attacker skeleton and frame once and pass them to `CheckBoneCollision`. Per target, reject on `(target.Position - agentPos).LengthSquared > _maxRangeForCheck` before touching `AgentVisuals` or `GetSkeleton`. Reuse the `List<(sbyte, Vec3)>` as a field.
- **Side note (not a perf finding)**: the `BoneCheckDuringAnimation.cs:15-24` comment says passing `100f` makes a "10 m distance cap"; `100f` lands in `maxDuration`, which the override never reads, and the real gate is the 20 m^2 (4.5 m) computed at `BoneCheck.cs:30`. `CreateTimedBoneCheck`/`CreateAnimationBoneCheck` (`BoneCollisionService.cs:12-26`) have no callers (`git grep`).
- **Delta**: pre-existing shape; the `IsCurrentOccupant` native lookup inside `AgentAdapter.IsActive()` came with #592 (`0c323437`, after June).
- **P1**: no.
- **Plan candidate**: yes. Contained to `BoneCheck`, `BoneCheckDuringAnimation` and `AgentAdapter.CustomAttack`.

### [PERF-L4-04] Give the warg tree's per-frame enemy scans a reused buffer and a flat bounding box

This extends seed F4 (IoC resolves in the same nodes); it does not re-report them.

- **Evidence**: `Main/Features/Warg/BehaviorTreeElements/NoEnemyCloseDecorator.cs:17` calls the ALLOCATING `SpatialGrid.GetNearAliveAgentsInRange(60, agent)`; `PeriodicallyCheckIfCanAttackAnyone.cs:23` and `:52` (`CheckOnceIfCanAttackEnemy`) do the same at 10 m. The zero-allocation overload exists (`Main/Features/AdvancedCombat/SpatialGrid.cs:142-145`) and its doc asks per-eval BT hot paths to use it (`:93-98`); no warg node does (`git grep -n GetNearAliveAgentsInRange -- Main/Features/Warg`).
- **Evidence**: `SpatialGrid.GetAgentsInRadius` (`SpatialGrid.cs:99-129`) walks the bounding box on all THREE axes at `CellSize` 20 (`:22`, `:105-117`): a 60 m query is 7 x 7 x 7 = 343 `Dictionary<(int,int,int), List<Agent>>.TryGetValue` calls, most on empty cells (vertical spread on a battlefield is a few metres). The whole in-radius set is copied into a fresh `List<Agent>` before the caller's loop can return on the first enemy.
- **Evidence (cadence)**: every warg tree is built with `base(10)` (10 ms, `WargBehaviorTree.cs:22`), and `BehaviorTreeAgentComponent.TickOnMissionThread` tests `(Tree._rootEvaluationDelay / 1000) < timeSinceLastEvaluation` in INTEGER division (`Main/BehaviorTreeWrapper/BehaviorTreeAgentComponent.cs:65`; the field is `int`, `Main/BehaviorTrees/BehaviorTreesCore.cs:36`), so the root runs every frame. With a rider and an enemy within 60 m, `NoEnemyCloseDecorator` returns false and the tree falls through to `CheckOnceIfCanAttackEnemy` (`WargBehaviorTree.cs:37-90`); the 1 s `SleepTask` runs only when no enemy is near. Both scans therefore run every frame for every engaged warg.
- **Scale estimate**: 80 engaged wargs with 200 agents within 60 m: per frame 80 x (343 + 8) = about 28,000 hash lookups, and 80 lists grown to 256 slots (final 2 KB array plus the doubling chain, about 4 KB each), about 320 KB of garbage a frame, about 19 MB a second at 60 fps. Frame time UNMEASURED (same `[MissionPerf]` method as PERF-L4-03).
- **Impact**: Gen0 GC pressure and hash work proportional to engaged wargs, on the main mission thread.
- **Effort**: S.
- **Risk**: LOW. Same results with fewer allocations; the sphere test on gathered agents already uses 3D distance, so a flatter bbox is safe as long as it still covers the query's z range.
- **Confidence**: HIGH on the shape (source read); MED on the scale numbers.
- **Fix sketch**: give each decorator a `List<Agent>` field and call the buffer overload; clamp the z loop to the cells the sphere actually spans at battlefield heights (or key the grid on (x, y) only). Optional: an "any enemy within r" query that stops at the first hit, for `NoEnemyCloseDecorator`. Fold into the rewrite of plan 003 PERF-07 together with F4.
- **Integer-division note**: the `/ 1000` truncation is harmless at today's 10 ms delay (the root would run every frame either way), but a future delay of, say, 2,500 ms would silently become 2 s. A `/ 1000f` fixes it for free while the file is open.
- **Delta**: pre-existing (tree cadence and scans predate June; the grid was reworked in `7402fa8e` and #592 without changing these callers).
- **P1**: no.
- **Plan candidate**: yes, folded into the plan 003 rewrite (PERF-07 plus F4 plus this).

## Supporting measurement: GC pressure in a large battle (context, not a finding)

`[MissionPerf]` heartbeat lines (`Main/Features/MissionPerf/Hooks/MissionPerfHeartbeatBehavior.cs:46-89`, a line every 5 s with frame stats and GC deltas) from `taom_debug_2026-09-21_12-20-32.log`, a 1,313-agent custom battle (elves against goblins, no creatures, 27 TAOM behaviors added per `[BattleLoad] ... TaomBehaviorsDone count=27`): before contact (t=+26 s to +61 s, `active=1313`) it holds 91 to 97 fps, avgMs 10.3 to 11.0, with 74 to 88 Gen0 and 20 to 24 Gen1 collections per 5 s window (about 16 Gen0 and 4.6 Gen1 a second). The spawn window logs `maxMs=1663.3`. Across all 3,148 heartbeat lines, windows under 200 active agents average 16 Gen0 per 5 s. None of this is attributable to TAOM from the log alone (vanilla allocates too), but it bounds the headroom: at battle scale the Gen1 rate is already several a second, so the per-frame garbage in PERF-L4-03 and PERF-L4-04 lands on an allocator that is busy. An A/B with a warg-heavy custom battle, same scene and size, is the measurement that would attribute it (method: `grep "\[MissionPerf\]"` and compare gc0/gc1 per window).

## Considered and rejected

- **BT listener dispatch is a linear scan per hit** (`Main/BehaviorTreeWrapper/BehaviorTreeMissionLogic.cs:188-201`, called twice from `OnAgentHit` `:348-355`). Only one tree type subscribes to a per-agent hit event (`WargTryToGoRage`, `OnSelfIsHit`; `git grep SubscriptionPossibilities.` finds four subscribers in all), so each hit walks at most one entry per warg. 100 wargs x 50 hits/s is 5,000 reference compares a second. Not worth a keyed map.
- **`SpatialGrid.UpdateGrid` runs in every mission, creature or not** (`AdvancedCombatBehavior.cs:39-47`). Every 2 s it rebuilds a dictionary over `AllAgents` (1,300 adds and a few hundred small lists every 2 s at the largest logged battle). Sub-millisecond every 2 s; the 2 s cadence itself is June PERF-01 (STILL_VALID, not re-reported).
- **`SpatialGrid.Remove` allocates a closure per deletion and `RemoveNow` scans every cell** (`SpatialGrid.cs:58-75`). Per agent deletion, not per frame; a few hundred cells. Negligible.
- **`AgentAdapterCache` takes a lock on every adapter lookup** (`Main/Adapters/AgentAdapterCache.cs:65-76`). Every caller now runs on the mission thread (#592), so the lock is uncontended (tens of ns). Removing it would trade the documented race guard for nothing measurable.
- **`MixedFormationsMissionBehavior` re-parses the cycle hotkey every frame** (`Main/Features/MixedFormations/Hooks/MixedFormationsMissionBehavior.cs:61,124-133`: MCM read, `Trim()`, `Enum.TryParse(ignoreCase)`). A microsecond or two per frame in field battles; a cache would add state for an unnoticeable win (`simplicity-criterion.md`: reject).
- **`AutonomousMovementPlayerController` scans `Mission.Agents` with `ContainsQ` every frame while a lock target is held** (`Main/Features/AdvancedCombat/AutonomousMovementPlayerController.cs:379`). One reference scan (1,300 compares at the largest logged battle), only for a mounted player with a lock. Negligible.
- **`TaomPartySpeedModel.CalculateFinalSpeed` runs twice per moving party per campaign frame** (engine: `MobileParty.ComputeNextMoveDistance` calls `CalculateSpeed()` then the `Speed` getter, `TaleWorlds.CampaignSystem.Party.MobileParty.cs:2842-2848`, `:418-429`). TAOM adds one small `CultureFeatAdapter` allocation (`CultureFeatAdapter.cs:37-38`), a walk of `GetTroopRoster()` (cached list, no allocation, `TroopRoster.cs:653-657`) and a lock-guarded dictionary read for hero parties (`CareerPassiveService.cs:110-133`). With about 1,000 moving parties (map census: `parties=2081 [lord=63 caravan=302 bandit=574 ...]`) that is about 2,000 tiny allocations a frame; real but small, and the base method already walks the same roster. Not worth a plan on its own.
- **`CaravansCampaignBehavior_GetTradeScoreForTown_Patch` recomputes the distance vanilla just computed** (`Main/Features/CaravanTrade/Hooks/CaravansCampaignBehavior_GetTradeScoreForTown_Patch.cs:40-41` versus vanilla `CaravansCampaignBehavior.cs:969`). It doubles one distance query per (caravan, town) scored, but scoring only happens when a caravan leaves a fortification (1/3 chance an hour, `CaravansCampaignBehavior.cs` `HourlyTickParty`), and from inside a settlement `DistanceHelper` takes the cached settlement-to-settlement path (`Helpers.DistanceHelper.cs:141-144`). Bounded at a few thousand cached lookups per game hour over 221 towns. Low.
- **27 linear `Hero.AllAliveHeroes` scans by string id** (`git grep -c` over `Main`; examples `Main/Adapters/ArmyMembershipAdapter.cs:313-324`, `ServiceDiplomacyAdapter.cs:137-148`, `NamedCompanionAdapter.cs:12-84`). 4,764 heroes in the logged campaign, tens of microseconds each, and every site read is event-scoped (joining an army, a dialogue, a menu). A tidiness item for Lane 2, not a performance one.
- **Wall-clock `DateTime.Now` in BT sleeps and cooldowns** (`Main/BehaviorTreeWrapper/Tasks/SleepTask.cs:22,30`, `Decorators/WaitNSecondsTickDecorator.cs:21,24`, `WargCanNotFindEnemyDecorator.cs:29`, spider and elephant-like cooldowns). About 100 ns per read per sleeping creature per frame: not a perf issue. The behavioural side (sleeps and cooldowns keep running while the game is paused or in slow motion) is a correctness question for Lane 1.
- **Campaign per-frame `TickEvent` handlers** (Refuge, FieldCamp, SupplyLines, FieldCommission, InventorySearch, EnlistmentMaintenance; read at their `OnTick` bodies). Each is gated early or throttled on game time (for example `RefugeService.FrameTick` `:309-324`), and the `MobileParty.All` scans found in those features sit behind the throttles or resolve a cached reference first (`SupplyRouteVisualService.cs:177-195`). No per-frame world sweep found.
- **The other per-frame diagnostics** (`Patch91` stall probes, `CharacterTableau.OnTick` census, `[MissionPerf]`, `[MapLoad]` heartbeat): each is an early-return or timestamp on the steady path, as their comments claim and the code shows (`Patch91_MissionTickStallProbes.cs:15-42`, `CharacterTableau_OnTick_ResidencyCensus_Patch.cs:49-60`, `MissionPerfHeartbeatBehavior.cs:46-70`). Only the loading-window trace (PERF-L4-02) breaks its own contract.
- **Settlement nameplate alpha postfix** (per visible nameplate per frame, `SettlementNameplateWidget_DetermineTargetAlphaValue_Patch.cs:41-55`) already caches its settings (`NameplateFadeSettingsProvider.cs:22`). Clean.
